# Changelog

All notable changes to the ERD Studio extension.

The `Unreleased` heading below is renamed to the released version by the deploy workflow
(`scripts/release.mjs changelog`). Add user-facing notes under it as part of each PR.

Releases are patch bumps by default. To ship a minor or major version, write it into the
heading — `## Unreleased — 1.0.0` — and the workflow releases exactly that.

## 2.0.3 — 2026-11-11

### Added

- **Import SQL DDL… reads a catalog export too:** pick a `.csv` (or `.tsv`) of your database's columns, one row per column, in the same Open dialog, and it becomes a draft like any import, with keys and relationships when the file has them. **Bring In Your Data Model…** gives the query for Databricks (Unity Catalog), SQL Server and Azure SQL, PostgreSQL and MySQL, beside each card's own export: one query and a download, no notebook (Databricks' catalog does not show column defaults or identity columns, so the notebook route still keeps those). The docs add DuckDB's and list the column names any other database's query can use. A file without key columns imports its tables and columns, and the draft says the file had no keys. A download that holds only the first rows (the query counts its rows) is refused, and so is a file of more than 100,000 columns: export one schema at a time.

- **ERD Studio: Suggest Relationships…** proposes the relationships a diagram's column names and keys point at, for you to accept or leave: a list in four parts (**Strong**, **Likely**, **Possible**, **Direction unknown**), each with the reasons in plain words. Only the strong ones (a declared key backs them) are ticked; with no key declared, nothing is ticked and the list says why. For one whose direction nothing settles, it asks "Which way does this relationship point?", as the New Relationship dialog does, or you skip it. Everything you accept is added in one change, stored as a relationship you drew yourself, and **Edit > Undo** takes them all back; nothing is kept about the ones you leave. Run it from the Command Palette or the canvas tab's **⋯** menu. After an import whose diagram has no relationships, a notification offers **Review Suggestions** once, when ERD Studio found at least one likely relationship (its number counts only those).
- **The canvas tells you what it is not drawing.** When something you wrote in a file cannot be drawn, a strip above the diagram now says so, with the file, the line and a link to open it, and it stays until the file is fixed. It covers a relationships file your diagram does not import (with an **Add the import** button, one edit you can undo), a `Ref` or `[ref: …]` written inside a table file, a relationships file with a syntax error or merge conflict, and a `.dbml` saved in a folder ERD Studio does not read (it says where the file belongs). Before, these were written only to the log, or shown once per session, so a hand edit could look like a reload that had failed.
- **A relationship you write by hand is drawn when you save it.** When you save a relationships file in VS Code and an open diagram needs to import it (the first `Ref` between two of its tables, even in the layer's own relationships file, or a `Ref` in a new file), ERD Studio adds the `use *` line to the diagram for you and the line appears, with a short note naming the file. It is one edit you can undo with Cmd+Z (Ctrl+Z). A file changed outside this window (a git checkout or pull, another program, an AI assistant writing the file) never changes your diagrams: the strip offers **Add the import** instead.
- **ERD Studio: Reload Diagrams from Disk** (Command Palette): reads every file again and redraws the open diagrams. You should not need it, since diagrams redraw by themselves when a file is saved; it is there for a folder where file changes do not reach VS Code (some network drives and containers). It writes nothing.

### Changed

- **Bring In Your Data Model… is in the Diagrams view's + menu**, under the imports, so a project that already has diagrams has a visible way to the import guide besides the Command Palette.
- **The import guide shows every source at once.** Each source (Databricks, Snowflake, Power BI, Fabric, SQL Server, PostgreSQL, MySQL, DBML and the rest) is one line until you open it, so the whole list fits in view without scrolling; a source ERD Studio found in your folder starts open.
- **Each source in the import guide shows its logo** beside its name, so you can spot the one you use.
- **An open source in the import guide reads as steps.** Copy the query, run it and save the result, import the file: numbered, with one main button at the end, and what does not come in said after it. Where a source has two ways in, the card shows the one to use and the other is a single line saying when to use it (on Databricks: "Need column defaults or identity columns? Use a notebook instead."); on PostgreSQL and MySQL the dump is shown and the catalog query is the other way.
- **Bring In Your Data Model… is also a row in Help & Feedback.**
- **The import guide folds its long queries.** A query or notebook cell longer than six lines shows as one line ("Show all 48 lines") with **Copy** beside it, so the Databricks, SQL Server, PostgreSQL and MySQL cards no longer push the other sources off the page.
- **A diagram whose file has a mistake keeps saying so.** The red message over the diagram now comes back on every save while the file is still broken, and the strip above the diagram says the picture is the last one that could be read, until the file reads again. Before, a dismissed message stayed gone and the old picture was left with no explanation.
- **The "does not import it" message no longer says any edit to the diagram adds the import.** Moving a table saves only positions. The canvas now offers **Add the import**, and `erd-studio doctor` gives the line to write.

### Fixed

- **Send Feedback** no longer fails silently from the Command Palette: if the report can't be opened, ERD Studio says so, copies your title and description to the clipboard, and offers **Open GitHub Issues** and **Try Again**. The Send Feedback dialog shows the same plain sentence instead of a raw error.
- When VS Code can't open your browser, Send Feedback offers **Copy Link** and **Copy Report** instead of printing a long link in the message. When commenting on an existing issue, it tells you the report is already on the clipboard and which issue to paste it on.
- When the feedback API key can't be saved or cleared, the message explains that VS Code's secret storage isn't available on this machine, and **Learn More** opens VS Code's troubleshooting page.
- When ERD Studio needs to reload the window (after an update, or when a diagram loses its connection) and some files couldn't be saved, it now asks in a dialog that names them, with **Show Files** to open the first one.
- **Hand edits are picked up in more cases.** A change to `layers.json` (a layer's name or colour) now redraws the open diagrams, not only the sidebar. A diagram also checks its files when you click back into it, and redraws if a table or relationships file changed without VS Code telling ERD Studio.
- **A diagram no longer gets stuck when its file could not be saved or changed behind an unsaved copy.** It is drawn from the file on disk and says that the open copy has unsaved changes.
- **A redraw that fails inside ERD Studio is no longer silent.** The diagram says it may be out of date and offers **Reload from disk**.

## 2.0.2 — 2026-11-10

### Fixed

- **New Relationship:** on a short window the **Stored in** picker no longer runs into the Role field's hint. It sits in a band of its own above the buttons, with a divider where the fields above scroll away (#275).
- **Convert Project to DBML, then Undo:** the undo now also removes the empty folders the conversion made for its new files (`gold/diagrams`, `silver/tables/public`, …), so the project is exactly as it was. A folder that existed before, or that you have put a file in since, stays (#275).
- **Edits keep a DBML file's own layout:** renaming a table, Move Table, new relationships and deletes now change only the lines they must, in every `.dbml` file. They no longer re-align other columns or `use` lines (even when a new name is the longest in its group), add blank lines between Refs you kept together, leave two blank lines where a deleted line was, or put a new `use` line above the file's opening comment. In a file in ERD Studio's layout the lines an edit writes line up with their neighbours where they fit, and **Format Document** still re-aligns a whole file when you ask (#275).
- **Undo after Remove from Diagram and Delete Table File puts things back in the right order.** Edit > Undo on the diagram now first brings back the deleted table file, with its relationships and its place in other diagrams, and only the next Undo puts the table back on the diagram. Before, the first Undo brought back the table's `use` line while its file was still deleted, so the diagram showed an empty "No columns" table that other DBML tools could not read. The files an Undo brings back are saved straight away, so you no longer need Save All. This works for YAML tables on JSON diagrams too.
- **The Delete Table File question no longer says "its place in 0 other diagrams".** When nothing else uses the table, it now just says it removes the table's file. Delete Table in the Table Library leaves out a count of 0 the same way.

## 2.0.0 — 2026-11-10

**ERD Studio 2.0 is a major release: new projects are stored as DBML.** Nothing changes in your project until you run **ERD Studio: Convert Project to DBML**. Before converting, commit your work: Undo works while VS Code stays open, and git is the safety net. Existing YAML and JSON projects keep loading and stay fully editable. What breaks is for tools that read `.erd-studio` directly: a new project writes `.dbml` files under a folder per layer (`<layer>/tables/<schema>/<name>.dbml`, `<layer>/relationships/<file>.dbml` and `<layer>/diagrams/<name>.dbml`, each diagram keeping its table positions inside it) instead of `.yml` and `.json`, and `erd-studio doctor --json` gains `erd.storage` (`dbml`, `yaml` or `mixed`), which says which kind a project writes.

**If you tried a 1.9 pre-release:** 2.0 does not read the folder layout 1.9 wrote. Restore your YAML/JSON files from git (the commit before the conversion) and run ERD Studio: Convert Project to DBML again. A 1.9 pre-release cannot read a 2.0 project: update before opening one.

### Added
- **Import SQL DDL… reads Oracle, Google BigQuery, Amazon Redshift and SQLite.** Each is a dialect of its own in the pick and is detected from the scripts: Oracle SQL*Plus scripts and `DBMS_METADATA` output (`PROMPT`, `SET`, `/` lines, PL/SQL, `q'[…]'` strings, identity columns, `VARCHAR2` and `NUMBER(p,s)` kept as written, keys added by `ALTER TABLE … ADD ( CONSTRAINT … )`, `COMMENT ON` descriptions; storage, tablespace and partition clauses left out), BigQuery DDL (`` `project.dataset.table` `` names, `STRUCT<…>` and `ARRAY<…>` columns, `OPTIONS(description = …)` and `SET OPTIONS` as descriptions, triple-quoted and raw strings, `#` comments, `NOT ENFORCED` keys; `PARTITION BY` and `CLUSTER BY` left out), Redshift DDL (`ENCODE`, `DISTKEY`, `SORTKEY`, `DISTSTYLE` and `IDENTITY(…)` left out and listed) and SQLite schemas (square-bracket names, `AUTOINCREMENT`, typeless columns as `unknown`; virtual tables, SQLite's own `sqlite_…` tables and triggers left out). The start screen now offers an Oracle script like any other.
- **Context fields: one list of what your team records about each table.** A table's grain, purpose and decisions, its owner, how sensitive it is: an optional `.erd-studio/fields.yml` lists the fields your project records on tables and on columns, in the order the Detail panel shows them. A bare name (`- purpose`) is a built-in field as ERD Studio ships it; `- key: …` is a built-in in your own words, or a field of your own with a label, a type (`text`, `value`, `choice` with its `values`, or `yes-no`), one sentence of guidance, who fills it in (`filled_by: anyone`, `people`, or `dbt` for a value copied from the dbt model's `meta:`) and which tables it suits (`show_for: dimensions` or `facts`, read from the table's role). Without the file you get the starting set: Grain, Purpose, Decisions, Open questions, Table role, History on dimensions and Measures on facts, and Natural key, SCD type and Additivity on columns. The file is committed with your model, so every teammate's canvas and every AI assistant follow the same list. See [Field list](docs/semantic-domain-json-reference.md#field-list-erd-studiofieldsyml).
- **One rule for every field in a `.dbml` table: `<key>: '<value>'`.** Built-in or your own, on the `Table` line or on a column (`purpose: '…'`, `decisions: '…'`, `owner: 'crm-team'`, `pii: 'true'`), with no prefix, so a table file reads like your field list and your assistant has one rule to follow. Names DBML and ERD Studio use themselves (`note`, `default`, `schema`, `alias`, `meta_json`, anything starting `erd_`, `rationale_` or `meta_`) can never be a field. A list or a map copied from dbt still goes into the one `meta_json` setting.
- **Two new fields on every table: Decisions and Open questions.** Decisions holds a choice a later editor might undo, and why, so nobody "fixes" it. Open questions holds what is still undecided: assistants write the question there and ask you, then move your answer into Decisions. Source of truth, Freshness, Known issues and Retention (filled in by people only) for tables, and Business rule for columns, are ready to add to `fields.yml`.
- **The Detail panel shows your fields, in your order.** Each field gets a text box, a one-line box or a dropdown (a choice, a yes or no, the table role), with its guidance as the placeholder and a **from dbt** or **people only** hint where it has one. Nothing with a value is hidden: a setting your list does not name shows under **Not in your list**, and a retired field is marked **Retired**. **+ Add field** still adds a field of your own. **ERD Studio: Customise Fields…** (or **Customise fields** in the panel) opens `fields.yml`; without one it opens the starting set as an unsaved file, so nothing is written until you save it. A change to `fields.yml` (a pull, a hand edit or your assistant's) shows on every open diagram straight away. The physical stage shows the design's fields too, read-only.
- **`erd-studio doctor` checks your fields** (`erd.fields` in `--json`): a reserved, badly spelt or repeated key in `fields.yml` is an error with its line (next step `fix-fields-file`), a name that is not a built-in is a warning ("purpse is not a built-in field. Did you mean purpose?"), and so are a value outside a choice's list and one field written two ways in one table. It also counts tables with older spellings, retired fields and fields your list does not name.
- **`fields.yml` has a JSON Schema** (`schemas/fields.schema.json`): with Red Hat's YAML extension, VS Code completes the built-in names, types and `filled_by`, with each built-in's guidance in the list, and flags a reserved key.
- **Your AI assistant follows the field list.** The AI helper files (harness v46) replace the fixed design rationale and the team's metadata list with one **Fields** section: read `fields.yml`, fill each field the way its type and `filled_by` say, never write a placeholder, keep every setting the list does not name, and edit an older spelling where it is. `/erd-studio-setup` proposes a list from your modelling style and the metadata your dbt models already record, saves it with one yes, and leaves out the dbt keys you list under `left_out`. A `## Metadata` table in `modelling-approach.md` keeps working: the assistant offers once to move it into `fields.yml`.
- **The safety check now covers GitHub Copilot, Codex and Gemini CLI too.** Set Up My AI Helper adds a small hook for each of those assistants it finds (as Claude Code already had) that pauses the first edit to an `.erd-studio` file in each session until the assistant has loaded ERD Studio's format rules; it then retries and carries on. The hook only ever pauses that one edit and never approves anything. GitHub Copilot's goes in `.github/copilot/settings.local.json` (read by the Copilot CLI and Copilot sessions in VS Code), Codex's in `.codex/hooks.json` (Codex asks you to trust it in `/hooks` first) and Gemini CLI's in `.gemini/settings.json`; ERD Studio keeps the Copilot and Codex files out of git and leaves your other settings in all three as they are. A settings file with comments in it is left alone, and Set Up My AI Helper says so. On Windows, Claude Code's check needs Git Bash, and GitHub Copilot's and Codex's don't run. Cursor and Antigravity CLI aren't supported yet and keep relying on the always-on skill. See [Working with your AI assistant](docs/ai-assistants.md#the-safety-check).
- **A Relationships view in the sidebar.** Every relationship in the project, under each of its tables: **→** the tables it points at, **←** the tables that point at it, with the columns and the cardinality (`customer_sk · N:1`). Click one to see it on a diagram: the diagram that shows both tables opens (you pick one when several do) with the relationship's line selected, its columns lit and the view centred on its two tables. When no diagram shows it yet, the click opens where it is written instead, as the row's **Open in File** icon always does (the `Ref` line in a DBML project, the table's file or the diagram in an older YAML/JSON project). A relationship that names a table or column the Table Library does not have is listed first, under **Needs attention**.
- **Projects are stored as DBML, an open format, one folder per layer.** Under `.erd-studio/`, each layer (bronze, silver, gold, …) has three folders: `tables/<schema>/` with one `.dbml` file per table, declared `Table <schema>.<name>` (the schema folder is the table's schema: a source system, a domain or the warehouse schema), `relationships/` with the relationships as `Ref` lines (one default file per layer, `<layer>/relationships/<layer>.dbml`, which you can split into more files however you like), and `diagrams/` with one `.dbml` file per diagram: the tables it shows (`use` lines), the relationships files it needs, its sticky notes, then its `Project`. A `README.md` explains the folders. DBML parsers 9.1 and 11+ read the project as it is (10.x too, unless a folder in its path has a space): open a diagram file in another DBML tool and it shows that diagram. ERD Studio edits these files in place: your hand edits, comments and the DBML settings it does not use (`not null`, defaults, indexes, enums, …) are kept, and saving without a change leaves a file byte for byte as it was. A table file that does not parse is shown as unreadable and never rewritten.
- **Positions live in the diagram file, and Cmd+Z undoes a drag.** A diagram keeps where its tables and sticky notes sit as an `erd_layout` setting in its `Project`, one line per table (`fct_order 400 200`), sorted by name, which other DBML tools ignore. Moving a table changes only those lines, as one edit of the diagram, so **Cmd+Z** (or **Edit > Undo**) puts it straight back, and the sidebars are not refreshed. When git leaves conflict markers inside `erd_layout`, only positions differ: the diagram opens with the first copy of each line, ERD Studio saves no move until you keep either side, and `doctor` says so.
- **Tables keep their schema, and relationships stay where you put them.** A table added on a canvas goes into the diagram's layer; its schema folder is dbt's configured schema for a model with one (`+schema` or `config(schema=…)`), the same on every machine and never the schema dbt built in your dev target, else the layer's name. **Import DBML…** keeps a table's `Table sales.orders` schema, and says when it reuses an existing folder spelled differently in case. A new relationship goes into the relationships file that already holds most of its foreign-key table's relationships, in any layer, else that table's layer's default file; an existing one is always changed where it is, so a file you split by hand stays split. A relationship that any relationships file already holds is refused, with the file and line. Every diagram imports exactly the relationships files it needs, kept up to date in the same edit, so other DBML tools draw the same relationships ERD Studio does.
- **Language modes and icons for DBML files.** Under `.erd-studio`, a diagram, a table and a relationships file open as **DBML Diagram**, **DBML Table** and **DBML Relationships**, each with its own icon in the Explorer, on tabs and in the ERD Studio views, and the same highlighting, comments and Format Document as any `.dbml` file. The icons show under a file icon theme with no `.dbml` icon of its own (Seti works), and only in the default `.erd-studio` folder (a custom `erdStudio.semanticDir` keeps plain `.dbml` files).
- **ERD Studio: Convert Project to DBML** moves an existing YAML/JSON project to DBML in one step. It shows what it will write first, as a scrollable list in a **Convert to DBML** tab: a one-line summary, then **Handled for you** (fixes it makes by itself, such as a diagram that names a table in another case, or a table file with a key written twice with the same value), **Left as YAML until fixed** (or **Left as JSON**, for diagrams: a file it cannot read or write as DBML, such as one that does not parse or has a key written twice with different values: it stays exactly as it is, with **Open** at the file and line, and running Convert again after fixing it finishes the job; **Check Again** re-reads it straight away), **Kept as missing on their diagrams** (a table a diagram lists that has no table file stays on the diagram, drawn as missing exactly as before, until you create it with **Add from dbt**), then the tables, relationships files, diagrams, files removed and notes, with Convert and Cancel always in view (and `erd-studio doctor` previews the same plan). The same project always gives the same plan, and every converted diagram is checked to draw what it drew before. Everything is applied as one undoable edit, and it lists what it changed on the way: relationships it moved from diagram files into the Table Library, YAML comments and keys ERD Studio does not read (kept as `//` comment lines), and relationships it cannot write as a live `Ref` yet because a table has no file (kept as `// erd-studio pending:` lines and still drawn; they become live once both tables have files, and renaming, moving or deleting a table keeps them in step). An empty table file, a dbt schema file copied into the Table Library and a diagram in a folder `layers.json` does not list are left as they are, each with what it is. A table file with git merge conflicts or a tab indent, and a diagram in a format that no longer loads, say what to do. A table file named `.yaml` (or `.YML`) is left with the name to give it rather than called missing, and doctor's `unlinkedTable` line says the same. `erd-studio doctor` lists every file Convert would leave with its problem, and says when Convert fixes one by itself. A composite relationship of one column pair is converted as a single relationship, with a note. Metadata keeps its key order, in Convert and in every later edit of a DBML table. It puts each table under a layer (its library folder when that is a layer, else the layer of the diagrams that show it when they agree, else the first layer in `layers.json`) and a schema folder (the table's `schema`, else its library folder, else `public`), listing every choice in its notes, and writes each relationship to its foreign-key table's layer's default relationships file. It refuses only where leaving a file as it is would not help: a layer named `tables`, `templates` or `logical-models`, files an ERD Studio 1.9 pre-release wrote (it lists them to delete first), an existing DBML table or relationships file it must change but cannot (it names the file to fix), or its own check failing (with **Send Feedback**). Convert then opens a converted diagram (or file); **Edit > Undo** straight after, with it in front, puts every file back. It also finishes a half-converted or mixed project. When you open a diagram in a YAML project the editor offers it once, in a dialog you answer (**Convert…**, **Don't Ask Again**, or Cancel for not now); **Don't Ask Again** keeps it quiet.
- **`erd-studio doctor`** reports `storage` (`dbml`, `yaml` or `mixed`), the DBML problems of every file with their line and severity (and, for a missing or wrong line, the exact line to write; a hand-written `Metadata` block outside a table's own file, whose values the canvas does not show, is a `foreignMetadata` warning), and the Convert preview. New next steps: `fix-dbml-file`, `resolve-format-conflicts`, `finish-dbml-conversion` (which also lists the files Convert left as they are until fixed), `import-dbml-file` and `reconvert-dbml-project` (files from an ERD Studio 1.9 pre-release, `legacyDbmlTree`: one error for the project, with the steps); new warnings `unlinkedTable` (a table on a diagram with no table file, or one still in YAML, named by the file the diagram draws it from), `pendingRelationship`, `missingRelationshipsUse` / `extraRelationshipsUse` (a diagram that lacks, or does not need, a relationships file's `use *` line), `dbmlOutsideKnownFolders` (a `.dbml` where ERD Studio does not read it, with where it belongs; a `Silver/` folder gets "layer folders are lower-case ids; rename Silver/ to silver/ and set its label in layers.json"), `dbmlLayerNotConfigured`, `unexpectedFileInDbmlFolder`, `relationshipsFileHoldsOther`, `schemaFolderMismatch`, `unqualifiedTable`, `schemaProperty` and the `erd_layout` checks (`layoutBadLine`, `layoutDuplicateKey`), and new errors `duplicateTableName` (one name in two table files), `layoutBadValue` and `layoutMergeConflict`. Warnings never raise a next step. A `diff` fix for a DBML relationship names the file that holds it and changes it in place. `update-harness` now covers every AI helper you installed (Claude Code, `.agents`, Copilot, Gemini, `AGENTS.md`), and helper files from a newer ERD Studio are reported ("Update ERD Studio") and never replaced.
- **Opening DBML files.** A diagram's `.dbml` (in a `diagrams/` folder) opens on the canvas; a table or relationships file opens as text (their source-control diff and the merge editor work as for any text file). Any other `.dbml` opened on the canvas, such as a tab restored from a 1.9 pre-release, shows a page saying what it is and how to reopen it as text. A dbdiagram.io single-file `.dbml` dropped into a `diagrams/` folder shows a banner with **Import these tables…**.
- **ERD Studio works in any folder, no dbt needed.** Open a folder and the ERD Studio sidebar offers **New Diagram** (draw your first data model from scratch) and an import (a DBML file from dbdiagram.io or any DBML tool, SQL DDL scripts or a Power BI semantic model). **New Diagram** creates the `.erd-studio/` folder and its layers the first time you use it; opening a folder writes nothing and shows no prompts. Without a `dbt_project.yml` the canvas shows only your logical design. A folder that already has an `.erd-studio/` folder starts ERD Studio by itself, and any dbt project in the workspace is still preferred, as before. To compare your design with what dbt built, open the dbt project's folder.
- **One start screen, one click to a diagram.** The **Get started with ERD Studio** walkthrough and the empty **Diagrams** view now offer the same starts, and only the ones that fit the folder: **New Diagram**, **Import…** (a DBML file, SQL DDL scripts or a Power BI semantic model) and **Open an example…**; in a dbt project **Import from dbt** comes first; in a YAML/JSON project from before 2.0, **Convert to DBML** comes first. Each surface has one main button and the other starts as quiet links. The walkthrough opens by itself on a first install only in an empty window (in a folder, the draft takes its place), on its start step; the **ERD Studio Tour** tab and the empty sidebar work in an empty window too: there they offer **Open Folder** and an example. The **Diagrams** view keeps its start buttons until the project's first diagram exists, rather than showing empty layer rows; after that, each layer ends with a **New Diagram…** row and the tree with **New Layer…**, and its **+** offers **Import DBML…** and the other ways to start one.
- **The start screen suggests where to begin.** ERD Studio takes a quick look at the folder you open, on your machine only (nothing about your files is sent anywhere), and puts the likeliest start first as the one main button on the walkthrough and the empty **Diagrams** view: **Import your Power BI semantic model** when the folder holds a Power BI or Fabric semantic model, **Import your SQL scripts** when it holds `CREATE TABLE` scripts, **Import your DBML file** when it holds a DBML file, each going straight to that import (one click less than **Import…**), with a line saying why ("This folder has CREATE TABLE scripts."), each ending in the draft; **Import your DBML file** opens the file dialog with that file already chosen, so **Import** takes it in one press. The look reads only the start of each SQL file, however big, and a report-only Power BI project (one connected to a published semantic model, with no model of its own) is not taken for a semantic model. The empty **Diagrams** view shows "Loading diagrams…" until the suggestion is ready, so its main button never changes under your cursor. With nothing to import, **New Diagram** leads and **Open an example…** comes second. **Import…** stays as a quieter choice everywhere, and every surface offers at most four starts. In a YAML/JSON project from before 2.0, **Convert to DBML** is the one main button and the project's other starts sit under it as links.
- **ERD Studio offers your first diagram as soon as it opens the folder.** In a folder with no diagram yet, where ERD Studio finds an obvious start (CREATE TABLE scripts, a Power BI or Fabric semantic model, a DBML file, a dbt project, or a project from an older ERD Studio), one notification offers it: "ERD Studio found CREATE TABLE scripts in this folder (24 tables). Show them as a diagram? Nothing is saved until you keep it." with **Show Me** (the draft, below) and **Don't Ask Again for This Folder** (then that folder gets no automatic draft and no walkthrough either; one short line confirms it, with **Undo**). It is shown once per folder: closing it leaves the sidebar's button and the draft on the ERD Studio icon, never another notification. ERD Studio now also starts in a folder that holds `.sql`, `.dbml` or semantic-model files, so the offer comes without opening the sidebar first; it stays quiet in a folder of queries. Turn it off for one folder with **ERD Studio: Turn Off Start Suggestions for This Folder** (on with **…Turn On…**), or for a whole repository by committing `"erdStudio.startSuggestions": false` in `.vscode/settings.json`. ### Changed
- **Imported columns keep NOT NULL as DBML writes it.** In a DBML project, a column imported as `not null`, `unique`, `increment` or with a `default` now reads `[not null, default: 'new']` in its table file, as dbdiagram.io and every DBML tool read it, instead of `meta_json: '{"dbml":{"not_null":true}}'`. Tables from an earlier 2.0 build read as before and keep their `meta_json` until that value changes; a `default` such as `0` stays there. The AI helper files (harness v47) say so.
- **Watch the Tour is re-recorded for 2.0 (2:48; 2:25 in a folder without dbt).** It opens on every source the import reads (dbt, Databricks, Snowflake, Power BI, Microsoft Fabric, PostgreSQL, SQL Server, MySQL, Oracle, BigQuery, Redshift, MariaDB, SQLite and DBML), gets a PostgreSQL database's DDL out with one `pg_dump` (and names Snowflake's one `GET_DDL` query), imports it through **Import SQL DDL…** with its dialect detected among the nine, and adds a 2,000-table diagram whose lines are routed around its tables in the background, with a hovered table's arrows flowing along its relationships.
- **Bring In Your Data Model… shows one step to get your DDL out, for a whole schema or database.** Each source's card now has a single step, with no "1." in front of it, and alternatives sit in a short note under it instead of reading like a second step: Databricks shows only the notebook cell that writes a whole schema (the one-table `SHOW CREATE TABLE` step is gone), Snowflake shows `GET_DDL('SCHEMA', …)` with a note for a whole database, and Power BI's "No such option?" is a note. ### Fixed
- **An import no longer quietly swaps in another model's table of the same name.** When a DBML file, SQL scripts or a Power BI model has a table whose name your project already has, in any layer, ERD Studio used the project's table as it was: the file's other columns were not added, the relationships that needed them were left out, and the diagram showed another model's table without saying so. Now the project's table is used only when it has the same columns (by name). Otherwise the file's table is imported as its own, named after the new diagram (`customer` in a *warehouse* diagram becomes `warehouse_customer`, with `customer` as its warehouse name), with every column and relationship, and the project's table is not changed. Importing the same file again uses that copy rather than making another. Step by step, the import asks first and offers **Use the project's table as it is**, saying how many columns and relationships that leaves out; the draft says which tables were kept as their own and which layer every reused table comes from, and **Change options…** asks the question.
- **A diagram that fails to load now says whose problem it is.** When ERD Studio itself fails to show a diagram, the canvas says so (*ERD Studio couldn't show this diagram*), that your files haven't changed, and offers **Retry** and **Send Feedback** with the error filled in, paths removed, instead of `Error:` and the raw exception. A diagram file ERD Studio reads but can't accept (a missing or non-numeric `schemaVersion`, a format it no longer reads) says it is the file's problem and offers **Open as Text** and **Retry**, not Report a Bug. A diagram saved by a newer ERD Studio offers **Update ERD Studio**. (#261)
- **Refresh Manifest no longer says "try again shortly" forever.** A `manifest.json` dbt is still writing gets **Try Again**. If it is still unreadable on that retry, or there is no earlier copy to show, ERD Studio says it isn't valid JSON, that this is a problem in the file dbt wrote, and offers **Run dbt parse** and **Open File**. A manifest too large to read in time is said to be ERD Studio's limit, with **Send Feedback**. A failure inside the refresh now shows ERD Studio's own message with **Send Feedback** and **Try Again**, instead of VS Code's generic error. (#263)
- **Strip Legacy Domain Tags lists the files it skipped.** Instead of "see Output", the summary says how many files couldn't be changed (nothing in them was touched) and offers **Show Skipped Files**, which lists each one with why: not valid YAML, couldn't be read, or couldn't be written. A failure while scanning shows ERD Studio's own message with **Send Feedback**. (#263)
- **Import SQL DDL… recognises a `pg_dump` file as PostgreSQL** from its header and its `ALTER TABLE ONLY` lines, even when its tables use only types other dialects share (`integer`, `character varying`), so the dialect pick marks it detected.
- **A very large diagram's lines find their way around the tables about twice as soon after it opens.** Routing started before the tables had their final sizes, and the out-of-date pass ran to the end before the real one began, so the lines of a 2,000-table diagram took about 4.7 seconds to settle. That pass is now stopped as soon as the tables are measured: about 2.3 seconds.
- **Import SQL DDL… reads names that start with a digit.** A schema such as `340b_silver` or a column such as `3RD_PARTY_VENDOR` (Databricks, Spark, MySQL and Hive take them unquoted) no longer makes the table look like one without a column list, which left it out without naming it.
- **Import SQL DDL… reads `CREATE TABLE t (a INT, …) AS SELECT …`** (Snowflake, Databricks, Lakeflow streaming tables): a column list that types every column is the table, read with its keys and references; the query that fills it is not imported, and the log says so. A table made from a query or another table with no column list of its own (`AS SELECT`, `LIKE`, `CLONE`) is now named, with its line, under Not imported instead of only counted.
- **Import SQL DDL… reads a Snowflake table comment written before the column list** (`CREATE TABLE t COMMENT = '…' (…)`), as the table's description (and such a file is offered as SQL DDL when you import a folder), and a Databricks column's `COMMENT "…"` in double quotes.
- **Import SQL DDL… reads Lakeflow (Delta Live Tables) pipelines:** an expectation (`CONSTRAINT n EXPECT (…) ON VIOLATION …`) is listed as not kept instead of failing its table.
- **Import SQL DDL… reads more template placeholders:** Airflow's `{{ params['name'] }}` and Python's `{schema}.orders`, as names.
- **Import SQL DDL… detects the dialect of more warehouse scripts:** Snowflake scripts with `::` casts and `$$` bodies (read as PostgreSQL before), BigQuery scripts whose backquoted paths hold placeholders (read as MySQL), and Databricks scripts with Lakeflow statements or a column's own `CONSTRAINT … FOREIGN KEY REFERENCES` (read as Snowflake or PostgreSQL).
- **Import from dbt reads a description or data type given as a YAML alias** (`description: *shared_desc`), which came in empty. Seeds and snapshots now also read YAML merges (`<<: *defaults`) and a column list given as an alias (`columns: *cols`), as models already did.
- **Import SQL DDL…: `CREATE OR REPLACE TABLE` of a table already read replaces it**, as the database does: the later definition is the table, and the log names both lines (before, the first was kept and the later one reported as a duplicate). `CREATE OR ALTER TABLE` takes the new column list and keeps the table's foreign keys. A plain `CREATE TABLE` of a table already read still keeps the first.
- **Import SQL DDL… reads Snowflake's and Databricks' `IDENTIFIER(…)` names** (`IDENTIFIER($tbl)`, `IDENTIFIER(:tbl)`, `IDENTIFIER('db.s.orders')`, `IDENTIFIER(:catalog || '.s.orders')`) as the names inside them, which failed their tables.
- **Import SQL DDL… leaves out a session's temporary tables** (`CREATE TEMPORARY`, `TEMP`, `VOLATILE` and `LOCAL TEMPORARY TABLE`), each named with its line under Not imported, as it already did SQL Server's `#tables`. Oracle's `GLOBAL TEMPORARY TABLE`, a lasting definition, is still imported, and so is a Lakeflow (Delta Live Tables) `TEMPORARY LIVE` or `TEMPORARY STREAMING TABLE`, a pipeline's dataset.
- **Import SQL DDL… keeps a foreign key the SQL grammar did not read** (Snowflake's `c INT FOREIGN KEY REFERENCES t` with no column list, which means `t`'s primary key, or one followed by `MATCH PARTIAL`): it is read from the file and the log says so, instead of being dropped without a word. One that names a table with no primary key is logged as not kept, with why.
- **Import SQL DDL… reads Databricks and MySQL column names that start with a digit and have no underscore** (`2fa`, `3rd`); Spark's typed numbers (`10L`, `3D`) stay numbers.
- **Import SQL DDL… tells Snowflake from Databricks more reliably:** a column's `FOREIGN KEY REFERENCES` and `TIMESTAMP_NTZ` / `TIMESTAMP_LTZ` are both dialects' and no longer decide alone (a Snowflake script with them was read as Databricks); Unity Catalog's `CREATE CATALOG` / `USE CATALOG`, an exported Databricks notebook and `GENERATED … AS IDENTITY` in a `CREATE OR REPLACE TABLE` point to Databricks; a BigQuery script with one backquoted column name is no longer undecided.
- **Import SQL DDL…: the Not imported lines stay at most 300 characters** when a file's path is long: the path is shown by its end.
- **Import SQL DDL…: a partition kept as a table gets its parent's keys.** With **Keep each partition as a table**, each PostgreSQL partition (`PARTITION OF`, or `ATTACH PARTITION` in a pg_dump) now has its parent's primary key, unique keys and foreign keys, as PostgreSQL creates them on every partition (a key written `ON ONLY` or `ALTER TABLE ONLY` only on partitions attached after it); an `INHERITS` child gets none.
- **Import SQL DDL…: a SQL Server computed column of `ISNULL(expr, constant)` is NOT NULL,** as SQL Server reads it (for example AdventureWorks' `LineTotal` and `SalesOrderNumber`). Any other computed column stays nullable.
- **Import SQL DDL… keeps every table of a SQL Server install script with its data.** An `INSERT` with no `;` (Northwind's `Insert Into … Values` lines, batched by `GO`) ran to the next `;` in the file when a big script's data was taken out, so the `CREATE TABLE`s after the last data batch vanished without a word (5 of Northwind's 13 tables).
- **Import SQL DDL… reads more real-world schemas whole.** A key written in another case than its columns (TPC-H's `Primary Key(L_ORDERKEY)` on `l_orderkey`) no longer fails the whole import, and MySQL and Snowflake no longer drop such a one-column key. The keys of an `ALTER TABLE t ADD ( CONSTRAINT … , CONSTRAINT … )` list (as Oracle writes them) are read in every dialect: before, the list was skipped and its primary and foreign keys were lost without a word. `ALTER TABLE TPCD.REGION …` in a script whose tables have no schema adds its keys to `REGION`. Databricks / Spark `CREATE TABLE … AS SELECT CAST(NULL AS integer) AS id, … WHERE 1 = 0` (OMOP CDM for Spark) is read as the empty table of typed columns it is. SQL Server's inline `INDEX ix NONCLUSTERED (…)`, `CLUSTERED COLUMNSTORE` and `HASH` in a column list no longer fail the table, and `INDEX ix UNIQUE (…)` is a unique key. A foreign key that is its table's key, to a unique column that is not the other table's key, is drawn one-to-one. Tables with no schema join the default schema the others name (Northwind's `Orders` and `[dbo].[Region]`).
- **`CREATE TABLE x (LIKE y)`** (PostgreSQL, Redshift) is listed as a table without a column list of its own, no longer as a table that could not be read; and **`ALTER TABLE … ADD COLUMN x MAP<STRING, INT>`** (or any type with a comma inside `<…>`) adds one column, no longer two.
- **A comment on a view** is listed as a skipped comment, no longer as "a comment on … which is not in the files"; a comment stays on the table it was written about when a later script renames that table; and a foreign key to a table outside the files names its table as imported.
- **Import SQL DDL… reads the dialect from the scripts' code, never from their data or names.** What a string holds no longer counts, so MySQL's Chinook script is no longer taken for Databricks because of `'Emerson String Quartet'`, and a column named `bytes`, `number` or `sortkey`, or a PostGIS `geography` column, no longer points at BigQuery, Oracle or Redshift. A BigQuery script with `` `project.dataset.table` `` names and `STRUCT<…>` columns is no longer read as Databricks (which flattened its names).
- **Import SQL DDL: a lost quote no longer hides the tables after it.** A quoted name or string that lost one of its quotes (`CREATE TABLE a" (`, `COMMENT 'it's`) used to pair with the next quote in the file, so every table after it could vanish without a word. Now a quoted name never runs past its line, and a string that runs across the end of one statement into the next `CREATE TABLE` is read as the broken one: the tables after it import, and the broken table is reported with its line. A table whose column list sits behind a stray quote is reported as a table that did not read, not as "a CREATE TABLE without a column list".

The comma is now put in and listed, as in PostgreSQL. A quote lost inside a BigQuery `OPTIONS(description = …)` no longer takes the next column with it (the table is reported). A table with a column named `location`, or a generated column, behind a stray quote is reported with its line instead of being skipped as a `CREATE TABLE … AS SELECT`. An Oracle table that does not read names the real line and cause, not `NOT NULL ENABLE`, and is read without the grammar when it can be. - **Import SQL DDL… keeps column types and schemas as written.** `timestamp with time zone`, `int unsigned`, `vector(20)`, `nvarchar(max)`, `[decimal](18, 2)` and domain or alias type names come in verbatim. `USE`, `USE SCHEMA`, `SET search_path` and `CREATE SCHEMA s CREATE TABLE …` set the schema for the tables after them, so tables keep their schema and cross-schema foreign keys resolve. SQL Server `MS_Description` properties (bracketed or bare level names, and `sp_updateextendedproperty`) are imported as descriptions; computed columns are typed `computed` with a note instead of taking their expression as the type; `DEFAULT NULL` is no longer stored as a default.
- **Import SQL DDL… never hides a mistake in a script as a smaller import.** A comma missing between two columns, or after a column's constraints, is put in and the table imported, with a note naming the line ("a comma added between price and year"), instead of the next column disappearing into the previous one's type; only if the table still does not read is it reported at that line ("a comma missing before year"); a constraint the script named is no longer dropped by `DROP CONSTRAINT IF EXISTS orders_pkey` (only an unnamed one has that name); a unique key on an expression is listed under Not imported instead of becoming a key on a column named `lower` that stopped the whole import; and two placeholders such as `${bronze.schema}.orders` and `${silver.schema}.orders` stay two tables. A table defined twice is no longer counted as a table that could not be read, each problem is logged once, and the dialect pick no longer reads a large script five times over before it appears.
- **Import Power BI or Fabric Semantic Model… keeps more of the model, exactly.** A `dateTime` column Power BI marks date-only or time-only comes in as `date` or `time`; descriptions are kept exactly as written (no full stop added); `isNullable: false` is kept as not null and TMSL `isUnique` as unique. When relationships join a column that is not the table's key, that column is marked unique with a note; a date table whose Mark-as-date-table key (`Date`) no relationship joins is keyed on the one column every relationship joins (`DateKey`), and its date column stays unique. A model with a measure table no longer fails; TMDL values in double quotes, classic-Mac line endings, whole-database TMDL scripts, Tabular Editor deployment scripts and UTF-16 `model.bim` files read; Cyrillic and Greek names become readable snake_case names.
- **Import Power BI or Fabric Semantic Model… names the diagram after the model.** The suggested name and the Project note use the `.SemanticModel` folder or Fabric's display name instead of the tool default "SemanticModel".
- **Import DBML keeps what the file writes.** A default keeps its text (`0.0`, `10.50`, `1e3`, `TRUE`, not the parser's `0`), a primary key keeps its own name, a file with a byte-order mark is read instead of refused, and a one-to-one's unique key in a file ERD Studio did not export is kept.
- **The note that every relationship is saved as optional now counts what the source said.** For a DBML file, SQL scripts or a semantic model alike, it counts the relationships whose foreign-key columns are NOT NULL in the source ("40 relationships were not optional; the other 56 may be empty") instead of the references written without a `?`, and counts each drawn relationship once.
- **An import no longer says details "are not lost" when some were.** For SQL scripts and semantic models the note now says only where the details ERD Studio has no field for are kept. The **Not imported** list no longer shows the same line twice.
- **Import from dbt keeps dbt's `not_null` tests and names every link it does not draw.** `not_null` (scalar, with config, under `data_tests:`, dbt_expectations', contract constraints) is kept on the column and counted in the optional-relationships note. Every relationship from a drawn model to one it does not draw is listed ("person.location_id → location: drawn when you add location"), a relationships test to a `source()` is listed under Not drawn instead of disappearing, and the draft says when a `relationships_where` condition is not kept and which models have no columns in their yml. It also reads the `test_name:` format, model-level tests with `column_name:` and YAML aliases (`tests: *key_tests`).
- **Suggested diagram names keep acronyms, product names and letters whole** and use one separator: `baw-server-on-postgresql`, `sm-sales-sense`, `strasse` for Straße, `ventes_cafe` for Ventes_Café.
- **The detail panel no longer warns "Multiple primary keys detected" on a composite key,** and a long type is cut with an ellipsis (its tooltip shows it whole) instead of hiding the column name.
- **A late Show Me on the start suggestion, after a diagram was kept, opens the Diagrams view** instead of a second draft.

- **The AI setup guide stops and asks you about a git merge conflict** ([#150](https://github.com/liam-machine/erd-studio/issues/150)). When the checking tool finds a diagram or model file that git left with two versions after a merge, `/erd-studio-setup` now shows you the file and line and asks which version to keep (saying so when only table positions differ, as either is then safe). It never picks a version itself and never runs git commands; once you have resolved and saved the file, it checks again. Your AI helper files update with this release, so ERD Studio offers its usual **Update All** prompt.

### Fixed
- **A model file that spells a column's type `data_type:` — as dbt's schema.yml does — now shows that type** ([#144](https://github.com/liam-machine/erd-studio/issues/144)) on the canvas and in `erd-studio` instead of `unknown` — and in the Confluence app once it updates to this version. The next time ERD Studio writes that model's file — any canvas edit to that model or to a relationship stored in it, but not just moving it around — the key is renamed `dataType`, keeping its value and any comment on the line. Where a column has both, `dataType` wins and `data_type` is left as you wrote it, to delete yourself. `erd-studio doctor` names the files and columns that use the dbt spelling, and separately the columns that have both.
- **A value written as a YAML alias (`dataType: *int # note`) in a model file now stays exactly as written when ERD Studio saves that file.** A save used to replace the alias with a copy of its value and drop any comment on the line, even when nothing about that value changed. A value you do change on the canvas is written in place of the alias, and the line's comment is kept.
- **YAML anchors, aliases and numbers in a model file now survive a save** ([#157](https://github.com/liam-machine/erd-studio/issues/157)). A model with an alias inside a `relationships:` entry (such as `role: *buyer`) could not be saved at all — every edit failed with "this relationship entry cannot be read"; it now saves. A key ERD Studio does not manage that reuses a value (`x-note: *grain`) keeps what it said when you change or clear that value on the canvas, instead of silently following the change or failing the save. A save no longer rewrites numbers you did not change (`007`, `1e3`, `.5` and `+1` used to come back as `7`, `1e+3`, `0.5` and `1`) or quotes `description: true`, and the comment on a value that becomes a list or map (such as `meta: ~ # later`) is kept. **Move Relationships to Model Library** now leaves a model file whose `relationships:` list holds a YAML anchor or alias for you, and names it, instead of dropping the anchor.
- **The same link saved at both ends is drawn once**, from the fact's copy whatever the file order, and adding the same link the other way round is refused as a duplicate. **Deleting the line removes both copies**, so it no longer comes back.
- **Editing a model on the canvas no longer rewrites its `relationships:` list.** Renaming a column or changing a description used to rewrite the whole list in the model's file, deleting entries ERD Studio could not read (a typo such as `one_to_many`, an entry missing an end), comments inside the list and any extra keys on an entry. A save now leaves the list exactly as written unless the relationships themselves change, and then edits only the entries that changed. Entries it cannot read are always kept, and an edit it cannot make safely (for example when `relationships:` is not a list) is refused with the file and line named.
- **Unsaved edits in a model file are no longer overwritten.** If a model file is open in a tab with unsaved changes, a canvas edit that would rewrite or delete it now stops and names the file, instead of replacing your unsaved text.
- **A diagram with unresolved git merge conflicts now says so** ([#145](https://github.com/liam-machine/erd-studio/issues/145)). When two people move models on different branches, git can leave conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) in the diagram's file. The canvas used to call that "Invalid JSON" — which looked like corruption — and only after a second or so of retrying. It now explains at once that the diagram has unresolved merge conflicts, names the line, says that when only positions conflict either side is safe to keep, and offers **Open as Text to Resolve**; the diagram reloads by itself as soon as the resolved file is saved. A model file with conflict markers reads "Unresolved git merge conflict on line N" on its node instead of a YAML error, and `erd-studio diff`, `export` and `doctor` report both cases as merge conflicts. `doctor` lists a conflicted diagram as the first thing to sort out, and a model file that does not parse straight after it, both before installing or running dbt, and tells an AI assistant to show you the file and line and ask which side to keep rather than choose one or run git itself.
- **Editing a diagram that git has just left in conflict says "merge conflict"** ([#151](https://github.com/liam-machine/erd-studio/issues/151)). If the diagram was already open when a merge wrote conflict markers into its file, an edit made before the canvas refreshed was refused with a raw JSON error such as `Expected property name…`. It is still refused, with nothing saved, and now says the file has unresolved git merge conflicts and the line of the first one, as opening the diagram does.
- **Add Existing Model, Add models from dbt and Draw from dbt no longer overwrite a relationship you already have.** They used to replace it with dbt's version, wiping its role and changing its cardinality in every diagram. They now keep yours and only add the links that are missing. A link another diagram still draws from its own copy goes into the new diagram's file instead of replacing that drawing.
- **Changing a relationship saved more than once keeps its role.** The line's ⇄ swap or a new cardinality now updates the link as a whole: every copy becomes one entry, with the role shown on the line. If the copies have different roles, it asks you to edit the relationship and choose one, rather than drop one. Re-keying a link that a diagram file held twice moves both copies, and a diagram file holding the same link twice now draws it once.
- **Deleting a relationship tells you if another diagram still draws its own copy** and names that diagram, so the line doesn't seem to come back. That copy is left for you to delete.
- **A broken file no longer changes where new relationships are saved.** A diagram or model file that could not be read (for example during a merge conflict) used to count as holding no relationships, which could switch a project between keeping relationships in each diagram and keeping them in the model library. Such a file is now counted by what its text shows.
- **The unsaved-edits check now works on Windows and macOS.** It compared file paths letter for letter, so a tab whose path VS Code spelled in a different case (a lower-case drive letter such as `c:` on Windows, for example) was missed and its unsaved text could be overwritten. Paths are now compared the way the operating system compares them. The same check protects **Move Relationships to Model Library** and the automatic update of `selectors.yml`.
- **Draw from dbt no longer overwrites unsaved edits in a model file.** When it would add a relationship to a model file that is open with unsaved changes, it now stops before writing anything and names the file.
- **Saving a model no longer adds `dataType: unknown` to columns that have no type.** A column written without a `dataType` stays that way unless you give it one.
- **Files keep their Windows (CRLF) line endings.** Saving a model from Draw from dbt, renaming one, a canvas edit to the open diagram, the v4 → v5 migration and Move Relationships to Model Library could turn a file's CRLF line endings into LF, changing every line in the diff. Each file now keeps the line endings it had.
- **A new relationship no longer inherits another's comment or `role:`.** When one save removed a relationship and added an unrelated one to the same model file, the new entry took over the removed entry's comments and extra keys. It now does so only when the two share an end, as in a column or model rename.
- **Renaming a column no longer writes `cardinality: many-to-one` into its relationship entries.** An entry with no `cardinality:` keeps it unwritten when a rename changes one of its ends.
- **Stripping legacy domain tags keeps your dbt schema files' line endings.** A schema `.yml` with Windows (CRLF) line endings stays CRLF.
- **Relationships whose names differ only in case now draw.** An entry such as `toModel: Dim_Customer` for the model `dim_customer`, or a column spelled `Customer_ID` for `customer_id`, used to be missing from the canvas even though Compare to Physical matched it. It is now drawn with the real names, and the next time you change that relationship it is saved with them too (its comments and extra keys stay). Renaming or removing a column or model now also follows entries that spell it in another case.
- **Renaming a column or model now reaches every diagram.** A diagram that keeps its own copy of a relationship (a project that keeps relationships per diagram, or a copy left as it is) used to keep the old name after a rename in another diagram, so its line disappeared. The rename now rewrites those copies too — and, for a model, that diagram's model list — in the same step, so one undo puts everything back. Only the renamed names change in those files; their layout and line endings stay as they were. If one of those diagram files is open with unsaved changes, the rename stops and names it.
- **Cmd+Z / Ctrl+Z on the canvas now undoes an edit completely.** Pressing it (or Cmd+Shift+Z to redo) after an edit that changed model files, such as ⇄ moving a link to the other model's file or deleting a link saved at both ends, reverted those files only in memory: they were left open as unsaved tabs and the canvas did not redraw. It now saves them and redraws, as the toolbar's Undo and Redo buttons do.
- **A diagram is no longer mistaken for another project's on Windows and macOS.** The check that a diagram belongs to the open dbt project compared folder paths letter for letter, so the same folder spelled in another case could be refused. It now compares them the way the operating system does.
- **Draw from dbt, Add models from dbt and Add Existing Model now fill in column types from your warehouse catalog** (`target/catalog.json`, written by `dbt docs generate`) when your schema .yml has no `data_type:`, the same way the Physical tab does. A column no source gives a type to is left blank rather than set to `unknown`.
- **Retry on a diagram that failed to open no longer flashes "Canvas disconnected".** Pressing Retry on the error page could briefly show a message saying ERD Studio had been updated or restarted and offering to reload the window, although nothing was wrong. That message now only appears when ERD Studio really gives no answer for 5 seconds.

## 1.0.1 — 2026-09-12

### Added

- **`target/catalog.json` is read when it exists, so the Physical view finally knows your
  warehouse.** dbt copies `manifest.json`'s column types straight out of your schema YAML,
  so the stage named *Physical* has only ever shown you your own documentation reflected
  back. `catalog.json` — written by `dbt docs generate` — is the one artifact that has
  actually looked at the warehouse, and ERD Studio never opened it. It does now: real
  column types, and columns nobody got round to documenting. It is unioned with your
  declared columns rather than replacing them, because `dbt docs generate` runs far less
  often than `dbt run` and a catalog-wins rule would hide a column you added an hour ago
  and propose you delete it. Absent catalog, nothing changes. BigQuery's catalog
  reports nested `STRUCT` fields as dotted paths (`address.city`); those leaves are
  folded into their parent rather than rendered as columns no schema YAML could match.
- **Every physical model says where its shape came from.** A chip on the node and a row in
  the details panel name the source — warehouse, your YAML, the manifest, or just a file
  on disk — so a `varchar` on the canvas no longer has to be taken on trust. Types resolve
  warehouse → your `data_type:` → manifest, and a column nothing declares is left blank
  rather than invented.

### Changed

- **The Physical view no longer needs you to have run dbt.** Existence used to mean
  "present in the compiled manifest", so on a project with no `manifest.json` every single
  model rendered as a grey ghost — the canvas said *nothing here exists* when what it meant
  was *you have not run dbt lately*. A model now exists because your dbt project contains
  it: a `.sql`, `.py` or `.csv` under your model, seed or snapshot paths, or a schema YAML,
  manifest node or catalog relation naming it. Models dbt has **disabled** are the one
  exception — `enabled: false` leaves the file on disk but makes `ref()` fail, so a bare
  file no longer counts as existing for them, and a ghost says which of the two reasons
  applies: missing entirely, or disabled. (A disabled model your schema YAML still
  documents keeps what the YAML says — that is a different question.) Seeds and snapshots
  are covered too; they used to vanish from the stage silently.
- **A model you have designed but not built now appears as a ghost instead of vanishing.**
  The stage used to drop anything it could not resolve, so the one thing you most wanted to
  see — the gap between the design and the warehouse — was the thing it hid.

## 1.0.0 — 2026-09-12

**ERD Studio is 1.0.** The file format has been stable at schema v5 since 0.6.x, every
canvas edit has gone through a single atomic write path for as long, and the extension has
shipped fifty-three times without a breaking change to anything on disk. The version number
now says so. A `.erd-studio/` directory written today will keep opening, and any change that
would break one will come with a migration and a major version.

### Changed

- **A rewritten README.** It led with a slogan and a feature list and never said plainly what
  the extension is or how it works. It now opens with the idea — design your warehouse where
  you build it — then shows the whole design in one diagram: one YAML per model, one JSON per
  diagram, and a canvas that renders them. Editing either side updates the other, models are
  shared across diagrams, and it all stays in Git with no account, database or server. The
  reasons to use it are stated as outcomes rather than features, and the comparison with
  traditional tools such as erwin, which keep models in application-specific files or a
  separate modelling repository, is now explicit.
- **The README says how to use ERD Studio without dbt.** Logical modelling never needed a dbt

## 0.6.49 — 2026-09-07

### Added

- **Both bug and feature, with the odds.** The analysis panel shows the split rather than only the winner — *Feature request 86% · Bug 14%* — so a near-certainty no longer looks the same as a coin toss. When it is genuinely close it says **Close call — pick one in the header** instead of quietly presenting a guess as the answer.
- **The type is chosen for you, and yours to overrule.** The dialog opens as a bug because most reports are, and the analysis moves it to a feature request as your description takes shape — the title, the labels, the placeholders and the GitHub template all follow. `Bug | Feature` sits in the header the whole time: pick one and it stays picked, and the analysis stops moving it until you hand the choice back with **auto**. With no model configured the switch is still there, so a feature request is always one click away.
- **Diagnostics you can see before you send them.** Versions, OS, the domain summary and the recent-error count are shown as chips with the exact text one click away, and a **remove** toggle if you would rather not share them. They are attached by default and are never sent anywhere until you press Submit on GitHub.

- **AI assist, on by default and using your own model.** The dialog makes a single request that drafts a title, picks bug vs feature, pulls the steps out of your description and checks whether the issue has already been reported. Only what you typed is sent — diagnostics, file paths and model names never are. It uses whichever language model VS Code already offers you, so nothing new is configured and no destination of ours is involved; `erdStudio.feedback.aiAssist` turns the whole thing off. A strong match takes the dialog over and offers to add your details to the existing thread (or, when it was already fixed in a newer version, tells you to update instead of filing). Every suggestion lands in an editable field; nothing is decided for you, and a model outage never blocks a report.
- **One click to start, then nothing.** The first time your own model would be used on a machine, the panel shows a single **Analyse this for me** button ("Uses your own model. VS Code will ask once.") rather than running while you type — VS Code's access dialog should follow something you pressed. Once one analysis has come back, the panel simply keeps up with your description from then on, in that report and every future one. Dismiss VS Code's dialog and nothing breaks: the button comes back and the rest of the dialog is untouched. The same button is offered whenever the dialog opens with a description already filled in for you — the canvas error screen does that, and the text it fills in is the error itself — so nothing you did not write is ever sent without you asking for it.
- **Choose which model does the triage.** A picker in the analysis panel names every destination — Automatic, your editor's own model (Copilot), your own API endpoint, and the ERD Studio service — and switching is one click, remembered from then on. It exists because "Automatic" always tried your own model first and stopped there: if you have Copilot but would rather not spend it triaging your own bug report, you can now send it to the ERD Studio service instead (or the other way round, pinning your own model so nothing else is ever used). Destinations that cannot run on your machine are listed with the reason rather than hidden, and a pinned destination never quietly falls back to another one — if it stops working the dialog says so and leaves the picker there. Also `erdStudio.feedback.provider`, for setting it without opening the dialog.
- **AI assist settings and commands** — `erdStudio.feedback.aiAssist`, `erdStudio.feedback.provider`, `erdStudio.feedback.endpoint`, `erdStudio.feedback.model` and `erdStudio.feedback.hostedFallback`, with **ERD Studio: Set Feedback API Key** / **Clear Feedback API Key** storing the key in VS Code's secret storage, never in `settings.json`. Left on Automatic the order is your model first, then your endpoint, then the fallback below — and where none of them exists the panel is simply absent.
- **A hosted fallback, for when there is no model at all.** As a last resort the analysis can go to a small relay run by the extension author, which forwards your description to a named third-party AI provider under the author's account and that provider's terms, so the duplicate check works for people with no Copilot subscription and no endpoint of their own. It always asks first, naming **both** the relay and the provider that receives the text, and saying what leaves your machine; `erdStudio.feedback.hostedFallback: false` removes it outright. In this release that relay is **erd-studio.liam-is-an.ai**, run by the extension author, forwarding to **DeepSeek**. - **My Reports.** When you are signed in to GitHub in VS Code, a sidebar view lists the issues you filed from ERD Studio and their state — open with the comment count, implemented (with the version it shipped in, when that is known), or closed as not planned — refreshed every few hours, and one notification when something you reported ships. It is hidden entirely when you are not signed in; you are never prompted to sign in, and you can turn the whole thing off with `erdStudio.feedback.trackReports`.

### Changed

- **The canvas's top-right buttons no longer collide with the toolbar.** **Feedback** and **View File** are two labelled buttons pinned to the top-right corner, and on a laptop — or any window narrow enough, which with the sidebar open is most of them — the centred toolbar grew straight into them. ### Security

- **The feedback endpoint can only be set in your own settings.** `erdStudio.feedback.aiAssist`, `.provider`, `.endpoint`, `.model` and `.hostedFallback` are now machine-scoped and read only from your user settings, so a repository you open cannot redirect the analysis request — and the API key stored in VS Code's secret storage that goes with it — to a server of its author's choosing. - **"I want a new ability to…" is no longer classified as a bug.** Every fresh dialog told the model *"The user is filing this as a bug, but decide for yourself"* — because `bug` is simply the kind the dialog opens on, not something you had chosen. The model was being handed a false fact and asked to argue with it, and it mostly agreed. - **The dialog no longer freezes behind a notification.** Submitting waited for a notification to be dismissed before re-enabling anything, so Cancel, Escape, the backdrop and the close button were all dead until you noticed the toast.

## 0.6.47 — 2026-09-07

### Added

- **Report a Bug** — `ERD Studio: Report a Bug` (command palette, sidebar, canvas toolbar and error screens) opens a prefilled GitHub issue with diagnostics (versions, OS, domain summary, recent errors) and, from a canvas, copies a screenshot to the clipboard for pasting. Nothing is sent until you submit on GitHub.

Previously that flag was always passed with no way to turn it off and no warning; the launch is now confirmed in a modal that names the flags first.

### Fixed

- **Creating or renaming a model no longer overwrites someone else's model file** — the `logical-models/` library is shared by every domain, so "New Model" and "Rename Model" could silently replace an existing `logical-models/<name>.yml` (and everything in it) when the name was already taken elsewhere. Both now refuse the name and tell you which file already exists.
- **Undo restores the model file with the domain file** — a column, grain, role or rationale change writes `logical-models/*.yml` and the domain `.json`; the yml was written outside VS Code's undo stack, so one Cmd+Z rewound the domain and left the yml edited. They are now a single edit and a single undo step, and a rejected edit leaves both files untouched.
- **Harness files are never overwritten without asking** — installed AI harness files (`CLAUDE.md`, `AGENTS.md`, Copilot instructions, Gemini styleguide) used to be rewritten on activation whenever ERD Studio's schema version moved on. Out-of-date files now raise a prompt offering **Update All**, **Choose…** or **Dismiss**, and in `AGENTS.md` only the region between the ERD Studio markers is replaced — anything you wrote around it is preserved.
- **The physical stage shows models that are only in the manifest** — a model with no entry in a schema `.yml` was dropped from the physical diagram entirely, even when dbt clearly knew about it. Each model is now resolved from yml first and falls back to the manifest on its own, so it appears either way (and relationships come from the tests declared in both sources).
- **Model and column names now match across stages regardless of case** — `DIM_CUSTOMER` in the manifest and `dim_customer` in your logical design are recognised as the same thing, so the physical stage renders and the discrepancy report no longer reports the whole model as both "missing" and "extra". Names are still displayed exactly as they are written.
- **An error no longer throws away the diagram you were looking at** — a failed action used to replace the whole canvas with an error page, losing selection, zoom and pan. Errors now appear as a dismissable toast over the live canvas; the full-screen page (with Retry and Report a Bug) is reserved for a domain that fails to load at all.
- **`?` can be typed in text fields again** — the Shift+? legend shortcut fired while you were typing in a name, description or note, so the character never reached the input (and the legend flew open). Canvas shortcuts are now ignored whenever focus is in a text field.
- **SCD and additive types survive an inline column edit** — renaming a column or changing its data type on the canvas silently cleared that column's SCD type and additive type. Inline edits now leave fields they do not touch alone.
- **Reporting a bug from a hidden canvas no longer hangs** — the screenshot capture never completed when the editor tab was in the background; it now gives up after a short timeout and the bug report is submitted without the image instead of waiting forever.
- **Multi-select delete and drag are one undo step** — deleting a rubber-band selection that includes notes and standalone relationships now removes them in a single edit (one Cmd+Z restores everything, matching models), and dragging several notes together is persisted as one edit instead of one per note.
- **Undo/redo no longer double-saves** — each toolbar undo/redo wrote the domain file and re-rendered the canvas twice; it now does so once.
- **Undo/redo never saves a model file you are editing by hand** — a toolbar undo used to force-save *every* unsaved `logical-models/*.yml` buffer, including one open in another tab with work in progress. It now flushes only the files ERD Studio itself wrote for that domain.
- **Renaming a model on the canvas keeps comments and custom keys** — the renamed `logical-models/*.yml` is now carried over from the old file instead of being regenerated, so hand-written comments, key order and keys ERD Studio does not own survive the rename.
- **Adding an existing model writes nothing when the edit fails** — "Add Existing Model" seeded the library file before the domain edit, leaving an orphan `.yml` behind if the edit was rejected (and out of reach of undo). The file is now created in the same edit as the domain change.
- **"Add Existing Model" accepts every legal dbt model name again** — a hardening pass had started rejecting uppercase and digit-leading names (e.g. `DimCustomer`, `2024_snapshot`) that dbt itself allows. Names discovered in your dbt project are now only checked for file-path safety; the lowercase naming convention still applies to models you create or rename in ERD Studio.
- **One bad model name no longer blanks the whole canvas** — a hand-edited or AI-written domain file whose `logical.models` contained a name with a path separator failed to open at all. It now renders that single entry as a broken-reference node and draws the rest of the diagram.
- **Note resize is validated before it is written** — an `updateAnnotation` carrying a non-numeric width/height (or a non-string id) is rejected instead of writing `null` sizes into the domain file.
- **Migration only ever touches domain files** — an unrelated `.json` kept in a layer directory could be picked up as a migration candidate and silently restructured if you accepted the prompt. Only files with a `schemaVersion` are now considered.
- **Migration prompt names the real command** — the "unsupported domain format" message quoted a command title that does not exist; it now names **ERD Studio: Migrate Domains to Central Model Store** exactly as the palette shows it.
- **A refused layer change no longer leaves a phantom layer in the sidebar** — when `layers.json` cannot be read, ERD Studio refuses to overwrite it (so your file is never clobbered with defaults), but the add/rename/delete/recolour/reorder you attempted was still applied in memory: the tree, the layer badges and the "Create Domain" layer picker showed a layer that was not on disk until the window reloaded. - **Deleting a model cleans up its notes** — a canvas note linked to a deleted model kept a dashed edge pointing at a node that no longer exists. Removing models now clears those links (and their saved positions) the same way for both domain file formats.
- **No more redundant canvas refresh after an edit** — a column, grain or role change bounced back through the file watcher ~300 ms later and re-rendered the canvas a second time, clearing the selected column. Only `package.json`, `README.md`, `CHANGELOG.md`, `LICENSE`, the icons and the built `dist/` bundles ship. CI now fails if the packaged file list grows unexpectedly.

- **Deploy resilience** — the version bump is now computed against the latest published marketplace version (so a desynced repo can no longer fail with "version already exists") and is committed and pushed *before* publishing, so a failed publish never leaves `main` behind the marketplace.
