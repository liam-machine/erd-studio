# Harness and setup skill

> Moved out of the root `CLAUDE.md` so it loads only when needed. Loads when you read files under `src/harness/`; also read it before touching `src/services/harnessService.ts` or `harnessAssets.ts`.

## The setup skill

- **The skill** (`src/harness/claude/erd-studio-setup/`, installed to `.claude/skills/erd-studio-setup/` and/or `.agents/skills/erd-studio-setup/`) first Globs for `dbt_project.yml`: with none it takes the **Without dbt** route, the whole walkthrough in `references/without-dbt.md` (design a first diagram from a description of the business, start from **Import DBML…**, or enrich existing tables; checks with `doctor` and `export` only — never `diff`, never a dbt command, never "install dbt"; reads doctor's `dbtProject: false` / `skippedChecks` `not-dbt-project`; the design fields state the intended design, so the as-built rule and Target-design backlog do not apply). Otherwise it picks one of three routes itself after doctor and states it in one line, never asking: **quick start** (the default — `dbt parse` only if doctor asks, no catalog, one area mirrored from dbt with no style, `diff` until clean, hand over to the canvas, *then* offer the modelling style), **enrich** (doctor reports existing domains, e.g. a Draw from dbt draft — proposes keys, grain, natural keys, roles and rationale only where dbt backs them, one "Add these?", never rebuilds, renames or touches columns / types / relationships) and **full setup** (on request or when the user describes their style up front). Stage 0 names **ERD Studio: Draw from dbt…** once as the no-AI first diagram. Canvas-fallback mode lives in `references/troubleshooting.md` and the non-core dbt flavour wording in `references/dbt-setup.md`, keeping SKILL.md under the 500-line limit a test enforces. The full route walks doctor → dbt setup → choosing one area and a modelling style → building logical models with the `/erd-studio` schema skill, applying the approach only through logical-only fields → `diff` until clean → a conformance review (at most three fix rounds; drift on models the user already had is one question, defaulting to "match dbt") → handing over to the canvas. **The modelling style is detected, never asked cold** (Stage 3b): it reads `inventory.conventions` and confirms it in one plain sentence with the evidence and a yes default ("Your project looks like a medallion layout (bronze → silver → gold) with Kimball-style marts — … Sound right? Or describe how your team does it."), naming the best guess and the alternative in one question when `confidence` is weak; when `shape.sources` lacks `names` it says so ("Your models aren't named `dim_`/`fct_`, but they read like Kimball: …"), and when `sources` is only `structure` it words the style as a guess from table shape ("Your tables are shaped like a Data Vault — …"); an `inmon-3nf` guess from shape alone is always a real question ("…Is that how your team models, or should I just draw it as dbt has it?") whose "no" / "not sure" mirrors dbt; before concluding `none` it glances at the inventory descriptions and offers a clearly described style as a weak guess in the same one question; with `shape.style: none` it says "I couldn't see a particular modelling style, so I'll draw your model exactly as dbt has it." and mirrors dbt — no lookup, no saved approach file, no conformance review, and no style pushed (one is offered as an optional Stage 6 next step). An existing `modelling-approach.md` is confirmed in one line and not re-detected; a style the user describes in their own words beats the detection. An agreed style is looked up and saved to `.erd-studio/modelling-approach.md`. It runs the CLI explicitly (no `!` context injection), never runs `dbt run` / `build` / `seed` / `snapshot`, and falls back to the canvas sync plan and then a manual comparison when there is no CLI. `allowed-tools` pre-approves only `Read`, `Glob`, `Grep`, the two launcher paths and the subcommand-scoped bare `dbt` rules — Edit and Write always go through Claude Code's normal approval. **Two frontmatter variants are generated at install time** (`skillForTarget()` in `harnessAssets.ts`): the `.claude` copy is the source verbatim (Claude's `allowed-tools` list + `argument-hint`); the `.agents` copy keeps only the spec's portable fields (`AGENT_SKILL_FRONTMATTER_KEYS`: `name`, `description`, `license`, `compatibility`, `metadata`), dropped line by line so the kept ones stay byte-identical, with a structural YAML rewrite as fallback — Claude `Bash(prefix:*)` rules are not verified in the other tools. Bodies are identical; both get the version marker.
- **`.erd-studio/modelling-approach.md`** is optional free-form markdown for AI assistants (technique, the user's words, rules, field mapping, sources, date), plus an optional `## Metadata` section — the team's **metadata list** (Key / On / Values / Source `dbt` | `the team`), which `SCHEMA_CONTENT` ("The team's metadata list") tells every assistant to follow and the setup skill writes from `conventions.meta` after one yes (`references/metadata.md`; a file with only this section has no Technique line, so Stage 3b still detects the style). `SCHEMA_CONTENT` tells every harness to read and follow it; the extension **never parses it** — `classifySemanticPath()` returns `other`, layer detection only looks at directories, `listSubjectAreas()` only reads `{layer}/*.json`, and the Claude hook's `case` lets it through without spending the one-time check (`test/unit/modellingApproachFile.test.ts`, `harnessService.test.ts`). `test/skill-evals/erd-studio-setup/` holds its skill-creator evals (not run by vitest).

## Harness versioning

AI coding harness files (installed via `erdStudio.installCodingHarness`) embed a version marker to track staleness:

```
<!-- erd-studio-harness: N -->
```

**Key components in `src/services/harnessService.ts`:**

| Export | Purpose |
|--------|---------|
| `HARNESS_VERSION` | Current version string — bump when `SCHEMA_CONTENT` or generators change |
| `extractHarnessVersion(content)` | Parses version from file content, returns `null` if no marker |
| `detectStale(workspaceRoot)` | Returns installed `HarnessTarget[]` whose embedded version ≠ `HARNESS_VERSION`. Files with **no** marker are unmanaged (hand-written) and are never reported. For a managed Claude install staleness is **per file**: SYNC.md missing or outdated, or the setup skill carrying another marker, makes `claude` stale. A *missing* setup skill is deliberately **not** stale (it is reported by `harnessStatus()`; the v18 "Update All" writes it anyway) |
| `claudeManagedFiles()` / `agentsManagedFiles()` | Each skill target's version-marked files: `{.claude,.agents}/skills/erd-studio/SKILL.md`, its `SYNC.md`, and `{.claude,.agents}/skills/erd-studio-setup/SKILL.md` |
| `harnessStatus(workspaceRoot)` | Per-file `FileState` (`missing` / `current` / `outdated` / `unmanaged`, types in `src/types/harness.ts`) for every target — `claude` and `agents` each as `{ schemaSkill, setupSkill }` (schema folds in SYNC.md), plus `claude.hookRegistered` — read by the Welcome panel and `erd-studio doctor` |
| `installRecommended(workspaceRoot, { replaceUnmanaged, keepUnmanaged?, assistants? })` | The Welcome panel's one-click install over `recommendedSkillTargets(assistants)` (omitted = none detected = both folders). Returns `needs-confirmation` (writing nothing) when any selected SKILL.md is unmanaged and neither flag is set, `unchanged` when every selected folder is current, else `installed` / `updated` / `failed` with `filesWritten`; `targets` names the folders covered |
| `setupSkillFiles(target)` | The setup skill's files exactly as `install()` writes them for `claude` or `agents` |
| `CODEX_REGION_BEGIN` / `CODEX_REGION_END` | `<!-- BEGIN/END erd-studio-harness -->` markers wrapping the ERD section in `AGENTS.md`; updates replace only this region |
| `findCodexRegion(content)` / `mergeCodexContent(existing, generated)` | Locate / splice the managed `AGENTS.md` region (falls back to heading…version-marker for pre-v16 installs, appends when absent) |

Generated paths honour `erdStudio.semanticDir` (SKILL/SYNC content in both skill folders, the setup skill, the Claude PreToolUse hook, Copilot `applyTo`, Gemini, Codex).

**Five targets:** `claude`, `agents` (**Agent Skills — GitHub Copilot, Codex, Gemini CLI, Cursor**, primary `.agents/skills/erd-studio/SKILL.md`), `copilot` (instructions file), `gemini`, `codex` (`AGENTS.md` region). The schema skill's frontmatter is only `name` + `description`, so `claude` and `agents` share one generator. **The setup skill is a companion of both skill targets**, not a target of its own. Installing `claude` writes the schema skill, SYNC.md, `enforce-skill.sh`, the `.claude/settings.local.json` hook entry **and** `.claude/skills/erd-studio-setup/`; installing `agents` writes the schema skill, SYNC.md and `.agents/skills/erd-studio-setup/` — **no hook** (only Claude Code gets the enforce-skill guard; the other tools' hook formats differ). Setup files come from `harnessAssets.ts`; only SKILL.md gets the version marker, and the source `.md` files never contain one. A setup SKILL.md with no marker is the user's and is left untouched unless the install passes `replaceUnmanagedSetupSkill` — `install()`'s `overwrite` applies to the primary file only (the one the Update All / QuickPick prompt named), and only the Welcome panel's **Replace** passes the companion flag. **Gitignore rule:** each target's primary directory is added on its first install — except `agents`, which has **no `gitignorePattern` and is never ignored**: Gemini CLI's `read_file` refuses any path `.gitignore` matches (`respectGitIgnore` defaults to true), so an ignored `.agents/skills/` would let the guide activate and then stall at its first reference file. The setup directory `.claude/skills/erd-studio-setup/` is added only when `.claude/skills/erd-studio/` is listed — it follows the user's existing choice — and the check keys on the setup directory's first appearance, so v17 upgraders get the line too. **The hook command** is `[ -n "$CLAUDE_PROJECT_DIR" ] && bash "$CLAUDE_PROJECT_DIR/.claude/skills/erd-studio/enforce-skill.sh" || true` (`HOOK_COMMAND`), and the script exits 0 silently unless `tool_name` is exactly `Edit` or `Write`: GitHub Copilot runs `.claude/settings.local.json` hooks when Claude hooks are enabled and ignores the matcher. `mergeHookConfig` replaces any older ERD Studio hook command (legacy `check-skill.sh`, or the unguarded form) and keeps other hooks in the same entry.

**The PreToolUse hook only ever denies.** `enforce-skill.sh` blocks the first `.erd-studio` edit per Claude session (except `modelling-approach.md`, which has no file format) (deny text: "load the /erd-studio skill (file-format rules) before editing .erd-studio files, then retry. This is a one-time check per session — the /erd-studio-setup walkthrough expects it.") and otherwise exits 0 with **no output**, so Claude Code's normal permission flow decides. A test asserts the generated script never contains `"permissionDecision":"allow"`. Do not add an allow path back.

**Activation flow** (`src/extension.ts`): on startup, `detectStale()` runs. If stale targets are found, a warning notification offers "Update All" (updates immediately), "Choose…" (opens the install QuickPick with outdated targets pre-selected), or "Dismiss". Nothing is ever overwritten silently, unmanaged files are never flagged, and `AGENTS.md` content outside the BEGIN/END region is always preserved. When no harness files exist at all, the install QuickPick is offered once per workspace (tracked in `workspaceState`) — except on the fresh-install run that opens the Welcome panel, which skips it for that run only (the flag stays unset). The QuickPick labels existing unmanaged files honestly ("will be replaced" / "section will be appended").

**When to bump `HARNESS_VERSION`:** any change to `SCHEMA_CONTENT`, the generator functions, or naming conventions that would make previously installed harness files incorrect. Do **not** bump for unrelated extension changes — the version is independent of `package.json` version.
