# Harness and setup skill

> Moved out of the root `CLAUDE.md` so it loads only when needed. Loads when you read files under `src/harness/`; also read it before touching `src/services/harnessService.ts` or `harnessAssets.ts`.

## The setup skill

- **The skill** (`src/harness/claude/erd-studio-setup/`, installed to `.claude/skills/erd-studio-setup/` and/or `.agents/skills/erd-studio-setup/`) first Globs for `dbt_project.yml`: with none it takes the **Without dbt** route, the whole walkthrough in `references/without-dbt.md` (design a first diagram from a description of the business, start from **Import DBML…**, or enrich existing tables; checks with `doctor` and `export` only — never `diff`, never a dbt command, never "install dbt"; reads doctor's `dbtProject: false` / `skippedChecks` `not-dbt-project`; the design fields state the intended design, so the as-built rule and Target-design backlog do not apply). Otherwise it picks one of three routes itself after doctor and states it in one line, never asking: **quick start** (the default — `dbt parse` only if doctor asks, no catalog, one area mirrored from dbt with no style, `diff` until clean, hand over to the canvas, *then* offer the modelling style), **enrich** (doctor reports existing domains, e.g. an Import from dbt draft — proposes keys, grain, natural keys, roles and rationale only where dbt backs them, one "Add these?", never rebuilds, renames or touches columns / types / relationships) and **full setup** (on request or when the user describes their style up front). Stage 0 names **ERD Studio: Import from dbt…** once as the no-AI first diagram. Canvas-fallback mode lives in `references/troubleshooting.md` and the non-core dbt flavour wording in `references/dbt-setup.md`, keeping SKILL.md under the 500-line limit a test enforces. The full route walks doctor → dbt setup → choosing one area and a modelling style → building logical models with the `/erd-studio` schema skill, applying the approach only through logical-only fields → `diff` until clean → a conformance review (at most three fix rounds; drift on models the user already had is one question, defaulting to "match dbt") → handing over to the canvas. **The modelling style is detected, never asked cold** (Stage 3b): it reads `inventory.conventions` and confirms it in one plain sentence with the evidence and a yes default ("Your project looks like a medallion layout (bronze → silver → gold) with Kimball-style marts — … Sound right? Or describe how your team does it."), naming the best guess and the alternative in one question when `confidence` is weak; when `shape.sources` lacks `names` it says so ("Your models aren't named `dim_`/`fct_`, but they read like Kimball: …"), and when `sources` is only `structure` it words the style as a guess from table shape ("Your tables are shaped like a Data Vault — …"); an `inmon-3nf` guess from shape alone is always a real question ("…Is that how your team models, or should I just draw it as dbt has it?") whose "no" / "not sure" mirrors dbt; before concluding `none` it glances at the inventory descriptions and offers a clearly described style as a weak guess in the same one question; with `shape.style: none` it says "I couldn't see a particular modelling style, so I'll draw your model exactly as dbt has it." and mirrors dbt — no lookup, no saved approach file, no conformance review, and no style pushed (one is offered as an optional Stage 6 next step). An existing `modelling-approach.md` is confirmed in one line and not re-detected; a style the user describes in their own words beats the detection. An agreed style is looked up and saved to `.erd-studio/modelling-approach.md`. It runs the CLI explicitly (no `!` context injection), never runs `dbt run` / `build` / `seed` / `snapshot`, and falls back to the canvas sync plan and then a manual comparison when there is no CLI. `allowed-tools` pre-approves only `Read`, `Glob`, `Grep`, the two launcher paths and the subcommand-scoped bare `dbt` rules — Edit and Write always go through Claude Code's normal approval. **Two frontmatter variants are generated at install time** (`skillForTarget()` in `harnessAssets.ts`): the `.claude` copy is the source verbatim (Claude's `allowed-tools` list + `argument-hint`); the `.agents` copy keeps only the spec's portable fields (`AGENT_SKILL_FRONTMATTER_KEYS`: `name`, `description`, `license`, `compatibility`, `metadata`), dropped line by line so the kept ones stay byte-identical, with a structural YAML rewrite as fallback — Claude `Bash(prefix:*)` rules are not verified in the other tools. Bodies are identical; both get the version marker.
- **`.erd-studio/modelling-approach.md`** is optional free-form markdown for AI assistants (technique, the user's words, rules, field mapping, sources, date), plus an optional `## Metadata` section — the team's **metadata list** (Key / On / Values / Source `dbt` | `the team`), which `SCHEMA_CONTENT` ("The team's metadata list") tells every assistant to follow and the setup skill writes from `conventions.meta` after one yes (`references/metadata.md`; a file with only this section has no Technique line, so Stage 3b still detects the style). `SCHEMA_CONTENT` tells every harness to read and follow it; the extension **never parses it** — `classifySemanticPath()` returns `other`, layer detection only looks at directories, `listSubjectAreas()` only reads `{layer}/*.json` and `{layer}/diagrams/*.dbml` diagrams, and the Claude hook's `case` lets it through without spending the one-time check (`test/unit/modellingApproachFile.test.ts`, `harnessService.test.ts`). `test/skill-evals/erd-studio-setup/` holds its skill-creator evals (not run by vitest).

## Logical first: what a folder without dbt gets (v42)

Every harness file is written for the root it lands in: `install()`, `harnessStatus()`, `detectStale()` and `installRecommended()` read `hasDbtProjectFile(workspaceRoot)` themselves (the same answer as `erdStudio.hasDbtProject`), so no caller passes anything. **In a root without `dbt_project.yml` nothing installed carries a dbt instruction or the word dbt**; in a dbt project every file is byte for byte what v41 wrote, apart from the version marker.

- **Whole dbt-only files are not installed there:** the schema skill's `SYNC.md` (`DBT_ONLY_COMPANIONS`) and the setup skill's `references/dbt-setup.md`, `metadata.md` and `verify-and-fix.md` (`dbtOnly` in `harnessAssets.ts`). Two files install under another name there (`logicalPath`): `references/without-dbt.md` → `references/walkthrough.md` (the whole walkthrough) and `references/dbt-explained.md` → `references/glossary.md`.
- **Shared text is scoped in the source** with `<!-- dbt-only -->…<!-- /dbt-only -->` (kept only in a dbt project) and `<!-- no-dbt -->…<!-- /no-dbt -->` (kept only without one), read only by `applyDbtScope()` in `harnessAssets.ts`. A span may cover part of a line or whole lines (cut with its last line break); the block form, each marker alone on its line, goes around a code block so its fences stay at line start (a test parses those blocks). Spans never nest. The same markers work inside the `SKILL_PART` / `DBML_PART` / `LEGACY_PART` / `SYNC_CONTENT` strings and the generators, which call `applyDbtScope()` on their output. A `HarnessAsset`'s `content` is the dbt project's copy (markers removed) — what other tests read — and `source` is the authored text.
- **The scope is marked**: each version-marked file written without dbt carries `LOGICAL_SCOPE_MARKER` (`<!-- erd-studio-harness-scope: logical -->`) after the version marker; a dbt project's carry none. A current file whose scope does not match its root reads as `outdated` (`fileState(path, dbt)`, and the Codex region by its own text), so a folder that gains `dbt_project.yml` later is offered Update All / Set Up My AI Helper, which writes the dbt files — and one that loses it is rewritten without. **Without dbt, only ERD Studio's own dbt-only files are removed** (`dbtLeftovers()`): a v41-or-older install, or one made while the folder held `dbt_project.yml`, left `SYNC.md` and the dbt references there. A `SYNC.md` goes only when it carries a marker that is not newer; a reference (no marker) only when its text is one ERD Studio shipped (`SHIPPED_SETUP_REFERENCE_HASHES` in `src/services/harnessShippedReferences.ts` — add the new hash whenever a dbt-scope reference changes; `harnessShippedReferences.test.ts` prints it), and only while the setup SKILL.md is ours. Until the refresh removes them they make their skill read `outdated`. A hand-written or edited file is never touched, and nothing else is deleted: the plain-named copies stay once a folder gains dbt.
- `schemaSkillFiles({ dbt })`, `setupSkillFiles(target, { dbt })`, `generateContent(id, { dbt })`, `claudeManagedFiles(dbt)` and `agentsManagedFiles(dbt)` default to the dbt project's files.
- Line limits apply to each installed variant, not to the source (`harnessAssets.test.ts`, `harnessService.test.ts`): the dbt copy of the setup `SKILL.md` is at its limit, so change it only by replacing lines; a `no-dbt` span adds nothing there.

## Harness versioning

AI coding harness files (installed via `erdStudio.installCodingHarness`) embed a version marker to track staleness:

```
<!-- erd-studio-harness: N -->
```

**Key components in `src/services/harnessService.ts`:**

| Export | Purpose |
|--------|---------|
| `HARNESS_VERSION` | Current version string — bump when `SCHEMA_CONTENT` or generators change |
| `extractHarnessVersion(content)` | Parses version from file content, returns `null` if no marker |
| `detectStale(workspaceRoot)` | Returns installed `HarnessTarget[]` whose embedded version is **older** than `HARNESS_VERSION`. Files with **no** marker are unmanaged (hand-written) and are never reported, and nor is a **newer** marker (a teammate on a later ERD Studio, `isNewerHarnessVersion`). For a managed Claude install staleness is **per file**: a companion (SYNC.md, DBML.md, LEGACY.md) missing or older, or the setup skill carrying an older marker, makes `claude` stale. A *missing* setup skill is deliberately **not** stale (it is reported by `harnessStatus()`; the v18 "Update All" writes it anyway) |
| `claudeManagedFiles()` / `agentsManagedFiles()` / `codexManagedFiles()` | Each skill target's version-marked files: `{.claude,.agents}/skills/erd-studio/SKILL.md`, its companions `SYNC.md`, `DBML.md` and `LEGACY.md`, and `{.claude,.agents}/skills/erd-studio-setup/SKILL.md`; Codex's are `.agents/skills/erd-studio/DBML.md` and `LEGACY.md` |
| `harnessStatus(workspaceRoot)` | Per-file `FileState` (`missing` / `current` / `outdated` / `newer` / `unmanaged`, types in `src/types/harness.ts`) for every target — `claude` and `agents` each as `{ schemaSkill, setupSkill }` (schema folds in its companions), plus `claude.hookRegistered` and `hooks` (`{ copilot, codex, gemini }`, the other assistants' pre-edit hooks: script present **and** registered) — read by the Welcome panel and `erd-studio doctor` (whose `update-harness` covers every target). A `newer` file is never replaced by `install()`, Update All or the Welcome panel |
| `schemaSkillFiles({ dbt })` | The schema skill's files exactly as `install()` writes them: `SKILL.md`, `SYNC.md` (dbt projects only), `DBML.md`, `LEGACY.md` |
| `installRecommended(workspaceRoot, { replaceUnmanaged, keepUnmanaged?, assistants? })` | The Welcome panel's one-click install over `recommendedSkillTargets(assistants)` (omitted = none detected = both folders). Returns `needs-confirmation` (writing nothing) when any selected SKILL.md is unmanaged and neither flag is set, `unchanged` when every selected folder is current, else `installed` / `updated` / `failed` with `filesWritten`; `targets` names the folders covered |
| `setupSkillFiles(target, { dbt })` | The setup skill's files exactly as `install()` writes them for `claude` or `agents` (without dbt: no dbt-only reference, `walkthrough.md` / `glossary.md` names) |
| `CODEX_REGION_BEGIN` / `CODEX_REGION_END` | `<!-- BEGIN/END erd-studio-harness -->` markers wrapping the ERD section in `AGENTS.md`; updates replace only this region |
| `findCodexRegion(content)` / `mergeCodexContent(existing, generated)` | Locate / splice the managed `AGENTS.md` region (falls back to heading…version-marker for pre-v16 installs, appends when absent) |

Generated paths honour `erdStudio.semanticDir` (SKILL/SYNC content in both skill folders, the setup skill, the Claude PreToolUse hook and the other assistants' hook scripts, Copilot `applyTo`, Gemini, Codex).

**Five targets:** `claude`, `agents` (**Agent Skills — GitHub Copilot, Codex, Gemini CLI, Cursor**, primary `.agents/skills/erd-studio/SKILL.md`), `copilot` (instructions file), `gemini`, `codex` (`AGENTS.md` region). The schema skill's frontmatter is only `name` + `description`, so `claude` and `agents` share one generator. **The setup skill is a companion of both skill targets**, not a target of its own. Installing `claude` writes the schema skill, SYNC.md, `enforce-skill.sh`, the `.claude/settings.local.json` hook entry **and** `.claude/skills/erd-studio-setup/`; installing `agents` writes the schema skill, SYNC.md and `.agents/skills/erd-studio-setup/`. The other assistants' pre-edit hooks are separate (next section). Setup files come from `harnessAssets.ts`; only SKILL.md gets the version marker, and the source `.md` files never contain one. A setup SKILL.md with no marker is the user's and is left untouched unless the install passes `replaceUnmanagedSetupSkill` — `install()`'s `overwrite` applies to the primary file only (the one the Update All / QuickPick prompt named), and only the Welcome panel's **Replace** passes the companion flag. **Gitignore rule:** each target's primary directory is added on its first install — except `agents`, which has **no `gitignorePattern` and is never ignored**: Gemini CLI's `read_file` refuses any path `.gitignore` matches (`respectGitIgnore` defaults to true), so an ignored `.agents/skills/` would let the guide activate and then stall at its first reference file. The setup directory `.claude/skills/erd-studio-setup/` is added only when `.claude/skills/erd-studio/` is listed — it follows the user's existing choice — and the check keys on the setup directory's first appearance, so v17 upgraders get the line too. **The hook command** is `[ -n "$CLAUDE_PROJECT_DIR" ] && bash "$CLAUDE_PROJECT_DIR/.claude/skills/erd-studio/enforce-skill.sh" || true` (`HOOK_COMMAND`), and the script exits 0 silently unless `tool_name` is exactly `Edit` or `Write`: GitHub Copilot runs `.claude/settings.local.json` hooks when Claude hooks are enabled and ignores the matcher. `mergeHookConfig` replaces any older ERD Studio hook command (legacy `check-skill.sh`, or the unguarded form) and keeps other hooks in the same entry.

**The other assistants' pre-edit hooks (v45)** live in `src/services/assistantHooks.ts` (pure: script, registered command, config merge) and are written by `HarnessService.installAssistantHooks()`: **GitHub Copilot** (the Copilot CLI and Copilot sessions in VS Code read it; VS Code's own local agent may not: `hooks.preToolUse` in `.github/copilot/settings.local.json`, top-level `permissionDecision: deny`, a Copilot matcher of every edit tool name), **Codex** (`hooks.PreToolUse` in `.codex/hooks.json`, matcher `apply_patch|Edit|Write`, the Claude `hookSpecificOutput` deny, paths read from the patch's `*** Update/Add/Delete File:` lines) and **Gemini CLI** (`hooks.BeforeTool` in `.gemini/settings.json`, matcher `write_file|replace`, `{"decision":"deny","reason":…}`, and `{}` — its documented no-decision — on every other call). **Not yet supported: Cursor** (its `preToolUse` blocks on output that is not a decision and documents only `permission: allow` for "go ahead", which this hook must never print; an exit-2 deny is untested there) **and Antigravity CLI** (Gemini CLI's successor for free-tier users). One script per tool at `<tool dir>/hooks/erd-studio-enforce-skill.sh` (`ASSISTANT_HOOKS`), carrying the version marker: a script there without it is the user's and that tool is skipped entirely, a newer one is never replaced. Each script reads `tool_name`/`toolName`, `session_id`/`sessionId` (none: a marker per project folder per day, never per machine) and the paths (`file_path`/`filePath`/`path` from the payload as sent, plus inside Copilot's JSON-encoded `toolArgs` decoded once, and patch headers that start the patch or a line — so a path inside file content or a patch body, which stays escaped, never counts; Windows backslashes folded), exempts `modelling-approach.md` like Claude's, keys its marker on `$TMPDIR` (else `/tmp`) per tool and session, and denies only after the marker is written. **It always exits 0 and the registered command ends in `|| true`**: the Copilot CLI fails closed on a hook error, so a broken hook would block every tool call. The command walks up from `$PWD` (Gemini: `$GEMINI_PROJECT_DIR`) to find the script and is a silent no-op without it; Copilot's `powershell` and Codex's `commandWindows` are `exit 0` (Windows is not enforced there; Gemini CLI has no Windows field and fails open). **Which tools:** `install()` registers `hookAssistants` filtered by `HOOK_READERS` (`claude` folder → Copilot only, `agents` → all three), plus any already registered (so Update All refreshes a hook and never adds one); `installRecommended` passes `recommendedHookAssistants(detected)` (none detected → Copilot and Codex, never Gemini CLI, whose settings file is shared) and is `unchanged` only while each of those is in `status.hooks` **or skipped on purpose** (`assistantHookSkipReason`: the user's own or a newer script, or a config with comments / not JSON / another shape — reported as `skippedHooks`, one sentence each in the Welcome panel's message, never retried as an `updated`); the Install AI Helper Files… QuickPick passes the same. Merges keep every other key and hook, replace an older ERD Studio entry (any string field naming the script) once, keep the file's indent, line endings and final newline, and leave a file with comments or trailing commas (JSONC: rewriting would lose them), one that is not JSON, or one whose `hooks`/event has another shape alone. **Gitignore:** a Copilot or Codex config ERD Studio *creates* is ignored, and its script with it (whenever the config is listed); Gemini CLI's is never ignored. `test/unit/assistantHooks.test.ts` runs every script with each tool's payload shape.

**The PreToolUse hook only ever denies**, and so does every other assistant's (no allow, approve or ask decision anywhere in a generated script or config — `assistantHooks.test.ts`). `enforce-skill.sh` blocks the first `.erd-studio` edit per Claude session (except `modelling-approach.md`, which has no file format) (deny text: "load the /erd-studio skill (file-format rules) before editing .erd-studio files, then retry. This is a one-time check per session — the /erd-studio-setup walkthrough expects it.") and otherwise exits 0 with **no output**, so Claude Code's normal permission flow decides. A test asserts the generated script never contains `"permissionDecision":"allow"`. Do not add an allow path back.

**Activation flow** (`src/extension.ts`): on startup, `detectStale()` runs. If stale targets are found, a warning notification offers "Update All" (updates immediately), "Choose…" (opens the install QuickPick with outdated targets pre-selected), or "Dismiss". Nothing is ever overwritten silently, unmanaged files are never flagged, and `AGENTS.md` content outside the BEGIN/END region is always preserved. When no harness files exist at all, the install QuickPick is offered once per workspace (tracked in `workspaceState`) — except on the fresh-install run that opens the Welcome panel, which skips it for that run only (the flag stays unset). The QuickPick labels existing unmanaged files honestly ("will be replaced" / "section will be appended").

**The schema guide is three parts** (native DBML storage, v35): `SKILL_PART` (what to write, read from doctor's `erd.storage`; the DBML layout; edit rules; and every rule the formats share), `DBML_PART` (the DBML format in full) and `LEGACY_PART` (the YAML/JSON v5/v6 rules of projects from before 2.0, **complete, never condensed**). The two skill targets install them as `SKILL.md` plus the version-marked companions `DBML.md` and `LEGACY.md` beside it (like `SYNC.md`), so each file stays under the 500-line skill limit (`harnessService.test.ts` caps every generated skill file at 500 lines and 48 KB); the single-file targets Copilot and Gemini carry all three inline (`SCHEMA_CONTENT`). Codex reads only the first 32 KiB of `AGENTS.md` (`project_doc_max_bytes`), so its region carries `SKILL_PART` alone (`CODEX_CONTENT`, capped at 26 KB by a test) and points at `.agents/skills/erd-studio/DBML.md` and `LEGACY.md`, which the `codex` install writes beside its region (`CODEX_COMPANIONS`, the Agent Skills copies byte for byte, under the same companion rules: a hand-written one is kept unless Replace was confirmed, a newer one is never replaced; a re-install without overwrite repairs a missing or outdated one) as the recommended install does; a missing or outdated one makes `codex` outdated in `harnessStatus()` and stale in `detectStale()`. When they are missing anyway, the region tells the assistant to ask the user to install them first. The parts refer to each other through `{SKILL}`, `{DBML}`, `{LEGACY}` and `{BESIDE}`, filled in by `schemaPart()` for each layout. The setup `SKILL.md` (its dbt project copy) is at its line limit: change it only by replacing lines.

**When to bump `HARNESS_VERSION`:** any change to `SCHEMA_CONTENT`, the generator functions, or naming conventions that would make previously installed harness files incorrect. Do **not** bump for unrelated extension changes — the version is independent of `package.json` version.
