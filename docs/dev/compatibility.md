# Confluence app and backward compatibility

> Moved out of the root `CLAUDE.md`, whose **Confluence and backward compatibility** rules always apply. This is the background. (It cannot live in `packages/CLAUDE.md`: `test/unit/packagesBoundary.test.ts` forbids naming the downstream product under `packages/`.)

## ERD Studio for Confluence

**ERD Studio for Confluence is live** — a paid Atlassian Marketplace app (Forge, Custom UI) in the **private** repo `liam-machine/erd-studio-pro` (`apps/confluence`). A Confluence macro reads a customer's `.erd-studio/` folder from their GitHub repo and renders one domain **read-only**. It is the outside consumer `@erd-studio/core` and `@erd-studio/renderer` exist for: the Forge backend calls core's `loadDisplaySubjectArea` (with every limit set — the repo content is untrusted) and the Custom UI renders the result with the renderer's `ErdCanvas` viewer, both pinned to an exact npm version. (Until erd-studio-pro PR #5 merges, the live app still runs a hand port of the renderer and loader pinned at extension v1.0.7; after it, a pin bump in that repo is all it takes to pick up a release from here. A branch stacked on it adds an **Export** panel that calls the renderer's re-exported `exportDiagram` / `diagramExportFileName` in the reader's browser, so the Mermaid and DBML output is part of that contract too.) Code flows public → private only: never copy anything from `erd-studio-pro` into this repo.

What that means here:

- **Every change under `packages/` is a change to a shipped product**, released to npm on merge to `main` without a manual step. Treat the packages' public API (every export of each entry point, `ErdCanvas` props, exported types, the `DisplaySubjectArea` shape, the `loadDisplaySubjectArea` options and its four error classes, the `--vscode-*` variables the README lists) as a contract with the Confluence app.
- **The viewer path is the Confluence product.** A renderer change must keep `ErdCanvas` with `viewer` working (no `CanvasHost` posts, no VS Code globals, no editing affordance appearing for readers); `ErdCanvas.viewer.test.tsx` pins it.
- The Confluence backend caches the built `DisplaySubjectArea` per commit and the frontend renders it, so a renderer may meet a `DisplaySubjectArea` built by an older core. New `DisplaySubjectArea` / `DisplayTable` / `DisplayColumn` / `DisplayRelationship` fields are **optional**, and the renderer must draw correctly when they are absent. Removing or changing the meaning of a field is a breaking change (MINOR while `0.x`) and needs a cache-key bump on the Confluence side — say so in the PR.

## Backward compatibility: old files must always render

The on-disk format keeps changing (v4 inline models → v5 model library, layer folders, `alias`, relationships moving from the domain file into model ymls, canonical `many-to-one` storage, `meta`, v6's table naming, and **2.0's native DBML storage**, …). The extension can migrate a project; **the Confluence app cannot** — it only reads whatever is committed in a customer's repo, which may have been written by any extension version from any point in history, and nobody will run a migration before a Confluence page renders it. So:

- **Never drop a read path.** `@erd-studio/core` must load every format a released extension has written, for as long as the Confluence app ships: `detectSubjectAreaFormat()` → `v4`, `v5` and `v6` load (v6, the table naming of #162 — written by the extension since #182, so every migrated project is v6 — is normalised to the v5 keys right after validation by `normaliseSubjectAreaDocument`, and read beside `logical-models/` from `tables/`; the Confluence app needs core 0.3.0 or later to read it) (v4 also gets the `erdStudio.migrateToV5` prompt, in the extension only); DBML projects (from 0.4.0, through the `dbml` option), including hand-written DBML: unquoted 11.0 values, `use *` and extension-less `use` paths, `Table gold.x` qualifiers, `Metadata` blocks and Refs in any operator form; a flat model library and one with layer folders; relationships in the domain file, in the library, or both; `one-to-many` records as well as canonical ones; a model file with or without `alias`, `meta`, `relationships:`; a YAML `rationale:` holding only the six keys of the first release (or keys it does not know); the 2.0 pre-releases' field spellings, `rationale_<key>`, `meta_<key>` and `meta_json` entries, beside the bare `<key>` settings 2.0 writes (D34); a missing `layers.json` (default layers) and a missing `fields.yml` (the starting set). Format changes are **additive on read**: a new writer may stop producing an old shape, but the reader keeps accepting it and normalises it (as `normaliseRelationships` does for old relationship records). `hybrid` / `legacy` (pre-v4) layouts are still rejected — extending read support to them is welcome, narrowing it anywhere is not.
- **New fields are optional with a defined default when absent**, in the domain JSON, model yml and `layers.json` alike, and the default must render what an older file meant. A field that changes meaning gets a new name rather than a reinterpretation of old files.
- **Unknown keys are ignored, not rejected** — a file written by a *newer* extension must still render in a Confluence app pinned to an older core, with the new detail simply missing. Only a newer `schemaVersion` (in JSON) or a newer `erd_schema_version` (on a DBML diagram's `Project`) may refuse (`SubjectAreaValidationError`), and that is a deliberate format break with a MAJOR-level release note. In DBML, an unknown `Project` key, DBML's own settings ERD Studio does not model, and a setting whose name is not an identifier are kept byte for byte by the writer and ignored by the reader. Since context fields (D34) any other table or column setting is read as a field — a team field when no list names it, shown under "Not in your list" — and is still kept byte for byte until it is edited, so nothing a file says is hidden. In `fields.yml` an unknown key is ignored and a newer `version:` is read for what the core understands; in a cached `fields` list an unknown `type`, `filledBy`, `showFor` or `home.kind` renders as read-only text, never dropped.
- **Pin it with a fixture.** DBML twins of the core fixtures live in `packages/core/test/fixtures/dbml/` (compared through `normaliseForStorageEquivalence`), and `test/fixtures/dbml-native/` is the extension's DBML project. Before changing how a format is written, add (or keep) a fixture of the old shape under `packages/core/test/fixtures/` and a golden in `packages/core/test/fixtures/golden/` that `loadDisplaySubjectArea` must still produce (`v4-inline` is the model). An old-format golden is regenerated only when the rendering of that old file is *meant* to change; never delete one because the extension no longer writes that shape.
- `docs/semantic-domain-json-reference.md` documents what the extension *writes*; keep a "still read" note there for every superseded shape so the contract the Confluence app depends on is written down.

## The 2.0 format: native DBML storage

| Format | Written by | Files | Read by core |
|---|---|---|---|
| DBML (`erd_schema_version: '7'`; `'8'` for a diagram showing two tables of one name) | extension 2.0+ (new projects, Convert Project to DBML; `'8'` from 2.0.4) | `<layer>/tables/<schema>/<name>.dbml` (`Table <schema>.<name>`), `<layer>/relationships/<file>.dbml`, `<layer>/diagrams/<name>.dbml` (positions in its Project's `erd_layout`), a root `README.md` | 0.4.0+, only with `dbml: dbmlStorageReader` from `@erd-studio/core/dbml` (`'8'`: 0.5.0+) |
| DBML, 1.9 pre-release tree | the 1.9.0–1.9.3 pre-releases only | `tables/[<folder>/]<name>.dbml`, `tables/[<folder>/]_relationships.dbml`, `<layer>/<name>.dbml` + `<layer>/<name>.dbdiagram` | **never** (the one exception below) |
| v6 (`schemaVersion: 6`) | extension 1.6+ after the naming migration | `tables/**.yml`, `<layer>/<name>.json` | 0.3.0+ |
| v5 / v4 | earlier extensions | `logical-models/**.yml`, `<layer>/<name>.json` | every core (v4 inline models too) |

- **The Confluence app needs core 0.4.0 and the `dbml` option** to draw a DBML project: bump `@erd-studio/core` and `@erd-studio/renderer` to 0.4.0, pass `dbml: dbmlStorageReader` to `loadDisplaySubjectArea`, let its bundler include `@dbml/parse` (a runtime dependency of core, loaded only by the subpath), and bump its cache key. Until then, an older core given a `.dbml` diagram path fails **transiently**: `SubjectAreaFileError('invalid-json')` with `transient: true` (it tries to parse the DBML as JSON), so the page shows a retryable error rather than a wrong drawing. A JSON diagram in a mixed project that lists a DBML table draws it as a missing table on every core, 0.4.0 included, while the extension (which lists the layer folders) draws it: an accepted parity gap. Only an older core also fails on a `.dbml` diagram path.
- **The version marker** of a DBML diagram is the `Project`'s `erd_schema_version` (`DBML_SCHEMA_VERSION`, 7; a missing key reads as 7). `CURRENT_SCHEMA_VERSION` (8) is the newest version core reads in any format; `CURRENT_JSON_SCHEMA_VERSION` (6) is the JSON ceiling, so a JSON file declaring 7 is still refused exactly as before. Version 8 reads exactly as 7: it is reserved for a diagram that holds two tables with one name in different schema folders, so a core or extension that cannot tell them apart refuses that one diagram instead of drawing the two as one. Core's diagram writer writes `'8'` on the edit that gives a diagram such a pair and `'7'` again on the edit that leaves it none (`DBML_TWIN_SCHEMA_VERSION`); a diagram with no pair keeps the version line it has, or none, byte for byte. That refusal by older readers is a deliberate format break, so the release that first lets a user put such a pair on a diagram needs the MAJOR-level release note.
- **Reads stay tolerant per file** (the spec's D6): one table file that does not parse renders as a placeholder, a relationships file is read Ref by Ref, and a diagram reads with every construct it does not own blanked. A future core must keep reading every shape 2.0 writes, including the `?` marks on Refs and selective `use { table x }` lines.
- **The one exception to "never drop a read path": the 1.9 pre-release tree** (Liam's decision, 2026-10-29). The 1.9.0–1.9.3 pre-releases wrote DBML in a different tree, and core 0.4.0, the only core that read it, was never published, so no Confluence install can hold such a project. 2.0 reads none of it: core's classifier marks those paths `legacy` and its loader refuses them with `legacyDbmlFileMessage` (a `SubjectAreaValidationError`); the extension and `doctor` say to restore the YAML/JSON from git and run Convert Project to DBML again. There is no migration code.
- **The Confluence app must find diagrams at `*/diagrams/*.dbml`** and pass that path as `domainPath` (a follow-up in the private repo). A `.dbml` anywhere else is refused with core's not-a-diagram message.
- **Add Layer refuses `tables`, `templates` and `logical-models`** (case-insensitive, `RESERVED_LAYER_NAMES`) in every project, YAML included (it already refused `tables`). This is the one change the layer-first tree makes that a YAML/JSON project can see (2.0 also offers such a project the Convert dialog and adds `erd.storage` to `doctor --json`). Existing layers with those names keep loading; only a new one is refused. `relationships` and `diagrams` stay allowed layer names.

## Two tables of one name (schema-scoped identity)

Since extension 2.0.4 a DBML table is its schema folder and name (`TableId`, core's `tableIdentity.ts`), so `bronze/tables/bqs/addresse.dbml` and `bronze/tables/ccc/addresse.dbml` are two tables (on-disk rules: `docs/semantic-domain-json-reference.md` → Two tables of one name). What that means for old files and older readers:

- **A project where no two tables share a name reads, renders, exports and is written byte for byte as before.** Every existing golden is unchanged, and `packages/core/test/fixtures/dbml/alias-workaround/` (the `ccc_addresse` with `alias: 'addresse'` shape 2.0.0–2.0.3 needed) has goldens made by the old code that are never regenerated. No file is rewritten on open.
- **The one rendering change in an existing project** is a library that already held a second same-named table in another schema folder (2.0.0–2.0.3 showed it as "(duplicate — ignored)"): it is now a table of its own, and a Ref written `ccc.addresse.x`, which those versions drew on the `bqs` copy, now belongs to `ccc.addresse`. That is the fix.
- **`erd_schema_version: '8'`** is written only while a diagram shows both tables of such a pair (and `'7'` again when it no longer does); every other diagram keeps its version line. Extensions 2.0.0–2.0.3 and any reader on core 0.4.x refuse that one diagram with "Please update the extension" (`SubjectAreaValidationError`), rather than drawing one table twice under one node id and saving a stray layout line or an edit to the wrong file. This is the deliberate format break the rule above asks a release note for; the extension still ships as a patch (Liam's decision), and the CHANGELOG says so. A diagram that shows only one of the two is version 7 and opens everywhere; an older extension's edits on it still go to the first file of that name (those versions' own bug), so a team upgrades together.
- **The packages: a pinned MINOR (core 0.5.0, renderer 0.5.0).** `DisplayTable.name` stays unique within a diagram and is what relationship ends, positions keys, `stubColumns` and sticky links refer to, but for the two tables of such a pair it now holds `<schema>.<name>` (the schema spelled as the `use` path's folder, in core and in the extension alike), with the table's own name in the new optional `tableName`. That widens what `name` can hold, so it is a meaning change: the Confluence app must bump its pin to 0.5.0 and **its cache key**, since a `DisplaySubjectArea` cached by 0.4.x for a version-7 diagram that already listed both tables is wrong (one table twice). A renderer given an older core's payload (no `tableName`) draws `name`, exactly as before; an older renderer given a newer payload draws two nodes, its only flaw a header reading `ccc.ccc.addresse`. Anything outside the packages that treats `name` as a file stem or dbt model name must use `tableName ?? name`.
- **The Confluence app on core 0.4.x** draws a diagram that shows one of the two correctly and refuses one that shows both (version 8). A hand-written version-7 diagram that shows both is drawn with one table twice there until the pin is bumped.
- **Mixed versions in one team.** An older extension shows the second table as "(duplicate — ignored)" and `doctor` reports `duplicateTableName`; its rename, move or delete of the first table re-spells the other's Refs. Nothing in a newer version can stop that: upgrade a team together.

## Context fields (D34)

Every field is one bare setting, `<key>: '<value>'`, and `.erd-studio/fields.yml` lists a project's fields (`docs/dev/fields.md`). What that means for old files and older readers:

- **Old spellings render the same.** `rationale_<key>`, `meta_<key>` and `meta_json` entries are the same fields as the bare keys; `packages/core/test/fixtures/rationale-and-meta/` and its goldens pin them, and `test/fixtures/dbml-native/` stays in the old spelling as the extension's old-spelling project. A project with no `fields.yml` draws what it drew before, plus the empty Decisions and Open questions rows, with Design marked Retired.
- **The package change is additive.** `Rationale` gains six optional keys, `DisplaySubjectArea` one optional `fields` (only when the project has a `fields.yml`, so every older golden stays byte-identical), core exports `fields.ts` and `fieldsFile.ts`, and `loadDisplaySubjectArea` reads `fields.yml` only with the new `readFieldsFile: true` option (default off; a broken or oversized file warns and is left out, never a new error class). The renderer draws `subjectArea.fields ?? STARTING_FIELD_LIST`, so a `DisplaySubjectArea` from an older core renders with the starting set. The Detail panel changed (one Fields section in place of the rationale, metadata, role and grain sections), so recommend a Confluence cache-key bump with the 0.4.0 pin.
- **Mixed versions in one team.** A 2.0 pre-release from before context fields ignores bare settings (it shows only the old spellings), and its edits keep every setting byte for byte, so nothing is lost. **A pre-2.0 extension clearing the last of the six legacy rationale keys on a YAML table deletes the whole `rationale:` map, the new keys (`decisions`, `openQuestions`, …) included**; 2.0 removes only the cleared key. Versions before 2.0 cannot open `.dbml` tables at all. Upgrade a team together.
- **Storage is not export.** The rich DBML export still writes `rationale_<key>` / `meta_*` / `meta_json`, and Import DBML still reads them (every catalogue rationale key through `rationaleKeyOf`) and keeps another tool's bare settings in `meta.dbml`. Writing bare keys in the export, and reading bare fields on import, are follow-ups.
