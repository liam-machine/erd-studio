# Confluence app and backward compatibility

> Moved out of the root `CLAUDE.md`, whose **Confluence and backward compatibility** rules always apply. This is the background. (It cannot live in `packages/CLAUDE.md`: `test/unit/packagesBoundary.test.ts` forbids naming the downstream product under `packages/`.)

## ERD Studio for Confluence

**ERD Studio for Confluence is live** — a paid Atlassian Marketplace app (Forge, Custom UI) in the **private** repo `liam-machine/erd-studio-pro` (`apps/confluence`). A Confluence macro reads a customer's `.erd-studio/` folder from their GitHub repo and renders one domain **read-only**. It is the outside consumer `@erd-studio/core` and `@erd-studio/renderer` exist for: the Forge backend calls core's `loadDisplaySubjectArea` (with every limit set — the repo content is untrusted) and the Custom UI renders the result with the renderer's `ErdCanvas` viewer, both pinned to an exact npm version. (Until erd-studio-pro PR #5 merges, the live app still runs a hand port of the renderer and loader pinned at extension v1.0.7; after it, a pin bump in that repo is all it takes to pick up a release from here. A branch stacked on it adds an **Export** panel that calls the renderer's re-exported `exportDiagram` / `diagramExportFileName` in the reader's browser, so the Mermaid and DBML output is part of that contract too.) Code flows public → private only: never copy anything from `erd-studio-pro` into this repo.

What that means here:

- **Every change under `packages/` is a change to a shipped product**, released to npm on merge to `main` without a manual step. Treat the packages' public API (every export of each entry point, `ErdCanvas` props, exported types, the `DisplaySubjectArea` shape, the `loadDisplaySubjectArea` options and its four error classes, the `--vscode-*` variables the README lists) as a contract with the Confluence app.
- **The viewer path is the Confluence product.** A renderer change must keep `ErdCanvas` with `viewer` working (no `CanvasHost` posts, no VS Code globals, no editing affordance appearing for readers); `ErdCanvas.viewer.test.tsx` pins it.
- The Confluence backend caches the built `DisplaySubjectArea` per commit and the frontend renders it, so a renderer may meet a `DisplaySubjectArea` built by an older core. New `DisplaySubjectArea` / `DisplayTable` / `DisplayColumn` / `DisplayRelationship` fields are **optional**, and the renderer must draw correctly when they are absent. Removing or changing the meaning of a field is a breaking change (MINOR while `0.x`) and needs a cache-key bump on the Confluence side — say so in the PR.

## Backward compatibility: old files must always render

The on-disk format keeps changing (v4 inline models → v5 model library, layer folders, `alias`, relationships moving from the domain file into model ymls, canonical `many-to-one` storage, `meta`, v6's table naming, and **2.0's native DBML storage**, …). The extension can migrate a project; **the Confluence app cannot** — it only reads whatever is committed in a customer's repo, which may have been written by any extension version from any point in history, and nobody will run a migration before a Confluence page renders it. So:

- **Never drop a read path.** `@erd-studio/core` must load every format a released extension has written, for as long as the Confluence app ships: `detectSubjectAreaFormat()` → `v4`, `v5` and `v6` load (v6, the table naming of #162 — written by the extension since #182, so every migrated project is v6 — is normalised to the v5 keys right after validation by `normaliseSubjectAreaDocument`, and read beside `logical-models/` from `tables/`; the Confluence app needs core 0.3.0 or later to read it) (v4 also gets the `erdStudio.migrateToV5` prompt, in the extension only); DBML projects (from 0.4.0, through the `dbml` option), including hand-written DBML: unquoted 11.0 values, `use *` and extension-less `use` paths, `Table gold.x` qualifiers, `Metadata` blocks and Refs in any operator form; a flat model library and one with layer folders; relationships in the domain file, in the library, or both; `one-to-many` records as well as canonical ones; a model file with or without `alias`, `meta`, `relationships:`; a missing `layers.json` (default layers). Format changes are **additive on read**: a new writer may stop producing an old shape, but the reader keeps accepting it and normalises it (as `normaliseRelationships` does for old relationship records). `hybrid` / `legacy` (pre-v4) layouts are still rejected — extending read support to them is welcome, narrowing it anywhere is not.
- **New fields are optional with a defined default when absent**, in the domain JSON, model yml and `layers.json` alike, and the default must render what an older file meant. A field that changes meaning gets a new name rather than a reinterpretation of old files.
- **Unknown keys are ignored, not rejected** — a file written by a *newer* extension must still render in a Confluence app pinned to an older core, with the new detail simply missing. Only a newer `schemaVersion` (in JSON) or a newer `erd_schema_version` (on a DBML diagram's `Project`) may refuse (`SubjectAreaValidationError`), and that is a deliberate format break with a MAJOR-level release note. In DBML, an unknown `Project` key, table or column setting is kept byte for byte by the writer and ignored by the reader.
- **Pin it with a fixture.** DBML twins of the core fixtures live in `packages/core/test/fixtures/dbml/` (compared through `normaliseForStorageEquivalence`), and `test/fixtures/dbml-native/` is the extension's DBML project. Before changing how a format is written, add (or keep) a fixture of the old shape under `packages/core/test/fixtures/` and a golden in `packages/core/test/fixtures/golden/` that `loadDisplaySubjectArea` must still produce (`v4-inline` is the model). An old-format golden is regenerated only when the rendering of that old file is *meant* to change; never delete one because the extension no longer writes that shape.
- `docs/semantic-domain-json-reference.md` documents what the extension *writes*; keep a "still read" note there for every superseded shape so the contract the Confluence app depends on is written down.

## The 2.0 format: native DBML storage

| Format | Written by | Files | Read by core |
|---|---|---|---|
| DBML (`erd_schema_version: '7'`) | extension 2.0+ (new projects, Convert Project to DBML) | `tables/[<folder>/]<name>.dbml`, `tables/[<folder>/]_relationships.dbml`, `<layer>/<name>.dbml` + `<layer>/<name>.dbdiagram` | 0.4.0+, only with `dbml: dbmlStorageReader` from `@erd-studio/core/dbml` |
| v6 (`schemaVersion: 6`) | extension 1.6+ after the naming migration | `tables/**.yml`, `<layer>/<name>.json` | 0.3.0+ |
| v5 / v4 | earlier extensions | `logical-models/**.yml`, `<layer>/<name>.json` | every core (v4 inline models too) |

- **The Confluence app needs core 0.4.0 and the `dbml` option** to draw a DBML project: bump `@erd-studio/core` and `@erd-studio/renderer` to 0.4.0, pass `dbml: dbmlStorageReader` to `loadDisplaySubjectArea`, let its bundler include `@dbml/parse` (a runtime dependency of core, loaded only by the subpath), and bump its cache key. Until then, an older core given a `.dbml` diagram path fails **transiently**: `SubjectAreaFileError('invalid-json')` with `transient: true` (it tries to parse the DBML as JSON), so the page shows a retryable error rather than a wrong drawing. A JSON diagram in a mixed project that lists a DBML table draws it as a missing table on an older core.
- **The version marker** of a DBML diagram is the `Project`'s `erd_schema_version` (`DBML_SCHEMA_VERSION`, 7; a missing key reads as 7). `CURRENT_SCHEMA_VERSION` (7) is the newest version core reads in any format; `CURRENT_JSON_SCHEMA_VERSION` (6) is the JSON ceiling, so a JSON file declaring 7 is still refused exactly as before.
- **Reads stay tolerant per file** (the spec's D6): one table file that does not parse renders as a placeholder, a relationships file is read Ref by Ref, and a diagram reads with every construct it does not own blanked. A future core must keep reading every shape 2.0 writes, including the `?` marks on Refs and selective `use { table x }` lines.
