## Tests and CI

Tests use vitest with `vscode` module aliased to `test/__mocks__/vscode.ts` (a stateful mock: `inspect()`-backed configuration via `_setMockConfiguration`, in-memory `WorkspaceEdit`/`applyEdit`, command registry that throws on duplicate ids, `_simulateMessage` for webview messages). `vitest.config.ts` mirrors two esbuild settings — an `md-text` transform plugin (a `.md` import is its text) and the `__ERD_CLI_VERSION__` define — so harness and CLI code runs unbundled. `test/globalSetup.ts` builds `dist/manifestWorker.js` before the run so manifest tests pass on a fresh clone. Fixture dbt projects live in `test/fixtures/` (`dbt-project` is the main one; `dbt-project-modern-tests` covers `data_tests:` / `arguments:` / versioned refs; the `-empty-manifest`, `-malformed`, `-sparse`, `-zero-byte` variants cover manifest edge cases).

CI (`.github/workflows/ci.yml`) runs on every PR into `main` or `develop` and on every push to `develop` (i.e. after each merge there): `npm audit --omit=dev --audit-level=high`, compile, build, a **CLI smoke test** (`doctor --no-dbt` must exit 0; `diff --all` may exit 1 for drift but never 2–4), `npm pack --dry-run` of both packages, test, package, and fails if `vsce ls --no-dependencies` lists more than 60 files. An informational `packages-plan` job writes what `publish-packages.yml` would release to npm once the PR reaches `main` into the run summary. A further job type-checks, builds and smoke-tests `mcp-server/` (which imports `src/services/*` and bundles `src/workers/manifestWorker.ts` — an accidental `import 'vscode'` in a shared service fails there). A `telemetry` job runs the telemetry Worker's own `npm test` / `npm run check`, a credential-free `wrangler deploy --dry-run` and its D1 migrations against a throwaway local database.

## Data flow

```
{layer}/{domain}.json ─┐
logical-models/**.yml ─┤  (+ v6 tables/**.yml)
                       └→ SubjectAreaService.getSubjectArea() ─→ UnifiedSubjectArea ─→ .logical → DisplaySubjectArea
                                                                                          │
schema .yml + source files ─→ YmlParserService ─┐                                         │
manifest.json              ─→ ManifestService  ─┼→ buildPhysicalSubjectArea() ─→ DisplaySubjectArea │
catalog.json               ─→ CatalogService   ─┘                                         │
                                                                                          │
                                                    [message] ─→ graphTransformer ─→ React Flow
```

1. **ManifestService** parses `{target-path}/manifest.json` in a worker thread (`dist/manifestWorker.js`, plain `JSON.parse` — there is no streaming parser or `stream-json` dependency) so 40MB+ files do not block the extension host. `src/workers/manifestExtractor.ts` (pure, shared with tests) extracts model nodes, relationship test nodes (`relationships`, `relationships_where`, custom), `unique` tests and `unique_combination_of_columns` tests, plus the names in the manifest's `disabled` section (the veto on filesystem existence — see step 4), resolving dbt versioned models (`model.proj.name.vN`, `ref('m', v=N)`) to the latest version. A missing manifest is definitive (`ManifestMissingError`, `isMissing` flag); a malformed one is treated as transient (dbt mid-write) and the last known good result is served with `isStale`. Runaway parses are abandoned after `DEFAULT_PARSE_TIMEOUT_MS`.
2. **DbtProjectConfig** (`src/services/dbtProjectConfig.ts`) reads `target-path` / `model-paths` / `seed-paths` / `snapshot-paths` from `dbt_project.yml` once at activation; ManifestService, CatalogService, YmlParserService, FileWatcherService and the staleness check all use those paths rather than hard-coded `target/`, `models/`, `seeds/` and `snapshots/`. `modelPathsGlob()` is the yml/staleness glob, `sourcePathsGlob()` the wider one the source watcher uses, and `resolveCatalogPath()` locates `{target-path}/catalog.json`.
3. **SubjectAreaService** reads a domain JSON → `UnifiedSubjectArea` (the parsing and repair rules are `@erd-studio/core`'s `domain.ts`), resolving each model name through **TableLibraryService** (`logical-models/{name}.yml` or `logical-models/{folder}/{name}.yml`, then the same under v6's `tables/` (#181; written since #182 under the v6 keys, which `renderTable` renames to v5 for the edit and back after — `TableNamingWriteRefused` only for a file holding a key in both namings; new files go to `tables/` when `projectNamingOf()` is not `v5`; a name in both is a reported conflict, `tableNamingConflicts()`; `tables/` is a layer folder instead when `tablesDirIsLayer()`), found by `findTableFile()`; parsed with `yaml` `parseDocument` and written back by editing that same document in place, so comments, key order and unknown keys survive every UI write — including a canvas rename, which carries the old file's document across via `serializeTable(model, fromName)`. Two exceptions: a file that fails to parse is regenerated from scratch (except one whose only errors are keys written twice: it is read with the last copy winning, carries a `loadWarning`, and every write to it throws `DuplicateKeyWriteRefused`, #164), and folded `>` block scalars are re-emitted on one line, value unchanged. A number keeps the text it was written with (`keepNumberText`: `007` stays `007`), a scalar the reader already reads as the wanted value is never rewritten, and every YAML alias — under a managed key or not, or inside a `relationships:` entry — reads after a save what it read before unless the canvas changed that very key (`settleKeptAliases` writes it out as a literal when its anchor was rewritten or removed; #157). A missing file renders as a placeholder with a warning), then extracts a stage section via `getSubjectAreaStage()` → `DisplaySubjectArea`. Malformed `viewConfig.positions` entries and relationships missing endpoints are dropped with a console warning.
4. For physical stage: `SubjectAreaService.buildPhysicalSubjectArea(unified, ymlData, manifest, catalog)` resolves each logical model against the dbt **project**, not against the manifest alone. **Existence** is `sourceFile ∪ yml ∪ manifest ∪ catalog`, where the source-file branch (a `.sql`/`.py`/`.csv` stem under a model/seed/snapshot path, indexed by `YmlData.sourceFiles`) is vetoed by `ManifestData.disabledModels` — `ref()` to a disabled model fails, so a bare file must not read as "exists". A model in none of those is **still emitted**, with `existsInProject: false`, a `missingReason` (`'absent'` | `'disabled'`), no columns and no `provenance`, and is kept out of `physicalModelNames` so it pulls in no edges — it ghosts on the canvas instead of vanishing. **Columns** come from two kinds of source: the *declared* list is the yml when present, else the manifest per model (one source — the manifest's columns are a compiled copy of the same yml patch, so disagreement there is only staleness), and the *observed* list is `catalog.json`. With a catalog node the rendered list is their union in catalog order with declared-only columns appended; with none it is the declared list, exactly as before. The declared spelling always wins for display (Snowflake's UPPERCASE keys never relabel the canvas). **Types** fall through catalog → declared `data_type:` → manifest → `''`; **descriptions** run the other way (yml → manifest → catalog `comment`, because `persist_docs` writes the dbt description *into* that comment); **`schema`** is manifest → catalog `metadata.schema` → `''` (manifest first: the two agree on the value and differ only in case, and with neither the node badge falls back to the layer abbreviation). Catalog nodes resolve by manifest `unique_id` first, then by normalised name. **`provenance`** (`{ columns: PhysicalColumnSource[]; types: PhysicalColumnSource }`) is computed in the same pass — `columns` lists every contributing source most-authoritative-first, `types` names the highest-authority source that supplied any type. It is runtime-only: nothing about it is persisted, and `buildLogicalDisplaySubjectArea` (the logical literal) never sets it. **Relationships are derived from the union of yml and manifest relationship tests** (deduped; never copied from logical; `catalog.json` carries no constraint information and contributes no edges). Cardinality is inferred from `unique`/`unique_combination_of_columns` tests merged from both sources (no unique test = "many" side). Model and column names are matched case-insensitively (`normaliseName()` in `src/services/nameUtils.ts`). Relationships are scoped to models within the domain to prevent conformed dimensions from pulling in external edges. See `derivePhysicalRelationships()` in `domainService.ts`. YmlParserService parses `models:` schema yml under the configured model paths only (seed/snapshot `seeds:` / `snapshots:` blocks, from any of the three roots, go to `YmlData.resourceDocs` and, like the manifest's `seed.`/`snapshot.` nodes in `ManifestData.resourceDocs`, supply **descriptions only** — never existence, columns or edges), but walks model, seed and snapshot paths for source files (skipping `dbt_packages`, `dbt_modules`, venvs), reads both `tests:` and `data_tests:` keys, `unique` as a scalar or map form, and dbt 1.10 `arguments:` nesting; both parsers accept versioned `ref('model', v=2)`. **CatalogService** (`src/services/catalogService.ts`) reads `{target-path}/catalog.json` — written by `dbt docs generate` — for real warehouse column lists and types, caching the "no catalog" answer too, so it must be invalidated on `onCatalogChanged` and in `refreshManifest`.
5. **DiscrepancyService** compares two `DisplaySubjectArea` objects (case-insensitive keys, raw names preserved on the report) to produce a `DiscrepancyReport`. The canvas and the `erd-studio diff` CLI reach it through the **same three pure cores**, which is the only reason the two can never disagree: `buildLogicalDisplaySubjectArea(domain, viewConfig, stubColumns?)` (`src/services/stageDisplay.ts` — a thin wrapper over `@erd-studio/core`'s `toDisplaySubjectArea`, the same function the provider's `buildDisplaySubjectArea` calls with its editor payload, so the logical `DisplaySubjectArea` has one implementation), `computeSubjectAreaDiff({ subjectAreaService, ymlData, manifest, catalog }, domainPath, sourceStage, targetStage?)` (`src/services/stageDiff.ts` — reads the domain once, builds both stages, runs `compare()` with the domain's `stubColumns`; `handleToggleDiscrepancy` calls nothing else) and `buildSyncPlan(report, selections, ctx)` / `allSelections(report, truth)` (`src/services/syncPlanBuilder.ts` — `handleGenerateSyncPlan` keeps only the setting read, the file write and the posts). Reject any comparison logic written locally in the CLI or the provider. `checkManifestStalenessFromMtimes()` (`src/services/manifestStaleness.ts`) is the matching pure core for the staleness banner: `stalenessService` feeds it `findFiles` mtimes, the CLI a capped (5000-file) fs walk. The CLI parses the manifest with `ManifestService`'s `parseInProcess: true` option — `extractManifestData` on the calling thread, no worker, same result and error wording.
6. Extension sends `domainLoaded` / `stageData` message to webview (`domainLoaded` carries `autoLayout: true` for a fresh, wholly unpositioned domain — see **Edit pipeline**)
7. **graphTransformer** converts `DisplaySubjectArea` → React Flow nodes + edges (with optional discrepancy overlays); `nodeOverlays.applyNodeOverlays` layers dimming/expansion on top with identity preservation so memoised nodes skip re-rendering
8. **elkLayout** runs ELK auto-layout in a Web Worker (injected at build time as `__ELK_WORKER_CODE__`; 30 s timeout, failures surface as a toast)

## Webview (`webview/`)

The canvas itself lives in `@erd-studio/renderer` (see `packages/CLAUDE.md`); `webview/` is the editor built around it. `App.tsx` wraps everything in `CanvasStoreProvider` (the singleton store below) and `CanvasEnvironmentProvider` (`host/vscodeCanvasHost.ts`, which forwards canvas edits to `acquireVsCodeApi().postMessage`), and gets its nodes, edges and click handlers from the renderer's `useCanvasGraph`.

| Directory | Purpose |
|-----------|---------|
| `components/` | React components — `EmptyCanvas/` (logical, editable, zero-model card: **Add models from dbt** posts `addModelsFromDbt`, **New model** opens the New Design Model dialog; `pointer-events: none` overlay), `Graph/DragLine`, `DiscrepancyPanel/`, `WelcomeModal/`, `Toolbar/` (StageTabs; the top-right corner actions — Export (a `⤓` glyph the size of the `⋯` trigger, so a third label does not make the corner collapse ~155px of window sooner), Send Feedback, View File — collapse to an overflow `⋯` menu only when `measureCorner()` finds they would overlap the top-centre toolbar — measured from the live layout, because the toolbar's width depends on the domain name, the search box and the stage-specific controls, and a CSS breakpoint could only approximate it; where nothing can be measured the labels stay), `FeedbackDialog/` (dialog incl. the header `KindSwitch`, `AnalysisPanel` incl. the destination picker, `DuplicateTakeover`, `DiagnosticsChips`, `FeedbackFooter`), `Toast/`, dialogs |

`erdStudio.feedback.aiAssist`, `.provider`, `.endpoint`, `.model` and `.hostedFallback` are contributed with `"scope": "machine"` and are additionally listed in `USER_SCOPED_SETTINGS` (`src/services/configService.ts`), so `getErdStudioSetting()` reads **only** their global value. A repository's checked-in `.vscode/settings.json` must never be able to point the analysis request — and the API key from secret storage that travels with it — at a host of its author's choosing. Do not remove either half: the scope keeps the value out of `inspect()`, and the list is what makes that true for this codebase's hand-rolled precedence chain.

## Message protocol

Extension <-> Webview communication uses discriminated unions on `type` field:
- **Extension -> Webview**: `domainLoaded`, `stageData`, `discrepancyReport`, `manifestStaleness`, `syncPlanGenerated`, `openFeedback`, `feedbackContext`, `feedbackAnalysis`, `feedbackSubmitted`, `error`
- **Webview -> Extension**:
  - telemetry only: `layoutFinished` (`{ ms, ok }` after every auto layout; bucketed to a `layout*` feature, writes nothing, on the physical allowlist)
  - lifecycle/navigation: `ready`, `dismissWelcome`, `dismissManifestHint` (no payload; the × on the logical stage's **Run dbt parse** hint, `webview/components/Canvas/ManifestHint.tsx` — the webview hides it at once, the host writes `MANIFEST_HINT_DISMISSED_KEY` to `workspaceState` and records `manifestHintDismissed`; the hint shows while a logical `domainLoaded` / `stageData` carries `manifestMissing: true`, which the host sets only when `manifestService.isMissing` and the workspace has not dismissed it — never on physical payloads; not on the physical allowlist), `openGettingStarted`, `viewFile` (optional `{ line, column? }`, `validateViewFilePayload`: the **Open at Line N** button of the "isn't valid JSON" screen, #186, opens the file with the cursor there; with no payload — the toolbar's View JSON — it opens as before), `openModelFile`, `requestReload`, `closeEditor` / `openAnotherDomain` (no payload; the **Close** and **Open Another Diagram…** buttons of the `domain-missing` screen, #161 — the host disposes the panel / runs `erdStudio.openDomain` with no file; write nothing, on the physical allowlist), `switchStage`, `refreshManifest`, `undo`, `redo`, `exportDiagram` (no payload, `validateExportDiagramPayload`; the toolbar's **Export** corner button / overflow item — the host runs `erdStudio.exportDiagram` with the panel's document Uri; writes no domain data and always exports the logical design; on the physical allowlist)
  - schema mutations: `addModel`, `addExistingModel`, `addExistingModels` (`{ modelNames }`, 1–`ADD_EXISTING_TABLES_LIMIT` (200) names, `validateAddExistingModelsPayload`; the Add Existing Model dialog with several rows ticked, #160 — v5 only, written by the same `applyDbtModels` as `addModelsFromDbt` but uncapped, keeping models dbt has disabled, and naming picks already in the domain in any case), `addModelsFromDbt` (no payload; the host opens the Draw-from-dbt scope picker, excluding models already in the domain, then writes every picked model and its relationships in one `applySubjectAreaEdit` — `autoLayout: true` when the domain was empty), `renameModel`, `removeModel`, `removeModels`, `addColumn`, `removeColumn`, `updateColumn`, `reorderColumns`, `toggleColumnKey`, `updateModelDescription`, `updateModelGrain`, `updateModelAlias`, `updateModelRole`, `updateModelRationale`, `addRelationship`, `updateRelationship`, `editRelationship`, `removeRelationship`, `removeRelationships`
  - canvas metadata: `updatePositions`, `addAnnotation`, `updateAnnotation`, `removeAnnotation`, `removeAnnotations`
  - sync/discrepancy: `toggleDiscrepancy`, `generateSyncPlan`, `runDbtCompile`, `runDbtParse` (no payload; the physical stage notice's **Run dbt parse** — `runDbtParse()` in `src/commands/runDbtParse.ts`, also behind the "no manifest" notifications, runs `dbt parse` in a terminal in the project root and the manifest watcher refreshes the canvas), `launchClaudeSync`
  - feedback: `requestFeedbackContext`, `analyzeFeedback`, `setFeedbackProvider`, `submitFeedback`, `copyFeedbackReport`, `openFeedbackLink`

Every type in the unions has a live sender and handler — do not add a message type without wiring both ends (unknown types are logged by the `default:` branch, never silently dropped). Multi-select operations are batched: `addExistingModels`, `addModelsFromDbt`, `removeModels`, `removeAnnotations`, `removeRelationships` and `updatePositions` (which carries `annotations?: [{id,x,y}]` for notes moved in the same drag) each produce **one** `WorkspaceEdit`, one save, one `domainLoaded` — i.e. one undo step. `switchStage` carries a `requestId` that the host echoes on `stageData` so the webview can drop stale replies (`webview/lib/stageRequest.ts`).

**Physical stage guard.** While a panel is viewing the physical stage the host rejects every message not in `NON_MUTATION_TYPES` (`src/providers/SemanticEditorProvider.ts`) with a `"Physical stage is read-only"` `error`.

Positions and annotations are allowed because they live in the shared `viewConfig` (physical inherits logical positions); `generateSyncPlan` is the physical-stage "Compare to Logical" flow; the six feedback types write no domain data at all (`setFeedbackProvider` writes a user setting, never a file); `openGettingStarted` (no payload, sent by the WelcomeModal's **Watch the short tour** link) only runs `erdStudio.showGettingStarted`. `closeEditor` and `openAnotherDomain` only close the tab or open the diagram picker. `openModelFile` (`{ modelName }`, sent by the **Open file** button on a node whose `logical-models` file has a YAML error — `DisplayTable.loadError`) only opens that yml in a text editor at the error line. `runDbtParse` writes no domain data (only dbt's own `target/`), and the physical stage is exactly where a missing manifest shows. `exportDiagram` writes nothing (Save As… writes only the file the user names in the save dialog) and always exports the logical design, so it is allowed on both stages. `addModelsFromDbt` is a schema mutation and is **not** on it (the guard refuses it before any picker opens). `undo`/`redo` are deliberately **not** allowed (the toolbar hides them there) — they would rewind the logical document under a derived view.

**Edit pipeline.** All domain-file writes go through `applySubjectAreaEdit()` in `SemanticEditorProvider` — the only place a domain `WorkspaceEdit` is built: parse → mutate → replace whole document → `applyEdit` → `document.save()` → refresh, with `pendingUpdates` held so the change listener never double-saves. Edits are saved immediately; the custom editor never sits dirty. (That brief dirty state is also what turns a preview tab into a pinned one — see the note on `erdStudio.openDomain` under Update recovery.) A mutator throws `EditAborted` to bail out after reporting its own error; pass `errorLabel` for the applyEdit-rejected case and `onSuccess` for follow-up work such as `selectorsService.scheduleRegenerate()`. `applyTableEdit()` routes `logical-models/*.yml` changes through the **same** `WorkspaceEdit` (`modelFiles: { save: [{ model, fromName? }], delete }`) so a model edit and its domain change are atomic and one undo step — never `fs.writeFileSync` a model file from a handler (`addExistingModel` seeds a new library file the same way, so a rejected edit leaves no orphan yml). `fromName` names the file whose existing YAML document supplies comments / key order / unknown keys: a rename passes the OLD name so hand-written content is carried to the new file instead of being regenerated. Every file the pipeline writes is recorded in `ownWrites` **after** the bytes land (the tracker stats the file), so the watchers skip our own saves; the refreshes they used to drive are issued directly instead — `sendSubjectAreaData` for the editing panel, `refreshSubjectAreasReferencingTable(name, exceptPanelKey)` for other open panels, and the `onDidWriteSubjectArea` event for the tree / model library views. An undo/redo flushes only the yml documents this provider itself wrote for that domain (`editedTablePaths`) — a model file the user is hand-editing in another tab is never force-saved. Cmd+Z / Cmd+Shift+Z on the canvas is VS Code's own undo, not the toolbar's `undo` message: the change listener sees `TextDocumentChangeReason.Undo` / `Redo` on the domain file, or on an `editedTablePaths` file while the panel is active, and after `NATIVE_UNDO_SETTLE_MS` runs the same `flushUndoRedo` as the toolbar (the mock's `_fireDidChangeTextDocument` drives it in tests). Payloads are validated at the message boundary by `src/providers/payloadValidation.ts` (model names via the shared `TABLE_NAME_PATTERN` in `src/types/naming.ts`, column lists incl. duplicates, `keyType`, `cardinality`, `modelRole`, finite positions); `TableLibraryService.tablePath` refuses names that escape `logical-models/`. The message listener is wrapped in `withMessageErrorBoundary()` so a throwing handler posts an `error` instead of becoming an unhandled rejection. A domain file deleted or renamed outside ERD Studio (#161) is never written back: `applySubjectAreaEdit` and undo/redo refuse once `document.uri.fsPath` is gone, the change listener does not save it, and `syncSubjectAreaFilePresence()` (called by both semantic-file watchers) moves every open canvas whose file is gone to the `domain-missing` error screen, and re-reads one whose file is back. Refresh paths (watchers, external edits, stage switches) never write — only the initial `ready` load persists auto-computed positions, and only for a **partially** positioned domain. A **fresh** domain (≥1 model, not one `viewConfig.positions` entry — typically written by an AI assistant with `viewConfig: {}`; `isFreshLayout()`) is the exception: on the logical stage `sendSubjectAreaData` still puts the simple `computeNewTablePositions` placement in the payload (so nothing paints at 0,0) but writes nothing, and sets `autoLayout: true` on the `domainLoaded` message. The webview stores it as `pendingAutoLayout`; `useFirstOpenAutoLayout` (in `Toolbar`) waits until every model has a node, clears the flag and calls the same `runLayout` as the Layout button / Shift+L — ELK, `fitView`, one `updatePositions` (one edit, one undo step). Every other `domainLoaded` / `stageData` overwrites the flag, so a later unflagged payload cancels a layout that has not started. If ELK fails the toast shows and nothing is written, so the next open asks again. Physical never carries the flag.

## Activation (`src/extension.ts`)

- **Project detection** — `src/services/projectDiscovery.ts` (vscode-free). `resolveDbtProject()` walks the workspace **once** (`findDbtProjectCandidates`: workspace folder roots in workspace order, then a depth-3 BFS for `dbt_project.yml`, skipping `node_modules`, `dbt_packages`, `.git`, `target`, venvs and dot-dirs) and picks, in order: `erdStudio.projectPath` → the **Select dbt Project…** pick stored in `workspaceState` under `SELECTED_PROJECT_KEY` (honoured only while it is still a candidate) → auto-detection, i.e. the first candidate with ERD data (`semanticDir` or a legacy `erd-studio/`), else the first candidate (#82). The pick is deliberately **per machine and never a setting**: an absolute path written to `.code-workspace` / `.vscode/settings.json` would leak into files teams commit; `projectPath` stays the explicit, shareable override. `projectPath` may name **any existing folder** (#111): a dbt project under one of the workspace folders is preferred, then any directory, so ERD Studio runs without dbt (no manifest — the physical stage shows its notice, and `manifestHintFlag()` suppresses the logical Run dbt parse hint while the root has no `dbt_project.yml`). Auto-detection, the picker, `hasMultipleDbtProjects` and the CLI's `--project` finder stay dbt-only. A `projectPath` that is not a folder comes back as `invalidSetting` and is shown as a warning, not only logged. `erdStudio.selectDbtProject` offers **Auto-detect** (clears the pick) plus every candidate, confirms in a modal and reloads the window itself; while `projectPath` is set it points at the setting instead. `erdStudio.hasMultipleDbtProjects` (refreshed on `onDidChangeWorkspaceFolders`) reveals the view-title button, and `SubjectAreaTreeProvider.setProjectRow()` puts a clickable **project row** (`contextValue` `dbtProject`, runs `erdStudio.selectDbtProject`) at the top of the tree. The requester asked for a button in the tab itself, and VS Code shows view-title icons only on hover. The row appears only alongside layers: an empty tree must stay empty so the welcome view, which has its own Select dbt Project link, still shows. `SemanticEditorProvider.resolveCustomTextEditor` refuses a domain file whose owning project (`findOwningDbtProject(file, workspaceRoot)`, nearest ancestor with `dbt_project.yml` **or** the open root itself, so a dbt-less root nested in a dbt repo owns its files) is not the open one — it would otherwise read another project's models and manifest and write model yml into the wrong project — and renders a scriptless page plus a notification that run `erdStudio.selectDbtProject` with that project. With no project found, `registerFallbackCommands()` registers every contributed command (plus aliases) with a "no dbt project" warning and a stub custom editor, so nothing reports "command not found".
- **`erdStudio.reportBug`** (titled **Send Feedback**), **`erdStudio.showGettingStarted`** and **`erdStudio.trySampleProject`** are registered before any early return so they always work — the three ids in `PRE_REGISTERED_COMMANDS`, in that order, with `reportBug` staying `registered()[0]`. The Welcome panel's project-path deps are late-bound through `let gettingStartedDeps` (the same pattern as `editorProviderForFeedback`); without a project it gets `noProjectGettingStartedDeps()`. `ReportTrackingService` and `MyReportsTreeProvider` are constructed immediately after `editorProviderForFeedback = editorProvider` — before `refreshContextKeys()` is defined and synchronously called — and the provider gets the tracker via `setReportTracking()` rather than a sixth constructor argument.
- **Update recovery** — if the extension version changed since last activation and a canvas is open, the host offers a save-all + window reload (`recoveryService`); the webview also detects orphaning and sends `requestReload`. The custom editor is registered with `retainContextWhenHidden`. `erdStudio.openDomain` (the Domains tree, the picker, the status bar, the Welcome panel) opens with `{ preview: true }` (#167) — `vscode.openWith` with no options pins the tab — so browsing reuses one preview tab; VS Code pins it on the first edit (the `applyEdit` marks the document dirty for the moment before its save, and a dirty editor is pinned) and ignores the option when `workbench.editor.enablePreview` is off. Create Domain, the rename and Draw from dbt keep a pinned tab. The first open of a partially positioned or fresh domain writes positions, which pins that tab once.
- **First run** — the Welcome panel opens automatically **once per machine**, and only for a fresh install. At the very top of `activate()` (before the no-project early return), no stored `lastActivatedVersion` and no `erdStudio.gettingStartedShown` sets the globalState flag `erdStudio.gettingStartedPending` (`GETTING_STARTED_PENDING_KEY`) — the panel needs a dbt project, and by the time the user opens one `lastActivatedVersion` is stored and the activation would look like an upgrade. In the project path, pending and not shown → write `erdStudio.gettingStartedShown` (`GETTING_STARTED_SHOWN_KEY`) and clear pending **first** (so a crash cannot loop), and **skip that run's harness install QuickPick** (`HARNESS_INSTALL_PROMPTED_KEY` is left unset, so the once-per-workspace offer still comes on a later activation) (the panel offers the one-click setup instead), then open the **walkthrough** (`contributes.walkthroughs` id `erdStudio.getStarted`, opened as `WALKTHROUGH_ID` = `liamwynne.erd-studio#erdStudio.getStarted`; five steps — watch, sample, openProject, draw, enrich — each illustrated by an SVG in `media/walkthrough/`), falling back to `GettingStartedPanel.createOrShow()` if the walkthrough command throws. The no-project first run opens the walkthrough the same way. An upgrader (never pending, never shown) gets the shown flag and one non-modal "new short getting-started video…" notice whose **Watch** runs `showGettingStarted`. A module-level `gettingStartedAutoOpened` guard stops a second activation in the same host (`_resetFirstRunGuardForTests()` resets it); two windows racing may both open it once, which is accepted. The stale-harness "Update All" prompt is independent and can coexist. `extension.activate.test.ts`'s `makeContext` pre-seeds `gettingStartedShown: true` so every other test is unaffected.
- **No unprompted writes** — activation may rename a legacy `erd-studio/` dir to `.erd-studio/` (with a notice) but otherwise writes nothing: `SelectorsService.regenerate()` returns `noop` when there is nothing to write, harness updates and v4→v5 migration always prompt. The **second documented exception** is the CLI launcher: near the end of activation `void cliLauncher.refreshIfInstalled(...)` rewrites `~/.erd-studio-cli` — outside the workspace — but **only if `launcher.json` already exists**, i.e. only after the user clicked **Set Up My AI Helper** once. It never throws and never toasts (errors go to the console). Nothing else may install the launcher: `installCodingHarness` and the stale-harness "Update All" do not touch the home directory.
- **No project, no toast** — opening a folder without a dbt project shows no warning (the sidebar's welcome view explains it); an explicit `erdStudio.projectPath` that holds no `dbt_project.yml` is still reported.
- **Existing diagrams** — once per workspace (`DIAGRAMS_NUDGE_SHOWN_KEY`), a project with domains and no canvas open gets one notice offering **Open <most recently modified domain>** (`mostRecentlyModified()`); it is skipped (flag left unset) on the run that opens the walkthrough or shows the upgrade notice, so only one prompt shows at a time, and it writes nothing. A left status bar item (`DIAGRAMS_STATUS_ID`, `$(type-hierarchy) ERD N`, hidden at 0, refreshed by `refreshContextKeys()` and `deleteDomain`) runs `erdStudio.openDomain`, which with no file argument shows the domain picker.
- **Context keys** `erdStudio.hasSemanticDir` / `erdStudio.hasLogicalModelsDir` are refreshed by `refreshContextKeys()` after every relevant watcher event and command. `erdStudio.hasTrackedReports` (which gates the **My Reports** view) is deliberately **not** one of them — `ReportTrackingService` sets it itself, so activation never has to reference the service from `refreshContextKeys`.
- **Settings changes** to `semanticDir` / `projectPath` (either prefix) prompt for a window reload.
- **Projects stored as DBML by a newer ERD Studio** (the 1.9 pre-release or 2.0) — this version cannot read them, so it guards them instead (`src/services/dbmlStorageGuard.ts`, vscode-free: `detectDbmlStorage()`, `DBML_STORAGE_MESSAGE`; editor side `src/providers/dbmlStorageGuardUi.ts`). Evidence is a `.dbml` table or `_relationships.dbml` in the `tables/` library (top level or one folder down, not while `tables/` is a layer, never a saved export), or a layer-folder `.dbml` diagram declaring `erd_schema_version`; it is read fresh on every check (folder listings and the first 64 KB of a few files), plus a `**/*.dbml` watcher. When found: one non-modal notice per session with **Update ERD Studio** (`extension.open`, falling back to the Extensions search), the context key `erdStudio.dbmlStorage` (both views empty → their DBML `viewsWelcome`; the view-title buttons that write are hidden; the Table Library view shows), every `DBML_GUARDED_COMMANDS` command (registered via `registerGuarded`) refuses with the message, the custom editor renders an update page instead of the canvas, an open canvas refuses every message outside `DBML_GUARD_ALLOWED_MESSAGE_TYPES` and `applySubjectAreaEdit` refuses as a backstop, `SelectorsService` returns `noop` (`isBlocked`), and activation skips the harness offers, the v4 migration prompt and the layer-config prompt. `erd-studio doctor` reports `erd.dbmlStorage` with an `update-erd-studio` first step. A YAML / JSON project is untouched. **2.0 reads DBML, so the merge of the native DBML storage branch removes this guard** (delete both files, their call sites and tests; `docs/dev/releasing.md` lists them). Until then it stands down by itself on a core whose `CURRENT_SCHEMA_VERSION` is 7 or more (`DBML_READING_SCHEMA_VERSION`), and a test fails there to say it is still in.

## Watchers (`src/watchers/FileWatcherService.ts`)

Own writes are recorded in `ownWrites` (`src/services/ownWriteTracker.ts`, path + mtime/size, 5 s TTL) by `SemanticEditorProvider` (the editor write path — domain file, model yml saves, creates and deletes), `TableLibraryService`, `LayerService` and the `deleteDomain` command, and consumed in the callbacks that watch files the extension itself writes (domain `.json` changes and deletes, `layers.json`, `{logical-models,tables}/**/*.yml`) so an extension save never triggers a second identical refresh. The manifest, catalog and `dbt_project.yml` callbacks have nothing to consume — the extension never writes those. One watcher covers both dbt artifacts (`{target-path}/{manifest.json,catalog.json}`) on separate debounce keys, firing `onManifestChanged` or `onCatalogChanged`; one covers dbt source files (`{model,seed,snapshot}-paths/**/*.{yml,yaml,sql,py,csv}`) and fires `onDbtYmlChanged` on create and delete of any of them but on change only for yml — a `.sql` body edit changes no shape the physical stage reads. `renameDomain` (`extension.ts`) is the one gap: its create+delete `WorkspaceEdit` records neither path, so the old file's delete is seen as external. `classifySemanticPath()` ensures only `{layer}/{domain}.json` fires `onSemanticFileDeleted` (coalesced to one `{ uris }` event per burst); `layers.json` has its own `onLayerConfigChanged`. `LayerService.loadConfig()` is mtime-validated and refuses to overwrite an unreadable/invalid `layers.json` (`getLoadError()`).

## Discrepancy system

Cross-stage comparison is handled by `DiscrepancyService.compare(source, target)`:

| Active Stage | Available Comparisons |
|-------------|----------------------|
| Physical | Compare to Logical |
| Logical | Compare to Physical |

Discrepancy statuses for models/columns/relationships: `matched`, `extra`, `missing`, `type-mismatch` and `undeclared` (columns), `cardinality-mismatch` (relationships). `undeclared` is the case where exactly one stage declares a data type at all — it gets its own status and its own `summary.undeclaredColumns` count rather than inflating the mismatch count, and `deriveColumnAction` still resolves it like a mismatch so "write `data_type:` into the yml" stays reachable. Ghost nodes appear for missing models. Two suppressions, with different switches: the domain's `stubColumns` list is the user's own, and hides missing-column discrepancies only; separately `compare()` automatically drops models with `existsInProject === false` from both sides (and from `summary.totalModels`), and reports a model whose only evidence is a source file (`columns: []` and `provenance.columns === ['file']`) as `matched` with no column rows, on either side — otherwise one undocumented model would emit its counterpart's whole column list as differences. Type comparison splits a base from its parameters with a matched-delimiter scan (so `timestamp(6) without time zone` and `STRUCT<a INT64>` both keep their real base), canonicalises the spellings adapters actually emit (`character varying` → `string`, `NUMBER`/`numeric` → `decimal`, `INT64` → `int`, `TIMESTAMP_NTZ` → `timestamp`, `TIMESTAMP_LTZ` → `timestamptz`), treats absent parameters on either side as compatible, and has exactly one cross-family rule: a whole-number decimal matches an integer. Sync plans are written to `.erd-studio/.sync-plan.json` by `generateSyncPlan`; **Execute with Claude** confirms the exact terminal command before launching.
