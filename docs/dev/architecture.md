## Tests and CI

Tests use vitest with `vscode` module aliased to `test/__mocks__/vscode.ts` (a stateful mock: `inspect()`-backed configuration via `_setMockConfiguration`, in-memory `WorkspaceEdit`/`applyEdit`, command registry that throws on duplicate ids, `_simulateMessage` for webview messages). `vitest.config.ts` mirrors two esbuild settings — an `md-text` transform plugin (a `.md` import is its text) and the `__ERD_CLI_VERSION__` define — so harness and CLI code runs unbundled. `test/globalSetup.ts` builds `dist/manifestWorker.js` before the run so manifest tests pass on a fresh clone. Fixture dbt projects live in `test/fixtures/` (`dbt-project` is the main one; `dbt-project-modern-tests` covers `data_tests:` / `arguments:` / versioned refs; the `-empty-manifest`, `-malformed`, `-sparse`, `-zero-byte` variants cover manifest edge cases).

CI (`.github/workflows/ci.yml`) runs on every PR into `main` or `develop` and on every push to `develop` (i.e. after each merge there): `npm audit --omit=dev --audit-level=high`, compile, build, a **CLI smoke test** (`doctor --no-dbt` must exit 0; `diff --all` may exit 1 for drift but never 2–4; `doctor` and `export --all` on the DBML fixture `test/fixtures/dbml-native`), the native DBML end-to-end script (`npm run test:e2e:dbml -- --no-build`: Convert a copy of `dbt-project`, compare `doctor`, `diff`, `export` and every display before and after, and compile every written `.dbml` in DBML 9.1.1, 10.3.1 and 11.0.0), `npm pack --dry-run` of both packages, test, package, and fails if `vsce ls --no-dependencies` lists more than 60 files. An informational `packages-plan` job writes what `publish-packages.yml` would release to npm once the PR reaches `main` into the run summary. A further job type-checks, builds and smoke-tests `mcp-server/` (which imports `src/services/*` and bundles `src/workers/manifestWorker.ts` — an accidental `import 'vscode'` in a shared service fails there). A `telemetry` job runs the telemetry Worker's own `npm test` / `npm run check`, a credential-free `wrangler deploy --dry-run` and its D1 migrations against a throwaway local database.

## Data flow

```
{layer}/diagrams/{domain}.dbml       ─┐   DBML (2.0 default)        subjectAreaCodec / core's @erd-studio/core/dbml readers
  (positions in its Project's erd_layout)
{layer}/tables/{schema}/{name}.dbml ─┤
{layer}/relationships/*.dbml        ─┤   (Refs attached to their FK table; a diagram draws the files it imports)
{layer}/{domain}.json               ─┤   YAML/JSON (before 2.0)   parseSubjectAreaJson / parseTableText
logical-models/**.yml               ─┤   (+ v6 tables/**.yml)
                                     └→ SubjectAreaService.getSubjectArea() ─→ UnifiedSubjectArea ─→ .logical → DisplaySubjectArea
                                                                                          │
schema .yml + source files ─→ YmlParserService ─┐                                         │
manifest.json              ─→ ManifestService  ─┼→ buildPhysicalSubjectArea() ─→ DisplaySubjectArea │
catalog.json               ─→ CatalogService   ─┘                                         │
                                                                                          │
                                                    [message] ─→ graphTransformer ─→ React Flow
```

1. **ManifestService** parses `{target-path}/manifest.json` in a worker thread (`dist/manifestWorker.js`, plain `JSON.parse` — there is no streaming parser or `stream-json` dependency) so 40MB+ files do not block the extension host. `src/workers/manifestExtractor.ts` (pure, shared with tests) extracts model nodes, relationship test nodes (`relationships`, `relationships_where`, custom), `unique` tests and `unique_combination_of_columns` tests, plus the names in the manifest's `disabled` section (the veto on filesystem existence — see step 4), resolving dbt versioned models (`model.proj.name.vN`, `ref('m', v=N)`) to the latest version. A missing manifest is definitive (`ManifestMissingError`, `isMissing` flag); a malformed one is treated as transient (dbt mid-write) and the last known good result is served with `isStale`. Runaway parses are abandoned after `DEFAULT_PARSE_TIMEOUT_MS`.
2. **DbtProjectConfig** (`src/services/dbtProjectConfig.ts`) reads `target-path` / `model-paths` / `seed-paths` / `snapshot-paths` from `dbt_project.yml` once at activation; ManifestService, CatalogService, YmlParserService, FileWatcherService and the staleness check all use those paths rather than hard-coded `target/`, `models/`, `seeds/` and `snapshots/`. `modelPathsGlob()` is the yml/staleness glob, `sourcePathsGlob()` the wider one the source watcher uses, and `resolveCatalogPath()` locates `{target-path}/catalog.json`.
3. **SubjectAreaService** reads a diagram → `UnifiedSubjectArea`. **A `.dbml` diagram** (native DBML storage, `docs/plans/native-dbml-storage.md`) is read by core's `parseSubjectAreaDbml` (through the codec, `src/providers/subjectAreaCodec.ts`, `codecFor(path)`) into the same plain v5 object a JSON file gives (`schemaVersion` 5; the DBML version travels beside it), with its members from the table `use` lines (then `erd_unlinked_tables`) and its positions from its Project's `erd_layout`; a member is resolved by its `use` path first, and only the relationships held in the files the diagram imports are drawn (the same filter for the canvas and the CLI; a file it should import but does not is logged and toasted once per session, `unimportedRelationshipsMessage`); **TableLibraryService** resolves each member by name (the YAML libraries in core's `tableFileCandidates` order, `logical-models/` then `tables/`, then the DBML tables of every layer's `tables/<schema>/`; a DBML table is shadowed by any earlier file of the same name), never with `existsSync`, through one **library index**, `src/services/tableLibraryIndex.ts`: a single listing of the semantic dir, both YAML libraries (top level and one folder down) and each layer folder's `tables/<schema>/` and `relationships/` answers `findTableFile`, `listTableFiles` (duplicates included), `listRelationshipsFiles`, the folders, `hasTablesLibrary` and `tablesDirIsLayer` (the module functions share its rules), and is re-validated on each use by the signatures (inode, mtime, size) of every directory it listed and of `layers.json`, so a file added, renamed or removed outside ERD Studio is seen with no watcher event; a directory changed within `RACY_MS` of a build is not trusted on its signature until it is older), reads a `.dbml` table with `parseTableDbml` (one table per file, tolerant per file: a file that does not parse is a placeholder with a `dbml*` `loadError`), and attaches every relationships file's Refs to their FK table (`attachRelationships`). `detectProjectStorage` (core; host `projectStorageOf`) says what new files are written as: `dbml`, `yaml` or `mixed`. **A domain JSON** (the parsing and repair rules are `@erd-studio/core`'s `domain.ts`), resolving each model name through **TableLibraryService** (`logical-models/{name}.yml` or `logical-models/{folder}/{name}.yml`, then the same under v6's `tables/` (#181; written since #182 under the v6 keys, which `renderTable` renames to v5 for the edit and back after — `TableNamingWriteRefused` only for a file holding a key in both namings; new files go to `tables/` when `projectNamingOf()` is not `v5`; a name in both is a reported conflict, `tableNamingConflicts()`; `tables/` is a layer folder instead when `tablesDirIsLayer()`), found by `findTableFile()`; parsed with `yaml` `parseDocument` and written back by editing that same document in place, so comments, key order and unknown keys survive every UI write — including a canvas rename, which carries the old file's document across via `serializeTable(model, fromName)`. Two exceptions: a file that fails to parse is regenerated from scratch (except one whose only errors are keys written twice: it is read with the last copy winning, carries a `loadWarning`, and every write to it throws `DuplicateKeyWriteRefused`, #164), and folded `>` block scalars are re-emitted on one line, value unchanged. A number keeps the text it was written with (`keepNumberText`: `007` stays `007`), a scalar the reader already reads as the wanted value is never rewritten, and every YAML alias — under a managed key or not, or inside a `relationships:` entry — reads after a save what it read before unless the canvas changed that very key (`settleKeptAliases` writes it out as a literal when its anchor was rewritten or removed; #157). A missing file renders as a placeholder with a warning), then extracts a stage section via `getSubjectAreaStage()` → `DisplaySubjectArea`. Malformed `viewConfig.positions` entries and relationships missing endpoints are dropped with a console warning.
4. For physical stage: `SubjectAreaService.buildPhysicalSubjectArea(unified, ymlData, manifest, catalog)` resolves each logical model against the dbt **project**, not against the manifest alone. **Existence** is `sourceFile ∪ yml ∪ manifest ∪ catalog`, where the source-file branch (a `.sql`/`.py`/`.csv` stem under a model/seed/snapshot path, indexed by `YmlData.sourceFiles`) is vetoed by `ManifestData.disabledModels` — `ref()` to a disabled model fails, so a bare file must not read as "exists". A model in none of those is **still emitted**, with `existsInProject: false`, a `missingReason` (`'absent'` | `'disabled'`), no columns and no `provenance`, and is kept out of `physicalModelNames` so it pulls in no edges — it ghosts on the canvas instead of vanishing. **Columns** come from two kinds of source: the *declared* list is the yml when present, else the manifest per model (one source — the manifest's columns are a compiled copy of the same yml patch, so disagreement there is only staleness), and the *observed* list is `catalog.json`. With a catalog node the rendered list is their union in catalog order with declared-only columns appended; with none it is the declared list, exactly as before. The declared spelling always wins for display (Snowflake's UPPERCASE keys never relabel the canvas). **Types** fall through catalog → declared `data_type:` → manifest → `''`; **descriptions** run the other way (yml → manifest → catalog `comment`, because `persist_docs` writes the dbt description *into* that comment); **`schema`** is manifest → catalog `metadata.schema` → `''` (manifest first: the two agree on the value and differ only in case, and with neither the node badge falls back to the layer abbreviation). Catalog nodes resolve by manifest `unique_id` first, then by normalised name. **`provenance`** (`{ columns: PhysicalColumnSource[]; types: PhysicalColumnSource }`) is computed in the same pass — `columns` lists every contributing source most-authoritative-first, `types` names the highest-authority source that supplied any type. It is runtime-only: nothing about it is persisted, and `buildLogicalDisplaySubjectArea` (the logical literal) never sets it. **Relationships are derived from the union of yml and manifest relationship tests** (deduped; never copied from logical; `catalog.json` carries no constraint information and contributes no edges). Cardinality is inferred from `unique`/`unique_combination_of_columns` tests merged from both sources (no unique test = "many" side). Model and column names are matched case-insensitively (`normaliseName()` in `src/services/nameUtils.ts`). Relationships are scoped to models within the domain to prevent conformed dimensions from pulling in external edges. See `derivePhysicalRelationships()` in `domainService.ts`. YmlParserService parses `models:` schema yml under the configured model paths only (seed/snapshot `seeds:` / `snapshots:` blocks, from any of the three roots, go to `YmlData.resourceDocs` and, like the manifest's `seed.`/`snapshot.` nodes in `ManifestData.resourceDocs`, supply **descriptions only** — never existence, columns or edges), but walks model, seed and snapshot paths for source files (skipping `dbt_packages`, `dbt_modules`, venvs), reads both `tests:` and `data_tests:` keys, `unique` as a scalar or map form, and dbt 1.10 `arguments:` nesting; both parsers accept versioned `ref('model', v=2)`. **CatalogService** (`src/services/catalogService.ts`) reads `{target-path}/catalog.json` — written by `dbt docs generate` — for real warehouse column lists and types, caching the "no catalog" answer too, so it must be invalidated on `onCatalogChanged` and in `refreshManifest`.
5. **DiscrepancyService** compares two `DisplaySubjectArea` objects (case-insensitive keys, raw names preserved on the report) to produce a `DiscrepancyReport`. The canvas and the `erd-studio diff` CLI reach it through the **same three pure cores**, which is the only reason the two can never disagree: `buildLogicalDisplaySubjectArea(domain, viewConfig, stubColumns?)` (`src/services/stageDisplay.ts` — a thin wrapper over `@erd-studio/core`'s `toDisplaySubjectArea`, the same function the provider's `buildDisplaySubjectArea` calls with its editor payload, so the logical `DisplaySubjectArea` has one implementation), `computeSubjectAreaDiff({ subjectAreaService, ymlData, manifest, catalog }, domainPath, sourceStage, targetStage?)` (`src/services/stageDiff.ts` — reads the domain once, builds both stages, runs `compare()` with the domain's `stubColumns`; `handleToggleDiscrepancy` calls nothing else) and `buildSyncPlan(report, selections, ctx)` / `allSelections(report, truth)` (`src/services/syncPlanBuilder.ts` — `handleGenerateSyncPlan` keeps only the setting read, the file write and the posts). Reject any comparison logic written locally in the CLI or the provider. `checkManifestStalenessFromMtimes()` (`src/services/manifestStaleness.ts`) is the matching pure core for the staleness banner: `stalenessService` feeds it `findFiles` mtimes, the CLI a capped (5000-file) fs walk. The CLI parses the manifest with `ManifestService`'s `parseInProcess: true` option — `extractManifestData` on the calling thread, no worker, same result and error wording.
6. Extension sends `domainLoaded` / `stageData` message to webview (`domainLoaded` carries `autoLayout: true` for a fresh, wholly unpositioned domain — see **Edit pipeline**)
7. **graphTransformer** converts `DisplaySubjectArea` → React Flow nodes + edges (with optional discrepancy overlays); `nodeOverlays.applyNodeOverlays` layers dimming/expansion on top with identity preservation so memoised nodes skip re-rendering
   - **Hover focus and relationship flow** (`useHoverFocus`, `lib/canvasFocus.ts`, `lib/hoverIntent.ts`, `components/Graph/EdgeFlow.tsx`). Resting the pointer on a table previews its neighbourhood. The preview is ephemeral store state, `hoverFocus` and `flowFocus` (`CanvasFocus` sets), never persisted, posted or written, with no message type. It is not dimmed through `applyNodeOverlays`: every `setEdges` re-renders every `FkEdge` (each reads all edges for distribution), which is fine once per click but not on every pointer move. Instead a root class, `erd-flow--hover-focus` on `<ReactFlow>`, fades everything in CSS, and each table and line reads its own role with an O(1) selector returning a primitive. Precedence: hover previews over click and search dimming; leaving restores them untouched (hover never writes `data.dimmed`); the clicked table stays at 0.4 opacity; a click and a hover use the same connectivity rule (`computeCanvasFocus`), except that the hover preview lights only the hovered table's own lines (`ownLinesOnly`). Hover intent waits 120 ms (60 ms to switch tables, 150 ms grace on leave), and is suppressed while a button is held, the viewport moves, a column drag or annotation link drag is live, a context menu is open, or the device has no fine hover pointer; a node drag freezes the focus (grabbing another table moves the focus to it first, and the dropped table is previewed on release). The lines of `flowFocus = hoverFocus ?? focus(selection)` carry SMIL glyphs from the `1` end to the `*` end (`flowModeFor`: chevrons; both ways for many-to-many; two dots meeting for one-to-one; none on a `missing` line). A click selection's glyphs move for `SELECTION_FLOW_SETTLE_MS` (6 s) and then stand still, so a table left selected does not keep the webview animating. With the OS reduce-motion setting on, more than 40 flowing lines, or a settled selection, the glyphs are still: a plain `translate() rotate()` on a straight run of the path (`lib/pathGeometry.ts`), never a frozen SMIL frame, because Chrome stops applying `path` / `rotate` / `keyPoints` changes to an ended `fill="freeze"` animation. Glyphs scale up as the canvas zooms out (up to 2.5×) so they stay about 8 screen px; none are drawn below zoom 0.35 or in print. It behaves the same in viewer mode and on the Physical tab.
8. **elkLayout** runs ELK auto-layout in a Web Worker (injected at build time as `__ELK_WORKER_CODE__`; 30 s timeout, failures surface as a toast)

## Webview (`webview/`)

The canvas itself lives in `@erd-studio/renderer` (see `packages/CLAUDE.md`); `webview/` is the editor built around it. `App.tsx` wraps everything in `CanvasStoreProvider` (the singleton store below) and `CanvasEnvironmentProvider` (`host/vscodeCanvasHost.ts`, which forwards canvas edits to `acquireVsCodeApi().postMessage`), and gets its nodes, edges and click handlers from the renderer's `useCanvasGraph`.

|-----------|---------|

`erdStudio.feedback.aiAssist`, `.provider`, `.endpoint`, `.model` and `.hostedFallback` are contributed with `"scope": "machine"` and are additionally listed in `USER_SCOPED_SETTINGS` (`src/services/configService.ts`), so `getErdStudioSetting()` reads **only** their global value. Do not remove either half: the scope keeps the value out of `inspect()`, and the list is what makes that true for this codebase's hand-rolled precedence chain.

## Message protocol

Extension <-> Webview communication uses discriminated unions on `type` field:
- **Extension -> Webview**: `loading` (the first answer to `ready`, posted before the diagram is read: `{}` then `{ tables }`; see **Opening a canvas**), `domainLoaded`, `stageData` (both envelopes carry an optional `logicalOnly?: true` beside `manifestMissing` — see **Logical-only mode** under Activation; it is never inside `DisplaySubjectArea`, and absent means the physical stage is available, as every older payload meant), `discrepancyReport`, `manifestStaleness`, `syncPlanGenerated`, `existingTables` (the answer to `requestExistingTables`), `revealRelationship` (`{ fromModel, toModel, pairs }`: the Relationships view's **Open in Diagram…**; `SemanticEditorProvider.revealRelationship` holds it per document URI until that canvas has answered `ready` with its diagram, switching a physical canvas to logical first; the webview's `useRevealRelationship` selects the line whose pairs match by `linkKey` and centres both tables once the first layout and the saved viewport have settled, or shows a toast when the diagram does not draw it), `openFeedback`, `feedbackContext`, `feedbackAnalysis`, `feedbackSubmitted`, `error`
- **Webview -> Extension**:
  - telemetry only: `layoutFinished` (`{ ms, ok }` after every auto layout; bucketed to a `layout*` feature, writes nothing, on the physical allowlist)
  - lifecycle/navigation: `ready`, `requestExistingTables` (no payload; the Add Existing Table dialog opening while a row has `detailsPending`; reads only, on the physical allowlist), `dismissWelcome`, `dismissManifestHint` (no payload; the × on the logical stage's **Run dbt parse** hint, `webview/components/Canvas/ManifestHint.tsx` — the webview hides it at once, the host writes `MANIFEST_HINT_DISMISSED_KEY` to `workspaceState` and records `manifestHintDismissed`; the hint shows while a logical `domainLoaded` / `stageData` carries `manifestMissing: true`, which the host sets only when `manifestService.isMissing` and the workspace has not dismissed it — never on physical payloads; not on the physical allowlist), `openGettingStarted`, `showLogs` (no payload; the load-error screen's and the **Canvas disconnected** overlay's **Show Logs** — runs `erdStudio.showLogs`, writes nothing, on the physical allowlist), `viewFile` (optional `{ line, column? }`, `validateViewFilePayload`: the **Open at Line N** button of the "isn't valid JSON" screen, #186, opens the file with the cursor there; with no payload — the toolbar's View JSON — it opens as before), `openModelFile`, `requestReload`, `closeEditor` / `openAnotherDomain` (no payload; the **Close** and **Open Another Diagram…** buttons of the `domain-missing` screen, #161 — the host disposes the panel / runs `erdStudio.openDomain` with no file; write nothing, on the physical allowlist), `switchStage`, `refreshManifest`, `undo`, `redo`, `exportDiagram` (no payload, `validateExportDiagramPayload`; the toolbar's **Export** corner button / overflow item — the host runs `erdStudio.exportDiagram` with the panel's document Uri; writes no domain data and always exports the logical design; on the physical allowlist)
  - schema mutations: `addModel`, `addExistingModel`, `addExistingModels` (`{ modelNames }`, 1–`ADD_EXISTING_TABLES_LIMIT` (200) names, `validateAddExistingModelsPayload`; the Add Existing Model dialog with several rows ticked, #160 — v5 only, written by the same `applyDbtModels` as `addModelsFromDbt` but uncapped, keeping models dbt has disabled, and naming picks already in the domain in any case), `addModelsFromDbt` (no payload; the host opens the Draw-from-dbt scope picker, excluding models already in the domain, then writes every picked model and its relationships in one `applySubjectAreaEdit` — `autoLayout: true` when the domain was empty), `renameModel`, `removeModel`, `removeModels`, `addColumn`, `removeColumn`, `updateColumn`, `reorderColumns`, `toggleColumnKey`, `updateModelDescription`, `updateModelGrain`, `updateModelAlias`, `updateModelRole`, `updateModelRationale`, `addRelationship`, `updateRelationship`, `editRelationship`, `removeRelationship`, `removeRelationships`
  - canvas metadata: `updatePositions`, `addAnnotation`, `updateAnnotation`, `removeAnnotation`, `removeAnnotations`
  - sync/discrepancy: `toggleDiscrepancy`, `generateSyncPlan`, `runDbtCompile`, `runDbtParse` (no payload; the physical stage notice's **Run dbt parse** — `runDbtParse()` in `src/commands/runDbtParse.ts`, also behind the "no manifest" notifications, runs `dbt parse` in a terminal in the project root and the manifest watcher refreshes the canvas), `launchClaudeSync`
  - feedback: `requestFeedbackContext`, `analyzeFeedback`, `setFeedbackProvider`, `submitFeedback`, `copyFeedbackReport`, `openFeedbackLink`

Every type in the unions has a live sender and handler — do not add a message type without wiring both ends (unknown types are logged by the `default:` branch, never silently dropped). Multi-select operations are batched: `addExistingModels`, `addModelsFromDbt`, `removeModels`, `removeAnnotations`, `removeRelationships` and `updatePositions` (which carries `annotations?: [{id,x,y}]` for notes moved in the same drag) each produce **one** `WorkspaceEdit`, one save, one `domainLoaded` — i.e. one undo step. `switchStage` carries a `requestId` that the host echoes on `stageData` so the webview can drop stale replies (`webview/lib/stageRequest.ts`).

**Physical stage guard.** While a panel is viewing the physical stage the host rejects every message not in `NON_MUTATION_TYPES` (`src/providers/SemanticEditorProvider.ts`) with a `"Physical stage is read-only"` `error`.

Positions and annotations are allowed because they live in the shared `viewConfig` (physical inherits logical positions); `generateSyncPlan` is the physical-stage "Compare to Logical" flow; the six feedback types write no domain data at all (`setFeedbackProvider` writes a user setting, never a file); `openGettingStarted` (no payload, sent by the WelcomeModal's **Watch the short tour** link) only runs `erdStudio.showGettingStarted`. `closeEditor` and `openAnotherDomain` only close the tab or open the diagram picker. `openModelFile` (`{ modelName }`, sent by the **Open file** button on a node whose `logical-models` file has a YAML error — `DisplayTable.loadError`) only opens that yml in a text editor at the error line. `runDbtParse` writes no domain data (only dbt's own `target/`), and the physical stage is exactly where a missing manifest shows. `exportDiagram` writes nothing (Save As… writes only the file the user names in the save dialog) and always exports the logical design, so it is allowed on both stages. `addModelsFromDbt` is a schema mutation and is **not** on it (the guard refuses it before any picker opens). `undo`/`redo` are deliberately **not** allowed (the toolbar hides them there) — they would rewind the logical document under a derived view.

**DBML writes** (native DBML storage) use the same pipeline. The codec parses a `.dbml` diagram to the v5 object every handler mutates and renders it back by **splicing** at parser node offsets (core's `editSubjectAreaDbml`, `erd_layout` included, rewritten only when a position or sticky box changed). Table and relationships files are planned by the pure `planDbmlLibraryWrites` (`src/services/dbmlLibraryWrites.ts`), which only places tables and Refs in files (a new Ref by the relationships index's two-step rule, an existing one edited in the file that holds it) and builds their text with `editTableDbml` / `renderNewTableDbml` / `editRelationshipsDbml`. A no-op save is byte-identical, and a file that does not parse is refused (`DbmlEditRefused`), never regenerated. Every edit that creates or deletes files is applied by the one helper `applyFileWrites` (`src/providers/applyFileWrites.ts`: creates first, relationships files before tables, then replaces, renames, deletes, all in one `WorkspaceEdit`; on a `false` from `applyEdit` it reconciles what landed); the fs paths outside the editor (`writeNewSubjectArea`, Convert's resume) use `writeFilesWithRollback` (`src/services/fsFileWrites.ts`). Relationship edits on a DBML diagram always use `home = 'library'` (DBML diagrams hold no Refs).

**Edit pipeline.** All domain-file writes go through `applySubjectAreaEdit()` in `SemanticEditorProvider` — the only place a domain `WorkspaceEdit` is built: parse → mutate → replace whole document → `applyEdit` → `document.save()` → refresh, with `pendingUpdates` held so the change listener never double-saves. Edits are saved immediately; the custom editor never sits dirty. (That brief dirty state is also what turns a preview tab into a pinned one — see the note on `erdStudio.openDomain` under Update recovery.) A mutator throws `EditAborted` to bail out after reporting its own error; pass `errorLabel` for the applyEdit-rejected case and `onSuccess` for follow-up work such as `selectorsService.scheduleRegenerate()`. `applyTableEdit()` routes `logical-models/*.yml` changes through the **same** `WorkspaceEdit` (`modelFiles: { save: [{ model, fromName? }], delete }`) so a model edit and its domain change are atomic and one undo step — never `fs.writeFileSync` a model file from a handler (`addExistingModel` seeds a new library file the same way, so a rejected edit leaves no orphan yml). `fromName` names the file whose existing YAML document supplies comments / key order / unknown keys: a rename passes the OLD name so hand-written content is carried to the new file instead of being regenerated. Every file the pipeline writes is recorded in `ownWrites` **after** the bytes land (the tracker reads what the file holds), so the watchers skip our own saves; the refreshes they used to drive are issued directly instead — `sendSubjectAreaData` for the editing panel, `refreshSubjectAreasReferencingTable(name, exceptPanelKey)` for other open panels, and the `onDidWriteSubjectArea` event for the tree / model library views. An undo/redo flushes only the yml documents this provider itself wrote for that domain (`editedTablePaths`) — a model file the user is hand-editing in another tab is never force-saved. When VS Code undoes only the diagram's own part of a step (`UndoRedoService._tryToSplitAndUndo`, after a file in it was edited since), and that part was the one-character anchor, the `.dbml` is left dirty with the text it has on disk: `flushUndoRedo` saves it, and when no other file was saved and every file the canvas created still exists, stops there: no send, no `onDidWriteSubjectArea`, no library invalidation. A DBML undo whose only change is inside `erd_layout` (`sameOutsideErdLayout(disk, document)`) is a layout-only rewind: saved, the canvas re-sent, `layoutOnly` fired, nothing invalidated and neither tree refreshed. Cmd+Z / Cmd+Shift+Z on the canvas is VS Code's own undo, not the toolbar's `undo` message: the change listener sees `TextDocumentChangeReason.Undo` / `Redo` on the domain file, or on an `editedTablePaths` file while the panel is active, and after `NATIVE_UNDO_SETTLE_MS` runs the same `flushUndoRedo` as the toolbar (the mock's `_fireDidChangeTextDocument` drives it in tests). **Layout-only edits** (`isLayoutOnlyChange` in `subjectAreaCodec.ts`: only `viewConfig.positions` and sticky-note boxes — `x`, `y`, `width`, `height` — differ; an edit that changed nothing is not one) take `applyLayoutOnlyEdit`, in either storage, unless they carry `modelFiles` or `otherDomains` or the DBML diagram is not writable or holds its own tables: a DBML diagram splices its own `erd_layout` (`layoutOnlyText`: unformatted, one minimal-range replace, `minimalPrimary`; a conflicted `erd_layout` turns it into a toast), a JSON diagram writes its own text (it holds the positions). Nothing is planned against the library (no `planTableWrites`, library plan, attachment, settle pass or diagram render) and nothing in it is invalidated; the DBML reading is primed from the new text (`primeLayoutOnlyReading`), so the next drag compiles nothing. The edit is one `WorkspaceEdit` of the diagram alone, one save and one native undo step, and `onDidWriteSubjectArea` carries `layoutOnly: true`, on which `extension.ts` refreshes neither tree. `handleUpdatePositions` aborts (`EditAborted`) when every table was dropped where it already was. Drags that queue up behind a running edit are folded into one `updatePositions` edit by `queuePositions` (later positions win) while that batch is still the last thing queued — never across another edit, so edits stay in order; folded drags are one undo step. `applyFileWrites` leaves out any replace whose text the file already holds (no edit, no save, no watcher event); the primary is the exception, because VS Code's Undo on the canvas undoes the last edit of the canvas's own document: an edit that changes only other files (a table's column, say) gives the unchanged primary the one-character anchor `undoAnchor` (its first non-line-break character replaced by itself) instead of a full-range replace of the whole diagram, and the anchor's save rewrites the diagram with the same bytes. A move never needs it: it changes the diagram's own `erd_layout`. A drop in place writes nothing at all. The canvas side keeps the store's node and edge objects for everything a domain update left the same (`reuseUnchanged` in the renderer's `useCanvasGraph`), so the optimistic update after a drag re-renders only the moved tables and their edges. After an edit the provider drops only what it wrote (`TableLibraryService.invalidatePaths(writtenPaths(applied))`, never the blanket `invalidateCache()`, which Convert and the bulk commands keep): each written table's parse, a written relationships file's reading, and the library index when a table file appeared or went. The attachment of Refs (`libraryAttachment`) is memoised against each table's fingerprint (name, folder, storage, DBML alias, column names and keys), so a table re-read for a description or a note keeps the memo; an undo/redo drops this canvas's `editedTablePaths` and the index. The Subject Areas tree counts a diagram's tables with `SubjectAreaService.countSubjectAreaTables` (the file alone, no table resolved) and lists the subject areas once per render; the Table Library caches each diagram's members by mtime + size and, for a table file not read in its current version (`peekTableFileError` is undefined), shows it at once and reads it in background slices, rendering again only when one needs fixing. Payloads are validated at the message boundary by `src/providers/payloadValidation.ts` (model names via the shared `TABLE_NAME_PATTERN` in `src/types/naming.ts`, column lists incl. duplicates, `keyType`, `cardinality`, `modelRole`, finite positions); `TableLibraryService.tablePath` refuses names that escape `logical-models/`. The message listener is wrapped in `withMessageErrorBoundary()` so a throwing handler posts an `error` instead of becoming an unhandled rejection. A domain file deleted or renamed outside ERD Studio (#161) is never written back: `applySubjectAreaEdit` and undo/redo refuse once `document.uri.fsPath` is gone, the change listener does not save it, and `syncSubjectAreaFilePresence()` (called by both semantic-file watchers) moves every open canvas whose file is gone to the `domain-missing` error screen, and re-reads one whose file is back. Refresh paths (watchers, external edits, stage switches) never write — only the initial `ready` load persists auto-computed positions, and only for a **partially** positioned domain. A **fresh** domain (≥1 model, not one `viewConfig.positions` entry — typically written by an AI assistant with `viewConfig: {}`; `isFreshLayout()`) is the exception: on the logical stage `sendSubjectAreaData` still puts the simple `computeNewTablePositions` placement in the payload (so nothing paints at 0,0) but writes nothing, and sets `autoLayout: true` on the `domainLoaded` message. The webview stores it as `pendingAutoLayout`; `useFirstOpenAutoLayout` (in `Toolbar`) waits until every model has a node, clears the flag and calls the same `runLayout` as the Layout button / Shift+L — ELK, `fitView`, one `updatePositions` (one edit, one undo step). Every other `domainLoaded` / `stageData` overwrites the flag, so a later unflagged payload cancels a layout that has not started. If ELK fails the toast shows and nothing is written, so the next open asks again. Physical never carries the flag.

**Opening a canvas.** The `ready` handler first posts `loading` (`postLoading`: `{}`, then `{ tables }` from `countSubjectAreaTablesInText` over the document's text — no table is read), each followed by `yieldToEventLoop()` (`src/services/libraryWarmUp.ts`, a real `setTimeout(0)` captured at load so test fake timers cannot stall it), so the message leaves the host before the read blocks it; the webview's `useReconnectWatchdog` then waits `LOADING_STALL_MS` (2 min) instead of `RECONNECT_GRACE_MS` and shows "Loading N tables…" (`editor-message__spinner`). `SubjectAreaService.getSubjectArea` runs inside `TableLibraryService.withIndexSnapshot` (the index is validated once, not per lookup) and builds the unified area inside `readingTables(members, …)`: a member's relationships come from `scopedAttachment` — the whole-library memo when it is still valid, else `memberAttachment` (`src/services/memberAttachment.ts`) over the Refs naming a member or a member's DBML alias, with ends resolved as `dbmlTableLookup` resolves them by name, falling back to `libraryAttachment` for a library holding YAML, a dangling or alias end, or a file that does not read. So a cold open reads the members and the other ends of their Refs, not the library (`test/unit/scopedTableReads.test.ts` holds it equal to the whole-library attach on random libraries). A DBML diagram is read through `readDbmlDiagram` (`src/services/dbmlDiagramReadings.ts`: the last four readings by layer folder, stem, text and layout; each caller gets a copy), so the read, `holdsOwnTables`, the telemetry survey and the edit pipeline's `parseSubjectAreaFile` share one reading, and core keeps diagram compiles in their own cache (`compileOne(…, { diagram: true })`) so reading the tables never evicts the diagram. Positions computed for a partly placed diagram are written by `autoPositionNewTables`; when that went out as a layout-only write (`onLayoutOnly`) the diagram is not read again. `buildWebviewPayload` lists the Table Library from `tablePreviews` (cached parses, no attach, no copies); with more than `EXISTING_TABLES_READ_AT_MOST` (100) unread files, those rows go out by name and path with `detailsPending` (core's optional `ExistingTablePreview.detailsPending`), and the dialog posts `requestExistingTables`, answered by `sendExistingTables` (reads the rest in 20 ms slices, then posts `existingTables`). The relationship survey (`recordRelationshipState`, telemetry) runs `RELATIONSHIP_SURVEY_DELAY_MS` (3 s) after the open, only while telemetry is on and the canvas is open. **Background read.** `LibraryWarmUp` (started by `extension.ts` 1.5 s after activation) reads every unread table file (`unreadTableFiles` / `warmTableFile`: through the caches, nothing reported) in `WARM_UP_SLICE_MS` (12 ms) slices with a turn of the event loop between them, then each relationships file in a slice of its own, then `warmLibraryAttachment` once. Every canvas message and `resolveCustomTextEditor` call `noteForegroundWork()`, which holds the next slice until the host has been quiet for `WARM_UP_QUIET_MS` (300 ms). Reads only; the caches check mtime + size, so a file changed meanwhile is read again by whoever needs it.

## Activation (`src/extension.ts`)

- **Project detection** — `src/services/projectDiscovery.ts` (vscode-free). `resolveDbtProject()` walks the workspace **once** (`findDbtProjectCandidates`: workspace folder roots in workspace order, then a depth-3 BFS for `dbt_project.yml`, skipping `node_modules`, `dbt_packages`, `.git`, `target`, venvs and dot-dirs) and picks, in order: `erdStudio.projectPath` (`source: 'setting'`) → the **Select dbt Project…** pick stored in `workspaceState` under `SELECTED_PROJECT_KEY` (honoured only while it is still a candidate; `'picked'`) → auto-detection, i.e. the first candidate with ERD data (`semanticDir` or a legacy `erd-studio/`), else the first candidate (#82; `'auto'`) → with **no dbt project anywhere**, the first workspace folder holding ERD data (`'erdData'`; workspace folder roots only, no search below them) → the first workspace folder (`'folder'`). Any dbt project still beats a plain folder with ERD data. `DbtProjectResolution.hasDbt` is `hasDbtProjectFile(root)`; false means the host runs **logical-only** (below). Only an empty window (no folders, no valid `projectPath`) resolves to `root: undefined`. The pick is deliberately **per machine and never a setting**: an absolute path written to `.code-workspace` / `.vscode/settings.json` would leak into files teams commit; `projectPath` stays the explicit, shareable override. `projectPath` may name **any existing folder** (#111): a dbt project under one of the workspace folders is preferred, then any directory, so ERD Studio runs without dbt (logical-only, as for an auto-detected plain folder; `manifestHintFlag()` also suppresses the logical Run dbt parse hint while the root has no `dbt_project.yml`). `candidates`, `autoRoot`, the picker and `hasMultipleDbtProjects` stay dbt-only. The CLI's `resolveProjectRoot` (`src/cli/context.ts`) mirrors this resolution: walking up from the current directory, the nearest folder holding `dbt_project.yml` or the semantic dir wins (so a design folder nested in a dbt repo is its own logical-only root, as the extension opens it), a dbt project up to three levels below the current directory beats a design folder, and `--project` accepts a logical-only folder (see `docs/dev/onboarding-and-cli.md` → The CLI on a logical-only root). A `projectPath` that is not a folder comes back as `invalidSetting` and is shown as a warning, not only logged. `erdStudio.selectDbtProject` offers **Auto-detect** (clears the pick) plus every candidate, confirms in a modal and reloads the window itself; while `projectPath` is set it points at the setting instead. `erdStudio.hasMultipleDbtProjects` (refreshed on `onDidChangeWorkspaceFolders`) reveals the view-title button, and `SubjectAreaTreeProvider.setProjectRow()` puts a clickable **project row** (`contextValue` `dbtProject`, runs `erdStudio.selectDbtProject`) at the top of the tree. The requester asked for a button in the tab itself, and VS Code shows view-title icons only on hover. The row appears only alongside layers: an empty tree must stay empty so the welcome view, which has its own Select dbt Project link, still shows. `SemanticEditorProvider.resolveCustomTextEditor` refuses a domain file whose owning project (`findOwningDbtProject(file, workspaceRoot)`, nearest ancestor with `dbt_project.yml` **or** the open root itself, so a dbt-less root nested in a dbt repo owns its files) is not the open one — it would otherwise read another project's models and manifest and write model yml into the wrong project — and renders a scriptless page plus a notification that run `erdStudio.selectDbtProject` with that project. With no root — now only an empty window — `registerFallbackCommands()` registers every contributed command (plus aliases) with the no-project warning ("ERD Studio: Open a folder first. Any folder works; a dbt project also gets the Physical view.", with the existing buttons) and a stub custom editor, so nothing reports "command not found". A plain folder takes the full project path and registers every real command.

The Welcome panel's project-path deps are late-bound through `let gettingStartedDeps` (the same pattern as `editorProviderForFeedback`); without a project it gets `noProjectGettingStartedDeps()`. `ReportTrackingService` and `MyReportsTreeProvider` are constructed immediately after `editorProviderForFeedback = editorProvider` — before `refreshContextKeys()` is defined and synchronously called — and the provider gets the tracker via `setReportTracking()` rather than a sixth constructor argument.

VS Code matches the selector case-insensitively, a tab restored from 1.9 keeps its editor and `vscode.openWith` ignores the selector, so a `.dbml` that `classifySemanticFile` says is not a diagram gets the **not-a-diagram page** (`notADiagramMessage` + `REOPEN_AS_TEXT_SENTENCE`: the 1.9 text for a pre-release file, "is a DBML table or relationships file, not a diagram" for those, else where diagrams live), never a reroute. Activation in a YAML project writes nothing for DBML: the Convert offer is a modal dialog on a canvas `ready` (`maybeOfferDbmlConversion`, once a session, never after Don't Ask Again or with `erdStudio.dbml.offerConvert` off; Cancel is Not Now; decided from the file listing alone, never a plan). `erdStudio.storage`, `erdStudio.hasSemanticDir` / `erdStudio.hasLogicalModelsDir` are refreshed by `refreshContextKeys()` after every relevant watcher event and command. `erdStudio.tablesLoading` is set true with `erdStudio.diagramsLoading`, just before `erdStudio.hasProject`, and is cleared only by a Table Library root `getChildren` that finds **no rows** (a listing with rows sets it true again); it is also true while a root `getChildren` lists the library from scratch (`TableLibraryService.indexIsCold()`: no index yet, or one a full `invalidateCache()` dropped); the provider sets it through the callback `extension.ts` passes (`TableLibraryTreeProvider.isLoading()`), never `refreshContextKeys`. The welcome view's "Loading tables…" entry uses it, and the empty-state entry is gated on `!erdStudio.tablesLoading`. `erdStudio.diagramsLoading` does the same for the **ERD Studio** view (`erdStudio.domainTree`): set true just before `erdStudio.hasProject` (only when a root resolved) and cleared only by a `SubjectAreaTreeProvider` root `getChildren` that finds no rows (its `onLoadingChange` callback; a listing with rows sets it true again). Neither key is cleared by a listing with rows: VS Code applies a context key as soon as it arrives but draws the rows a little later, so clearing it on the first listing flashed the empty-state text over a full project (seen at 1,100 tables). `viewsWelcome` only shows for a view whose provider is registered and returned no rows, so the view is created right after `erdStudio.hasProject` is set, before any service, with a `DeferredTreeDataProvider` (`src/providers/deferredTreeDataProvider.ts`): it answers the root with no rows until the real provider is attached (where the view used to be created) and a turn has passed since an empty answer, then fires one `onDidChangeTreeData`, and passes every request, change and drag and drop to the real provider after — no "There is no data provider registered" and no blank pane while activation and the first listing run; its "Loading diagrams…" entry needs `erdStudio.hasProject && erdStudio.diagramsLoading`, and both "No diagrams yet." entries are gated on `!erdStudio.diagramsLoading`. `erdStudio.hasTrackedReports` (which gates the **My Reports** view) is deliberately **not** one of them — `ReportTrackingService` sets it itself, so activation never has to reference the service from `refreshContextKeys`.
- **Sidebar views** (`erd-studio` container, in order): **Diagrams** (`erdStudio.domainTree`, `SubjectAreaTreeProvider`), **Table Library** (`erdStudio.modelLibrary`), **Relationships** (`erdStudio.relationships`, `RelationshipsTreeProvider`, shown with the Table Library) and **Help & Feedback** (`erdStudio.help`, `HelpTreeProvider`, starts collapsed; **My Reports** is a row there once the tracking service has a report). Each title bar carries at most one icon (`test/unit/sidebarLayout.test.ts`): the Diagrams view's is the `erdStudio.newMenu` submenu (+: New Subject Area, Draw from dbt, Import DBML, New Layer); everything else is a labelled row, a row's inline action, or in a **…** menu. A creatable layer row has `contextValue` `layerCreatable` and offers New Diagram inline; `createDomain` accepts that row or a layer id. The Relationships view is `buildRelationshipsOverview` (`src/services/relationshipsOverview.ts`, pure) over `TableLibraryService.listTables()` plus the JSON diagrams' own relationships (`readSubjectAreaRelationships`); it reads unread table files in 50 ms slices first, lists again whenever the Table Library refreshes (its `onDidChangeTreeData`, so the refresh gate holds it too), and is only asked while visible. A row's click is the code-only `erdStudio.openRelationshipSource` (the Ref's line via `relationshipLocation`, the FK table's yml, or the diagram); **Open in Diagram…** (`erdStudio.openInDiagram`) opens a diagram whose members include both tables. Nothing in these views writes.
- **Settings changes** to `semanticDir` / `projectPath` (either prefix) prompt for a window reload.

## Commands that create or export files

Not the canvas edit pipeline: these create new files or write only what the user saves.

- **Draw from dbt…** (`erdStudio.drawFromDbt`, `src/commands/drawFromDbt.ts`, draft from the pure `src/services/dbtDraft.ts`) and **Import DBML…** (`erdStudio.importDbml`, `src/commands/importDbml.ts`, plan from the pure `src/services/dbmlImport.ts`) each create a **new** subject area plus the table files the library lacks, through the one shared, vscode-free writer `writeNewSubjectArea` (`src/services/newSubjectAreaWriter.ts`): new table files via `saveTable`, the subject area file with `wx`, then any existing library table that gained a relationship, `ownWrites` after each write, and everything put back on failure. In a project that writes DBML the subject area is a `.dbml` diagram in `<layer>/diagrams/`: its table files, relationships files, diagram (positions included), README on a new root and the settle re-render of other DBML diagrams are one `applyDbmlBatch`, written by `writeFilesWithRollback`. **New Subject Area**, Rename and Delete, Organise Table Library and Give Duplicate Its Own Name follow the project's storage the same way (the pure planners in `src/commands/dbmlLifecycle.ts`); Open Example Diagram goes through Import's writer. **Convert Project to DBML** (`erdStudio.convertProjectToDbml`, `src/commands/convertProjectToDbml.ts`) plans with the pure `planDbmlConversion` (`src/services/dbmlConversion.ts`, input from `readDbmlConversionInput`), shows the plan (or its refusals) in the **Convert to DBML** webview panel (`src/providers/ConvertToDbmlPanel.ts`: one at a time, nonce-only CSP, its own small validated protocol in the pure `src/services/dbmlConversionReview.ts`, not part of the canvas protocol in `src/types/messages.ts`; it writes nothing and hands Convert / Cancel / Check Again back to the command; a refusal's **Open** sends an index into the host's list, never a path), and applies the plan with one `applyFileWrites`. `erd-studio doctor`'s text preview stays `describeDbmlConversion`. A file they would change that is dirty in an editor stops them before any write. In `extension.ts` both call one `refreshAfterNewSubjectArea` closure. Both are registered after the no-project early return and listed in `NO_LEGACY_ALIAS`; Import DBML needs no dbt files.
- **Export Diagram…** (`erdStudio.exportDiagram`, `src/commands/exportDiagram.ts`) and **Export All Diagrams…** (`erdStudio.exportAllDiagrams`, `src/commands/exportAllDiagrams.ts`) export the logical stage as Mermaid, DBML or **Rich DBML** (`dbml-rich`, one file per diagram with the positions in its Project's `erd_layout`), through `src/services/diagramExport.ts` — the same read `erd-studio export` uses, so the bytes match. They write no ERD Studio file.

Details of the DBML formats, the parser pin and the import mapping: `docs/dev/dbml.md`.

## Watchers (`src/watchers/FileWatcherService.ts`)

Own writes are recorded in `ownWrites` (`src/services/ownWriteTracker.ts`) by `SemanticEditorProvider` (the editor write path — domain file, model yml saves, creates and deletes), `TableLibraryService`, `LayerService` and the `deleteDomain` command, and consumed in the callbacks that watch files the extension itself writes (domain `.json` / `.dbml` changes and deletes, `{semanticDir}/**/*.{json,dbml}`, classified by path: a diagram is a domain event, positions included; a `<layer>/relationships/*.dbml` fires its own debounced `onRelationshipsChanged`, which redraws every open canvas because its Refs may name any table; `layers.json`; table files, `{logical-models,tables}/**/*.yml` and `*/tables/*/*.dbml`) so an extension save never triggers a second identical refresh. A record is matched by **content** (the size and a SHA-1 of the bytes on disk right after the write; a delete matches while the file is still gone), not by a time window: a watcher callback that runs long after the save, because the host was busy, still sees the save as ours (the old 5 s TTL did not, and a 10 s stall made every save an "external change" that redrew the canvas and the trees again). A match consumes the record (and older ones for the path) and still matches a duplicate event of the same bytes for `CONSUMED_GRACE_MS` (2 s); a mismatch forgets the path's records, so an external edit is always reported. Records nothing consumed are dropped after `MAX_RECORD_AGE_MS` (10 min, a memory bound; at most 8 per path). The editor's write paths (`applyAndSaveWrites`, the YAML path of `applySubjectAreaEdit`, `flushUndoRedo`) and the bulk commands **Convert Project to DBML** and **Migrate to the New File Naming** (every file they create, replace, move or delete) also announce their files with `expectWrite` before the edit and `settleWrites` after the saves: while a path is pending (at most `MAX_PENDING_MS`, 60 s), the watcher callback (`FileWatcherService.debounceOwnWrite`) waits another debounce instead of deciding, because after a stall the timer can fire before the save's completion is processed. The manifest, catalog and `dbt_project.yml` callbacks have nothing to consume — the extension never writes those. One watcher covers both dbt artifacts (`{target-path}/{manifest.json,catalog.json}`) on separate debounce keys, firing `onManifestChanged` or `onCatalogChanged`; one covers dbt source files (`{model,seed,snapshot}-paths/**/*.{yml,yaml,sql,py,csv}`) and fires `onDbtYmlChanged` on create and delete of any of them but on change only for yml — a `.sql` body edit changes no shape the physical stage reads. `renameDomain` (`extension.ts`) is the one gap: its create+delete `WorkspaceEdit` records neither path, so the old file's delete is seen as external. A layout change arrives as a change to its diagram (`layout: true`). A `.yml` table or `.json` diagram ERD Studio did not write appearing in a DBML project fires `onForeignFormatCreated` (one warning per session offering **Update AI Helper Files**; the file is never converted or deleted). `classifySemanticPath()` ensures only `{layer}/{domain}.json` and `{layer}/{domain}.dbml` fire `onSemanticFileDeleted` (coalesced to one `{ uris }` event per burst); `layers.json` has its own `onLayerConfigChanged`. `LayerService.loadConfig()` is mtime-validated and refuses to overwrite an unreadable/invalid `layers.json` (`getLoadError()`).

- **Bursts.** Every table file shares one debounce (`tables`): a batch reports one `onTableChanged` per table, then one `onTablesChanged` with them all, and logs one line (`External change to N table files: a, b, c and N-3 more`). At `BULK_CHANGE_MIN_EVENTS` (20) events on the project's files (the diagram and table watchers), each within the debounce of the last — Edit > Undo of Convert Project to DBML, a branch switch — the watcher raises `onBulkChangeStarted` and every `debounceOwnWrite` callback waits until the files have been quiet for one debounce; `onBulkChangeSettled({ reported })` fires once they have all run. `extension.ts` holds `editorProvider.holdRefreshes()` and `viewRefreshes` from start to settle, so the trees and context keys refresh once, the library index is built once for the batch (`extension.ts` handles `onTablesChanged`, not each table: `invalidateTables(names)` resolves every name inside one index snapshot and drops their files together, because the disk is not stable yet — Undo can still be deleting files when the batch runs, and a folder changed within `RACY_MS` makes every unsnapshotted lookup list the library again; `refreshContextKeys` runs once per batch, inside one snapshot), no canvas redraws from half-written files, and every open canvas redraws once (`refreshAllOpenSubjectAreas`) when anything was reported (not only own writes) or when a canvas refresh was dropped while held (`holdRefreshes()`'s release returns whether one was): Convert's own redraw after its write lands inside the burst of its own files, which outlasts Convert's hold, so it is made at the settle instead. A hold marks each open canvas in `pendingUpdates`, which silences its change listener; a native undo/redo that reaches a canvas only a hold marked (`heldPanels`) is remembered and flushed when that hold releases, never dropped, and an undo counts as the canvas's only with the canvas in front or during its own toolbar undo, not because a hold marked it.

## Logging (`src/services/logger.ts`)

One logger for the extension host, the CLI, the manifest worker's host side and the MCP server. The module imports **nothing** (no `vscode`, no Node built-ins), so any bundle may log through it; `test/unit/loggerBoundary.test.ts` pins that.

- **Levels and sink.** `log` (no prefix) and `createLogger(scope)` (`[scope] message`) write `trace` / `debug` / `info` / `warn` / `error` to one pluggable `LogSink`. `activate()` plugs in `vscode.window.createOutputChannel('ERD Studio', { log: true })` — a `LogOutputChannel` (VS Code 1.74+, in `@types/vscode` 1.85), whose own level menu filters what shows — first thing, and unplugs it on dispose. Nothing else sets a sink.
- **The console.** `warn` and `error` also go to `console.warn` / `console.error`, exactly as the `console.*` calls they replaced did: the extension host's log, the CLI's `--verbose` capture (which swaps `console.*` while it runs, so the console is looked up on every call) and the tests' spies keep seeing them. `info`, `debug` and `trace` reach the sink only; without one (CLI, MCP, tests) they are silent. **Never `console.log`**: it is the MCP server's stdio protocol stream. `writeLog(…, mirrorToConsole: false)` keeps a line out of the console (used by `ErrorLog.record`, whose lines never went there).
- **What is logged.** Activation: version, VS Code version, platform, then `Project: <DBML|YAML|mixed> storage, N table file(s), M diagram(s), dbt project|no dbt project; project read X ms into activation` (`logProjectSummary`), and `Activated in X ms` as the last line of `activate()`. Opening a diagram: `[Canvas] Opening <path>`, each phase of `sendSubjectAreaData` (`phaseTimer`: dbt files, the diagram and its tables, positions saved for new tables, building the canvas; `info` on the first load, `debug` on a refresh) and `Opened <path>: N tables posted X ms after ready`. Each position save: tables / notes, ms, whether it was a layout-only write. Convert Project to DBML (`[Convert to DBML]`): files read, each planning phase (the same `CONVERT_PROGRESS` texts the notification shows) with its time, the plan's counts, each refusal (`warn`) and file left as is, then each writing phase and the outcome. Table files that fail to read: path and `line:column`. At `debug`: each sidebar tree render (`[Subject Areas]`, `[Table Library]`, marked when the library is read from scratch), each library index build, a full cache drop, and every watcher event that is an outside change; at `trace`: each own write a watcher ignored. The background library read logs when it finishes (`info`).
- **The buffer.** The last `LOG_BUFFER_CAPACITY` (200) `info` / `warn` / `error` lines are kept in memory, raw. Only Send Feedback reads it (`redactedRecentLog()` in `feedbackService.ts`, through `redactPaths()`), and only when the user ticks the opt-in box (see `docs/dev/feedback.md`). **Telemetry never imports the logger or reads the buffer** (`loggerBoundary.test.ts`): telemetry fields hold no name, path or message, and log lines hold all three.
- **Show Logs.** `erdStudio.showLogs` (`SHOW_LOGS_COMMAND`, `src/services/showLogs.ts`, in `PRE_REGISTERED_COMMANDS` and `NO_LEGACY_ALIAS`) reveals the channel. `SHOW_LOGS_BUTTON` sits on Convert's own failures, the canvas's Move Relationships failure, the **Convert to DBML** tab's refused page (`showLogs` panel message), the canvas load-error screen and the **Canvas disconnected** overlay (`showLogs` webview message). It is also in the **ERD Studio** view's (`erdStudio.domainTree`) **…** menu.
- **Writing a new line.** Prefer `createLogger('<Area>')`; put file paths in local lines freely (the feedback path redacts them), but identify a diagram by its absolute path rather than its name where you can, so the redacted copy shows its shape, not its name. Time a multi-step job with `phaseTimer`. Keep chatty per-file lines at `debug` / `trace`.

## Discrepancy system

Cross-stage comparison is handled by `DiscrepancyService.compare(source, target)`:

| Active Stage | Available Comparisons |
|-------------|----------------------|
| Physical | Compare to Logical |
| Logical | Compare to Physical |

Discrepancy statuses for models/columns/relationships: `matched`, `extra`, `missing`, `type-mismatch` and `undeclared` (columns), `cardinality-mismatch` (relationships). `undeclared` is the case where exactly one stage declares a data type at all — it gets its own status and its own `summary.undeclaredColumns` count rather than inflating the mismatch count, and `deriveColumnAction` still resolves it like a mismatch so "write `data_type:` into the yml" stays reachable. Ghost nodes appear for missing models. Two suppressions, with different switches: the domain's `stubColumns` list is the user's own, and hides missing-column discrepancies only; separately `compare()` automatically drops models with `existsInProject === false` from both sides (and from `summary.totalModels`), and reports a model whose only evidence is a source file (`columns: []` and `provenance.columns === ['file']`) as `matched` with no column rows, on either side — otherwise one undocumented model would emit its counterpart's whole column list as differences. Type comparison splits a base from its parameters with a matched-delimiter scan (so `timestamp(6) without time zone` and `STRUCT<a INT64>` both keep their real base), canonicalises the spellings adapters actually emit (`character varying` → `string`, `NUMBER`/`numeric` → `decimal`, `INT64` → `int`, `TIMESTAMP_NTZ` → `timestamp`, `TIMESTAMP_LTZ` → `timestamptz`), treats absent parameters on either side as compatible, and has exactly one cross-family rule: a whole-number decimal matches an integer. Sync plans are written to `.erd-studio/.sync-plan.json` by `generateSyncPlan`; **Execute with Claude** confirms the exact terminal command before launching.
