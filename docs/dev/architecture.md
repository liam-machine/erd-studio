## Tests and CI

Tests use vitest with `vscode` module aliased to `test/__mocks__/vscode.ts` (a stateful mock: `inspect()`-backed configuration via `_setMockConfiguration`, in-memory `WorkspaceEdit`/`applyEdit`, command registry that throws on duplicate ids, `_simulateMessage` for webview messages). `vitest.config.ts` mirrors two esbuild settings — an `md-text` transform plugin (a `.md` import is its text) and the `__ERD_CLI_VERSION__` define — so harness and CLI code runs unbundled. `test/globalSetup.ts` builds `dist/manifestWorker.js` before the run so manifest tests pass on a fresh clone. Fixture dbt projects live in `test/fixtures/` (`dbt-project` is the main one; `dbt-project-dbml` is the same project after Convert Project to DBML, generated by `scripts/regen-dbt-dbml-fixture.ts` and kept in step by `test/unit/dbtProjectDbmlFixture.test.ts`, so `test/unit/dbtLoop.storage.test.ts` runs the Physical tab, Compare, Sync, Add Tables from dbt, Import from dbt and `selectors.yml` on both storages; `dbt-project-modern-tests` covers `data_tests:` / `arguments:` / versioned refs; the `-empty-manifest`, `-malformed`, `-sparse`, `-zero-byte` variants cover manifest edge cases).

CI (`.github/workflows/ci.yml`) runs on every PR into `main` or `develop` and on every push to `develop` (i.e. after each merge there): `npm audit --omit=dev --audit-level=high`, compile, build, a **CLI smoke test** (`doctor --no-dbt` must exit 0; `diff --all` may exit 1 for drift but never 2–4; the same `doctor` and `diff --all` on `test/fixtures/dbt-project-dbml`, and `doctor` and `export --all` on the DBML fixture `test/fixtures/dbml-native`), the native DBML end-to-end script (`npm run test:e2e:dbml -- --no-build`: Convert a copy of `dbt-project`, compare `doctor`, `diff`, `export` and every display before and after, and compile every written `.dbml` in DBML 9.1.1, 10.3.1 and 11.0.0), `npm pack --dry-run` of both packages, test, package, and fails if `vsce ls --no-dependencies` lists more than 60 files. An informational `packages-plan` job writes what `publish-packages.yml` would release to npm once the PR reaches `main` into the run summary. A further job type-checks, builds and smoke-tests `mcp-server/` (which imports `src/services/*` and bundles `src/workers/manifestWorker.ts` — an accidental `import 'vscode'` in a shared service fails there). A `telemetry` job runs the telemetry Worker's own `npm test` / `npm run check`, a credential-free `wrangler deploy --dry-run` and its D1 migrations against a throwaway local database.

## Data flow

```
{layer}/diagrams/{domain}.dbml       ─┐   DBML (2.0 default)        subjectAreaCodec / core's @erd-studio/core/dbml readers
  (positions in its Project's erd_layout)
{layer}/tables/{schema}/{name}.dbml ─┤
{layer}/relationships/*.dbml        ─┤   (Refs attached to their FK table; a diagram draws the files it imports)
{layer}/{domain}.json               ─┤   YAML/JSON (before 2.0)   parseSubjectAreaJson / parseTableText
logical-models/**.yml               ─┤   (+ v6 tables/**.yml)
                                     └→ SubjectAreaService.getSubjectArea() ─→ UnifiedSubjectArea ─→ .logical → DisplaySubjectArea
                                                                                          │
schema .yml + source files ─→ YmlParserService ─┐                                         │
manifest.json              ─→ ManifestService  ─┼→ buildPhysicalSubjectArea() ─→ DisplaySubjectArea │
catalog.json               ─→ CatalogService   ─┘                                         │
                                                                                          │
                                                    [message] ─→ graphTransformer ─→ React Flow
```

1. **ManifestService** parses `{target-path}/manifest.json` in a worker thread (`dist/manifestWorker.js`, plain `JSON.parse` — there is no streaming parser or `stream-json` dependency) so 40MB+ files do not block the extension host. `src/workers/manifestExtractor.ts` (pure, shared with tests) extracts model nodes, relationship test nodes (`relationships`, `relationships_where`, custom), `unique` tests and `unique_combination_of_columns` tests, plus the names in the manifest's `disabled` section (the veto on filesystem existence — see step 4), resolving dbt versioned models (`model.proj.name.vN`, `ref('m', v=N)`) to the latest version. A missing manifest is definitive (`ManifestMissingError`, `isMissing` flag); a malformed one is treated as transient (dbt mid-write) and the last known good result is served with `isStale`. Runaway parses are abandoned after `DEFAULT_PARSE_TIMEOUT_MS`.
2. **DbtProjectConfig** (`src/services/dbtProjectConfig.ts`) reads `target-path` / `model-paths` / `seed-paths` / `snapshot-paths` from `dbt_project.yml` once at activation; ManifestService, CatalogService, YmlParserService, FileWatcherService and the staleness check all use those paths rather than hard-coded `target/`, `models/`, `seeds/` and `snapshots/`. `modelPathsGlob()` is the yml/staleness glob, `sourcePathsGlob()` the wider one the source watcher uses, and `resolveCatalogPath()` locates `{target-path}/catalog.json`.
3. **SubjectAreaService** reads a diagram → `UnifiedSubjectArea`. **A `.dbml` diagram** (native DBML storage, `docs/plans/native-dbml-storage.md`) is read by core's `parseSubjectAreaDbml` (through the codec, `src/providers/subjectAreaCodec.ts`, `codecFor(path)`) into the same plain v5 object a JSON file gives (`schemaVersion` 5; the DBML version travels beside it), with its members from the table `use` lines (then `erd_unlinked_tables`) and its positions from its Project's `erd_layout`; a member is resolved by its `use` path first, and only the relationships held in the files the diagram imports are drawn (the same filter for the canvas and the CLI; a file it should import but does not is logged, `unimportedRelationshipsMessage`, and is a "not shown" note on the canvas with **Add the import**: see **The canvas follows the files** under Watchers); **TableLibraryService** resolves each member by name (the YAML libraries in core's `tableFileCandidates` order, `logical-models/` then `tables/`, then the DBML tables of every layer's `tables/<schema>/`; a DBML table is its schema folder and name, shadowed only by an earlier DBML file of the same schema folder and name (another layer, or a schema folder differing only in case) or by a YAML file of the same name, and a name two schema folders hold is read by identity (`findTableById`, `tableEntryAt`), never by the bare name, which answers the first in index order), never with `existsSync`, through one **library index**, `src/services/tableLibraryIndex.ts`: a single listing of the semantic dir, both YAML libraries (top level and one folder down) and each layer folder's `tables/<schema>/` and `relationships/` answers `findTableFile`, `listTableFiles` (duplicates included), `listRelationshipsFiles`, the folders, `hasTablesLibrary` and `tablesDirIsLayer` (the module functions share its rules), and is re-validated on each use by the signatures (inode, mtime, size) of every directory it listed and of `layers.json`, so a file added, renamed or removed outside ERD Studio is seen with no watcher event; a directory changed within `RACY_MS` of a build is not trusted on its signature until it is older), reads a `.dbml` table with `parseTableDbml` (one table per file, tolerant per file: a file that does not parse is a placeholder with a `dbml*` `loadError`), and attaches every relationships file's Refs to their FK table (`attachRelationships`). `detectProjectStorage` (core; host `projectStorageOf`) says what new files are written as: `dbml`, `yaml` or `mixed`. **A domain JSON** (the parsing and repair rules are `@erd-studio/core`'s `domain.ts`), resolving each model name through **TableLibraryService** (`logical-models/{name}.yml` or `logical-models/{folder}/{name}.yml`, then the same under v6's `tables/` (#181; written since #182 under the v6 keys, which `renderTable` renames to v5 for the edit and back after — `TableNamingWriteRefused` only for a file holding a key in both namings; new files go to `tables/` when `projectNamingOf()` is not `v5`; a name in both is a reported conflict, `tableNamingConflicts()`; `tables/` is a layer folder instead when `tablesDirIsLayer()`), found by `findTableFile()`; parsed with `yaml` `parseDocument` and written back by editing that same document in place, so comments, key order and unknown keys survive every UI write — including a canvas rename, which carries the old file's document across via `serializeTable(model, fromName)`. Two exceptions: a file that fails to parse is regenerated from scratch (except one whose only errors are keys written twice: it is read with the last copy winning, carries a `loadWarning`, and every write to it throws `DuplicateKeyWriteRefused`, #164), and folded `>` block scalars are re-emitted on one line, value unchanged. A number keeps the text it was written with (`keepNumberText`: `007` stays `007`), a scalar the reader already reads as the wanted value is never rewritten, and every YAML alias — under a managed key or not, or inside a `relationships:` entry — reads after a save what it read before unless the canvas changed that very key (`settleKeptAliases` writes it out as a literal when its anchor was rewritten or removed; #157). A missing file renders as a placeholder with a warning), then extracts a stage section via `getSubjectAreaStage()` → `DisplaySubjectArea`. Malformed `viewConfig.positions` entries and relationships missing endpoints are dropped with a console warning.
4. For physical stage: `SubjectAreaService.buildPhysicalSubjectArea(unified, ymlData, manifest, catalog)` resolves each logical model against the dbt **project**, not against the manifest alone. **Existence** is `sourceFile ∪ yml ∪ manifest ∪ catalog`, where the source-file branch (a `.sql`/`.py`/`.csv` stem under a model/seed/snapshot path, indexed by `YmlData.sourceFiles`) is vetoed by `ManifestData.disabledModels` — `ref()` to a disabled model fails, so a bare file must not read as "exists". A model in none of those is **still emitted**, with `existsInProject: false`, a `missingReason` (`'absent'` | `'disabled'`), no columns and no `provenance`, and is kept out of `physicalModelNames` so it pulls in no edges — it ghosts on the canvas instead of vanishing. **Columns** come from two kinds of source: the *declared* list is the yml when present, else the manifest per model (one source — the manifest's columns are a compiled copy of the same yml patch, so disagreement there is only staleness), and the *observed* list is `catalog.json`. With a catalog node the rendered list is their union in catalog order with declared-only columns appended; with none it is the declared list, exactly as before. The declared spelling always wins for display (Snowflake's UPPERCASE keys never relabel the canvas). A logical table **seeded from dbt** (`seedTableFromDbt` in `src/services/dbtDraft.ts`: Import from dbt, Add Tables from dbt, Add Existing Model) takes the same columns, so it compares clean the moment it is drawn: the declared columns in declared order, then every catalog-only column in catalog order (a name the catalog reports ALL CAPS, the warehouse folding an unquoted identifier, is lowercased; any other spelling is kept), each typed by the same `resolveColumnType` fallthrough. A model with no declared columns gets no catalog columns either: Import from dbt and Add Tables from dbt do not list it, and Add Existing Model adds it as an empty table. The Add Existing Model dialog counts the seeded columns (`seededColumnCount`, from the cached catalog until the dialog asks for its full list). A sync plan's `add-column-to-logical` for a column neither the yml nor the manifest declares carries the same lowercased name in `columnName`, so a table finished by Sync is spelled as one drawn from dbt. **Types** fall through catalog → declared `data_type:` → manifest → `''`; **descriptions** run the other way (yml → manifest → catalog `comment`, because `persist_docs` writes the dbt description *into* that comment); **`schema`** is manifest → catalog `metadata.schema` → `''` (manifest first: the two agree on the value and differ only in case, and with neither the node's badge hover card says no dbt schema was resolved; the badge itself always names the layer). Catalog nodes resolve by manifest `unique_id` first, then by normalised name. **`provenance`** (`{ columns: PhysicalColumnSource[]; types: PhysicalColumnSource }`) is computed in the same pass — `columns` lists every contributing source most-authoritative-first, `types` names the highest-authority source that supplied any type. It is runtime-only: nothing about it is persisted, and `buildLogicalDisplaySubjectArea` (the logical literal) never sets it. **Relationships are derived from the union of yml and manifest relationship tests** (deduped; never copied from logical; `catalog.json` carries no constraint information and contributes no edges). Cardinality is inferred from `unique`/`unique_combination_of_columns` tests merged from both sources (no unique test = "many" side). Model and column names are matched case-insensitively (`normaliseName()` in `src/services/nameUtils.ts`). Relationships are scoped to models within the domain to prevent conformed dimensions from pulling in external edges. See `derivePhysicalRelationships()` in `domainService.ts`. YmlParserService parses `models:` schema yml under the configured model paths only (seed/snapshot `seeds:` / `snapshots:` blocks, from any of the three roots, go to `YmlData.resourceDocs` and, like the manifest's `seed.`/`snapshot.` nodes in `ManifestData.resourceDocs`, supply **descriptions only** — never existence, columns or edges), but walks model, seed and snapshot paths for source files (skipping `dbt_packages`, `dbt_modules`, venvs), reads both `tests:` and `data_tests:` keys, `unique` as a scalar or map form, and dbt 1.10 `arguments:` nesting; both parsers accept versioned `ref('model', v=2)`. **CatalogService** (`src/services/catalogService.ts`) reads `{target-path}/catalog.json` — written by `dbt docs generate` — for real warehouse column lists and types, caching the "no catalog" answer too, so it must be invalidated on `onCatalogChanged` and in `refreshManifest`.
5. **DiscrepancyService** compares two `DisplaySubjectArea` objects (case-insensitive keys, raw names preserved on the report) to produce a `DiscrepancyReport`. The canvas and the `erd-studio diff` CLI reach it through the **same three pure cores**, which is the only reason the two can never disagree: `buildLogicalDisplaySubjectArea(domain, viewConfig, stubColumns?)` (`src/services/stageDisplay.ts` — a thin wrapper over `@erd-studio/core`'s `toDisplaySubjectArea`, the same function the provider's `buildDisplaySubjectArea` calls with its editor payload, so the logical `DisplaySubjectArea` has one implementation), `computeSubjectAreaDiff({ subjectAreaService, ymlData, manifest, catalog }, domainPath, sourceStage, targetStage?)` (`src/services/stageDiff.ts` — reads the domain once, builds both stages, runs `compare()` with the domain's `stubColumns`; `handleToggleDiscrepancy` calls nothing else) and `buildSyncPlan(report, selections, ctx)` / `allSelections(report, truth)` (`src/services/syncPlanBuilder.ts` — `handleGenerateSyncPlan` keeps only the setting read, the file write and the posts). Reject any comparison logic written locally in the CLI or the provider. Every redraw of the open canvases (`refreshAllOpenSubjectAreas`: Refresh Manifest, a new catalog, a changed relationships file) re-runs an open Compare through `handleToggleDiscrepancy` when it was made from the stage on screen (`lastCompareAgainst !== activeStage`), so the overlay, the staleness banner and the `lastDiscrepancyReport` that Sync plans from never describe the data before the refresh. `checkManifestStalenessFromMtimes()` (`src/services/manifestStaleness.ts`) is the matching pure core for the staleness banner: `stalenessService` feeds it `findFiles` mtimes, the CLI a capped (5000-file) fs walk. The CLI parses the manifest with `ManifestService`'s `parseInProcess: true` option — `extractManifestData` on the calling thread, no worker, same result and error wording.
6. Extension sends `domainLoaded` / `stageData` message to webview (`domainLoaded` carries `autoLayout: true` for a fresh, wholly unpositioned domain — see **Edit pipeline**)
7. **graphTransformer** converts `DisplaySubjectArea` → React Flow nodes + edges (with optional discrepancy overlays); `nodeOverlays.applyNodeOverlays` layers dimming/expansion on top with identity preservation so memoised nodes skip re-rendering
   - **Hover focus and relationship flow** (`useHoverFocus`, `lib/canvasFocus.ts`, `lib/hoverIntent.ts`, `components/Graph/EdgeFlow.tsx`). Resting the pointer on a table previews its neighbourhood. The preview is ephemeral store state, `hoverFocus` and `flowFocus` (`CanvasFocus` sets), never persisted, posted or written, with no message type. It is not dimmed through `applyNodeOverlays`: every `setEdges` re-renders every `FkEdge` (each reads all edges for distribution), which is fine once per click but not on every pointer move. Instead a root class, `erd-flow--hover-focus` on `<ReactFlow>`, fades everything in CSS, and each table and line reads its own role with an O(1) selector returning a primitive. Precedence: hover previews over click and search dimming; leaving restores them untouched (hover never writes `data.dimmed`); the clicked table stays at 0.4 opacity; a click and a hover use the same connectivity rule (`computeCanvasFocus`), except that the hover preview lights only the hovered table's own lines (`ownLinesOnly`). Hover intent waits 120 ms (60 ms to switch tables, 150 ms grace on leave), and is suppressed while a button is held, the viewport moves, a column drag or annotation link drag is live, a context menu is open, or the device has no fine hover pointer; a node drag freezes the focus (grabbing another table moves the focus to it first, and the dropped table is previewed on release). The lines of `flowFocus = hoverFocus ?? focus(selection)` carry SMIL glyphs from the `1` end to the `*` end (`flowModeFor`: chevrons; both ways for many-to-many; two dots meeting for one-to-one; none on a `missing` line). A click selection's glyphs move for `SELECTION_FLOW_SETTLE_MS` (6 s) and then stand still, so a table left selected does not keep the webview animating. With the OS reduce-motion setting on, more than 40 flowing lines, or a settled selection, the glyphs are still: a plain `translate() rotate()` on a straight run of the path (`lib/pathGeometry.ts`), never a frozen SMIL frame, because Chrome stops applying `path` / `rotate` / `keyPoints` changes to an ended `fill="freeze"` animation. Glyphs scale up as the canvas zooms out (up to 2.5×) so they stay about 8 screen px; none are drawn below zoom 0.35 or in print. It behaves the same in viewer mode and on the Physical tab.
8. **elkLayout** runs ELK auto-layout in a Web Worker (injected at build time as `__ELK_WORKER_CODE__`; 30 s timeout, failures surface as a toast)

## Webview (`webview/`)

The canvas itself lives in `@erd-studio/renderer` (see `packages/CLAUDE.md`); `webview/` is the editor built around it. `App.tsx` wraps everything in `CanvasStoreProvider` (the singleton store below) and `CanvasEnvironmentProvider` (`host/vscodeCanvasHost.ts`, which forwards canvas edits to `acquireVsCodeApi().postMessage`), and gets its nodes, edges and click handlers from the renderer's `useCanvasGraph`.

| Directory | Purpose |
|-----------|---------|
| `components/` | React components — `EmptyCanvas/` (logical, editable, zero-model card: **Add models from dbt** posts `addModelsFromDbt`, **New model** opens the New Design Model dialog; `pointer-events: none` overlay), `Graph/DragLine`, `DiscrepancyPanel/`, `Toolbar/` (StageTabs; the top-right corner actions — Export (a `⤓` glyph the size of the `⋯` trigger, so a third label does not make the corner collapse ~155px of window sooner), Send Feedback, View File — collapse to an overflow `⋯` menu only when `measureCorner()` finds they would overlap the top-centre toolbar — measured from the live layout, because the toolbar's width depends on the domain name, the search box and the stage-specific controls, and a CSS breakpoint could only approximate it; where nothing can be measured the labels stay), `FeedbackDialog/` (dialog incl. the header `KindSwitch`, `AnalysisPanel` incl. the destination picker, `DuplicateTakeover`, `DiagnosticsChips`, `FeedbackFooter`), `Toast/`, dialogs |
| `store/` | Zustand singleton (`editorStore.ts`) — the renderer's `createCanvasSlice(set)` (selection, nodes/edges, expansion, context menus, column selection) plus the editor's own state: dialogs, active stage, discrepancy, toast/error, feedback dialog (diagnostics, capabilities, analysis). Its `setDomain` overrides the slice's with the full reset (error, physical-source notice, discrepancy/sync, canvas mode) and must stay last in the initialiser |
| `hooks/` | `useMessageBus` (extension comms; `useSend()` for a stable sender), `useVsCodeApi` (+ `getVsCodeApi()`), `useCanvasShortcuts` (global keydown — reads store via `getState()`, registered once), position/state persistence (flushed on `visibilitychange`/`pagehide`) |
| `host/` | `vscodeCanvasHost.ts` — the `CanvasHost` the renderer's components post edits to |
| `lib/` | `elkLayout` (the ELK runner; node sizing comes from `@erd-studio/renderer/sizing` and is re-exported), `keyboardShortcuts`, `stageRequest`, `stageUtils`, `validation` |
| `styles/` | `host.css` — the webview's `html, body, #root` sizing, loaded after the renderer's `theme.css` (CSS custom properties mapping VS Code theme vars) |

**The draft preview (`webview-draft/`, Draft-first, `docs/dev/draft-first.md`).** A sixth esbuild target, in both the build and the watch branches of `esbuild.js`: `webview-draft/index.tsx` → `dist/draft.js` + `dist/draft.css` (browser IIFE, React, the renderer's `ErdCanvas` in viewer mode, the `__ELK_WORKER_CODE__` define like the canvas), type-checked by `tsconfig.webview.json` and kept out of the VSIX as source (`.vscodeignore` `webview-draft/**`; the two bundles take the VSIX from 42 to 44 files, under CI's 60). It is its own page with its own protocol (`DraftToWebview` / `DraftToHost` in `src/types/draft.ts`, every message checked by `parseDraftToHost` against the draft on show), hosted by `src/providers/DraftPreviewPanel.ts` (`erdStudio.draftPreview`, a singleton tab with no serializer, nonce-only CSP with no `unsafe-inline`, `localResourceRoots` `dist/` only): the canvas webview's protocol, `messages.ts` and `NON_MUTATION_TYPES` are untouched. It writes nothing and runs no command; the flow that asked acts on the answer (`DraftPreview.ask`). Its first-open ELK options are the canvas's own (`webview/lib/firstOpenLayout.ts`), so the preview looks like the diagram Keep makes.

**Two tables of one name in different schema folders** (schema-scoped identity, `docs/dev/dbml.md` → Table identity): a message names a table on the diagram by its `DisplayTable.name` (its name, or `<schema>.<name>` where two members share it), and every handler turns that text into a table through one function, `SemanticEditorProvider.canvasTable`, which resolves it among the diagram's members (`DiagramMemberTable`, `src/services/diagramMemberTable.ts`, kept beside the parsed object by the DBML codec) and acts on the file that member's `use` line reads; text that names no member is refused ("not on this diagram"). Relationship edits turn the diagram's names into the library's references (`<schema>.<name>` where the library holds the name twice) for the one planner and back. A table not on the diagram is named by its file: `addExistingModel(s)` carry the optional `sourcePath(s)` (the Add Existing row's project-relative `sourcePath`; `validateAddExistingModelPayload` / `validateSourcePath`), "+ Add" posts the context row's `otherTablePath`, and a drop's URIs are kept as files (`tableFilesOfDroppedUris`). Those rows go by file only where a name alone cannot say which table (another schema folder has the name, or the diagram shows a namesake); every other add is by name, as before. A pick that mixes such rows with dbt models the library does not have adds the rows by file and seeds the rest in the same edit (`applyDbtModels`' `byFile`). A table added by file gets the relationships dbt's tests give it, as a by-name add does; a dbt model is matched to a table of a shared name by the schema dbt builds it in, never by its name alone (`dbtTestsOnTables`), and gives none when nothing tells. A Table Library drag that gave `noteLibraryDrag` its tables' files is added by those files; one that gave names only is added by name. When a namesake joins or leaves, the members whose reference changes are renamed in the same edit and the writer is told (`renamedMembers`), so each keeps its `use` line and position. Other diagrams' own relationship copies follow a column rename under what each calls the table (a DBML diagram's member whose `use` line reads that file, a JSON diagram's name only where it reads that table). A JSON diagram names tables by name alone: it reads the library's first table of a shared name, and an edit or relationship that would have to pick between two is refused with a sentence naming both schema folders. A diagram with no such pair, and every message about it, is exactly as before: every name is a bare name.

Every type in the unions has a live sender and handler — do not add a message type without wiring both ends (unknown types are logged by the `default:` branch, never silently dropped). Multi-select operations are batched: `addExistingModels`, `addModelsFromDbt`, `removeModels`, `removeAnnotations`, `removeRelationships` and `updatePositions` (which carries `annotations?: [{id,x,y}]` for notes moved in the same drag) each produce **one** `WorkspaceEdit`, one save, one `domainLoaded` — i.e. one undo step. `switchStage` carries a `requestId` that the host echoes on `stageData` so the webview can drop stale replies (`webview/lib/stageRequest.ts`).

**Physical stage guard.** While a panel is viewing the physical stage the host rejects every message not in `NON_MUTATION_TYPES` (`src/providers/SemanticEditorProvider.ts`) with a `"Physical stage is read-only"` `error`.

Positions and annotations are allowed because they live in the shared `viewConfig` (physical inherits logical positions); `generateSyncPlan` is the physical-stage "Compare to Logical" flow; the six feedback types write no domain data at all (`setFeedbackProvider` writes a user setting, never a file); `setLineStyle` writes only the user setting `erdStudio.canvas.lineStyle`; `openGettingStarted` (no payload, sent by the empty-diagram card's **set it up in the Welcome panel** link) only runs `erdStudio.showGettingStarted`. (The first-open WelcomeModal and its `dismissWelcome` message and `welcomeDismissed` flag are retired; an older host's `welcomeDismissed` is ignored.) `closeEditor` and `openAnotherDomain` only close the tab or open the diagram picker. `openModelFile` (`{ modelName }`, sent by the **Open file** button on a node whose `logical-models` file has a YAML error — `DisplayTable.loadError`) only opens that yml in a text editor at the error line. `runDbtParse` writes no domain data (only dbt's own `target/`), and the physical stage is exactly where a missing manifest shows. `exportDiagram` writes nothing (Save As… writes only the file the user names in the save dialog) and always exports the logical design, so it is allowed on both stages. `addModelsFromDbt` is a schema mutation and is **not** on it (the guard refuses it before any picker opens). `dropTables` (a Shift-drop on the canvas) adds tables, so it is **not** on it. `undo`/`redo` are deliberately **not** allowed (the toolbar hides them there) — they would rewind the logical document under a derived view.

**Dragging tables from the Table Library.** Hold Shift and drop Table Library rows (or table files from the Explorer) on an open diagram, and they are added where they land; a plain drop opens the table file, as VS Code opens any dragged file. Shift is VS Code's rule, not ours: while a drag that started in the workbench is in progress, VS Code sets `pointer-events: none` on every webview unless Shift is held, so only a Shift-drop reaches the canvas (without Shift the editor group takes it and opens the dragged files). (A variant that made the plain drop add — the drag carried a custom-scheme "drop receipt" for the editor area to open — was tried and withdrawn in favour of Shift-to-add, which also lands the tables where they are dropped.) Whether a drop reaches the webview at all is VS Code's and Chromium's decision, so the route that never depends on it is the Table Library's **Add to Diagram…** (`addToDiagramCommand`, `src/commands/goToTable.ts`): it offers the diagram in the active tab first (`activeSubjectAreaCanvasPath`, `withOpenDiagramFirst`) and writes through the same `handleAddExistingModels` edit.

- `TableLibraryDragController.handleDrag` (`src/providers/tableLibraryDrag.ts`, the view's `dragAndDropController`) collects the dragged tables (a table row, a schema or layer row's tables, never an ignored duplicate, at most `ADD_EXISTING_TABLES_LIMIT`), puts their files in `text/uri-list` (so a drop on a text editor or the Explorer behaves as for any file) and their names under `application/vnd.code.tree.erdstudio.modellibrary`, and calls `SemanticEditorProvider.noteLibraryDrag(tables, files?)` (the files optional, index for index; a drop adds by file where a name cannot say which table), which remembers the drag for `PENDING_LIBRARY_DRAG_MS` (60 s) and posts `libraryDragStarted` to every loaded logical canvas.
- `useLibraryDrop` (webview) shows the "Hold Shift and drop" hint, accepts a drag whose types carry URIs (`text/uri-list`, `application/vnd.code.uri-list`, `ResourceURLs`) or any drag while a `libraryDragStarted` is in progress, over an editable logical diagram only, asks for the drop effect the drag allows (`dropEffectFor`), and on drop posts `dropTables` with the flow position (`screenToFlowPosition`), the URIs it can read (`droppedUris`) and `fromLibrary: true` when the DataTransfer carries the Table Library's mime type (`isLibraryDrag`). On the physical stage (or a read-only diagram) the drop is taken but nothing is posted: the canvas says why in a notice toast (`DROP_REFUSED_READ_ONLY`). The viewer takes no drop. What VS Code (checked in 1.145) puts on a tree drag that reaches a webview: each declared `dragMimeTypes` entry and `ResourceURLs` as empty strings (the controller's real values stay in the workbench), the tree's mime type as `{ id, itemHandles }`, and, for rows with a `resourceUri`, their files under `application/vnd.code.uri-list` and `CodeFiles`. So the URIs of a tree drag are its table rows only, never a schema or layer row's tables.
- `handleDropTables` uses the remembered drag when the drop is `fromLibrary` (so a drag of a schema row with a table row adds what the hint said), else resolves the `file:` URIs to library table files (`tablesOfDroppedUris`, `src/services/tableDrop.ts`, paths compared as the file system does, Windows URIs such as `file:///c%3A/…` included), else uses the remembered drag (once either way). Tables already on the diagram are selected (`revealTable`) with a one-line note; the rest go through `handleAddExistingModels` with `dropAt`, so `applyDbtModels` places them by `dropGridPositions` (the first under the pointer, then a grid `DROP_GRID_COLUMNS` = 4 wide) in the same edit: one `WorkspaceEdit`, one undo step. The first added table is then selected.

**DBML writes** (native DBML storage) use the same pipeline. The codec parses a `.dbml` diagram to the v5 object every handler mutates and renders it back by **splicing** at parser node offsets (core's `editSubjectAreaDbml`, `erd_layout` included, rewritten only when a position or sticky box changed). Table and relationships files are planned by the pure `planDbmlLibraryWrites` (`src/services/dbmlLibraryWrites.ts`), which only places tables and Refs in files (a new Ref by the relationships index's two-step rule, an existing one edited in the file that holds it) and builds their text with `editTableDbml` / `renderNewTableDbml` / `editRelationshipsDbml`. A no-op save is byte-identical, and a file that does not parse is refused (`DbmlEditRefused`), never regenerated. Every edit that creates or deletes files is applied by the one helper `applyFileWrites` (`src/providers/applyFileWrites.ts`: creates first, relationships files before tables, then replaces, renames, deletes, all in one `WorkspaceEdit`; on a `false` from `applyEdit` it reconciles what landed); the fs paths outside the editor (`writeNewSubjectArea`, Convert's resume) use `writeFilesWithRollback` (`src/services/fsFileWrites.ts`). Relationship edits on a DBML diagram always use `home = 'library'` (DBML diagrams hold no Refs).

**Edit pipeline.** All domain-file writes go through `applySubjectAreaEdit()` in `SemanticEditorProvider` — the only place a domain `WorkspaceEdit` is built: parse → mutate → replace whole document → `applyEdit` → `document.save()` → refresh, with `pendingUpdates` held so the change listener never double-saves. Edits are saved immediately; the custom editor never sits dirty. (That brief dirty state is also what turns a preview tab into a pinned one — see the note on `erdStudio.openDomain` under Update recovery.) A mutator throws `EditAborted` to bail out after reporting its own error; pass `errorLabel` for the applyEdit-rejected case and `onSuccess` for follow-up work such as `selectorsService.scheduleRegenerate()`. `applyTableEdit()` routes `logical-models/*.yml` changes through the **same** `WorkspaceEdit` (`modelFiles: { save: [{ model, fromName? }], delete }`) so a model edit and its domain change are atomic and one undo step — never `fs.writeFileSync` a model file from a handler (`addExistingModel` seeds a new library file the same way, so a rejected edit leaves no orphan yml). `fromName` names the file whose existing YAML document supplies comments / key order / unknown keys: a rename passes the OLD name so hand-written content is carried to the new file instead of being regenerated. Every file the pipeline writes is recorded in `ownWrites` **after** the bytes land (the tracker reads what the file holds), so the watchers skip our own saves; the refreshes they used to drive are issued directly instead — `sendSubjectAreaData` for the editing panel, `refreshSubjectAreasReferencingTable(name, exceptPanelKey)` for other open panels, and the `onDidWriteSubjectArea` event for the tree / model library views. An undo/redo flushes only the yml documents this provider itself wrote for that domain (`editedTablePaths`) — a model file the user is hand-editing in another tab is never force-saved. When VS Code undoes only the diagram's own part of a step (`UndoRedoService._tryToSplitAndUndo`, after a file in it was edited since), and that part was the one-character anchor, the `.dbml` is left dirty with the text it has on disk: `flushUndoRedo` saves it, and when no other file was saved and every file the canvas created still exists, stops there: no send, no `onDidWriteSubjectArea`, no library invalidation. A DBML undo whose only change is inside `erd_layout` (`sameOutsideErdLayout(disk, document)`) is a layout-only rewind: saved, the canvas re-sent, `layoutOnly` fired, nothing invalidated and neither tree refreshed. Cmd+Z / Cmd+Shift+Z on the canvas is VS Code's own undo, not the toolbar's `undo` message: the change listener sees `TextDocumentChangeReason.Undo` / `Redo` on the domain file, or on an `editedTablePaths` file while the panel is active, and after `NATIVE_UNDO_SETTLE_MS` runs the same `flushUndoRedo` as the toolbar (the mock's `_fireDidChangeTextDocument` drives it in tests). **Layout-only edits** (`isLayoutOnlyChange` in `subjectAreaCodec.ts`: only `viewConfig.positions` and sticky-note boxes — `x`, `y`, `width`, `height` — differ; an edit that changed nothing is not one) take `applyLayoutOnlyEdit`, in either storage, unless they carry `modelFiles` or `otherDomains` or the DBML diagram is not writable or holds its own tables: a DBML diagram splices its own `erd_layout` (`layoutOnlyText`: unformatted, one minimal-range replace, `minimalPrimary`; a conflicted `erd_layout` turns it into a toast), a JSON diagram writes its own text (it holds the positions). Nothing is planned against the library (no `planTableWrites`, library plan, attachment, settle pass or diagram render) and nothing in it is invalidated; the DBML reading is primed from the new text (`primeLayoutOnlyReading`), so the next drag compiles nothing. The edit is one `WorkspaceEdit` of the diagram alone, one save and one native undo step, and `onDidWriteSubjectArea` carries `layoutOnly: true`, on which `extension.ts` refreshes neither tree. `handleUpdatePositions` aborts (`EditAborted`) when every table was dropped where it already was. Drags that queue up behind a running edit are folded into one `updatePositions` edit by `queuePositions` (later positions win) while that batch is still the last thing queued — never across another edit, so edits stay in order; folded drags are one undo step. `applyFileWrites` leaves out any replace whose text the file already holds (no edit, no save, no watcher event); the primary is the exception, because VS Code's Undo on the canvas undoes the last edit of the canvas's own document: an edit that changes only other files (a table's column, say) gives the unchanged primary the one-character anchor `undoAnchor` (its first non-line-break character replaced by itself) instead of a full-range replace of the whole diagram, and the anchor's save rewrites the diagram with the same bytes. A move never needs it: it changes the diagram's own `erd_layout`. Delete Table File after Remove from Diagram (#274) anchors too: the prompt's answer runs in the canvas's edit queue (`runQueued`) and, while that canvas is still open (`deleteOriginOf`), `deleteTablesWithCascade` (DBML) or `deleteTableFilesFromCanvas` (YAML) makes the diagram the edit's primary (its settle rewrite, else the anchor) and saves it, so Cmd+Z on the canvas rewinds the delete before the remove and never brings back a `use` line for a file that is gone. Their writes go into `editedTablePaths`, and the files they deleted into `deletedTablePaths`, so the undo flush saves what it rewound and redraws even when only a deleted file came back. The Table Library's Delete Table has no canvas and stays unanchored. A drop in place writes nothing at all. The canvas side keeps the store's node and edge objects for everything a domain update left the same (`reuseUnchanged` in the renderer's `useCanvasGraph`), so the optimistic update after a drag re-renders only the moved tables and their edges. After an edit the provider drops only what it wrote (`TableLibraryService.invalidatePaths(writtenPaths(applied))`, never the blanket `invalidateCache()`, which Convert and the bulk commands keep): each written table's parse, a written relationships file's reading, and the library index when a table file appeared or went. The attachment of Refs (`libraryAttachment`) is memoised against each table's fingerprint (name, folder, storage, DBML alias, column names and keys), so a table re-read for a description or a note keeps the memo; an undo/redo drops this canvas's `editedTablePaths` and the index. The Subject Areas tree counts a diagram's tables with `SubjectAreaService.countSubjectAreaTables` (the file alone, no table resolved) and lists the subject areas once per render; the Table Library caches each diagram's members by mtime + size and, for a table file not read in its current version (`peekTableFileError` is undefined), shows it at once and reads it in background slices, rendering again only when one needs fixing. Payloads are validated at the message boundary by `src/providers/payloadValidation.ts` (model names via the shared `TABLE_NAME_PATTERN` in `src/types/naming.ts`, column lists incl. duplicates, `keyType`, `cardinality`, `modelRole`, finite positions); `TableLibraryService.tablePath` refuses names that escape `logical-models/`. The message listener is wrapped in `withMessageErrorBoundary()` so a throwing handler posts an `error` instead of becoming an unhandled rejection. A domain file deleted or renamed outside ERD Studio (#161) is never written back: `applySubjectAreaEdit` and undo/redo refuse once `document.uri.fsPath` is gone, the change listener does not save it, and `syncSubjectAreaFilePresence()` (called by both semantic-file watchers) moves every open canvas whose file is gone to the `domain-missing` error screen, and re-reads one whose file is back. Refresh paths (watchers, external edits, stage switches, the focus check, Reload Diagrams from Disk) never write, with one narrow exception (the import settle after an in-window save of a relationships file, below under **The canvas follows the files**) — only the initial `ready` load persists auto-computed positions, and only for a **partially** positioned domain. A **fresh** domain (≥1 model, not one `viewConfig.positions` entry — typically written by an AI assistant with `viewConfig: {}`; `isFreshLayout()`) is the exception: on the logical stage `sendSubjectAreaData` still puts the simple `computeNewTablePositions` placement in the payload (so nothing paints at 0,0) but writes nothing, and sets `autoLayout: true` on the `domainLoaded` message. The webview stores it as `pendingAutoLayout`; `useFirstOpenAutoLayout` (in `Toolbar`) waits until every model has a node, clears the flag and calls the same `runLayout` as the Layout button / Shift+L — ELK, `fitView`, one `updatePositions` (one edit, one undo step). Every other `domainLoaded` / `stageData` overwrites the flag, so a later unflagged payload cancels a layout that has not started. If ELK fails the toast shows and nothing is written, so the next open asks again. Physical never carries the flag.

**Opening a canvas.** The `ready` handler first posts `loading` (`postLoading`: `{}`, then `{ tables }` from `countSubjectAreaTablesInText` over the document's text — no table is read), each followed by `yieldToEventLoop()` (`src/services/libraryWarmUp.ts`, a real `setTimeout(0)` captured at load so test fake timers cannot stall it), so the message leaves the host before the read blocks it; the webview's `useReconnectWatchdog` then waits `LOADING_STALL_MS` (2 min) instead of `RECONNECT_GRACE_MS` and shows "Loading N tables…" (`editor-message__spinner`). `SubjectAreaService.getSubjectArea` runs inside `TableLibraryService.withIndexSnapshot` (the index is validated once, not per lookup) and builds the unified area inside `readingTables(members, …)`: a member's relationships come from `scopedAttachment` — the whole-library memo when it is still valid, else `memberAttachment` (`src/services/memberAttachment.ts`) over the Refs naming a member or a member's DBML alias, with ends resolved as `dbmlTableLookup` resolves them by name, falling back to `libraryAttachment` for a library holding YAML, a dangling or alias end, or a file that does not read. So a cold open reads the members and the other ends of their Refs, not the library (`test/unit/scopedTableReads.test.ts` holds it equal to the whole-library attach on random libraries). A DBML diagram is read through `readDbmlDiagram` (`src/services/dbmlDiagramReadings.ts`: the last four readings by layer folder, stem, text and layout; each caller gets a copy), so the read, `holdsOwnTables`, the telemetry survey and the edit pipeline's `parseSubjectAreaFile` share one reading, and core keeps diagram compiles in their own cache (`compileOne(…, { diagram: true })`) so reading the tables never evicts the diagram. Positions computed for a partly placed diagram are written by `autoPositionNewTables`; when that went out as a layout-only write (`onLayoutOnly`) the diagram is not read again. `buildWebviewPayload` lists the Table Library from `tablePreviews` (cached parses, no attach, no copies); with more than `EXISTING_TABLES_READ_AT_MOST` (100) unread files, those rows go out by name and path with `detailsPending` (core's optional `ExistingTablePreview.detailsPending`), and the dialog posts `requestExistingTables`, answered by `sendExistingTables` (reads the rest in 20 ms slices, then posts `existingTables`). The relationship survey (`recordRelationshipState`, telemetry) runs `RELATIONSHIP_SURVEY_DELAY_MS` (3 s) after the open, only while telemetry is on and the canvas is open. **Background read.** `LibraryWarmUp` (started by `extension.ts` 1.5 s after activation) reads every unread table file (`unreadTableFiles` / `warmTableFile`: through the caches, nothing reported) in `WARM_UP_SLICE_MS` (12 ms) slices with a turn of the event loop between them, then each relationships file in a slice of its own, then `warmLibraryAttachment` once. Every canvas message and `resolveCustomTextEditor` call `noteForegroundWork()`, which holds the next slice until the host has been quiet for `WARM_UP_QUIET_MS` (300 ms). Reads only; the caches check mtime + size, so a file changed meanwhile is read again by whoever needs it.

## Line routing

Relationship lines are routed around the tables, every line in one pass over the whole diagram, in the renderer (`packages/renderer/src/lib/edgeRouting/`), so the editor canvas and `ErdCanvas` draw them the same way.

- **Pipeline.** `EdgeRouter` (`packages/renderer/src/canvas/EdgeRouting.tsx`, rendered by `CanvasBackdrop`) subscribes to `routingInputKey` (node boxes and edge handles) and `draggingNodesKey`, and on the next animation frame calls its canvas's `EdgeRoutingEngine` (`createEdgeRoutingEngine`, `lib/edgeRouting/index.ts`, held in a ref). The engine builds a `RoutingInput` (`input.ts`: card boxes, and each line's anchors as `FkEdge` places them), runs `routeAll`: the route-around router (`routers/orthogonal/*`: A* on a sparse grid around the padded cards, then nudging lines that share a channel apart), `render/pathRender.ts` (corners rounded / curved, crossings hops / halo, hops sized for the zoom, curved corners tightened so a crossing can be bridged) and, for x-ray, `render/tunnels.ts`. The routes go into the canvas store's `edgeRoutes`; `FkEdge` draws its route (and its `*` / `1` labels at the routed anchors) when it has one, else the smooth-step path as before. `EdgeOverlay` draws the x-ray stretches above the cards. Self-loops always draw their own loop.
- **Styles** (`lib/edgeRouting/lineStyle.ts`, `LINE_STYLE_OPTIONS`): `curved` = curved corners, halo crossings (a canvas-coloured casing, the under line cut in `strokeD`), x-ray under tables; `hops` = rounded corners, hops, nothing drawn under tables. The editor takes the style from `erdStudio.canvas.lineStyle` (the `lineStyle` message), `ErdCanvas` from its `lineStyle` prop; the knobs themselves are internal.
- **Per canvas.** Each `EdgeRouter` owns its engine and so its router (`createAvoidRouter()`), whose memory of the last pass (sticky sides and slots, lines kept while a card moves) is never shared between two canvases on a page. The grid and A* scratch buffers are reused, but a pass is synchronous and clears them.
- **Local grids** (`routers/orthogonal/router.ts`, `params.ts`). Up to `LOCAL_FROM_CARDS` (150) cards, one grid covers the whole diagram, as it always has. Past that, one grid would grow with the square of the diagram (every card's edges cross every other card's: ~650 MB of search state on an uneven 2,000-card layout), so each line is routed on its own local grid (`localGrid`): its two cards' box plus `LOCAL_MARGIN` (400 px). Every card that touches the box is on the grid whole and blocked, everything outside the box is closed, and the lines already routed through it are replayed onto it (their coordinates become grid lines; `GrowingIndex` finds them), so crossings and shared channels still cost what they do. A route that reaches the box's edge, or finds no way round, is routed again on a grid `LOCAL_GROWTH` (2.5×) wider, up to the whole diagram plus its outer ring; a grid over `LOCAL_MAX_NODES` (1.5 M) is not built. A search that runs out of `MAX_POPS` is not widened (a wider grid only searches longer): it gets one greedy retry (`RESCUE_WEIGHT`, `RESCUE_CROSS`: crossings nearly free) before it would fall back to a path through the cards. On local grids, long lines are greedier from the start (`LOCAL_LONG_*`). Small diagrams route byte-for-byte as before. The nudging pass finds nearby lines through a `SegmentIndex` (`nudge.ts`) and groups segments in one sweep, rather than comparing every pair. Measured on generated layered diagrams (opening / one card moved): 500 cards ~0.2 s / 40 ms, 1,000 ~0.5 s / 100 ms, 2,000 (2,700 lines) ~1.4 s / 230 ms, with no line left under a card.
- **Performance guard** (`createEdgeRoutingEngine`). Up to `MAIN_THREAD_MAX_LINES` (100) lines a pass runs on the main thread, and a drag re-routes only what the move touches (40 tables / 60 lines: ~16 ms cold, ~6 ms a frame). When a drag frame takes more than `DRAG_REROUTE_BUDGET_MS` (12 ms), or the last pass outside a drag more than `DRAG_HOLD_AFTER_MS` (50 ms), the rest of the drag holds the routes: the dragged cards' lines are dropped from them (they draw smooth step, which follows the card) and everything is routed once when the drag ends. A larger diagram (or a smaller one whose main-thread pass took over 50 ms) routes in the canvas's **worker**, so opening or editing it never pauses the canvas: `update` returns `'pending'` with the last routes still right for the current card boxes (a moved or resized card's lines fall back), and the worker's answer arrives through the engine's `onUpdate` into `setEdgeRoutes`, keeping the previous object for every route that draws the same (so after a drop only the changed lines re-render). One pass is in the worker at a time; only the newest waiting request is sent next, an answer to a superseded request is dropped, and a drag holds the routes. A *cold* pass (the worker has finished none yet, or `COLD_PASS_SHARE` (half) of the cards moved or changed size since its last one) is not waited for: a newer, different request terminates that worker and starts a fresh one with the newest job, so a diagram opened before its cards are measured routes once, not twice (2,000 tables: ~4.7 s → ~2.3 s to routed lines). Each worker has a generation, and events from a stopped one are ignored. A warm pass (a few cards moved) is still waited for, to keep the router's memory. With the worker there is no size limit (`MAX_ROUTED_LINES` is `Infinity`); without it, more than `MAX_ROUTED_LINES_WITHOUT_WORKER` (150) lines are not routed. A main-thread pass over `ROUTING_HARD_LIMIT_MS` (150 ms) moves that size to the worker when there is one (turns routing off when there is not); a worker pass over `WORKER_HARD_LIMIT_MS` (20 s, a safety net) turns it off for that canvas at that size. Nothing is logged per frame. The canvas root carries `data-edge-routing` (`<pass> <ms>ms <routes>`, e.g. `routed 2201ms 2743`) for tests and debugging; nothing styles off it.
- **The worker** (`lib/edgeRouting/worker/`): `entry.ts` runs `routeAll` (its own module, `routeAll.ts`, so the worker bundles no React) with one router per worker, so each canvas keeps its own router memory. It is bundled to a string by `packages/renderer/scripts/edgeRoutingWorker.cjs` and inlined as `__ERD_EDGE_ROUTING_WORKER__` by `esbuild.js` (webview and draft page) and the package's `build.mjs`, then started from a blob URL by `client.ts` (`createRoutingWorker`), like the ELK worker: the editor's CSP already allows `worker-src blob:`. Where the code is not inlined (unit tests), `Worker` is missing, the CSP refuses a blob worker, or the worker crashes, the canvas routes on the main thread under the lower cap. `npm run watch` builds the worker once, at start: restart it after changing the router.
- **Edge labels** (`components/Graph/EdgeLabels.tsx`). `FkEdge` portals its HTML labels into React Flow's label layer through `EdgeLabels`, not `<EdgeLabelRenderer>`: the latter finds the layer with a store selector that runs `domNode.querySelector` per edge on every store update, which on 2,000 tables / 2,743 lines was ~45% of a drag. `labelLayerOf` finds it once per canvas root (a WeakMap, looked up again only if the layer left the DOM). Same element, same output; a drag frame there went from ~350 ms to ~150 ms.
- **Failure.** `routeAll` wraps the router, the renderer and the tunnels in `safely`: an exception leaves those lines on smooth step and the engine warns once per canvas. The canvas never breaks.
- **Colour on hover** (`EdgeRouting.css`, logical-only canvases only, `.editor-canvas--neutral`): lines, `*` / `1` and role labels are neutral grey at rest; the lit and flowing lines of the hovered or selected table, their adornments, their arrows (`.fk-edge__flow--logical`) and their lit x-ray take `--diagram-layer-color`, which `LayerLineColour` sets on the React Flow root from the diagram's `layerConfig.color` (else the grey). Table borders stay neutral; stage-coloured (dbt) canvases are unchanged.
- **Tests.** `packages/renderer/test/unit/edgeRouting.*` (router properties and stability, local grids on generated 400–1,000-card diagrams from `test/fixtures/edgeRouting/generated.ts`, renderer, tunnels, the engine and its guard with an injected clock and a fake worker, the worker script and build), `ErdCanvas.lineStyle.test.tsx`, `test/unit/lineStyleSetting.test.ts` (setting and host messages) and `test/unit/lineStyleApp.test.tsx` (toolbar and store). The routing scenarios are `packages/renderer/test/fixtures/edgeRouting/scenarios.ts`; `test/fixtures/line-lab/` is a logical-only project with three tangled diagrams for trying the styles by hand.

- **First run** — the Welcome panel opens automatically **once per machine**, and only for a fresh install. In the project path, pending and not shown **and the project has no diagrams yet** is the first run *spent there*: it writes the shown flag and clears pending, and the window is left for the draft (`firstRunLeftForDraft`: only `startSuggestion` or `diagramsNudge` may take it; the AI helper offer, the upgrade notice and the rest wait for a later window). When another prompt already holds the window (an earlier folder of the same extension host), it stays owed and counts `walkthroughWaited`. The no-project first run opens the walkthrough the same way (claiming that window's one prompt). An upgrader (never pending, never shown) is offered one non-modal notice, and gets the shown flag when it shows: with dbt, "new short getting-started video…" whose **Watch** runs `showGettingStarted`; logical-only (an existing `.erd-studio/`, no `dbt_project.yml`), "a new Welcome page: draw a diagram, import DBML…" whose **Open Welcome** runs the same command. ## Commands that create or export files

Not the canvas edit pipeline: these create new files or write only what the user saves.

- **Import from dbt…** (`erdStudio.drawFromDbt`, `src/commands/drawFromDbt.ts`, draft from the pure `src/services/dbtDraft.ts`) and **Import DBML…** (`erdStudio.importDbml`, `src/commands/importDbml.ts`, plan from the pure `src/services/dbmlImport.ts`; **Import SQL DDL…** and **Import Power BI or Fabric Semantic Model…** convert to DBML and run the same flow, `docs/dev/dbml.md`) each create a **new** subject area plus the table files the library lacks, through the one shared, vscode-free writer `writeNewSubjectArea` (`src/services/newSubjectAreaWriter.ts`): new table files via `saveTable`, the subject area file with `wx`, then any existing library table that gained a relationship, `ownWrites` after each write, and everything put back on failure. In a project that writes DBML the subject area is a `.dbml` diagram in `<layer>/diagrams/`: its table files, relationships files, diagram (positions included), README on a new root and the settle re-render of other DBML diagrams are one `applyDbmlBatch`, written by `writeFilesWithRollback`. **New Subject Area**, Rename and Delete, Organise Table Library and Give Duplicate Its Own Name follow the project's storage the same way (the pure planners in `src/commands/dbmlLifecycle.ts`); Open Example Diagram goes through Import's writer. **Convert Project to DBML** (`erdStudio.convertProjectToDbml`, `src/commands/convertProjectToDbml.ts`) plans with the pure `planDbmlConversion` (`src/services/dbmlConversion.ts`, input from `readDbmlConversionInput`), shows the plan (or its refusals) in the **Convert to DBML** webview panel (`src/providers/ConvertToDbmlPanel.ts`: one at a time, nonce-only CSP, its own small validated protocol in the pure `src/services/dbmlConversionReview.ts`, not part of the canvas protocol in `src/types/messages.ts`; it writes nothing and hands Convert / Cancel / Check Again back to the command; a refusal's **Open** sends an index into the host's list, never a path), and applies the plan with one `applyFileWrites`. `erd-studio doctor`'s text preview stays `describeDbmlConversion`. A file they would change that is dirty in an editor stops them before any write. In `extension.ts` both call one `refreshAfterNewSubjectArea` closure. Both are registered after the no-project early return and listed in `NO_LEGACY_ALIAS`; Import DBML needs no dbt files.
- **Export Diagram…** (`erdStudio.exportDiagram`, `src/commands/exportDiagram.ts`) and **Export All Diagrams…** (`erdStudio.exportAllDiagrams`, `src/commands/exportAllDiagrams.ts`) export the logical stage as Mermaid, DBML or **Rich DBML** (`dbml-rich`, one file per diagram with the positions in its Project's `erd_layout`), through `src/services/diagramExport.ts` — the same read `erd-studio export` uses, so the bytes match. They write no ERD Studio file.

- **Show Import Report** (`erdStudio.showImportReport`, `src/providers/ImportReportPanel.ts`, view from the pure `src/services/importReport.ts`, records in `src/services/importReportStore.ts`) writes nothing: a read-only webview of an import's loss ledger, held in memory for the last `MAX_IMPORT_REPORTS_HELD` imports. Palette only when `erdStudio.hasProject`; in `NO_LEGACY_ALIAS`, not pre-registered. Details: `docs/dev/dbml.md` → Loss ledger.

## Watchers (`src/watchers/FileWatcherService.ts`)

**The canvas follows the files; there is no refresh button.** Three parts and one narrow exception, and a change to any of them must keep all of them true:

1. **Every saved file redraws the canvases it feeds.** The diagram through its `TextDocument` (the custom editor's `onDidChangeTextDocument`, which saves a dirty document and re-sends; the save's result is checked, and a failed one is a `diagramUnsaved` note); table files (`onTablesChanged` → `queueTableRefresh`), relationships files (`onRelationshipsChanged`), `fields.yml` and `layers.json` (`onLayerConfigChanged` redraws the canvases too: a layer's label and colour are in the payload) → `refreshAllOpenSubjectAreas`. A refresh path never writes.
2. **What a file holds that cannot be drawn is said on the canvas**, not only in the log: the `filesNotShown` message (`src/types/filesNotShown.ts`) and the strip above the diagram (`webview/components/Canvas/FilesNotShownBanner.tsx`). `SemanticEditorProvider.sendFilesNotShown` runs after every logical-stage `domainLoaded` / `stageData` (after the diagram has gone out, like `canvasContext`) and posts the whole list each time, so a note goes by itself when its file is fixed. `collectFilesNotShown` (`src/services/filesNotShown.ts`, pure) only arranges what the readers already found, the same findings `doctor` reports (`test/unit/filesNotShown.test.ts` holds each note to `doctor`'s file and line; the canvas words them in short sentences of its own that name the file, and `doctor` keeps its longer wording): the diagram reader's import drift (`relationshipsNotImported`, with **Add the import** → `addRelationshipsImports`, one `applyStorageEdit` with `refreshRelationshipsUses`: an explicit edit, never done by a refresh, and made by itself only after an in-window save, item 4), the table reader's `refInTableFile` / `inlineRefInTableFile` / `useInTableFile` for the diagram's own tables (`notDrawnInTableFile`), a relationships file with `readable: false` (`relationshipsFileNotRead`), and a `.dbml` saved this session where no file is read (`fileNotRead`: the watcher's `onUnreadFileChanged` → `noteUnreadFile`, worded by `outsideKnownFoldersNote`, `src/services/unreadDbmlFile.ts`, which ends with the hint `doctor`'s `outsideKnownFoldersMessage` gives; only files the watcher saw written, so an export a team keeps in the folder is `doctor`'s to report, not a note on every canvas). Never call `collectDbmlProblems` from a refresh: it compiles every file (about 1.5 s at 1,100 tables). Three notes are about the picture itself and cannot be hidden: `diagramNotRead` (the diagram's file stopped reading over a live canvas: `postLoadError` → `noteNotDrawn`; the toast is also posted again on every change of the still-broken document, `reshowError`, while refreshes for other files keep the once-per-message rule of #64), `diagramUnsaved`, and `refreshFailed` (`guardRefresh` → `setRefreshFailureSink` → `noteRefreshFailed`, cleared by the next `refreshAllOpenSubjectAreas` that redraws every canvas; its button is `reloadFromDisk`). A note's file link is `openNotedFile`: the host opens only a file inside the semantic dir. No new telemetry key.
3. **A safety net for events that never arrive.** The library index, table and relationships readings, `layers.json` and `fields.yml` are all validated against the disk on every read, so any redraw shows the files as they are; what can be missing is the redraw. `revalidateAgainstDisk` (on `onDidChangeViewState` when a canvas becomes active, and from `onSemanticFileChanged` for a diagram) compares what the canvas was drawn from (`drawnFrom`: `TableLibraryService.filesSignature` of its tables and every relationships file, plus `layers.json` and `fields.yml`; a stat per file) with the disk, and the diagram's document with its file (a document left dirty by a failed save no longer follows the disk; redrawn once per version of the file). It never writes and never saves. **ERD Studio: Reload Diagrams from Disk** (`erdStudio.reloadFromDisk`, palette only, no toolbar button, `SemanticEditorProvider.reloadFromDisk`) drops every cache and redraws: the escape hatch for a setup where file events do not reach VS Code at all.
4. **The one exception: the import settle after an in-window save** (owner-approved; nothing else written from a change outside the canvas). A relationships file **saved in this window** reaches `SemanticEditorProvider.noteDocumentSaved` through `workspace.onDidSaveTextDocument` (wired in `extension.ts`). It is skipped unless it is a `.dbml` the classifier calls `relationships`, and when `ownWriteTracker.isPending(path)`: every ERD Studio save (an edit's `applyAndSaveWrites`, an undo's `flushUndoRedo`, the bulk commands) is announced with `expectWrite` before it starts, so our own saves never count. Saves within `SAVED_RELATIONSHIPS_SETTLE_MS` (100 ms; Save All) are gathered into one `settleImportsAfterSave`, which drops those files' readings (`invalidatePaths`) and, per open canvas and queued behind its edits (`queueEdit`), runs `addImportsAfterSave`: only a loaded **logical** canvas of a DBML diagram, with no hold (`refreshHolds`), no edit in flight (`pendingUpdates`), a clean document (`isDirty`, `saveFailed`), a diagram file that reads (`staleNote`), and a saved file that reads (`readRelationshipsFile(...).readable`). The diagram is read again (`getSubjectArea`), and only when its reader's drift (`relationshipsImportDrift`, the one rule `relationshipsImportsFor`) names a saved file does it make Add the import's edit (`handleAddRelationshipsImports(…, afterSave)`: the same `applyStorageEdit`, one `WorkspaceEdit` of that diagram, one save, one undo step, own writes recorded after the bytes land; a refusal, a rejected edit or a failed save posts no toast and leaves the strip's button, and a failed save is the `diagramUnsaved` note). The canvas is redrawn and told `canvasNotice` (`importsAddedMessage`: "Added gold/relationships/customers.dbml to this diagram so its relationships are drawn."), an info toast that hides after 6 s. Each open canvas is its own edit; closed diagrams are never touched (they settle on their next edit, or show the button when opened). Why a save and not the watcher: a disk change (git checkout or pull, another program, an assistant writing the file, another window) fires no save event here, so a branch switch never dirties a diagram. Auto-save (`files.autoSave` afterDelay / onFocusChange / onWindowChange), Save All, format on save and an extension's edit saved in this window all fire the save event and are treated like a typed save: each saves only what was edited in this window, the Ref must read and join two of the diagram's tables before anything is added, and the add is one undo step. No loop: the diagram write saves a diagram (not a relationships file) and is an own write; Cmd+Z on the canvas rewinds the diagram alone and saves it, so the strip offers the button again and nothing re-adds it until the user saves a relationships file again. Removing a Ref and saving removes nothing (no drift); the extra import is `doctor`'s `extraRelationshipsUse` and goes on the diagram's next edit, which recomputes its imports.

**Not done, on purpose:** unsaved edits to a table or relationships file are not previewed. The diagram's own file is not previewed either: its document is saved on every change and the canvas is drawn from the disk. The library reads the disk through signature-keyed caches shared with the CLI (no `vscode`), every edit refuses to plan over a dirty file, and `doctor`, the CLI and the Confluence viewer read the disk; a preview of buffers would draw a state none of them see and no edit accepts.

**Running dbt** (Run dbt parse, Run dbt compile, Run dbt deps). `chooseDbtCandidate` (`src/commands/dbtCandidate.ts`) picks the executable from `dbtExecutableCandidates()` (a project venv in the dbt project, then in each parent up to its workspace folder: `venvSearchDirs`, bounded by `workspaceFolderOf(root)`; the CLI passes no bound and searches the project folder only) with the trust rule (a project venv dbt the shell would not run needs the modal, `trustModalTitle(kind)`; an untrusted workspace never runs one); a per-root in-flight guard (`claimDbtFlow`, which returns the claim; `releaseDbtFlow(claim)` releases only its own) keeps a double click from starting two flows (`dbtParseBusy`). A flow never awaits a non-modal notification while it holds the claim (one can sit unanswered in the notification centre, which would make every later click "busy"): dbt-not-found and the Cloud CLI notice are not awaited, and the no-profiles notice releases the claim first; its Parse without your credentials re-claims through `followUp`. Parse then identifies the dbt (`identifyDbt`: dbt Core by stat via `coreInstallOf` in `src/services/dbtAdapters.ts`, redone every call, else `dbt --version`, cached per `executable:mtimeMs`; a Cloud CLI is skipped for a later candidate and never runs `parse`). The run is a `Pseudoterminal` (`src/commands/dbtTerminal.ts`, `createTerminal({ name, pty, isTransient: true })`, VS Code 1.85 API only) whose `open()` spawns the plan from `planDbtSpawn` (`src/services/dbtLaunch.ts`): the candidate's **absolute executable** (a venv's `bin/dbt` / `Scripts\dbt.exe` runs without activation), no shell except a quoted `.cmd`/`.bat` shim (`dbtSpawnCommand`, refusing `" % ! \r \n`), and a computed environment (`childEnv`: the venv / conda dirs first on PATH, `PYTHONUNBUFFERED`, no `DBT_LOG_FORMAT` / `DBT_PROJECT_DIR`, no `DBT_LOG_LEVEL` / `DBT_ENGINE_LOG_LEVEL` set to `none` (it prints nothing to classify), `NoDefaultCurrentDirectoryInExePath=1` on Windows). Nothing is ever typed into a shell, so there is no activate line (PowerShell rejected `"…\activate.bat" && dbt`). `startDbtProcess` (`src/services/dbtProcess.ts`) reports the exit code and a 64 KB in-memory tail of stdout+stderr; `stop()` (Ctrl+C, closing the terminal) is SIGTERM then SIGKILL to the process group, or the absolute `%SystemRoot%\System32\taskkill.exe /T /F` on Windows, and a no-op once the child has exited; `disposeDbtRuns` kills every child on deactivate. One run per project (`runDbtInTerminal` answers `busy`); a terminal closed before `open()` settles as stopped. A failure is classified by `classifyDbtFailure` (`src/services/dbtFailure.ts`, the text after the last `Encountered an error:` first) into a fixed category whose telemetry key is `DBT_PARSE_FAILURE_FEATURES` (a missing env var counts as the project's own when dbt had printed `Registered adapter:` before the error, `envVarFailedAfterAdapterLoad`, or `dbt_project.yml` uses it: a placeholder profile cannot help either); `failureNotice` gives the one-line cause and actions (Parse without your credentials, Run dbt deps then the command again, adapter / profile docs from `DBT_DOCS_URLS`, Show output, which replays the tail with `showDbtOutput`). dbt's output never reaches telemetry, the log or feedback. **Parse without your credentials** writes `throwawayProfileYaml(adapter)` to `<globalStorage>/dbt-parse-profile/<adapter>/profiles.yml` (tmp file + rename; `chooseThrowawayAdapter` picks from the installed adapters, `metadata.adapter_type` and requirements files, never a profiles.yml) and runs `dbt parse --profiles-dir <it> --profile erd_studio --target erd_studio` with `DBT_ENV_CUSTOM_ENV_ERD_STUDIO_THROWAWAY_PROFILE=1`, which dbt copies into `manifest.metadata.env`; `extractManifestData` sees the marker, blanks every model's and resourceDoc's `schema` and sets `placeholderProfile` (`ManifestService.placeholderProfile`, `doctor` says so). Whether dbt would find a profile is a stat only (`profilesYmlWouldBeFound`); with none and Parse without your credentials available (dbt Core with a supported adapter installed, after `IMPLIED`), the route that works is offered before any run; otherwise dbt runs normally and its own error is classified. A placeholder manifest's `adapter_type` is never used as the adapter hint (it is only the last placeholder pick). A parse counts as having written the manifest only when it exits 0 and the manifest's `mtimeMs` changed (or it was missing before); an unchanged old manifest means dbt wrote elsewhere (`dbtParseOkNoManifest`). After a parse that wrote the manifest, the notice offers **Open Physical view**: `DbtRunHost.openPhysical` (`src/commands/dbtRunHost.ts`, set by `activate()` in a dbt window) invalidates the manifest, brings the canvas to the front (`revealCanvas`: the target can be a background tab) and calls `switchStageForUri(uri, 'physical')`, whose untagged `stageData` the webview always applies, on `physicalSwitchTarget(origin)` (the asking canvas while open, else the last active one; logical canvases only). The manifest watcher captures `isDbtRunActiveOrRecent(root)` (a run going or finished within 15 s) before its first `await` and then skips its own "dbt manifest updated" toasts: the run announces its finish itself.

Own writes are recorded in `ownWrites` (`src/services/ownWriteTracker.ts`) by `SemanticEditorProvider` (the editor write path — domain file, model yml saves, creates and deletes), `TableLibraryService`, `LayerService` and the `deleteDomain` command, and consumed in the callbacks that watch files the extension itself writes (domain `.json` / `.dbml` changes and deletes, `{semanticDir}/**/*.{json,dbml}`, classified by path: a diagram is a domain event, positions included; a `<layer>/relationships/*.dbml` fires its own debounced `onRelationshipsChanged`, which redraws every open canvas because its Refs may name any table; `layers.json`; table files, `{logical-models,tables}/**/*.yml` and `*/tables/*/*.dbml`) so an extension save never triggers a second identical refresh. A record is matched by **content** (the size and a SHA-1 of the bytes on disk right after the write; a delete matches while the file is still gone), not by a time window: a watcher callback that runs long after the save, because the host was busy, still sees the save as ours (the old 5 s TTL did not, and a 10 s stall made every save an "external change" that redrew the canvas and the trees again). A match consumes the record (and older ones for the path) and still matches a duplicate event of the same bytes for `CONSUMED_GRACE_MS` (2 s); a mismatch forgets the path's records, so an external edit is always reported. Records nothing consumed are dropped after `MAX_RECORD_AGE_MS` (10 min, a memory bound; at most 8 per path). The editor's write paths (`applyAndSaveWrites`, the YAML path of `applySubjectAreaEdit`, `flushUndoRedo`) and the bulk commands **Convert Project to DBML** and **Migrate to the New File Naming** (every file they create, replace, move or delete) also announce their files with `expectWrite` before the edit and `settleWrites` after the saves: while a path is pending (at most `MAX_PENDING_MS`, 60 s), the watcher callback (`FileWatcherService.debounceOwnWrite`) waits another debounce instead of deciding, because after a stall the timer can fire before the save's completion is processed. The manifest, catalog and `dbt_project.yml` callbacks have nothing to consume — the extension never writes those. One watcher covers both dbt artifacts (`{target-path}/{manifest.json,catalog.json}`) on separate debounce keys, firing `onManifestChanged` or `onCatalogChanged`; one covers dbt source files (`{model,seed,snapshot}-paths/**/*.{yml,yaml,sql,py,csv}`) and fires `onDbtYmlChanged` on create and delete of any of them but on change only for yml — a `.sql` body edit changes no shape the physical stage reads. `renameDomain` (`extension.ts`) is the one gap: its create+delete `WorkspaceEdit` records neither path, so the old file's delete is seen as external. A layout change arrives as a change to its diagram (`layout: true`). A `.yml` table or `.json` diagram ERD Studio did not write appearing in a DBML project fires `onForeignFormatCreated` (one warning per session offering **Update AI Helper Files**; the file is never converted or deleted). `classifySemanticPath()` ensures only `{layer}/{domain}.json` and `{layer}/{domain}.dbml` fire `onSemanticFileDeleted` (coalesced to one `{ uris }` event per burst); `layers.json` has its own `onLayerConfigChanged`. `LayerService.loadConfig()` is mtime-validated and refuses to overwrite an unreadable/invalid `layers.json` (`getLoadError()`).

**`fields.yml`** (context fields, `docs/dev/fields.md`): one watcher on exactly `<semanticDir>/fields.yml` (the root only). A change invalidates the project's `FieldsService` and re-sends the subject area to every open editor, so the Detail panel follows a pull, a hand edit or an assistant's edit with no reload. A refresh path never writes, and ERD Studio never writes the file, so it has no own writes.

- **Bursts.** Every table file shares one debounce (`tables`): a batch reports one `onTableChanged` per table, then one `onTablesChanged` with them all, and logs one line (`External change to N table files: a, b, c and N-3 more`). At `BULK_CHANGE_MIN_EVENTS` (20) events on the project's files (the diagram and table watchers), each within the debounce of the last — Edit > Undo of Convert Project to DBML, a branch switch — the watcher raises `onBulkChangeStarted` and every `debounceOwnWrite` callback waits until the files have been quiet for one debounce; `onBulkChangeSettled({ reported })` fires once they have all run. `extension.ts` holds `editorProvider.holdRefreshes()` and `viewRefreshes` from start to settle, so the trees and context keys refresh once, the library index is built once for the batch (`extension.ts` handles `onTablesChanged`, not each table: `invalidateTables(names)` resolves every name inside one index snapshot and drops their files together, because the disk is not stable yet — Undo can still be deleting files when the batch runs, and a folder changed within `RACY_MS` makes every unsnapshotted lookup list the library again; `refreshContextKeys` runs once per batch, inside one snapshot), no canvas redraws from half-written files, and every open canvas redraws once (`refreshAllOpenSubjectAreas`) when anything was reported (not only own writes) or when a canvas refresh was dropped while held (`holdRefreshes()`'s release returns whether one was): Convert's own redraw after its write lands inside the burst of its own files, which outlasts Convert's hold, so it is made at the settle instead. A hold marks each open canvas in `pendingUpdates`, which silences its change listener; a native undo/redo that reaches a canvas only a hold marked (`heldPanels`) is remembered and flushed when that hold releases, never dropped, and an undo counts as the canvas's only with the canvas in front or during its own toolbar undo, not because a hold marked it.

## Logging (`src/services/logger.ts`)

One logger for the extension host, the CLI, the manifest worker's host side and the MCP server. The module imports **nothing** (no `vscode`, no Node built-ins), so any bundle may log through it; `test/unit/loggerBoundary.test.ts` pins that.

- **Levels and sink.** `log` (no prefix) and `createLogger(scope)` (`[scope] message`) write `trace` / `debug` / `info` / `warn` / `error` to one pluggable `LogSink`. `activate()` plugs in `vscode.window.createOutputChannel('ERD Studio', { log: true })` — a `LogOutputChannel` (VS Code 1.74+, in `@types/vscode` 1.85), whose own level menu filters what shows — first thing, and unplugs it on dispose. Nothing else sets a sink.
- **The console.** `warn` and `error` also go to `console.warn` / `console.error`, exactly as the `console.*` calls they replaced did: the extension host's log, the CLI's `--verbose` capture (which swaps `console.*` while it runs, so the console is looked up on every call) and the tests' spies keep seeing them. `info`, `debug` and `trace` reach the sink only; without one (CLI, MCP, tests) they are silent. **Never `console.log`**: it is the MCP server's stdio protocol stream. `writeLog(…, mirrorToConsole: false)` keeps a line out of the console (used by `ErrorLog.record`, whose lines never went there).
- **What is logged.** Activation: version, VS Code version, platform, then `Project: <DBML|YAML|mixed> storage, N table file(s), M diagram(s), dbt project|no dbt project; project read X ms into activation` (`logProjectSummary`), and `Activated in X ms` as the last line of `activate()`. Opening a diagram: `[Canvas] Opening <path>`, each phase of `sendSubjectAreaData` (`phaseTimer`: dbt files, the diagram and its tables, positions saved for new tables, building the canvas; `info` on the first load, `debug` on a refresh) and `Opened <path>: N tables posted X ms after ready`. Each position save: tables / notes, ms, whether it was a layout-only write. Convert Project to DBML (`[Convert to DBML]`): files read, each planning phase (the same `CONVERT_PROGRESS` texts the notification shows) with its time, the plan's counts, each refusal (`warn`) and file left as is, then each writing phase and the outcome. Table files that fail to read: path and `line:column`. At `debug`: each sidebar tree render (`[Subject Areas]`, `[Table Library]`, marked when the library is read from scratch), each library index build, a full cache drop, and every watcher event that is an outside change; at `trace`: each own write a watcher ignored. The background library read logs when it finishes (`info`).
- **The buffer.** The last `LOG_BUFFER_CAPACITY` (200) `info` / `warn` / `error` lines are kept in memory, raw. Only Send Feedback reads it (`redactedRecentLog()` in `feedbackService.ts`, through `redactPaths()`), and only when the user ticks the opt-in box (see `docs/dev/feedback.md`). **Telemetry never imports the logger or reads the buffer** (`loggerBoundary.test.ts`): telemetry fields hold no name, path or message, and log lines hold all three.
- **Show Logs.** `erdStudio.showLogs` (`SHOW_LOGS_COMMAND`, `src/services/showLogs.ts`, in `PRE_REGISTERED_COMMANDS` and `NO_LEGACY_ALIAS`) reveals the channel. `SHOW_LOGS_BUTTON` sits on Convert's own failures, the canvas's Move Relationships failure, the **Convert to DBML** tab's refused page (`showLogs` panel message), the canvas load-error screen and the **Canvas disconnected** overlay (`showLogs` webview message). It is also in the **ERD Studio** view's (`erdStudio.domainTree`) **…** menu.
- **Writing a new line.** Prefer `createLogger('<Area>')`; put file paths in local lines freely (the feedback path redacts them), but identify a diagram by its absolute path rather than its name where you can, so the redacted copy shows its shape, not its name. Time a multi-step job with `phaseTimer`. Keep chatty per-file lines at `debug` / `trace`.

## Discrepancy system

Cross-stage comparison is handled by `DiscrepancyService.compare(source, target)`:

| Active Stage | Available Comparisons |
|-------------|----------------------|
| Physical | Compare to Logical |
| Logical | Compare to Physical |

Discrepancy statuses for models/columns/relationships: `matched`, `extra`, `missing`, `type-mismatch` and `undeclared` (columns), `cardinality-mismatch` (relationships). `undeclared` is the case where exactly one stage declares a data type at all — it gets its own status and its own `summary.undeclaredColumns` count rather than inflating the mismatch count, and `deriveColumnAction` still resolves it like a mismatch so "write `data_type:` into the yml" stays reachable. Ghost nodes appear for missing models. Two suppressions, with different switches: the domain's `stubColumns` list is the user's own, and hides missing-column discrepancies only; separately `compare()` automatically drops models with `existsInProject === false` from both sides (and from `summary.totalModels`), and reports a model whose only evidence is a source file (`columns: []` and `provenance.columns === ['file']`) as `matched` with no column rows, on either side — otherwise one undocumented model would emit its counterpart's whole column list as differences. Type comparison splits a base from its parameters with a matched-delimiter scan (so `timestamp(6) without time zone` and `STRUCT<a INT64>` both keep their real base), canonicalises the spellings adapters actually emit (`character varying` → `string`, `NUMBER`/`numeric` → `decimal`, `INT64` → `int`, `TIMESTAMP_NTZ` → `timestamp`, `TIMESTAMP_LTZ` → `timestamptz`), treats absent parameters on either side as compatible, and has exactly one cross-family rule: a whole-number decimal matches an integer. Sync plans are written to `.erd-studio/.sync-plan.json` by `generateSyncPlan`, which takes every library path from `syncPlanLibraryLookups` (`syncPlanBuilder.ts`), as `diff` does: a table with no file yet is named where a table created from that diagram goes (`TableLibraryService.newTableHomeFor`: its layer, and on a DBML diagram its dbt custom schema's folder when one is configured), never the first layer of `layers.json`; **Execute with Claude** confirms the exact terminal command before launching.
