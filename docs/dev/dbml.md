# DBML storage, import and export

> Read before touching native DBML storage (anything under `packages/core/src/dbml/`, the subject-area codec, `planDbmlLibraryWrites`, `applyFileWrites`, Convert Project to DBML), the `erd_layout` codec, the rich DBML export, **Export All Diagrams…**, `erd-studio export --format dbml-rich|--all` **Import DBML…** or the converting imports (**Import SQL DDL…**, **Import Power BI or Fabric Semantic Model…**). The storage spec and its decisions (D1–D33) are `docs/plans/native-dbml-storage.md`; the on-disk format is `docs/semantic-domain-json-reference.md`; the user-facing page is `docs/leaving-erd-studio.md`; the import/export plan is `docs/plans/dbml-import-export.md` (history).

Since 2.0, **DBML is ERD Studio's storage**, in a layer-first tree: every file lives under a layer folder, `<layer>/tables/<schema>/<name>.dbml` (one `Table <schema>.<name>`), `<layer>/relationships/<file>.dbml` (Refs only, with the `use` lines they need; one default file per layer, `<layer>/relationships/<layer>.dbml`, split further by hand however a team likes) and `<layer>/diagrams/<name>.dbml` (table `use` lines, `use *` of exactly the relationships files its tables need, sticky-note `Note`s, then the `Project` with the positions in `erd_layout`). The kind of a file comes from its path alone (`classifySemanticFile`); a root `README.md` explains the folders. YAML/JSON projects from before 2.0 keep loading and stay editable; **Convert Project to DBML** moves one over. The 1.9 pre-release tree (`tables/**`, `<layer>/x.dbml`, `.dbdiagram`) is recognised and never read (below). Separately, DBML is still a way out (the single-file rich export, ready for `dbdiagram push`, which cannot read the split project) and a way in (**Import DBML…**, which always creates a new subject area). ERD Studio never contacts dbdiagram.io.

Undone moves plan nothing too: a table already declared as its new folder says, with no `use` line naming its old path, is home (`isHome`), and `repointUseLines`' `exists` leaves a line already right from the new place. A file of a kind dropped where that kind is not read (`misplaced`; with every moved file counted, since none is followed) is left with a warning; one whose layer folder, schema folder (`isSchemaFolderName`, Move Table's rule) or extension case keeps it from being read is `badName`; each has a button that undoes the event's renames (**Move It Back**, or **Rename Folder Back** / **Rename File Back** for one rename in place) and refreshes the views (the move back is an own write). ERD Studio's own renames (every `applyFileWrites` edit and Organise's) are announced to `ownFileOperations` as exact pairs and skipped once each; the update itself writes only replaces. One WorkspaceEdit through `applyLifecycleWrites`; unsaved files refuse with **Try Again**; a YAML/JSON project (`projectStorageOf` = `yaml`) is never touched |

## Export and import rules

- **Custom-property values are always quoted strings** (`scd_type: '2'`): unquoted typed values exist only from DBML 11.0 and break every 9.x / 10.x reader.
- **Every rich golden parses with no error and no warning** in all three parsers, and all three read it the same. Lint infos are allowed only where the model itself causes them (`MODEL_LINT_INFOS`).
- **Refs are written from the FK end** (a one-to-one from its key end: DBML, and the SQL its tools generate, read a one-to-one's second end as the FK), with `?` on an end that is not all primary-key columns (DBML 9+ reads a bare `>` as NOT NULL, which ERD Studio does not record). Import treats `?` as a plain cardinality.
- **Positions travel in `erd_layout`**, in the export's own Project, exactly as in a stored diagram (the same codec). dbdiagram.io ignores it and lays a pushed diagram out itself. The `.dbdiagram` sidecar (dbdiagram's own layout JSON) was removed in 2.0, read and write: nothing in ERD Studio reads or writes a dbdiagram layout any more.
- **Built only from public documentation.** dbdiagram's terms forbid reverse engineering: never read or copy code from the dbdiagram CLI package.
- **The name box and the dry run.** The diagram's name is taken as typed and saved as its file name ("Sales" → `sales`) by `validateTypedDiagramName` / `slugFromName` (`src/commands/diagramName.ts`), the one rule New Diagram, every import and Import from dbt share. The suggestion splits camel case (`AdventureSales` → `adventure-sales`, `splitWords`), and converted SQL from a generic folder (`database/`, `ddl/`…) is named after the schema its tables share, else the project folder (`sqlImportFileName`). The dry run counts relationships as the canvas draws them (`countLinks`: a composite once); in a DBML project it says every Ref is saved optional (`>?`, D18) with the one shared sentence `savedOptionalNote(requiredRefs, countedRefs)`, for a DBML file and a conversion (SQL, semantic model) alike: `requiredRefs` counts the refs whose foreign-key (many-side) columns are all NOT NULL or part of the table's primary key (a many-to-many is never one), `countedRefs` every relationship drawn (a reference too wide to be a composite once per pair). It is never shown for ERD Studio's own export, the bundled example (`DescribeDbmlImportOptions.example`) or a YAML project; `planDbmlImport` records it as a `savedOptional` ledger entry when the diagram holds no relationships, and the renderers filter that entry out of `ledgerNotes` so it is said once. D18 storage is unchanged. It calls `meta.dbml` "Not null, defaults, indexes and other details ERD Studio has no field for are kept in the table files" (no count: it mixed tables and columns), adding ", so they are not lost" only for a DBML file with no conversion origin whose ledger records no loss (`keptInMetaNote`); a conversion's note says "Not null, defaults and other details…" and stops at "kept in the table files". A file with no `erd_layout` (every dbdiagram.io file, every conversion) gets the plain "Layout: The diagram is laid out automatically when it opens…"; `erd_layout` is named only when the file has one. The Power BI rename note says "the original Power BI names are kept in the table files", never `meta`. With no file given, Import DBML…'s quick path drafts, and its Open dialog starts on, the `.dbml` the start screen's look counted (`findDefaultFile`, `findImportDbmlFile` in `importModel.ts`: the shared `listImportFiles` listing, the first of its first five `.dbml` files that is not ERD Studio's own export, 800 ms at most), chosen, else on the folder. Import Semantic Model… walks the picked folder counting only model files (`.tmdl`, `.bim`, `database.json`, then the `.json` files of each Save to Folder model: `walkSemanticModelFiles`, all `findSemanticModels` reads) toward its 5000-file bound, so a whole repository is a valid pick; past it, the error offers **Choose Another Folder**.
- **Import always creates a new subject area.** Library tables are reused, never overwritten, in the library's spelling. `isForeignKey` comes only from the `foreign_key` property, never from Refs. What DBML has and ERD Studio does not goes under `meta.dbml` (documented in `docs/semantic-domain-json-reference.md`); the rest is dropped and listed in the report.
- **ERD Studio's own export is read more trustingly** (its header, `ERD_STUDIO_DBML_HEADER_PREFIX`): any role text is kept, a one-to-one Ref's second end is the FK (the export writes it key end first, as DBML reads it, even when the keys say otherwise), and a sticky note linked to a table not in the diagram keeps the link; the `unique` its exporter adds to a one-to-one's FK column (a composite one's unnamed unique index) is dropped, since the relationship says it (`dropOneToOneUniques`). A foreign file gets only known roles, a key heuristic for one-to-one direction, and a dropped dangling link, and keeps a one-to-one FK column's `unique`: that key is the source's own (Sakila's `store.manager_staff_id`).
- **SQL DDL and semantic models go through Import DBML's flow, never around it.** Their commands convert to one DBML text and run `importDbml` with that text supplied (`suppliedDbmlUi`) and `source: 'sql'` / `'semanticModel'`, so the layer, the name, the dry run, the write (`writeNewSubjectArea`), the schema folders and every refusal are Import DBML's. The source changes only the title (`IMPORT_TITLES`), the telemetry keys (`IMPORT_SOURCE_TELEMETRY`) and the dry run (the `origin` of `summariseDbmlImportPlan`: "Import N tables and M relationships from 2 SQL files (PostgreSQL) into …", a layout line without `erd_layout`, the conversion's notes counted, and its skipped items as **Not imported:** with the first one and a count; the draft's details list every one). Converted DBML that does not read back is our failure (`*Failed`, Send Feedback), never the user's `*Invalid`. A conversion writes nothing itself; what it cannot express (views, indexes, grants, DAX measures…) is skipped and listed, not kept in `meta.dbml`.
- **Import accepts each property with an `erd_` prefix** (`erd_grain`) as well as plain; export writes plain names.
- **Import into a DBML project** (D19) reuses `planDbmlImport` unchanged and writes the new tables, relationships and diagram as `.dbml` through `writeNewSubjectArea`. DBML-only settings still go under `meta.dbml`, which a `.dbml` table stores as `meta_json`, exactly as in a YAML project, and so do another tool's bare custom properties, although a bare setting in a stored table is now a field (D34); hoisting them to native DBML settings, and reading them as fields, is a follow-up. Import reads the rich export's `rationale_<key>` for every catalogue key (`rationaleKeyOf`). A file with `use` lines is refused (it is part of a multi-file project, such as another ERD Studio 2.0 project), and so is a Save As target inside the semantic dir for an export ("Save the export outside .erd-studio/: files there are your diagrams' own storage."). A diagram file that declares Tables and no table `use` lines (a dropped-in dbdiagram download) shows the **Import these tables…** banner, and `doctor` raises `import-dbml-file`.
- **Telemetry**: `exportDbmlRich`, `exportAll`, `importDbml`, `importDbmlLayout`, `importDbmlCancelled`, `importDbmlInvalid` (the user's file is not valid DBML) and the error `importDbmlFailed`; Import SQL DDL… counts `importSqlDdl`, `importSqlDdlCancelled`, `importSqlDdlInvalid`, the dialect (`importSqlDialect*`) and `importSqlDdlFailed`, Import Semantic Model… `importSemanticModel`, `importSemanticModelCancelled`, `importSemanticModelInvalid` and `importSemanticModelFailed`; the picker, `importPick*` (`telemetry/README.md` → Onboarding funnel). Nothing else, and never a name or path. Open Example Diagram runs the same flow with `source: 'example'`: a finished run counts `exampleDiagram` instead of `importDbml` (retries included, since `source` travels in `deps`) and a cancel counts nothing; only `importDbmlFailed` is shared. **Storage and Convert** (D21, append-only on both sides): the features `dbmlProject` (presence, once), `convertToDbml`, `convertToDbmlOffered`, `convertToDbmlDeclined` (Don't Ask Again), `convertToDbmlNotNow`, `convertToDbmlCancelled`, `convertToDbmlRefused` and `dbmlForeignFormatWarned`, and the errors `modelFileDbmlSyntax`, `modelFileDbmlInvalid`, `modelFileDbmlStructure`, `domainLoadDbml` and `convertToDbmlFailed`. A DBML canvas counts as `schemaFormats` `'v5'`.

## Import fidelity: SQL DDL, semantic models, dbt

Every import is measured against real published schemas (`test/fixtures/real-world-imports/`, see Tests). The rule behind each part below is the same: **read everything a source declares, and for whatever cannot be kept as written, say so in the ledger** (`importLedger.ts`), so nothing is lost silently.

### The loss ledger

- **Outcomes:** `lost` (not kept), `changed` (kept, but not as written: a type rewritten, a key inferred), `repaired` (a SQL statement rewritten so the grammar reads it), `skipped` (counted only, never listed: what an existing line already reports, such as measures or a file's skipped views), `problem` (a unit that did not read at all). Each entry has a unit (`table`, `column`, `primaryKey`, `relationship`, `type`, `setting`…), a fixed cause, a short fixed `what`, an optional per-entry `detail` and `where` (file, line, table, column). Equal entries count up.
- **Rendering:** `ledgerNotes` renders `changed` and `repaired` (the draft's **Notes**); `ledgerLeftOut` renders `problem` first, then `lost`. **Not imported** is `dedupeLines([...ledgerLeftOut, ...origin.skipped, ...dropped])`. `ledgerLogLines` writes one ERD Studio log line per entry. Lines carry names and fixed phrases only, never file text (`ledgerText` sanitises).
- **Where it flows:** `convertSqlDdl` and `semanticModelToDbml` return `ledger`; the commands log it and pass it as `origin.ledger`; `planDbmlImport` adds its own to `DbmlImportReport.ledger`. The origin's `notice` (a partial SQL import's "3 of 71 tables could not be read…") becomes the draft banner's notice unless the draft was redrawn. A dbt draft's `DbtDraft.ledger` gives a Notes section, and its lost lines are added to **Not drawn** (tag `not imported`).

### SQL DDL

- **Isolation.** `convertSqlDdl` is partial: one table never vetoes the rest. It returns `ok: true` when at least one CREATE TABLE reads, with `problems` holding the units that did not (each also a `problem` ledger entry with a cause, a table and a line). `ok: false` remains only for no files, an unknown dialect or zero tables read. A table defined twice keeps its first definition (the duplicate check runs as each table is inserted). The result carries `tablesFound` and `readWith {grammar, repaired, salvaged}`.
- **Preparing the text** (`prepareText`, length-preserving, run before splitting both in `readFile` and in the start screen's count): the BOM becomes a space, a lone CR becomes LF, MySQL versioned comments become code, and template placeholders are neutralised (`sqlDdlPlaceholders.ts`: a catalog placeholder is dropped, any other becomes its inner name; strings and comments are never touched). Two different placeholders whose inner names end the same (`${bronze.schema}` and `${silver.schema}`, `source('raw','orders')` and `source('stg','orders')`) read as their full names instead (`bronze_schema`, `raw_orders`): `ambiguousPlaceholderNames` looks across every file of the import first, so a placeholder reads the same in each file. The ledger entry names the first placeholder in its detail (never as a table) and says a catalog was dropped only when one was.
- **Splitting** (`sqlDdlLexer.ts`): every Unicode space is a space; a string, quoted name, comment or `$$` body left open at EOF runs only to the end of its line; `DELIMITER x` sets the delimiter; a routine (CREATE PROCEDURE / FUNCTION / TRIGGER / EVENT) is one statement (to its GO in SQL Server, else by BEGIN / CASE … END); a `;` inside unbalanced parentheses ends the statement when the next line starts one; `COMMENT ON` at a line start starts a statement.
- **Repair ladder** (`sqlDdlRepair.ts`), only after the strict parse fails, cumulative rungs: (1) options — head modifiers and every trailing table option set aside, `COMMENT` kept as the note; (2) quote — names quoted in the target grammar's style, the catalog dropped; (3) types — exotic types behind a `varchar(9876NN)` placeholder, restored from the source span; (4) modifiers — unknown column modifiers and constraint extras set aside; (5) allTypes. When a rung reads, the rungs before it are dropped one by one while the table still reads (each rewrite is parsed once), so the ledger names only the changes the table needed: a column named like a keyword is not "quoted so it reads" when a VIRTUAL column was the problem. Then the other grammars are tried on the rewritten statement. A rewrite counts only if the grammar returns exactly the column names the source lists (a forgiving grammar can read stray words as a column), and a type with a stray word is never put behind a placeholder, so syntax errors stay errors. A comma missing between two columns is such a stray word (`strayTypeToken`): a type word that starts a line (other than one that only continues a type: `precision`, `with`, `unsigned`…), a word after the type's arguments that no type has there (`decimal(5,2) year`), or a word followed by a type's head word (`int year int`). When the table does not read, the comma is put in (`missingCommas`: also one missing after a column's constraints, a name starting a line followed by a type's head word, e.g. `REFERENCES p(id)⏎ note varchar`) right after the first column's text, so no line moves, and the table is read again once (`withMissingCommas`, up to 8 passes); each comma is a `repaired` entry ("a comma added between price and year") with its line. Only if it still does not read is it a problem, worded on the file as written: "a comma missing before year (after the column price)". A grammar that reads the columns without the comma keeps each column's own type (the as-written type ends at the stray word). Every change is a `repaired` entry with its line. Budget: `REPAIR_LADDER_MAX_TABLES` (300) or `REPAIR_LADDER_MAX_MS` (8 s); past it tables go to salvage and one `capped` entry says so.
- **Salvage** (`sqlDdlSalvage.ts`) reads the column list without a grammar into the grammars' raw shape. It is strict about structure: an empty definition, a missing type or an unknown word after a type or constraint is a problem with that token's line. A key part that is an expression (`UNIQUE KEY uk ((lower(email)))`) is an expression part, never a column named like its first word.
- **Keys the DBML could not hold:** a primary or unique key with an expression part (from a grammar or salvage) is a `lost` entry, never a key on its other columns alone; a key naming a column its table does not have is a `lost` entry too, so one table's key never makes the whole DBML unreadable.
- **Problem messages** are `CREATE TABLE x could not be read: <hint | salvage reason | cleaned diagnostic>`, the reason at most 80 characters, with a cause, a table and a line. They never echo SQL.
- **Structure from every source** (`sqlDdlStatements.ts`): keys and FKs come from inline and table constraints, every item of an ALTER TABLE action list (after an ADD, an item starting CONSTRAINT / FOREIGN / PRIMARY / UNIQUE / CHECK continues it), CREATE UNIQUE INDEX (expression and partial ones are listed under Not imported; unique indexes on views skipped) and ALTER … ADD CHECK (deferred, so a constraints file may come first). Schema changes replay in file order: DROP CONSTRAINT by the written or the generated name (`t_pkey`, `t_a_b_fkey`, `t_a_b_key`, `t_a_check`, `t_ibfk_N`; a generated name matches only a constraint the files left unnamed, as in the database), DROP FOREIGN KEY, DROP INDEX, DROP PRIMARY KEY, RENAME CONSTRAINT, ALTER INDEX RENAME. IF EXISTS of an unknown name is silent; without it the name goes to Not imported with its line. Every skipped ALTER action is named for what it is (`alterOwner`, `alterSetting`, `alterPartition`, else "ALTER TABLE action ERD Studio does not read").
- **Schema context:** USE / USE SCHEMA / USE db.s / SET search_path / SET SCHEMA / `set_config('search_path')` set the schema per file (each file starts in the default; `RESET` and `TO DEFAULT` reset it; SQL Server's and Snowflake's `USE db` pick a database, not a schema). `CREATE SCHEMA s CREATE TABLE …` puts its tables in `s`. The dialect's default schema (public, dbo) is written unqualified.
- **Procedural blocks:** a `DO $$ … $$` or `EXECUTE IMMEDIATE $$ … $$` body is re-tokenised where it stands, so its DDL keeps its true lines; IF / WHILE / BEGIN are scanned the same way. Routine bodies are never read. Dynamic `EXECUTE '…'` is a `lost` entry (its text is built at run time).
- **Verbatim types** (`sqlDdlColumns.ts`): a column's type is its source span, from the name to the first constraint word at depth 0, comments stripped, whitespace collapsed, SQL Server brackets taken off names. The grammar's `type_name` is used only with no span, or for an inline MySQL ENUM (its Enum keeps the values structured in `meta.dbml.enum`).
- **One-to-one** (`sqlDdlWriter.ts`, `cardinalityOf`): a link is one-to-one when its FK columns are the FK table's whole PK or exactly a unique key, written `Ref: pk_end - fk_end` (Import DBML stores a non-declared `-` from its second end unless only that end is a whole key). One whose FK is its table's key but whose target is not a key is written `>`, and the ledger says so.
- **FK actions** are written on the Ref as `[delete: …, update: …]` (DBML's five values), so the reference-settings report lists them. FK constraint names are never written (Import would read them as roles): a `changed` entry (`constraint`, `notDesign`).
- **What DBML cannot say:** ON UPDATE and generated-column expressions are `lost` entries; SQL Server computed columns are typed `computed` with the note "Computed column; its expression was not imported." and a `changed` entry; domains and alias types keep their name, with a `changed` entry naming the base type and CHECK; physical column settings and table options are counted on the file's skipped line (skip kinds `columnSetting`, `tableOption`); `DEFAULT NULL` is not a default.
- **Partitions** (`sqlDdlPartitions.ts`, resolved once every file is read, before keys and comments apply): a child with no columns of its own (`CREATE TABLE x PARTITION OF p`, `CREATE TABLE x () INHERITS (p)`, or a `CREATE TABLE` whose columns are all `p`'s joined by `ATTACH PARTITION` / `INHERITS` / `ALTER TABLE … INHERIT`, in any order or file) folds into `p` by default (`SqlDdlConvertOptions.partitions: 'fold'`), through every level: no table, one `changed` ledger note per child at its CREATE TABLE's line, its FKs drawn from `p` (de-duplicated), FKs to it pointed at `p`. A key, check, comment or column detail (type, NOT NULL, default; `PARTITION OF` column options) the child has and `p` does not is a `lost` entry at its own line; a copy of `p`'s is dropped quietly, and a later comment on the child replaces an earlier one. A column change to a child with no table yet (ADD / ALTER / RENAME / DROP COLUMN, SET DEFAULT…) waits in `childChanges` and is never applied to `p`: it is replayed on the child's table (built from `p`'s columns) once partitions resolve; a column it adds keeps the child as a table, and when the child still folds each change `p` lacks is a `lost` entry at the ALTER's line (a pg_dump copy's details are reported at their column or constraint line). DROP TABLE of such a child forgets it and what waits for it, every level; `CREATE TABLE IF NOT EXISTS` of it does nothing; a loop of partition links keeps the table (said). Two copies of one FK with different `ON DELETE` / `ON UPDATE` keep the first; the other's action is a `lost` setting at its line (`resolveRefs`). A child with columns `p` lacks, or with several parents, is kept and noted; an INHERITS child gets its parents' columns first (no keys). A parent the files never declare: a child with columns is kept and noted, one without is a `lost` table. `DETACH PARTITION` and `NO INHERIT` end the link in file order (a `PARTITION OF` child then becomes a table with its parent's columns); RENAME and DROP TABLE carry the records. `partitions: 'tables'` keeps every child as a table (a `PARTITION OF` child gets its parent's columns and key). Import SQL DDL…'s step-by-step flow asks once when the conversion folded any (`pickPartitions`, `result.partitions`); the quick path folds, and its Change Options… preselects that.
- **The command** (`importSqlDdl.ts`) logs every problem with `log.warn`, file and line. A partial import goes on to the draft with `origin.notice` (`sqlPartialNotice`) and `origin.ledger`. A total failure shows Open File and Show Logs, plus Try Another Dialect only when another dialect reads more. Every problem is logged once (the ledger's `problem` entries are left out of its log lines). The banner counts a table defined twice apart from the tables that could not be read ("1 of 70 tables could not be read; 1 table is defined twice (the first definition is kept)"). The dialect pick reads the scripts in every dialect first (`readAsDialects`, the detected dialect first, up to `RANK_ALL_DIALECTS_CHARS` = 4 MB, and within `RANK_DIALECTS_MS` = 3 s: until a dialect reads a table every one is tried, and after that another only while the time spent plus the slowest reading so far fits), ranks them (`rankSqlDialectReadings`: most tables read, fewest salvaged, fewest repaired, the detected dialect, likelihood) and labels each (`sqlDialectReadingLabel`: "reads 70 of 71 tables"). The quick path converts the detected dialect first and ranks all only when that reading is not whole. A file under the open folder is always named by its path under it. Telemetry keys are unchanged.

### Semantic models

- **Types:** for `dateTime`, the `UnderlyingDateTimeDataType` annotation wins; without it a date-only or time-only `formatString` gives `date` or `time`; otherwise `timestamp`. Each rewrite is a `changed` entry.
- **Keys:** `isKey` is the primary key. A table with no key reached through exactly one column gets that column as an inferred key. Any other column at a relationship's "one" end is written `unique` (Power BI requires it); inactive relationships count, and both ends of a one-to-one. **The one exception is a date table** (`dataCategory: Time`) whose `isKey` date column no relationship joins while every relationship joins one other column (DimDate's `DateKey`): Mark as date table set that `isKey` for time intelligence, so the joined column becomes the key and the date column stays `unique` (a `changed` entry "date table key" and a warning). A note is given when a table keeps an `isKey` beside a unique end, or has several joined columns and no inferred key. `isNullable: false` is not null; TMSL `isUnique` is unique.
- **Descriptions** are verbatim. A calculated table or column with no description gets the calculated sentence as its note; with one, the description stays exactly as written and the DAX not imported is only a `lost` "DAX expression" entry (every calculated table and column has one).
- **Formats:** TMDL, TMSL (`model.bim`), and Tabular Editor's Save to Folder (`semanticModelFolder.ts`: `database.json` with `tables/<T>/<T>.json` and its `columns/`, `measures/`, `partitions/`, `hierarchies/`, `calculationItems/` files, and model collections such as `relationships/`, `roles/`, `cultures/`, `expressions/`, put back together as one TMSL database and read by the TMSL reader). Its `LocalRelationships` (a table's `TabularEditor_Relationships` annotation), `LocalPerspectives` (`TabularEditor_Perspectives`) and `LocalTranslations` (`TabularEditor_Translated*`) are read; files are read in path order (so `PrefixFilenames` keeps the model's order, and without it tables and columns come in name order). `findSemanticModels` finds one by its `database.json` with `tables/` beside it; the command's walk (`walkSemanticModelFiles`) lists `.tmdl`, `.bim` and `database.json` first, then every `.json` under each `database.json`'s folder, all within the 5000-file bound.
- **Isolation:** one file never fails the model. A TMDL file that is not text, an object whose name has no closing quote, or a ```` ``` ```` block never closed is left out with a `problem` entry (`TMDL column with no closing quote`, file, line, table, column); the objects declared after a block never closed are named one by one (`… after a ``` block never closed`); an unreadable file under `tables/` names the table its file is named after. A Save to Folder file that does not parse is a `problem` with the line the parse stopped on (`parseJsonWithLines`), its table's other files counted with it. The read result is `ok` with `problems` (logged by the command) unless nothing is left to draw; then it fails with those problems.
- **Relationship settings:** `crossFilteringBehavior` or `securityFilteringBehavior` `bothDirections` (or security `none`) and `relyOnReferentialIntegrity` are `lost` / `noField` setting entries on the relationship's file and line (no warning).
- **Merges and appends:** `mCombinedSources` (with `powerQueryLet.ts`: a query's `let` steps, its `Table.NestedJoin` / `Join` / `FuzzyNestedJoin` / `FuzzyJoin` / `AddJoinColumn` / `Combine` calls, strings and comments respected) lists every source a query merges or appends, following steps to their navigation (`schema.item`), naming another table or shared query (a shared query that navigates by its warehouse table; parameters and functions are never sources), else `a file`, `a native query`, `tables listed at run time` or `its own rows`. Kept as `meta.power_bi_sources` (comma-separated, beside the primary `power_bi_source`) with a `changed` "Power Query merge" / "append" entry.
- **Name:** the `.platform` displayName; else the `<Name>.SemanticModel` or `.Dataset` folder; else a database or model name that is not a tool default (SemanticModel, Model, Dataset, Database, TabularProject…, a GUID); else the folder holding `model.bim`, or `X` for `X.bim`.
- **Warehouse source:** `meta.power_bi_source` (DBML `meta_power_bi_source`) holds `schema.item` from the partition's M navigation, a shared expression the query starts from, or a Direct Lake entity. Native queries, file sources and unparsed Power Query sources are `lost`.
- **Ledger:** `lost` / `notDesign` for every model feature an ERD has no place for (hierarchies, security roles, row filters, table and column permissions, perspectives, translated captions, Q&A metadata, data sources, Power Query expressions and parameters, Mark as date table, variations, KPIs, and the report settings `formatString`, `dataCategory`, `sortByColumn`, `summarizeBy`, `isDefaultLabel`, `isDefaultImage`, `displayFolder`); `changed` for date / time types, inferred keys, unique ends, the date-table key and a kept warehouse source; `skipped` for measures, calculation groups, auto date tables and skipped relationships (already in the skipped summary). Every entry carries its file and line: TMDL by its line reader, TMSL and Save to Folder by `parseJsonWithLines` (`jsonLines.ts`: `JSON.parse`'s values with the line of each object and key; a report setting is on its property's line).

### dbt (Import from dbt, `docs/dev/draft-first.md` §5.2)

`YmlData.notNullColumns` (scalar, with config, `data_tests:`, contract constraints; a where-limited, disabled or `not_null_proportion` test is not counted) and its manifest twin `ManifestData.notNullColumns` (`not_null` / dbt_expectations' test nodes without `config.where` or `row_condition`, column and model `not_null` / `primary_key` constraints) become `meta.dbml.not_null` and the D18 count (`DbtDraft.requiredRelationships`); `notNullColumnsOf` keys both by `identifierKey`, so a test's quoted `"Order Id"` matches the column `Order Id`, and `buildDbtDraft` spells each relationship end as the seeded column does. Every link from a drawn model to one not drawn is a `DbtDraft.undrawnLinks` entry (`why`: `addable`, `noColumns`, `notAModel`, `source`, `package` for another dbt project's model by `rootProjectsOf`, `disabled` by `disabledModelsOf`: the manifest's `disabled` and yml `config: enabled: false` unless the manifest builds the model; `noColumn` when a seeded table has no column the test names, so no line is drawn to nothing), listed in Not drawn and counted on the table's line. A relationship whose every test is conditional (`relationships_where`, a `where:` config; the yml reader and the manifest extractor mark it alike, and carry `RelationshipTestCondition` as written; `dbtTestsOf` reads the yml and the manifest as two copies of the same tests, so a link is conditional when either copy says every test of it is) is a `lost` constraint line with the test's file and line, and a `DbtDraft.relationshipConditions` entry that **Relationships** shows as text (`dbtConditionText`): the condition is user text shown on the draft only, never a ledger `what`. The project's sources (`YmlData.sources` with file and line, then any only `ManifestData.sources` has; enabled only, `identifier` / `quoting.identifier` kept) are `DbtDraft.sources`, one `skipped` ledger entry each, one Not drawn line (`dbtSourcesLine`) and one output-log line each (`dbtDraftLogLines`); a manifest source of another dbt project than `rootProjectsOf` (an installed package's) is not listed: they are listed, never offered as tables, because a source has no dbt model for the Physical tab, `selectors.yml`, Compare or Sync to match, and its `source.table` name can collide with a model's. The yml reader applies `<<:` merge keys wherever it reads a map (`deref` → `withMerges`, own keys first, at most 8 deep, each map merged once per file so a fan-out of anchors costs linear time) and draws a versioned model's latest version (`modelColumnNodes`). Models without columns get one Not drawn line; `dbtLayerSchemaNote` says which tables are written in the layer's schema; the banner ends with `DBT_KEEP_SELECTORS_SENTENCE`. The scorecard counts the truth's `filtered` links as `conditions` (shown, reported, silent).

## Storage rules

- **Splice, never regenerate** (D7): a writer touches only the nodes its edit changes, a derived block (`use` lines, `meta_json`, the PK form) only when its inputs changed, and a file that does not parse is refused. A no-op save is byte-identical.
- **One canonical layout** (spec §2.9). Every write of a `.dbml` ends with `formatDbml` through `src/services/dbmlWriters.ts`, so files converge on it: the first write that changes a hand-written or 1.9.x file tidies the whole file, keeping its element and setting order (the formatter never moves a token). New content is the writers' job: a table's body `Note` first with a blank line after it (W1); column settings `pk`, DBML's own, ERD Studio's, the fields, `note` last, and a setting an edit adds goes at its place in that order (the field band, table and column alike: after ERD Studio's typed settings come the rationale-home fields in `RATIONALE_FIELD_KEYS` order, then any setting ERD Studio does not read, then every `meta` spelling as one group (bare, `meta_<key>`, `rationale_<key>` and an existing `meta_json`), then a new `meta_json`, and `note` last; an edit keeps the spelling the value was read from, a clear removes every spelling of that home only, and an add uses the new-file spelling) (W2, `keyOrder` / `existingKeyOrder` in `writeTable.ts`, `ListPlan.orders` in `splice.ts`); a blank line between the Refs of different foreign-key tables in any relationships file a write changes (W3, `separateRefGroups`). **Never on the layout-only path**: a move splices only the `erd_layout` value, unformatted. Alignment means a new longest column name or `use` path re-pads its whole group, so such a write shows as a change to every line of the group in a diff.
- **Tolerant per file** (D6): each table file is parsed on its own, each relationships file Ref by Ref, each diagram with everything it does not own blanked. Display never uses a multi-file `rawDb`, so one broken table never blanks a diagram.
- **Selective `use` lines** for tables (`use { table x } from '…'`, never `use *`, which also imports Enums), `use *` only for relationships files; paths are posix, relative to the file, with `.dbml`. The reader also accepts `use *` and a path without the extension.
- **FK end marked possibly null on every Ref written** (D18): `>?`, `?-` (a one-to-one's FK is its second end) and `<>?`. A Ref already in a file keeps its marks byte for byte unless its unit changes.
- **Qualified, exact-case names** (D2, D30): a table file declares `Table <schema>.<name>`, the qualifier spelled exactly as its schema folder and the name as the file stem (compared case-insensitively on read; `doctor` warns `nameCaseDrift`). Every writer that creates or re-qualifies a table first sets `schema = schemaAsListed(layer, schema)` and uses that one string for the folder, the header, every `use` specifier and every Ref end (a header spelled differently from a specifier fails every parser with `[4000]`). The old `[schema: '…']` setting is no longer the schema (`schemaProperty` when it differs); an unqualified Table reads with its folder as the schema (`unqualifiedTable`, except under `public/`), a different qualifier with the qualifier (`schemaFolderMismatch`). Changing a schema is a move (`editTableDbml` `requalify`). The table name stays unique across the whole project (all layers and schemas); `_relationships` is an ordinary table name.
- **Layers** (D28): a DBML layer folder is a lower-case layer id (`^[a-z][a-z0-9_-]*$`) that is not hidden, not in `NON_SUBJECT_AREA_DIRS` and not reserved (`RESERVED_LAYER_NAMES` = `tables`, `templates`, `logical-models`, case-insensitive; `relationships` and `diagrams` are allowed, since the grammar is by depth). It need not be in `layers.json` for its tables and relationships to be read; a diagram needs its layer configured to open. Add Layer and Convert refuse a reserved name in every project ("`<name>` is reserved for ERD Studio's own folders; pick another name."); the display name is the layer's `label`. `tables`, `relationships` and `diagrams` are matched byte for byte (VS Code's globs are case-insensitive, so `gold/Diagrams/x.dbml` opens the canvas's not-a-diagram page; accepted and pinned).
- **Mixed projects** (D20): a DBML diagram may list only DBML tables and a DBML-owned Ref may name only DBML tables; the refusal says to run Convert Project to DBML. A JSON diagram may list both. The exceptions are Convert's own (D26/D27, below).
- **Members with no table file** (D26): a DBML diagram names them in the Project's `erd_unlinked_tables` (one quoted, comma-separated string, never empty), never as `use` lines. The reader appends them to the members and they resolve by name like any member (missing → placeholder, YAML → drawn from the `.yml`). The diagram writer keeps the key in sync: a name whose table now has a `.dbml` file moves to a `use` line on any edit that changes something (a no-op stays byte-identical), a removed member leaves it, and a new member with no file is still refused (D20). A table new in a library plan (`DbmlLibraryWritePlan.createdTables`) reaches every diagram that lists it through the settle pass. Only Convert writes a name there.
- **Pending relationships** (D27): `// erd-studio pending: Ref …` lines. In a relationships file they belong to their FK table like a Ref (`DbmlRelationshipsReading.pending`, attached by `attachRelationships`), so the canvas draws them; in a diagram they are its own relationships (`logical.relationships`), the only ones a DBML diagram holds. The relationships writer keeps a pending line while its unit is wanted and cannot be live, cuts it when its owner is listed without it (or deleted), and turns it live, with its `use` line, on any write to the file once both ends have `.dbml` files with those columns. A new unit that cannot be live is written pending only with `writePending` (Convert); a canvas edit is refused as before. Never a live Ref to a table with no file: it breaks the whole file in every DBML tool.
- **Large libraries**: by default every Ref of a layer lands in its default file, so a big layer concentrates merge conflicts there and makes other DBML tools load every table that file imports for any diagram that imports it. A team may split a relationships file by hand; ERD Studio never moves an existing Ref, so the split survives and new Refs follow their FK table's Refs. A file named after a schema (`<layer>/relationships/<schema>.dbml`) also takes the new Refs of that schema's tables that have none yet, so creating one splits a layer by schema from then on. A layer's default file can hold thousands of Refs (10,000 read in ~0.8 s); after a write the host primes the relationships cache with the written text, so the next snapshot re-reads nothing. `test/unit/dbmlPerformance.test.ts` holds the budgets (10,000 tables, 30,000 Refs).
- **Relationships files are never deleted** (D15), and an existing Ref is never moved to another file: it is edited in place, a column change included. A link held in any relationships file, live or pending, is refused when an edit would write it again.
- **Drags are diagram edits.** Positions live in the diagram, so a drag is one minimal-range splice of the diagram's `erd_layout` (`applyLayoutOnlyEdit`: no library plan, no settle, no format, `refreshWebview: false`, the `layoutOnly` event so neither sidebar tree refreshes), and the reading is primed from the new text (`primeLayoutOnlyReading`), so the next drag compiles nothing. Native Cmd+Z rewinds that one edit; `flushUndoRedo` sees a layout-only rewind (`sameOutsideErdLayout`) and only re-sends the canvas. A drop in place writes nothing. A conflicted `erd_layout` turns the drag into a toast.
- **History: the 1.9 layout file.** Until 2.0 the positions were a `.dbdiagram` file beside the diagram, written through a background `TextDocument` (never shown in a tab) and saved straight after, with an undo anchor to keep Cmd+Z on one file and a save of the rewound layout after an Undo so hot exit could not restore it as an unsaved tab. All of that was removed with the file in 2.0.

## Performance on a large library

A pre-release tester's project (about 1,100 tables, a 500-table diagram) showed what grows with the library. None of it was slow parsing (a DBML table parses in about 1 ms); it was work repeated per table. What keeps it linear, with the details in `docs/dev/architecture.md` (data flow step 3, **Edit pipeline**, **Opening a canvas**, **Background read**):

- **One library index** (`src/services/tableLibraryIndex.ts`, no `vscode`, shared with the CLI). One listing of the semantic dir, `logical-models/`, `tables/` and each layer's `tables/<schema>/` and `relationships/` (a DBML project lists `1 + layers × (2 + schemas)` directories) answers every name → file lookup, `listTableFiles`, the relationships files, the folders and `tablesDirIsLayer`. It validates itself on use by the signatures of the directories it listed and `layers.json`, so git, an AI assistant or another window adding a file needs no invalidate call. Never list a library folder per lookup again: that was 96% of opening a diagram.
- **Per-path invalidation.** An edit drops only the parses of the files it wrote (`TableLibraryService.invalidatePaths`, fed by `writtenPaths(applied)`), a written relationships file's reading with the attach memo, and the index only when a table file appeared or went. `invalidateCache()` with no argument (everything) is for Convert and the bulk commands only.
- **Scoped opens.** A diagram open reads its members and the other ends of their Refs (`readingTables`, `memberAttachment.ts`), compiles the diagram once (`dbmlDiagramReadings.ts`, core's per-diagram compile cache), and answers `ready` with `loading` before it reads anything. The rest of the library is read in the background (`LibraryWarmUp`).
- **Layout-only writes.** A drag, an auto layout or a note moved writes only the diagram's `erd_layout` (`viewConfig` in JSON storage), with no library plan or attach, and `onDidWriteSubjectArea` says `layoutOnly`, so neither sidebar tree refreshes. Own writes are matched by content, so a slow save never comes back as an outside change.
- **Cheap trees.** The Subject Areas count comes from the diagram text alone; the Table Library caches each diagram's members by mtime and size and reads unread table files in the background.
- **Linear DBML checks.** Convert's self-check and `doctor` compile file by file (`compileDbmlFilesSeparately`), which reports exactly what one whole-project compile does; @dbml/parse 11 resolves each Ref against every file of a multi-file layout, so the whole-project compile grows with the square of the library.

Measured on the synthetic 1,100-table project (fresh copy per run, median of three, host code driven through the vscode mock; f9a5bee → this branch):

| Operation (1,100 tables, 500-table diagram) | YAML | DBML |
|---|---|---|
| Both sidebar trees, first render | 8.9 s → 0.03 s | 15.0 s → 0.24 s |
| Open the diagram, first time | 3.2 s → 0.19 s | 5.7 s → 0.39 s |
| Open it again (Retry, reopen) | 2.8 s → 0.04 s | 4.9 s → 0.04 s |
| Move one table, with the refresh it triggers | 6.8 s → 2 ms | 10.7 s → 9 ms |
| Convert Project to DBML, plan | 24–28 s → 4.9 s | |
| `erd-studio doctor` | 40.7 s → 6.3 s | 54.6 s → 4.6 s |

**The formatter's cost** (2026-10-29, same synthetic projects, before/after on the same loaded machine, medians): a 1,100-table Convert plan 7.55 s → 7.63 s (+1%; formatting each new file costs ~0.5 ms per table, paid for by `asWritten` saves, which stop the library plan re-reading the tables Convert has just rendered, and by `separateRefGroups` parsing syntax only); one edit of the 500-table diagram 4.6 → 16 ms when it first tidies an unformatted file; a move 12–16 ms → 10–15 ms (never formatted, no compile). Formatting is linear in the file's size (`packages/core/test/unit/dbmlFormat.test.ts` holds a ratio test).

`test/unit/largeLibraryScaling.test.ts` locks this in by counting work, not time: directory listings, table-file reads and DBML compiles for lookups, both tree renders, a cold and a warm open, and a move, on a 1,100-table library it generates. A count that grows with the library fails it on any machine; its wall-clock budgets are only a backstop (3×, 8× on CI). `test/unit/dbmlPerformance.test.ts` covers a 10,000-table flat library.

## Adding a property

1. Add the name to `dbmlRichProperties.ts` (names already there are a contract: never rename one).
2. Write it in `exportDbmlRich.ts` and read it in `dbmlImport.ts`, both through the constant.
3. Cover it in `rich-features` and regenerate the goldens; the round-trip test must pass without a new exception.
4. Native storage reads and writes the same names (`dbmlRichProperties.ts` is shared): cover the property in a storage writer case and a DBML twin too.
5. A core change ships to npm and the Confluence app on merge: keep it additive (a package PATCH), with a line in `packages/core/CHANGELOG.md`.

A new **field** (a built-in purpose-style text, or a column flag) is not a property: it goes in the catalogue in `fields.ts` and is spelled by the field rules (`docs/dev/fields.md` → Adding a built-in field). The rich export spells it `rationale_<key>` or `meta_<key>` with no change here.
