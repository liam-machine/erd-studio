# DBML storage, import and export

> Read before touching native DBML storage (anything under `packages/core/src/dbml/`, the subject-area codec, `planDbmlLibraryWrites`, `applyFileWrites`, Convert Project to DBML), the rich DBML export, the dbdiagram layout file, **Export All Diagrams…**, `erd-studio export --format dbml-rich|dbml-layout|--all` or **Import DBML…**. The storage spec and its decisions (D1–D25) are `docs/plans/native-dbml-storage.md`; the on-disk format is `docs/semantic-domain-json-reference.md`; the user-facing page is `docs/leaving-erd-studio.md`; the import/export plan is `docs/plans/dbml-import-export.md` (history).

Since 2.0, **DBML is ERD Studio's storage**: a new project keeps one `.dbml` file per table in `tables/`, its relationships as `Ref` lines in each library folder's `_relationships.dbml`, and each diagram as a `.dbml` file of `use` lines (plus a `Project` and sticky-note `Note`s) with a `.dbdiagram` layout file beside it. YAML/JSON projects from before 2.0 keep loading and stay editable; **Convert Project to DBML** moves one over. Separately, DBML is still a way out (the single-file rich export plus its `.dbdiagram`, ready for `dbdiagram push`, which cannot read the split project) and a way in (**Import DBML…**, which always creates a new subject area). ERD Studio never contacts dbdiagram.io.

## Parser

- `@dbml/parse` **11.0.0**, exact pin, a root `dependency` and a **runtime dependency of `@erd-studio/core`** (the same exact pin, so every bundle holds one copy), imported only under `packages/core/src/dbml/` and exposed as the subpath `@erd-studio/core/dbml`; the main entry stays parser-free (the webview and renderer never contain it). Bundled into `dist/extension.js`, `dist/cli.js` and `mcp-server/dist/index.js`, one copy each (`test/unit/cli.noVscode.test.ts` asserts the CLI bundles the root pin, not a test alias, and that every bundle holds exactly one parser). The VSIX is packed with `--no-dependencies`, so nothing ships from `node_modules`.
- Tests read every written file and every rich export with 9.1.1 (`dbml-parse-v9`), 10.3.1 (`dbml-parse-v10`) and the pinned 11.0.0, the aliases core devDependencies hoisted to the root. The helpers are in `packages/core/test/exportParsers.ts` (`parseDbmlRich`, `readDbmlRich`, `RICH_DBML_PARSERS`, `MODEL_LINT_INFOS`) and `packages/core/test/dbmlWriterSupport.ts`. The v1 `toDbml` floor is still `@dbml/core` 2.4.2, and v1 is unchanged.
- **ERD Studio writes quoted values only** (`natural_key: 'true'`, `scd_type: '2'`, `erd_schema_version: '7'`), so DBML 9 and 10 tools read every file it writes. It **reads** 11.0's unquoted numbers and booleans on Tables, columns and Notes (as the literal's own text), keeps them byte for byte until that value is edited, and flags each with the `unquotedValue` warning (and in `doctor`). An unquoted word or phrase is an error in every parser.
- **The "quote the value" hint keys on 11.0.0's codes**: `3025` (column) and `3075` (table) in a table file, `3051` (Note) and `3063` (Project) in a diagram (`DBML_TABLE_QUOTE_HINT_CODES` / `DBML_DIAGRAM_QUOTE_HINT_CODES`). 9.1.1 numbers them differently, so a test that asserts a code runs with the pin only.
- **`updateElementSetting` (10.3.1+) is not used**: ERD Studio splices itself (it must also keep Metadata blocks, comments and formatting), and 9.1.1 lacks it.
- Code reads a file path only through `Filepath#absolute` (11.0.0 serialises a `filepath` as `{root, segments}`, 9.x / 10.x as `{path}`), and compiles under a fixed virtual root, so reads never depend on where the project lives (10.3.1 silently drops imported tables under a path with a space; `doctor` warns `pathWithSpace` for other 10.x tools).

## Export and import rules

- **Custom-property values are always quoted strings** (`scd_type: '2'`): unquoted typed values exist only from DBML 11.0 and break every 9.x / 10.x reader.
- **Every rich golden parses with no error and no warning** in all three parsers, and all three read it the same. Lint infos are allowed only where the model itself causes them (`MODEL_LINT_INFOS`).
- **Refs are written from the FK end** (a one-to-one from its key end: DBML, and the SQL its tools generate, read a one-to-one's second end as the FK), with `?` on an end that is not all primary-key columns (DBML 9+ reads a bare `>` as NOT NULL, which ERD Studio does not record). Import treats `?` as a plain cardinality.
- **The layout file** follows the shape of a file `dbdiagram pull` wrote from Liam's own diagram (`packages/core/test/dbdiagram-pull/`): `version` the string `"3.0.0"`, no `darkMode`, `schemaName: "public"` for a table with no schema, and `stickyNoteLayouts`, `referencePaths`, `tableGroupCollapseStates` written empty. The sticky-note layout shape is unknown, so sticky positions do not travel; the reader accepts entries loosely.
- **Built only from public documentation and that pulled file.** dbdiagram's terms forbid reverse engineering: never read or copy code from the dbdiagram CLI package.
- **Import always creates a new subject area.** Library tables are reused, never overwritten, in the library's spelling. `isForeignKey` comes only from the `foreign_key` property, never from Refs. What DBML has and ERD Studio does not goes under `meta.dbml` (documented in `docs/semantic-domain-json-reference.md`); the rest is dropped and listed in the report.
- **ERD Studio's own export is read more trustingly** (its header, `ERD_STUDIO_DBML_HEADER_PREFIX`): any role text is kept, a one-to-one Ref's second end is the FK (the export writes it key end first, as DBML reads it, even when the keys say otherwise), and a sticky note linked to a table not in the diagram keeps the link. A foreign file gets only known roles, a key heuristic for one-to-one direction, and a dropped dangling link.
- **Import accepts each property with an `erd_` prefix** (`erd_grain`) as well as plain; export writes plain names.
- **Import into a DBML project** (D19) reuses `planDbmlImport` unchanged and writes the new tables, relationships and diagram as `.dbml` through `writeNewSubjectArea`. DBML-only settings still go under `meta.dbml`, which a `.dbml` table stores as `meta_json`, exactly as in a YAML project; hoisting them to native DBML settings is a follow-up. A file with `use` lines is refused (it is part of a multi-file project, such as another ERD Studio 2.0 project), and so is a Save As target inside the semantic dir for an export ("Save the export outside .erd-studio/: files there are your diagrams' own storage."). A diagram file that declares Tables and no table `use` lines (a dropped-in dbdiagram download) shows the **Import these tables…** banner, and `doctor` raises `import-dbml-file`.
- **Telemetry**: `exportDbmlRich`, `exportAll`, `importDbml`, `importDbmlLayout`, `importDbmlCancelled`, `importDbmlInvalid` (the user's file is not valid DBML) and the error `importDbmlFailed`. Nothing else, and never a name or path. Open Example Diagram runs the same flow with `source: 'example'`: a finished run counts `exampleDiagram` instead of `importDbml` (retries included, since `source` travels in `deps`) and a cancel counts nothing; only `importDbmlFailed` is shared. **Storage and Convert** (D21, append-only on both sides): the features `dbmlProject` (presence, once), `convertToDbml`, `convertToDbmlOffered`, `convertToDbmlDeclined` (Don't Ask Again), `convertToDbmlNotNow`, `convertToDbmlCancelled`, `convertToDbmlRefused` and `dbmlForeignFormatWarned`, and the errors `modelFileDbmlSyntax`, `modelFileDbmlInvalid`, `modelFileDbmlStructure`, `domainLoadDbml` and `convertToDbmlFailed`. A DBML canvas counts as `schemaFormats` `'v5'`.

## Storage rules

- **Splice, never regenerate** (D7): a writer touches only the nodes its edit changes, a derived block (`use` lines, `meta_json`, the PK form) only when its inputs changed, and a file that does not parse is refused. A no-op save is byte-identical.
- **Tolerant per file** (D6): each table file is parsed on its own, each relationships file Ref by Ref, each diagram with everything it does not own blanked. Display never uses a multi-file `rawDb`, so one broken table never blanks a diagram.
- **Selective `use` lines** for tables (`use { table x } from '…'`, never `use *`, which also imports Enums), `use *` only for relationships files; paths are posix, relative to the file, with `.dbml`. The reader also accepts `use *` and a path without the extension.
- **FK end marked possibly null on every Ref written** (D18): `>?`, `?-` (a one-to-one's FK is its second end) and `<>?`. A Ref already in a file keeps its marks byte for byte unless its unit changes.
- **Unqualified, exact-case names** (D2): the file stem equals the declared name (compared case-insensitively on read; `doctor` warns `nameCaseDrift`). `_relationships` is reserved only for new `.dbml` tables.
- **Mixed projects** (D20): a DBML diagram may list only DBML tables and a DBML-owned Ref may name only DBML tables; the refusal says to run Convert Project to DBML. A JSON diagram may list both.
- **Large libraries**: every Ref of a folder lives in that folder's `_relationships.dbml`, so a flat library of thousands of tables concentrates merge conflicts in one file and makes every other DBML tool load every table of that folder for any diagram (one broken table there breaks those diagrams in other tools, never in ERD Studio). Use library folders; 2.0 has no automatic split. `test/unit/dbmlPerformance.test.ts` holds the budgets (10,000 tables, 30,000 Refs).

## Tests

- Storage: `packages/core/test/fixtures/dbml/` holds the DBML twin of every core fixture (`loadDisplayDomain.golden.test.ts` compares each through `normaliseForStorageEquivalence`), the writer cases are in `packages/core/test/dbmlWriterCases/`, `dbmlMultiParser.test.ts` compiles every writer output in all three parsers, and `dbmlCodecLaws.test.ts` holds the codec laws. `test/fixtures/dbml-native/` is the extension's logical-only DBML project; `npm run test:e2e:dbml` converts a copy of `dbt-project` and compares `doctor`, `diff`, `export` and every display before and after.
- Goldens: `packages/core/test/fixtures/golden/<fixture>.rich.dbml` and `<fixture>.dbdiagram` for every core fixture, plus `rich-features` (every mapping row). Regenerate with `UPDATE_GOLDEN=1` only for an intended change; a new golden file name must also go into `EXPECTED_FILES` in `test/unit/displayDomainGolden.test.ts`, or `UPDATE_GOLDEN=1` there deletes it.
- Import fixtures: `test/fixtures/dbml/` (`foreign/` written from dbdiagram's public syntax docs, `erd-studio/` a rich export with its layout, `dbdiagram-pull/` the pulled pair).
- `test/unit/dbmlRoundTrip.test.ts`: export → read → plan → write with the real `TableLibraryService` → load, compared field by field over every core fixture and the `dbt-project` subject areas, in v5 and v6 projects, with relationships in the library or the subject area file; a second export must equal the first. **Every allowed difference is listed, with its reason, in that file's header** — add one there, not in an assertion's tolerance.

## Adding a property

1. Add the name to `dbmlRichProperties.ts` (names already there are a contract: never rename one).
2. Write it in `exportDbmlRich.ts` and read it in `dbmlImport.ts`, both through the constant.
3. Cover it in `rich-features` and regenerate the goldens; the round-trip test must pass without a new exception.
4. Native storage reads and writes the same names (`dbmlRichProperties.ts` is shared): cover the property in a storage writer case and a DBML twin too.
5. A core change ships to npm and the Confluence app on merge: keep it additive (a package PATCH), with a line in `packages/core/CHANGELOG.md`.
