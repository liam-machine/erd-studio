## In a DBML project (2.0)

Everything below holds in memory for every project: relationships hang off the FK-side `SemanticTable`, `canonicalRelationship` decides the owner, `linkKey` / `sameLink` is the identity, `orientLink` the direction and `planRelationshipWrite` the one planner. **Only the storage differs** (spec §2.3–§2.4, `docs/plans/native-dbml-storage.md`):

- A relationship is one `Ref` line, stored once, in a relationships file `<layer>/relationships/<file>.dbml` (any layer); the owner is the canonical `fromModel`. Its ends are qualified as each table declares itself (`gold.fct_order.customer_key >? silver.dim_customer.customer_key`). A composite is one Ref (`a.(x, y) >? b.(u, v)`), split on read into entries sharing a `compositeKey` derived with core's `nextCompositeKey`. The role is the Ref's name.
- The writer always marks the FK end possibly null (`from.fc >? to.tc`, `to.tc ?- from.fc` for a one-to-one, whose FK is the second end, and `from.fc <>? to.tc`), keeps Refs sorted, and keeps one `use { table x } from '…'` line per table the file's Refs name. The reader accepts every operator form; `?` only decides a one-to-one's direction.
- The reader attaches every Ref from **any** relationships file to its owner (`attachRelationships`, core; `locations` says which file holds each link). There is no "home" file and nothing is ever moved: an existing Ref is edited in place, in whatever file holds it, a column change included (match 2b in `planDbmlLibraryWrites`). A Ref whose owner is a YAML table, or no table, is *orphaned*: not attached, reported by `doctor`.
- **Placement of a new Ref** (decision 5, `placeNewRef` in `src/services/dbmlRelationshipsIndex.ts`): the file, in any layer, already holding the most Refs of the same FK table (ties: path byte order); else the FK table's layer default file `<FK layer>/relationships/<FK layer>.dbml`, created when missing. The index is built once per plan from the pre-edit snapshot, so the placement never depends on the order of the edits in one plan. Convert writes every Ref to its FK table's layer default file. The sync plan's `relationshipsPath` is this placement ("where a new Ref goes"); `storedIn` is where an existing one is held.
- **Which files a diagram imports** (decision 6, `relationshipsImportsFor`): exactly the relationships files holding a live Ref between two of its `use` members, plus a file holding a pending line (D27) between two tables it draws; every edit that changes the pairs settles every DBML diagram it touches (`settleDbmlDiagramWrites`). A diagram draws only the relationships in files it imports.
- `planRelationshipWrite` still chooses the owner table; `planDbmlLibraryWrites` (`src/services/dbmlLibraryWrites.ts`, pure) only maps owners to files and builds the edits with core's `editRelationshipsDbml`. It checks `linkKey` across **every** relationships file (`[5001]` in other DBML tools: a new link that any file already holds is refused with the file and line), refuses any unit add while a relationships file does not read (the unreadable file may hold it), and refuses a DBML-owned Ref to a YAML table (D20, "Convert the project to DBML first"). DBML diagrams hold no Refs (`home = 'library'` always), and a relationships file is never deleted automatically.
- Delete Table cascades (D16): the file, the Refs it owns, other owners' Refs to it and every `use` line naming it (found through the index's `filesUsing`, so a hand-added `use` line with no Ref goes too), in one edit. Rename and Move rewrite Ref ends and `use` lines the same way; a move to another schema re-qualifies every end (`requalified`).


## Model folders

**Model folders are organisational only** (issue #76). Domains reference models by name, and names are unique across the whole library; lookup (`TableLibraryService.findTableFile`) is top level first, then folders alphabetically, then the same under v6's `tables/` (#181; written since #182, and where a project on the v6 naming creates new tables; a name in both libraries is drawn from `logical-models/` and reported), and a duplicate elsewhere is *shadowed* (ignored, flagged in the Model Library view). Dot-folders and deeper nesting are not scanned. **Folders are opt-in per project** — `TableLibraryService.groupsByFolder()` is true once any model file sits in a folder named after a configured layer (or the library is empty; callers pass the `layers.json` ids so a hand-made `Staging/` does not count). Only then does a model created from a canvas go to `logical-models/{domain layer}/`; a flat library stays flat, because a file in a folder is invisible to teammates on a version before 1.2.0 and flips everyone's Model Library to the grouped view. A rename keeps the file's folder; v4 migration applies the same rule (decided once, before writing; top level when several layers inline the model). `erdStudio.organizeModelLibrary` (`planOrganizeByLayer`) is the opt-in: it moves top-level files **and files in another configured layer's folder** into the folder of the single layer whose domains reference them, removes a layer folder it empties, never touches folders that are not in `layers.json` (reported in the dialog), and is idempotent. Migration only ever creates a folder for a configured layer. `@erd-studio/core`'s `loadDisplaySubjectArea` cannot list directories, so it probes the top level, then every layer folder alphabetically (the extension's order, so a duplicate resolves identically) — folders not named after a layer are visible to the extension only.

## Model name vs alias

**Model name vs alias.** A model's `name` is its identity everywhere (domain `logical.models`, relationship endpoints, `viewConfig.positions` keys, physical matching) and is unique across the whole library, as dbt model names are across a project — never make a folder part of it. The optional `alias` (model YAML, `SemanticTable.alias` / `DisplayTable.alias`) is the warehouse table name, dbt's `alias` config: two layers each get a `date` table as `silver_date` and `gold_date`, both `alias: date`. The canvas label comes from `computeTableLabels()` (`packages/renderer/src/lib/modelLabels.ts`: `alias ?? name`, schema-qualified when two nodes would read the same); `buildPhysicalSubjectArea` falls back to `(schema, alias ?? name)` only when the name finds nothing, as a pair and never on an ambiguous key. A second file with an existing name is shadowed: `SemanticEditorProvider.warnAboutDuplicateTables()` warns once per session, and `erdStudio.resolveDuplicateModel` (planner in `src/services/duplicateModelResolver.ts`) renames it to `{folder}_{name}` with `alias: {name}` and repoints that layer's domains in one `WorkspaceEdit`.

## Relationships

**Relationships are defined once, in the model library (issue #126).** A model yml may carry `relationships:` (`SemanticTable.relationships`, `TableRelationship` = `Relationship` minus `fromModel`, the file's own model). **The file is always the many (FK) side's (#133):** `canonicalRelationship()` (`packages/core/src/relationships.ts`) turns a `one-to-many` into the swapped `many-to-one` and leaves `one-to-one` / `many-to-many` as drawn; `upsertLibraryRelationship`, `routeToLibrary`, `planMoveToLibrary` / `resolveConflict` and the CLI's relationship fixes apply it (`set-cardinality` / `remove-relationship` name the stored entry's file, and `movesFrom` when a fix moves it), so a new fact never touches its dimensions' files. The same two columns joined either way round are **one link** — core's `linkKey` / `sameLink` (unordered, case-insensitive; `reverseRelationship` reads one from its other end) is the only identity: the reverse is refused as a duplicate, `mergeLibraryRelationships` draws it once (the library entry wins), and `DiscrepancyService` matches it whichever end each stage reads it from (a mismatch is reported in the source's direction). **Key evidence has one helper:** core's `keyEvidenceOf(model, columns, dbt?)` / `keyEvidence(model, column, dbt?)` (`packages/core/src/keyEvidence.ts`) → `whole-key` | `not-key` | `unknown` for a column set — the model's flags first (the full `isPrimaryKey` or `isNaturalKey` set is the key; in a model that flags any key, any other set is not), and only for a model that flags none dbt's tests (`buildDbtKeyIndex` over yml + manifest: a `unique` test, a `unique_combination_of_columns`, a column a `relationships` test leaves; `unique` beats `not-unique` in any order). Flags always win. `contradictsKeys` / `contradictsKeysOf` (column sets) and `keyedRelationship` ("keys win") build on it, and so does `keysContradictedRelationships` (#163): `toDisplaySubjectArea` (logical stage, optional `dbtKeyIndex`) sets `DisplayRelationship.keysContradict` on a stored entry the keys contradict — read as its `canonicalRelationship`, a composite on its column sets — never turning it round on read; the ⚠ / Turn round (⇄) on `FkEdge` and in the details panel (not for viewers), the exporters' comment (`backwardsRelationshipNote`, carried through `RawLink`), doctor's `erd.backwardsRelationships` and `maybeOfferTurnRound` (after the move offer, only when it did not ask; `RELATIONSHIP_BACKWARDS_DECLINED_KEY`) all read it; several Turn rounds are one write through `planRelationshipWrites`, which folds `planRelationshipWrite` so each op builds on the last, and `orientLink` (`packages/core/src/orientLink.ts`) is the one direction rule: symmetric, and **not decided** when nothing says — the New Relationship dialog then asks ("Which way does this relationship point?", two model-named choices, Create disabled; words in `webview/lib/relationshipDialog.ts`; the answer, not the storage, is what it asks for: the Ref or yml entry records it either way), never a default from drag order. The index reaches the read winner (`getSubjectArea(path, { dbtKeyIndex })` from the canvas and `computeSubjectAreaDiff`), the write planner, Move (`loadDbtKeyIndex` dep) and the editable payload (`withDbtKeyHints` → `DisplayColumn.dbtKey`; `isForeignKeyDeclared` is the stored FK flag). A drag is oriented by `orientDraggedRelationship` (`webview/lib/relationshipDirection.ts`, over `orientLink`); the dialog offers **Mark … as primary key** when the one side flags no key (ticked when dbt says the columns are unique or the user just answered the direction question) (`markKey` on `addRelationship` / `editRelationship`, `validateMarkKey`, applied by the planner in the same edit and refused if a key appeared), warns about a contradiction but allows **Create anyway** (`keysContradictionWarning`), ⇄ refuses one, and the move command re-homes library entries `keyedRelationship` moves (`planRehome`, entry by entry, never a sibling copy), leaving in place copies that disagree and any file `relationshipsRewriteLoses` flags. A link stored twice — in the library, or in one domain file — is drawn from a fixed winner, whatever the file or entry order: a copy in its home (not one-to-many), then one not leaving its model's whole key, then the lowest model name, then the lowest content (a labelled copy before its unlabelled twin). **Every canvas relationship edit is planned by the pure `planRelationshipWrite(op, { home, models, domainRelationships })`** (`src/services/libraryRelationships.ts`), run inside the provider's `commitRelationshipWrite` (one `applySubjectAreaEdit`, one undo step); the exhaustive checker (`test/unit/relationshipStateSpace.*`) calls the same function. An edit acts on the link: every copy, in both model files and the domain file, is folded into one entry in its home with the line's role (else any copy's; ⇄ / a context-menu cardinality is refused while copies carry different roles), and a delete drops every copy, then names other diagrams that still draw their own copy (`diagramsStillDrawing`, an info message, nothing written). An optional `role` (label, not identity; `normaliseRelationshipRole`, ≤ `RELATIONSHIP_ROLE_MAX_LENGTH` = 60) rides on `Relationship` / `DisplayRelationship` / `FkEdgeData`, the `addRelationship` / `editRelationship` payloads (an `updateRelationship` keeps the stored one) and every writer; 1.6.7 and earlier drop it when they rewrite that list. `@erd-studio/core`'s `mergeLibraryRelationships()` — called by `parseStageData`, so the canvas, CLI `diff`, MCP and the viewer all agree — draws the domain's own `logical.relationships` first, then every library relationship whose two ends are both in the domain; on the same endpoints (`relationshipKey`, case-insensitive) the library's cardinality wins with a warning. **Like layer folders it is opt-in per project, decided by what is on disk** (`usesLibraryRelationships` in `src/services/libraryRelationships.ts`): the library is the home for new relationships once any model file holds one, or while no domain file holds any (`SubjectAreaService.countSubjectAreaFileRelationships`) — so a new project starts there and a project with per-domain edges keeps them until `erdStudio.moveRelationshipsToLibrary` (`planMoveToLibrary` → modal from `describeMovePlan`: why, where by model file, every entry turned round and every diagram copy the library's version replaces (`turned`, `keptLibrary`), conflicts → one QuickPick per conflict over whole definitions — cardinality, role, and the FK end of a one-to-one — `resolveConflict` with the user's pick or left in place, never picked by the extension; diagram copies are stored as `keyedRelationship` reads them, a many-to-many from its lower end, so one run leaves nothing for a second; `applyMoveToTable` applies a settled plan, shared with the checker). `SemanticEditorProvider.maybeOfferRelationshipMove()` offers that command on a canvas `ready`, once a session, unless `RELATIONSHIP_MOVE_DECLINED_KEY` (workspaceState) is set, and only when `sharedRelationshipCount()` > 0 in a per-domain project; it writes nothing. In library mode an edited domain-file relationship moves to the library, and column rename/remove and model rename rewrite other models' entries through `applyTableEdit`'s `alsoSave` / `modelFiles.save`; Draw from dbt, Add models from dbt and Add Existing Model route through `routeToLibrary`, which never overwrites a link the library stores (its cardinality and role stay) and leaves a link another diagram draws from its own copy in the new domain's file (`drawnDiagramCopies`). Removing a model from a domain leaves its library relationships alone. **Ends spelled in another case** are respelled on read (`respellRelationship`, in `mergeLibraryRelationships` and the v4 reader) and a write respells only the entry it touches; every cascade matches without case (#133 L4). **Self-references** (`emp.mgr → emp.id`) are ordinary links stored in the model's own file; only a column pointing at itself is refused (`validateRelationshipEnds`); several loops on one node nest (`FkEdgeData.loopIndex`). **Composite foreign keys** (#133 L2) are one entry per column pair sharing `compositeKey` (never an array form — 1.6.7 would delete it; `mixed167.compositeKey.test.ts`); `compositeGroupProblem` decides validity, the read path keeps the key only on a valid group (`assembleGroups`), and a write acts on the group the canvas draws (`drawnGroupOf`): add / edit carry `extraPairs` (`validateExtraPairs`; singles already stored are taken in, a pair another group owns is refused), ⇄ / delete / column removal act on every member, and Move moves a group all or nothing (`planGroupMoves`, `planRehome` batches). The renderer folds a group into one edge (`foldComposites`, `relationshipDisplayKey`); the physical stage reads dbt ≥ 1.9 `foreign_key` constraints and `dbt_constraints.foreign_key` tests. **A rename reaches other diagrams' own copies** (#133 L5): `applySubjectAreaEdit`'s `otherDomains` rewrites every other v5 domain file a rename changes in the same `WorkspaceEdit`, refusing by name one open with unsaved edits.
