# Getting Started panel, launcher and erd-studio CLI

> Moved out of the root `CLAUDE.md` so it loads only when needed. Read before touching `GettingStartedPanel.ts`, `src/types/gettingStarted.ts`, `aiAssistants.ts`, `cliLauncherService.ts`, `dbtEnv.ts` or `src/cli/`. The setup skill itself is in `src/harness/CLAUDE.md`.

Onboarding for a beginner who has a dbt project and an AI coding assistant — **Claude Code, GitHub Copilot, Codex, Gemini CLI or Cursor**: a Welcome panel with a short getting-started video, a one-click **Set Up My AI Helper**, the `/erd-studio-setup` skill it installs (an [Agent Skill](https://agentskills.io), into `.claude/skills/` and/or `.agents/skills/`), and the read-only `erd-studio` CLI the skill runs to check its work. End-to-end tested with Claude Code only; the other four read the same skill from the open standard's `.agents/skills/` folder.

- **Commands.** `erdStudio.showGettingStarted` (**Watch Getting Started Video**, `$(play-circle)`, also `navigation@8` in the domain tree title bar and a link in its welcome view) is pre-registered and works without a project. `erdStudio.setupAiHelper` (**Set Up My AI Helper**, `$(sparkle)`) is registered on the project path only and gets the ordinary fallback stub without one. Both are in `NO_LEGACY_ALIAS`. `erdStudio.trySampleProject` (**Try the Sample Project**, `$(beaker)`, also a link in the domain tree's welcome view) is pre-registered and in `NO_LEGACY_ALIAS`: `trySampleProject()` (`GettingStartedPanel.ts`) shows a modal confirm (`SAMPLE_CONFIRM_MESSAGE`, **Download**), then — when `vscode.extensions.getExtension('vscode.git')` exists — runs `git.clone` with the fixed `SAMPLE_REPO_CLONE_URL` (VS Code asks for the folder and offers to open it); with no Git extension, or if `git.clone` throws, an info message (`SAMPLE_FALLBACK_MESSAGE`: Download ZIP, unzip, Open Folder) whose **Open on GitHub** opens the fixed `SAMPLE_REPO_URL`. Both URLs are constants in `src/types/gettingStarted.ts` (vscode-free) and never come from a webview. The sample repo (`liam-machine/erd-studio-sample`, a Kimball jaffle-shop on DuckDB shipping `target/manifest.json` + `catalog.json`) is **not** bundled in the VSIX.
- **The panel** (`src/providers/GettingStartedPanel.ts`, view type `erdStudio.gettingStarted`) is a singleton `WebviewPanel` with no serializer — it simply closes on reload. Its protocol is **its own union** in `src/types/gettingStarted.ts`, deliberately separate from the canvas's `messages.ts` (different webview, different host class, no physical-stage allowlist): to host `ready`, `refreshStatus` (the **Re-check** button — status is never cached), `setupAiHelper`, `copyPrompt` (optional `assistant`, validated against the five ids; omitted means Claude Code), `openClaude`, `openCopilotChat`, `openDomain`, `drawFromDbt` (no payload; runs `erdStudio.drawFromDbt`, then posts a fresh status), `openExternal` (`target` is one of `claudeCodeDocs` / `copilotDocs` / `codexDocs` / `geminiCliDocs` / `cursorDocs` / `videoOnline` / `dbtInstallDocs` / `sampleRepo` / `sampleCodespaces`, mapped to fixed URLs in `GETTING_STARTED_EXTERNAL_URLS` — a URL is never accepted from the webview), `trySample` (no payload; runs `erdStudio.trySampleProject`) and `videoError`; to webview `status` (`GettingStartedStatus`: project, `harness` per skill folder `{ claude, agents }`, launcher `missing`/`ready`/`stale`, derived `helper` state, Claude Code `missing`/`extension`/`cli`, detected `assistants`, domain count, and an optional text-only `summary` line from `computeProjectSummary()` via the optional `getProjectSummary` dep — `null` without a project or when it throws) and `setupResult` (outcome plus `groups`: every written path with a one-sentence plain explanation). `isGettingStartedToHost()` validates every inbound message, and every type has a live sender in the panel script and a handler on the host (the test checks both). With a project the panel has two sections, numbered in the order the cards show. **Your diagram** comes first: with domains, **Open your diagrams** (primary, `openDomain`) then **Draw another area from dbt**; with none, **Draw your dbt project — no AI needed** (primary **Draw from dbt**) plus a small **Create a blank diagram** link (`openDomain`). Then **Enrich with your AI assistant (optional)**, three cards — **Your AI assistant** (a ✓ chip per detected assistant; none found → **Get Claude Code** first, then links to the other four, and **Re-check**), **Set up my AI helper** (names the assistants it installs for), **Start the guided setup** (one row per detected assistant with exactly what to type — `/erd-studio-setup`, `$erd-studio-setup` for Codex, the sentence "Set up ERD Studio for this dbt project" for Gemini CLI, which has no per-skill command — a **Copy** button each, **Open Claude Code** and **Open Copilot Chat**; while `helper` is `missing` the card's state is `notready` and it shows `HELPER_FIRST_MESSAGE` ("Set up your AI helper first…") instead of the rows, and the host's `openClaude` / `openCopilotChat` handlers re-check `getStatus()` and offer **Set Up My AI Helper** rather than launching). There is no separate open-the-canvas card. With no project the steps collapse to "Open a folder containing dbt_project.yml" plus a **No dbt project yet? Try the sample** card (`.gs-sample`, primary **Try the sample project** button, and an **Open in Codespaces** button — `openExternal` `sampleCodespaces`, `SAMPLE_CODESPACES_URL` — rendered only while `SAMPLE_CODESPACES_LIVE` is true; it is `false` until the sample repo's devcontainer and diagram reach its `main`, which must happen **after** this extension release is published, and the walkthrough / README Codespaces links come back in the same follow-up). With a project, a small "New to this? Try it on the sample project first" link (`.gs-sample-link`) sits above the step cards. Both post `trySample`; visibility is CSS-driven by `data-project`. Every per-assistant element is rendered up front from `AI_ASSISTANTS` and shown/hidden by the script; no HTML is built from host data.
- **Assistant detection** (`detectAssistants()` in `src/types/aiAssistants.ts`, pure; the host's `detectAiAssistants()` gathers the inputs and **never spawns anything**): Claude Code = `claude` on PATH or in its installer homes (`locateClaudeCli`) or the `anthropic.claude-code` extension; GitHub Copilot = `github.copilot-chat` / `github.copilot` or `copilot` on PATH; Codex = `openai.chatgpt` or `codex`; Gemini = the Gemini CLI Companion `google.gemini-cli-vscode-ide-companion` or `gemini` (not `google.geminicodeassist`, Gemini Code Assist — a different product); Cursor = `vscode.env.appName` contains "Cursor" or `cursor-agent` on PATH. `isOnPath()` is the generic PATH(+PATHEXT) scan. `recommendedSkillTargets(assistants)`: `claude` when Claude Code is detected; `agents` when Codex or Gemini is, or Copilot / Cursor without Claude Code (both read `.claude/skills/` too, so installing both folders next to Claude would list every skill twice); **both when none is** (the user may install their assistant after setup — this default can show duplicates in Copilot/Cursor).
- **CSP and media.** `buildGettingStartedCsp()`: `default-src 'none'`, `img-src`/`media-src` limited to `webview.cspSource`, and `style-src`/`script-src` by **nonce only** — no `unsafe-inline`, no inline `style=` or event-handler attributes (tested). `localResourceRoots` is `media/onboarding/` only. Captions are added from `GETTING_STARTED_CUES` with `video.addTextTrack()` + `VTTCue` — there is no `<track>` and no shipped `.vtt`. A `<video>` error posts `videoError` and swaps in the poster with a **Watch in your browser** link; the transcript is always on the page.
- **Codec decision.** The mp4 is **H.264 (High, yuv420p, `+faststart`) with MP3 audio** (64 kbps mono 44.1 kHz), at most 8 MB and 65 s (`video/script.yaml` `maxDuration`; the product copy calls it a one-minute video) — the combination the VS Code webview guide documents ("use mp3 for the audio track"). Never AAC: VS Code's `libffmpeg` has **no AAC decoder**, so AAC-in-MP4 plays silently ([vscode#167685](https://github.com/microsoft/vscode/issues/167685)). `video/encode.sh` and `test/unit/gettingStartedMedia.test.ts` both assert h264 + mp3 (the esds object type `0x6B`, since MP3 and AAC share the `mp4a` entry), faststart, the size ceiling and exactly two files in `media/onboarding/`. Forks without H.264 (VSCodium-style builds) get the poster fallback.
- **Sound on by default.** The panel script calls `play()` unmuted first; only if the editor's autoplay policy rejects it does it fall back to muted playback with a centred **Turn on sound** button.
- **Set Up My AI Helper** (`runSetupAiHelper()`, shared by the command and the panel; never throws): (1) `HarnessService.installRecommended(root, { replaceUnmanaged: false, assistants })` — the skill folders `recommendedSkillTargets(assistants)` picks (`claude` → `.claude/skills/`, `agents` → `.agents/skills/`); (2) on `needs-confirmation`, a modal naming the hand-written file(s) with **Replace** (re-run with `replaceUnmanaged: true`) or **Keep mine** (re-run with `keepUnmanaged: true`: everything that is not hand-written is installed — schema skill, SYNC.md, hook, setup skill, the gitignore step — and each hand-written SKILL.md is left exactly as it is; the modal's detail, `keepMineInstalls(unmanaged, targets)`, names what that still installs); (3) `CliLauncherService.install()` — a launcher failure is reported but does not undo the skill install; (4) the message is `setupReadyMessage(assistants)`, naming the assistants; from the palette it is an info message with **Open Claude Code** (Claude detected) / **Open Copilot Chat** (Copilot detected) / **Copy prompt**; from the panel, the result renders inline instead (no toast). A cancelled modal shows nothing. This is the **only** route that installs the launcher.
- **Starting Copilot.** `openCopilotChat()` copies `/erd-studio-setup`, then runs `workbench.action.chat.open` (a string command id — no typings newer than 1.85) with `{ query, isPartialQuery: true, mode: 'agent' }` so the prompt is typed but not sent, in Agent mode (older builds ignore `mode`), falling back to a bare open if that argument form throws, and to the Copilot setup page when the command does not exist. Its message says how to switch to Agent mode if the chat is not in it; with a nested dbt project it adds that Copilot looks for skills in the folder VS Code has open. Codex, Gemini CLI and Cursor get Copy plus a one-line hint only.
- **Starting Claude.** `openClaudeCode()` detects the `claude` CLI by scanning `PATH` (+`PATHEXT` on win32, plus `~/.local/bin` and `~/.claude/local`) in JS — it never spawns `claude` — then the `anthropic.claude-code` extension. CLI route: a modal showing the exact command and folder, then a new terminal named **Claude Code** with `cwd` = the dbt project root and `MSYS_NO_PATHCONV=1` (so Git Bash does not turn `/erd-studio-setup` into a path) running `claude "/erd-studio-setup"` — typed with `sendText` when `claude` is on `PATH` (that line parses the same in bash, zsh, PowerShell and cmd), but an absolute path found off `PATH` is the terminal's own process (`shellPath` + `shellArgs`, `claudeTerminalLaunch()`), so no shell ever parses or expands it. Extension route: copy `/erd-studio-setup` and run the first available command in `CLAUDE_CODE_OPEN_COMMANDS`; with a nested dbt project the message offers an **Open <folder>** button (`vscode.openFolder`), because the extension's panel starts in the open workspace folder. Neither: open the Claude Code docs. When the workspace folder is not the dbt root, **Copy** gives `cd '<abs dbt root>' && claude "/erd-studio-setup"` on POSIX and `Set-Location -LiteralPath '<root>'; claude "/erd-studio-setup"` on Windows (PowerShell 5.1 has no `&&`) — single-quoted because the folder name comes from the file system and double quotes would still expand `$(…)`; a root containing a control character falls back to the bare prompt. The skill lives in the dbt root's `.claude/skills/`, and every success message says to restart Claude Code or run it from that folder.
- **The launcher** (`src/services/cliLauncherService.ts`, no `vscode`, every input injected): `~/.erd-studio-cli/lib/cli.js` (a **copy** of `dist/cli.js`, so an extension update deleting its old folder cannot break the shim), `launcher.json` (`extensionVersion`, `execPath`, `cliSha256`, `writtenAt`, `runtimeVerified`), `bin/erd-studio` (POSIX sh, 0755, written on **every** platform because Claude Code's Bash tool is Git Bash on Windows) and `bin/erd-studio.cmd` (Windows only). The shims prefer a `node` >= 18 on PATH and fall back to VS Code's Electron with `ELECTRON_RUN_AS_NODE=1` set only on the exec line (sh) or inside `setlocal` (cmd) — never exported. `install()` first checks that the Electron runtime actually runs a script (5 s timeout) and omits that branch if not. Every write is atomic (unique temp name, then rename). `refreshIfInstalled()` does nothing without a `launcher.json`; otherwise it rewrites when the running version is the same or newer (`compareVersions`) and something changed, or when the recorded `execPath` no longer exists — a newer recorded version is left alone (`skipped-newer`), and an `execPath`-only difference at the same version is not rewritten while the recorded runtime still exists, so two VS Code installs do not keep overwriting each other. `applySemanticDir()` never rewrites the `~/.erd-studio-cli` path in skill text (its `(?![\w-])` lookahead). No `PATH` changes: the skill always calls the absolute path.
- **The CLI** (`src/cli/`, `dist/cli.js`, read-only): `doctor [--no-dbt] [--dbt <path>] [--trust-venv]` (project, dbt executable and flavour via `dbtEnv` — `core-v1` / `fusion-v2` / `cloud-cli` — profiles, deps, artifact freshness, ERD layers / domains / format issues, the file naming `erd.naming` (`v5` / `v6` / `mixed`, `projectNamingOf()` over core's `detectProjectNaming` — the extension's own answer — and, when not `v6`, `erd.namingMigration`: `{ moves, rewrites, refusals, preview }`, what **Migrate to the New File Naming** would change, from the same `planNamingMigration`; a preview only, never a next step; with `erd.tablesFolderIsLayer` and `erd.namingConflicts` → a `resolve-naming-conflicts` step; a v5 / v6 key mix gets `fix-subject-area-naming` instead of `migrate-v5`), `harnessStatus()`, and ordered `nextSteps` with ready-to-run commands; a dbt inside a project-local venv that is not also what `PATH` resolves to is **never run** without `--trust-venv` — `doctor` is pre-approved in the skill's `allowed-tools`, and a cloned repo can ship any `.venv/bin/dbt`, so it is reported as `dbt.untrustedVenvDbt` with a `confirm-venv` step and the skill passes the flag only after showing the user the path. For the same reason the skill pre-approves only subcommand-scoped rules for bare `dbt` (`parse`, `docs generate`, `compile --write-catalog`, `debug`, `deps`, `--version`); a venv or absolute-path dbt always goes through Claude Code's own prompt. `.cmd`/`.bat` shims are spawned through cmd.exe with the path double-quoted by `dbtVersionSpawn()`, which refuses a path containing `"`, `%` or a line break), `inventory [--summary] [--models a,b]`, `diff (--domain <path> | --all) [--strict]`, `export (--domain <path> | --all) --format mermaid|dbml|dbml-rich|dbml-layout` and `version`. `inventory` (both shapes) carries **`conventions`** (`layering`, `shape` with `confidence` / `evidence` / `alternatives` / `sources`, `history.snapshots`, `meta`, `suggestedLayer`) from `src/cli/conventions.ts` and `src/cli/metaConventions.ts` — pure heuristics, no AI; read those files and their tests before changing a threshold or a signal. dbt's own `meta:` reaches the CLI only (`YmlParserService` / `manifestExtractor` via core's `readMeta()`); `buildPhysicalSubjectArea`, the diff and the canvas never read it. Shared flags: `--project` (the folder holding `dbt_project.yml`; without it, cwd → ancestors → depth-3 down), `--semantic-dir`, `--json`, `--quiet`, `--verbose` (otherwise the shared services' `console.*` output is silenced so it never mixes into the JSON Claude reads), `--help`, `--version`. `diff` is `computeSubjectAreaDiff(…, 'logical')` + `buildSyncPlan(report, allSelections(report, 'physical'))` turned into `fixes`, each `blocking` or `advisory`; a domain is **clean** at zero blocking fixes, and a `set-type` whose physical type is empty (dbt knows no type yet) is advisory unless `--strict`. A phantom model collapses to one `resolve-phantom` fix; v4 domains report `needsMigration: true` and no fixes; under `--all` a domain that fails to load gets its own `error` rather than stopping the run, and `--all` over a missing semantic dir or zero domains is exit 3 (`no-semantic-dir` / `no-domains`) — never a clean result over nothing. `export` (`src/cli/export.ts`) prints one domain's logical stage via `exportSubjectAreaFile` (with `dbtKeyIndexOf(ymlData, manifest)`, as `computeSubjectAreaDiff` passes it, and the `LayerService` for the layer's colour and label), so its bytes equal the extension's and core's goldens; human output is the export text alone on stdout (`> schema.dbml` works), `--json` is `{ cliVersion, domain, format, fileName, content }` with `domain` project-relative, and `--format` is matched without case. Formats: `mermaid`, `dbml` (portable, ERD Studio's fields in notes), `dbml-rich` (DBML for dbdiagram.io: the fields as custom properties, DBML 9.1+, its header naming `<name>.dbdiagram`) and the CLI-only `dbml-layout` — that `.dbdiagram` file itself (dbdiagram's layout JSON, the table positions), so `--format dbml-rich > sales.dbml` plus `--format dbml-layout > sales.dbdiagram` is what `dbdiagram push sales.dbml` reads. It takes exactly one `--domain`, or `--all` (never both — a usage error): every domain via `exportSubjectAreaFiles`, the same files and names **Export All Diagrams…** writes (by layer then file; `<layer>-<name>` when two layers hold a domain of the same name, then `-2`, `-3`, ignoring case), human output a JSON list of `{ fileName, content }` (with `dbml-rich` each `.dbml` followed by its `.dbdiagram`; with `dbml-layout` only the `.dbdiagram` files) and `--json` `{ cliVersion, format, files: [{ domain, fileName, content }], skipped: [{ domain, error: { code, message } }] }`. Under `--all` a domain that fails to load is skipped (a `skipped:` line on stderr in human mode) and the run exits 1; a missing semantic dir or zero domains is exit 3 (`no-semantic-dir` / `no-domains`), as `diff --all` (`listAllSubjectAreas`). `export` has no `--out` and never writes a file; load errors use `diff --domain`'s codes through the shared `describeSubjectAreaError` (exit 3), and a v4 domain exports normally rather than asking for migration. Sync-plan paths (`modelContext.*`) are forward-slash on every platform. Paths in the JSON are project-relative; error JSON is `{ cliVersion, error: { code, message } }` with no absolute paths.

| Exit code | Meaning |
|---|---|
| 0 | Success; for `diff`, every domain is clean. `doctor` exits 0 even with no project — reporting that is its job |
| 1 | `diff` found blocking drift, a v4 domain or a per-domain error; `export --all` skipped a domain it could not read |
| 2 | Usage error (unknown flag, flag on the wrong subcommand, `diff` with neither `--domain` nor `--all`, `export` without `--domain` (or `--all`) / `--format`, with more than one `--domain`, with both `--domain` and `--all`, or an unknown format) |
| 3 | Environment error: no `dbt_project.yml`, domain missing / invalid / unsupported, unknown layer |
| 4 | Internal error (stack to stderr) |
| 5 | Reserved for the **shim**: no runnable runtime (`launcher-stale`) — reopen the project in VS Code |
