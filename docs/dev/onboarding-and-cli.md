# Getting Started panel, launcher and erd-studio CLI

> Moved out of the root `CLAUDE.md` so it loads only when needed. Read before touching `GettingStartedPanel.ts`, `src/types/gettingStarted.ts`, `aiAssistants.ts`, `cliLauncherService.ts`, `dbtEnv.ts` or `src/cli/`. The setup skill itself is in `src/harness/CLAUDE.md`.

Onboarding has three starting points — no folder open, a folder without dbt (logical-only: start from scratch, from the built-in example or from DBML) and a dbt project (Draw from dbt) — plus an optional route for an AI coding assistant (**Claude Code, GitHub Copilot, Codex, Gemini CLI or Cursor**). The pieces: a Welcome panel with a short getting-started video, a one-click **Set Up My AI Helper**, the `/erd-studio-setup` skill it installs (an [Agent Skill](https://agentskills.io), into `.claude/skills/` and/or `.agents/skills/`), and the read-only `erd-studio` CLI the skill runs to check its work. End-to-end tested with Claude Code only; the other four read the same skill from the open standard's `.agents/skills/` folder.

- **Commands.** `erdStudio.showGettingStarted` (**Watch Getting Started Video**, `$(play-circle)`, also `navigation@8` in the domain tree title bar and a link in its welcome view) is pre-registered and works without a project. `erdStudio.setupAiHelper` (**Set Up My AI Helper**, `$(sparkle)`) is registered on the project path only and gets the ordinary fallback stub without one. Both are in `NO_LEGACY_ALIAS`. `erdStudio.trySampleProject` (**Try the Sample Project**, `$(beaker)`, also a link in the domain tree's welcome view) is pre-registered and in `NO_LEGACY_ALIAS`: `trySampleProject()` (`GettingStartedPanel.ts`) shows a modal confirm (`SAMPLE_CONFIRM_MESSAGE`, **Download**), then — when `vscode.extensions.getExtension('vscode.git')` exists — runs `git.clone` with the fixed `SAMPLE_REPO_CLONE_URL` (VS Code asks for the folder and offers to open it); with no Git extension, or if `git.clone` throws, an info message (`SAMPLE_FALLBACK_MESSAGE`: Download ZIP, unzip, Open Folder) whose **Open on GitHub** opens the fixed `SAMPLE_REPO_URL`. Both URLs are constants in `src/types/gettingStarted.ts` (vscode-free) and never come from a webview. The sample repo (`liam-machine/erd-studio-sample`, a Kimball jaffle-shop on DuckDB shipping `target/manifest.json` + `catalog.json`) is **not** bundled in the VSIX. `erdStudio.openExampleDiagram` (**Open Example Diagram**, in `NO_LEGACY_ALIAS`) is registered on the project path, so it works in any folder (an empty window gets the ordinary "Open a folder first" fallback stub): `openExampleDiagram()` (`src/commands/openExampleDiagram.ts`) feeds the inline `EXAMPLE_DBML` — the sample repo's six coffee-shop mart tables as a star schema, with ERD Studio's custom DBML properties — through the ordinary `importDbml` flow with only the file-reading half of the UI swapped (`exampleDbmlUi`), so the user still names the diagram and sees the dry-run summary before anything is written, and a plain folder gets `.erd-studio/` and `layers.json` only on that confirm. It goes in the `gold` layer when the project has one (else the import asks), has no `.dbdiagram` layout (the canvas lays it out on open), and ships no file (the VSIX 60-file cap). It is offered in the plain-folder sidebar welcome, the walkthrough's `newDiagram` step and the panel's logical-only state.
- **The panel** (`src/providers/GettingStartedPanel.ts`, view type `erdStudio.gettingStarted`) is a singleton `WebviewPanel` with no serializer — it simply closes on reload. Its protocol is **its own union** in `src/types/gettingStarted.ts`, deliberately separate from the canvas's `messages.ts` (different webview, different host class, no physical-stage allowlist): to host `ready`, `refreshStatus` (the **Re-check** button — status is never cached), `setupAiHelper`, `copyPrompt` (optional `assistant`, validated against the five ids; omitted means Claude Code), `openClaude`, `openCopilotChat`, `openDomain`, `drawFromDbt` (no payload; runs `erdStudio.drawFromDbt`, then posts a fresh status), `openExternal` (`target` is one of `claudeCodeDocs` / `copilotDocs` / `codexDocs` / `geminiCliDocs` / `cursorDocs` / `videoOnline` / `dbtInstallDocs` / `sampleRepo` / `sampleCodespaces`, mapped to fixed URLs in `GETTING_STARTED_EXTERNAL_URLS` — a URL is never accepted from the webview), `trySample` (no payload; runs `erdStudio.trySampleProject`), `openFolder` (no payload; VS Code's own folder picker), `createDomain`, `importDbml` and `openExample` (no payload; run `erdStudio.createDomain` / `erdStudio.importDbml` / `erdStudio.openExampleDiagram` — fixed command ids, never taken from the webview — then post a fresh status) and `videoError`; to webview `status` (`GettingStartedStatus`: project, `harness` per skill folder `{ claude, agents }`, launcher `missing`/`ready`/`stale`, derived `helper` state, Claude Code `missing`/`extension`/`cli`, detected `assistants`, domain count, `logicalOnly?: boolean` (a folder is open but its root has no `dbt_project.yml` — the resolution's `hasDbt` is false), and an optional text-only `summary` line from `computeProjectSummary()` via the optional `getProjectSummary` dep — `null` without a project or when it throws) and `setupResult` (outcome plus `groups`: every written path with a one-sentence plain explanation). `isGettingStartedToHost()` validates every inbound message, and every type has a live sender in the panel script and a handler on the host (the test checks both). The page has **three states**, CSS-driven from the status: **no folder open**, **logical-only** (a folder without dbt) and **dbt project** (the cards below, unchanged). The **logical-only** state's headline is "Design your data model in your repo; compare it with dbt when you're ready.", its first step **Draw your first diagram** (primary **New diagram** → `createDomain`), with a "New to data modelling?" **Open Example Diagram** link (`openExample`), then "Have a DBML file?" with **Import DBML…** (`importDbml`), the AI steps (**Set up my AI helper**, and **Start the guided setup** with `LOGICAL_SETUP_TEXT` — the skill's no-dbt route designs a first diagram with the user — and "Start your assistant in your project folder", without the word dbt) and "Using dbt? Open its folder to compare". In the logical-only and no-folder states the video does **not** autoplay: the poster shows with a **Watch the one-minute dbt tour** link (the video is a dbt tour). With a dbt project the panel has two sections, numbered in the order the cards show. **Your diagram** comes first: with domains, **Open your diagrams** (primary, `openDomain`) then **Draw another area from dbt**; with none, **Draw your dbt project — no AI needed** (primary **Draw from dbt**) plus a small **Create a blank diagram** link (`openDomain`). Then **Enrich with your AI assistant (optional)**, three cards — **Your AI assistant** (a ✓ chip per detected assistant; none found → **Get Claude Code** first, then links to the other four, and **Re-check**), **Set up my AI helper** (names the assistants it installs for), **Start the guided setup** (one row per detected assistant with exactly what to type — `/erd-studio-setup`, `$erd-studio-setup` for Codex, the sentence "Set up ERD Studio for this project" (`GEMINI_SETUP_SENTENCE`) for Gemini CLI, which has no per-skill command — a **Copy** button each, **Open Claude Code** and **Open Copilot Chat**; while `helper` is `missing` the card's state is `notready` and it shows `HELPER_FIRST_MESSAGE` ("Set up your AI helper first…") instead of the rows, and the host's `openClaude` / `openCopilotChat` handlers re-check `getStatus()` and offer **Set Up My AI Helper** rather than launching). There is no separate open-the-canvas card. With no folder open the steps collapse to an **Open the folder your data model lives in** card (any folder works; **Open a folder…** posts `openFolder`) plus a **Using dbt? Try the sample project** card (`.gs-sample`, primary **Try the sample project** button, and an **Open in Codespaces** button — `openExternal` `sampleCodespaces`, `SAMPLE_CODESPACES_URL` — rendered only while `SAMPLE_CODESPACES_LIVE` is true; it is `false` until the sample repo's devcontainer and diagram reach its `main`, which must happen **after** this extension release is published, and the walkthrough / README Codespaces links come back in the same follow-up). With a project, a small "New to this? Try it on the sample project first" link (`.gs-sample-link`) sits above the step cards. Both post `trySample`; visibility is CSS-driven by `data-project`. Every per-assistant element is rendered up front from `AI_ASSISTANTS` and shown/hidden by the script; no HTML is built from host data.
- **Walkthrough and sidebar welcome** (`package.json`). The walkthrough `erdStudio.getStarted` ("Design your data model in Git — from scratch, from DBML or from dbt — then let your AI assistant fill in the detail.") has seven steps, each shown by its `when`: `watch` (dbt project), `openProject` (`workspaceFolderCount == 0`, completes on `onContext:erdStudio.hasProject`), `newDiagram` (`!erdStudio.hasDbtProject`, **New Diagram** → `erdStudio.createDomain`, plus a second **Open Example Diagram** link; completes on either command — the example has no step id of its own), `draw` (dbt project), `importDbml` (always, **Import DBML…**), `enrich` (always; **Set Up My AI Helper**, then `/erd-studio-setup`) and `sample` (`!erdStudio.hasDbtProject`, "Using dbt? Try the sample project"). Each step has an SVG in `media/walkthrough/` (new ones only while the VSIX stays at or under 60 files); `extension.activate.test.ts` pins the ids. The domain tree's `viewsWelcome` has one entry per state: empty window (**Open Folder**), plain folder with no diagrams (`erdStudio.hasProject && !erdStudio.hasDbtProject`: **New Diagram**, **Import DBML**, "New to data modelling?" **Open Example Diagram**, the "Using dbt? Open its folder…" line, **Get started**), dbt project with no diagrams (**Draw from dbt** primary, "Rather start blank?" **New Diagram**, **Import DBML**) and the multi-project **Select dbt Project** entry. The context keys behind them are in `docs/dev/architecture.md` → Activation.
- **Assistant detection** (`detectAssistants()` in `src/types/aiAssistants.ts`, pure; the host's `detectAiAssistants()` gathers the inputs and **never spawns anything**): Claude Code = `claude` on PATH or in its installer homes (`locateClaudeCli`) or the `anthropic.claude-code` extension; GitHub Copilot = `github.copilot-chat` / `github.copilot` or `copilot` on PATH; Codex = `openai.chatgpt` or `codex`; Gemini = the Gemini CLI Companion `google.gemini-cli-vscode-ide-companion` or `gemini` (not `google.geminicodeassist`, Gemini Code Assist — a different product); Cursor = `vscode.env.appName` contains "Cursor" or `cursor-agent` on PATH. `isOnPath()` is the generic PATH(+PATHEXT) scan. `recommendedSkillTargets(assistants)`: `claude` when Claude Code is detected; `agents` when Codex or Gemini is, or Copilot / Cursor without Claude Code (both read `.claude/skills/` too, so installing both folders next to Claude would list every skill twice); **both when none is** (the user may install their assistant after setup — this default can show duplicates in Copilot/Cursor).
- **CSP and media.** `buildGettingStartedCsp()`: `default-src 'none'`, `img-src`/`media-src` limited to `webview.cspSource`, and `style-src`/`script-src` by **nonce only** — no `unsafe-inline`, no inline `style=` or event-handler attributes (tested). `localResourceRoots` is `media/onboarding/` only. Captions are added from `GETTING_STARTED_CUES` with `video.addTextTrack()` + `VTTCue` — there is no `<track>` and no shipped `.vtt`. A `<video>` error posts `videoError` and swaps in the poster with a **Watch in your browser** link; the transcript is always on the page.
- **Codec decision.** The mp4 is **H.264 (High, yuv420p, `+faststart`) with MP3 audio** (64 kbps mono 44.1 kHz), at most 8 MB and 65 s (`video/script.yaml` `maxDuration`; the product copy calls it a one-minute video) — the combination the VS Code webview guide documents ("use mp3 for the audio track"). Never AAC: VS Code's `libffmpeg` has **no AAC decoder**, so AAC-in-MP4 plays silently ([vscode#167685](https://github.com/microsoft/vscode/issues/167685)). `video/encode.sh` and `test/unit/gettingStartedMedia.test.ts` both assert h264 + mp3 (the esds object type `0x6B`, since MP3 and AAC share the `mp4a` entry), faststart, the size ceiling and exactly two files in `media/onboarding/`. Forks without H.264 (VSCodium-style builds) get the poster fallback.
- **Sound on by default.** The panel script calls `play()` unmuted first; only if the editor's autoplay policy rejects it does it fall back to muted playback with a centred **Turn on sound** button.
- **Set Up My AI Helper** (`runSetupAiHelper()`, shared by the command and the panel; never throws): (1) `HarnessService.installRecommended(root, { replaceUnmanaged: false, assistants })` — the skill folders `recommendedSkillTargets(assistants)` picks (`claude` → `.claude/skills/`, `agents` → `.agents/skills/`); (2) on `needs-confirmation`, a modal naming the hand-written file(s) with **Replace** (re-run with `replaceUnmanaged: true`) or **Keep mine** (re-run with `keepUnmanaged: true`: everything that is not hand-written is installed — schema skill, SYNC.md, hook, setup skill, the gitignore step — and each hand-written SKILL.md is left exactly as it is; the modal's detail, `keepMineInstalls(unmanaged, targets)`, names what that still installs); (3) `CliLauncherService.install()` — a launcher failure is reported but does not undo the skill install; (4) the message is `setupReadyMessage(assistants, { logicalOnly })`, naming the assistants; from the palette it is an info message with **Open Claude Code** (Claude detected) / **Open Copilot Chat** (Copilot detected) / **Copy prompt**. In a folder without `dbt_project.yml` (`logicalOnly`) the message still names the guided setup, adding that it designs the data model with the user (the skill's no-dbt route), and the palette toast has the same buttons; from the panel, the result renders inline instead (no toast). The command works in a plain folder: nothing gates it on dbt. A cancelled modal shows nothing. This is the **only** route that installs the launcher.
- **Starting Copilot.** `openCopilotChat()` copies `/erd-studio-setup`, then runs `workbench.action.chat.open` (a string command id — no typings newer than 1.85) with `{ query, isPartialQuery: true, mode: 'agent' }` so the prompt is typed but not sent, in Agent mode (older builds ignore `mode`), falling back to a bare open if that argument form throws, and to the Copilot setup page when the command does not exist. Its message says how to switch to Agent mode if the chat is not in it; with a nested dbt project it adds that Copilot looks for skills in the folder VS Code has open. Codex, Gemini CLI and Cursor get Copy plus a one-line hint only.
- **Starting Claude.** `openClaudeCode()` detects the `claude` CLI by scanning `PATH` (+`PATHEXT` on win32, plus `~/.local/bin` and `~/.claude/local`) in JS — it never spawns `claude` — then the `anthropic.claude-code` extension. CLI route: a modal showing the exact command and folder, then a new terminal named **Claude Code** with `cwd` = the dbt project root and `MSYS_NO_PATHCONV=1` (so Git Bash does not turn `/erd-studio-setup` into a path) running `claude "/erd-studio-setup"` — typed with `sendText` when `claude` is on `PATH` (that line parses the same in bash, zsh, PowerShell and cmd), but an absolute path found off `PATH` is the terminal's own process (`shellPath` + `shellArgs`, `claudeTerminalLaunch()`), so no shell ever parses or expands it. Extension route: copy `/erd-studio-setup` and run the first available command in `CLAUDE_CODE_OPEN_COMMANDS`; with a nested dbt project the message offers an **Open <folder>** button (`vscode.openFolder`), because the extension's panel starts in the open workspace folder. Neither: open the Claude Code docs. When the workspace folder is not the dbt root, **Copy** gives `cd '<abs dbt root>' && claude "/erd-studio-setup"` on POSIX and `Set-Location -LiteralPath '<root>'; claude "/erd-studio-setup"` on Windows (PowerShell 5.1 has no `&&`) — single-quoted because the folder name comes from the file system and double quotes would still expand `$(…)`; a root containing a control character falls back to the bare prompt. The skill lives in the dbt root's `.claude/skills/`, and every success message says to restart Claude Code or run it from that folder.
- **The launcher** (`src/services/cliLauncherService.ts`, no `vscode`, every input injected): `~/.erd-studio-cli/lib/cli.js` (a **copy** of `dist/cli.js`, so an extension update deleting its old folder cannot break the shim), `launcher.json` (`extensionVersion`, `execPath`, `cliSha256`, `writtenAt`, `runtimeVerified`), `bin/erd-studio` (POSIX sh, 0755, written on **every** platform because Claude Code's Bash tool is Git Bash on Windows) and `bin/erd-studio.cmd` (Windows only). The shims prefer a `node` >= 18 on PATH and fall back to VS Code's Electron with `ELECTRON_RUN_AS_NODE=1` set only on the exec line (sh) or inside `setlocal` (cmd) — never exported. `install()` first checks that the Electron runtime actually runs a script (5 s timeout) and omits that branch if not. Every write is atomic (unique temp name, then rename). `refreshIfInstalled()` does nothing without a `launcher.json`; otherwise it rewrites when the running version is the same or newer (`compareVersions`) and something changed, or when the recorded `execPath` no longer exists — a newer recorded version is left alone (`skipped-newer`), and an `execPath`-only difference at the same version is not rewritten while the recorded runtime still exists, so two VS Code installs do not keep overwriting each other. `applySemanticDir()` never rewrites the `~/.erd-studio-cli` path in skill text (its `(?![\w-])` lookahead). No `PATH` changes: the skill always calls the absolute path.
- **The CLI** (`src/cli/`, `dist/cli.js`, read-only): `doctor [--no-dbt] [--dbt <path>] [--trust-venv]` (project, dbt executable and flavour via `dbtEnv` — `core-v1` / `fusion-v2` / `cloud-cli` — profiles, deps, artifact freshness, ERD layers / domains / format issues, the file naming `erd.naming` (`v5` / `v6` / `mixed`, `projectNamingOf()` over core's `detectProjectNaming` — the extension's own answer — and, when not `v6`, `erd.namingMigration`: `{ moves, rewrites, refusals, preview }`, what **Migrate to the New File Naming** would change, from the same `planNamingMigration`; a preview only, never a next step; with `erd.tablesFolderIsLayer` and `erd.namingConflicts` → a `resolve-naming-conflicts` step; a v5 / v6 key mix gets `fix-subject-area-naming` instead of `migrate-v5`), `harnessStatus()`, and ordered `nextSteps` with ready-to-run commands; a dbt inside a project-local venv that is not also what `PATH` resolves to is **never run** without `--trust-venv` — `doctor` is pre-approved in the skill's `allowed-tools`, and a cloned repo can ship any `.venv/bin/dbt`, so it is reported as `dbt.untrustedVenvDbt` with a `confirm-venv` step and the skill passes the flag only after showing the user the path. For the same reason the skill pre-approves only subcommand-scoped rules for bare `dbt` (`parse`, `docs generate`, `compile --write-catalog`, `debug`, `deps`, `--version`); a venv or absolute-path dbt always goes through Claude Code's own prompt. `.cmd`/`.bat` shims are spawned through cmd.exe with the path double-quoted by `dbtVersionSpawn()`, which refuses a path containing `"`, `%` or a line break), `inventory [--summary] [--models a,b]` (with `logicalTables`: every table in the library — name, file, folder, description, grain, column count, primary key, columns unless `--summary`, the subject areas that draw it — restricted by `--models`), `diff (--domain <path> | --all) [--strict]`, `export (--domain <path> | --all) --format mermaid|dbml|dbml-rich|dbml-layout` and `version`. `inventory` (both shapes) carries **`conventions`** (`layering`, `shape` with `confidence` / `evidence` / `alternatives` / `sources`, `history.snapshots`, `meta`, `suggestedLayer`) from `src/cli/conventions.ts` and `src/cli/metaConventions.ts` — pure heuristics, no AI; read those files and their tests before changing a threshold or a signal. dbt's own `meta:` reaches the CLI only (`YmlParserService` / `manifestExtractor` via core's `readMeta()`); `buildPhysicalSubjectArea`, the diff and the canvas never read it. Shared flags: `--project` (the folder holding `dbt_project.yml`, or a folder holding the semantic dir and no dbt project; without it, walk up from cwd to the nearest folder holding `dbt_project.yml` or the semantic dir, then let a dbt project up to three levels below cwd (`findDbtProjectCandidates`) beat a design folder; `resolveProjectRoot` in `src/cli/context.ts`, detailed in the next bullet), `--semantic-dir`, `--json`, `--quiet`, `--verbose` (otherwise the shared services' `console.*` output is silenced so it never mixes into the JSON Claude reads), `--help`, `--version`. `diff` is `computeSubjectAreaDiff(…, 'logical')` + `buildSyncPlan(report, allSelections(report, 'physical'))` turned into `fixes`, each `blocking` or `advisory`; a domain is **clean** at zero blocking fixes, and a `set-type` whose physical type is empty (dbt knows no type yet) is advisory unless `--strict`. A phantom model collapses to one `resolve-phantom` fix; v4 domains report `needsMigration: true` and no fixes; under `--all` a domain that fails to load gets its own `error` rather than stopping the run, and `--all` over a missing semantic dir or zero domains is exit 3 (`no-semantic-dir` / `no-domains`) — never a clean result over nothing. `export` (`src/cli/export.ts`) prints one domain's logical stage via `exportSubjectAreaFile` (with `dbtKeyIndexOf(ymlData, manifest)`, as `computeSubjectAreaDiff` passes it, and the `LayerService` for the layer's colour and label), so its bytes equal the extension's and core's goldens; human output is the export text alone on stdout (`> schema.dbml` works), `--json` is `{ cliVersion, domain, format, fileName, content }` with `domain` project-relative, and `--format` is matched without case. Formats: `mermaid`, `dbml` (portable, ERD Studio's fields in notes), `dbml-rich` (DBML for dbdiagram.io: the fields as custom properties, DBML 9.1+, its header naming `<name>.dbdiagram`) and the CLI-only `dbml-layout` — that `.dbdiagram` file itself (dbdiagram's layout JSON, the table positions), so `--format dbml-rich > sales.dbml` plus `--format dbml-layout > sales.dbdiagram` is what `dbdiagram push sales.dbml` reads. It takes exactly one `--domain`, or `--all` (never both — a usage error): every domain via `exportSubjectAreaFiles`, the same files and names **Export All Diagrams…** writes (by layer then file; `<layer>-<name>` when two layers hold a domain of the same name, then `-2`, `-3`, ignoring case), human output a JSON list of `{ fileName, content }` (with `dbml-rich` each `.dbml` followed by its `.dbdiagram`; with `dbml-layout` only the `.dbdiagram` files) and `--json` `{ cliVersion, format, files: [{ domain, fileName, content }], skipped: [{ domain, error: { code, message } }] }`. Under `--all` a domain that fails to load is skipped (a `skipped:` line on stderr in human mode) and the run exits 1; a missing semantic dir or zero domains is exit 3 (`no-semantic-dir` / `no-domains`), as `diff --all` (`listAllSubjectAreas`). `export` has no `--out` and never writes a file; load errors use `diff --domain`'s codes through the shared `describeSubjectAreaError` (exit 3), and a v4 domain exports normally rather than asking for migration. Sync-plan paths (`modelContext.*`) are forward-slash on every platform. Paths in the JSON are project-relative; error JSON is `{ cliVersion, error: { code, message } }` with no absolute paths.
- **The CLI on a logical-only root** (a folder holding the semantic dir and no `dbt_project.yml`, the CLI's twin of the extension's logical-only mode). The `doctor`, `inventory` and `diff` JSON envelopes (`makeEnvelope`) carry `dbtProject` (true when the root holds `dbt_project.yml`; false for a logical-only root and for doctor's no-project result); `export`, `version` and the error JSON do not. Root resolution without `--project` walks up from the current directory to the nearest folder holding `dbt_project.yml` or the semantic dir, so a design folder nested in a dbt repo resolves to itself, not to the dbt project above (the extension never searches above the folder it opens); a dbt project up to three levels below the current directory still beats a design folder (`resolveProjectRoot`). `buildCliContext` builds `ManifestService`, `YmlParserService` and `CatalogService` with `enabled: false`, so nothing dbt is read — not even a `models/` folder that happens to exist — and both artifacts report `missing`. `doctor` never probes dbt (not even without `--no-dbt`), runs the ERD Studio and harness checks as usual, and adds `skippedChecks: { reason: 'not-dbt-project', checks: ['dbt', 'profiles', 'artifacts', 'projectFiles', 'deps'] }` (`DBT_CHECK_IDS`), with those blocks holding their "nothing found" values so the JSON keeps one shape; `nextSteps` never includes a dbt step (`install-dbt`, `run-parse`, `run-catalog`, …) and `fix-subject-area-naming` points at `export --domain` instead of `diff`, and `ready` says the dbt checks were skipped. It exits 0 when the logical files are fine. `inventory` returns empty `models`, `relationships`, `clusters` and `alreadyModelled`, "nothing detected" `conventions`, and the logical files (`domains`, `logicalTables`); its human output lists the designed tables. `export` reads the logical files as usual. `diff` exits 3 with code `not-dbt-project` (`DIFF_NEEDS_DBT_MESSAGE`: it needs a dbt project; doctor, inventory and export work without one). The setup skill's no-dbt route (`references/without-dbt.md`) runs only `doctor` and `export`. `mcp-server/` mirrors the resolution: `resolveProjectPath` accepts a folder holding `.erd-studio/` without `dbt_project.yml`, and builds its manifest service disabled there.
- **The CLI on native DBML storage** (2.0; spec `docs/plans/native-dbml-storage.md` §7.1). Every JSON change is additive. `doctor` adds **`erd.storage`** (`dbml` / `yaml` / `mixed`, `projectStorageOf()` over core's `detectProjectStorage` — the same answer the extension, the offer and the harness use; `dbml` when there is no `.erd-studio` yet; ignore `erd.naming` when it is `dbml`), **`erd.diagrams`** (`[{file, format}]`), **`erd.dbmlConversion`** (the Convert Project to DBML preview from `planDbmlConversion` + `describeDbmlConversion`, the same plan the Convert to DBML panel lists; a preview, never a next step on its own) and **`erd.dbmlProblems`** (`[{file, line, column, code, severity, message, mergeConflict?}]`, `src/cli/dbmlProblems.ts`): `compileDbmlProject` (the bundled 11.0.0 under the virtual root) over every diagram with its imports, each relationships file and each table file on its own, then ERD Studio's own checks with a **fixed severity** below. Human output prints `storage DBML|YAML|mixed` (`storage YAML, file naming vN` for a YAML project), the problems by severity, and the Convert preview. New `nextSteps`: **`fix-dbml-file`** (any problem of severity error without `mergeConflict`), **`resolve-format-conflicts`** (the same table or diagram in both formats, unless Convert's plan resumes that very target), **`finish-dbml-conversion`** (the plan resumes a half-applied conversion: `resumed` is not empty) and **`import-dbml-file`** (a diagram that declares Tables and has no table `use` lines: "Run ERD Studio: Import DBML… on <file>; it is a single-file DBML, not an ERD Studio diagram."). **Warnings never raise a next step**, so "run doctor until clean" loops end. Every conflicted `.dbml` or `.dbdiagram` file carries `mergeConflict: true` and routes to `resolve-merge-conflicts`, never `fix-dbml-file`. `fix-model-yaml` covers YAML files only (an unreadable `.dbml` table is reported once, as a DBML problem); `turn-round-relationships` names the owner's `tables/<folder>/_relationships.dbml` for a DBML owner. `update-harness` is raised when **any** installed target is outdated (Claude, `.agents`, Copilot, Gemini, `AGENTS.md`), adding "an AI helper from before 2.0 writes YAML into this DBML project" when storage is not `yaml`; a **newer** marker (a teammate on a later ERD Studio) is the `FileState` `'newer'`, reported as "Update ERD Studio: these helper files are from a newer version: …" and `harness.newer`, never `update-harness`, and never replaced. `inventory` entries and `logicalTables[]` gain `format`, members come from `use` lines, and `file` may be `.dbml`. `diff` sends a missing table to `pathForNewTable` and relationship fixes for a DBML owner to its folder's `_relationships.dbml`; an unreadable `.dbml` table gets the FixKind **`fix-dbml-file`**, and the error codes gain **`dbml-invalid`** (with `file:line`) and **`not-a-diagram`** (a `--domain` that is a table, relationships or layout file). `export --domain` and `diff --domain` accept a `.dbml` diagram (`.erd-studio/gold/sales.dbml` in the usage text). `dist/cli.js` bundles `@dbml/parse` (one copy, the root pin; `cli.noVscode.test.ts`).

## User-facing wording

Rules for the README, the user guides (`docs/dbt.md`, `docs/ai-assistants.md`, `docs/project-folder.md`, `docs/leaving-erd-studio.md`), the Marketplace `description`, the walkthrough, the welcome views, the Welcome panel and the CHANGELOG:

- Positioning: a logical data model tool in Git that works with the user's own AI assistant, compared with a physical model from dbt today and more sources later. Tagline: "Design your data model in Git. Let your AI build from it."
- DBML is "an open format" or "the open-source schema language behind dbdiagram.io", **never "an open standard"**. ERD Studio is "free to use, source available under the PolyForm Shield License", **never "open source"**.
- ERD Studio's native storage is DBML, an open format, and its edits are byte-preserving (hand edits and comments survive). Still never claim that export → dbdiagram.io → import is lossless, that DBML itself stores the layout (positions live in the `.dbdiagram` file beside the `.dbml`), that dbdiagram.io opens the split project directly (`dbdiagram push` takes the single-file export), or that ERD Studio syncs with dbdiagram.io. Older projects are "YAML/JSON projects from before 2.0": they keep working, and **ERD Studio: Convert Project to DBML** moves one over.
- Prose says **diagram**; say once per page that the commands call it a *subject area*. Command titles keep their text, so a command is named by its real title (**ERD Studio: New Subject Area**) and the sidebar button by its label (**New Diagram**).
- Say **Set Up My AI Helper**, never "harness", in the README and onboarding copy.
- Explain the tabs once as **Logical** (your design) · **Physical** (read from dbt). Where the reader may have dbt elsewhere: "Using dbt? Open its folder to compare your design with what dbt built."
- `/erd-studio-setup` and the `erd-studio` CLI work without dbt (the setup's no-dbt route designs a first diagram; the CLI needs a `.erd-studio` folder). Only `erd-studio diff` needs a `dbt_project.yml`: never tell a reader without dbt to install it.
- The root README never mentions telemetry and links only the AAC copy of the getting-started video (the jsDelivr `docs/assets/getting-started.mp4` URL).
- Every command, button and label named must exist in `package.json` or the UI as written.
