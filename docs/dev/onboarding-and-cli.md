# Getting Started panel, launcher and erd-studio CLI

> Moved out of the root `CLAUDE.md` so it loads only when needed. Read before touching `GettingStartedPanel.ts`, `src/types/gettingStarted.ts`, `aiAssistants.ts`, `cliLauncherService.ts`, `dbtEnv.ts` or `src/cli/`. The setup skill itself is in `src/harness/CLAUDE.md`.

Onboarding has three starting points — no folder open, a folder without dbt (logical-only: start from scratch, from an example, or from an import of DBML, SQL DDL or a Power BI / Fabric semantic model; the import guide shows how to export each source first) and a dbt project (Draw from dbt) — plus an optional route for an AI coding assistant (**Claude Code, GitHub Copilot, Codex, Gemini CLI or Cursor**). The pieces: a Welcome panel with a short getting-started video, a one-click **Set Up My AI Helper**, the `/erd-studio-setup` skill it installs (an [Agent Skill](https://agentskills.io), into `.claude/skills/` and/or `.agents/skills/`), and the read-only `erd-studio` CLI the skill runs to check its work. End-to-end tested with Claude Code only; the other four read the same skill from the open standard's `.agents/skills/` folder.

- **Commands.** `erdStudio.showGettingStarted` (**Watch the One-Minute Tour**, `TOUR_LABEL`, `$(play-circle)`; it opens the **ERD Studio Tour** tab (`GETTING_STARTED_TAB_TITLE`: never a second tab called Welcome beside VS Code's walkthrough tab), headed "The one-minute tour"; also a row of the sidebar's **Help & Feedback** view (`HELP_ACTIONS` in `src/providers/HelpTreeProvider.ts`, with **Set Up My AI Helper**, **Send Feedback** and **Show Logs**) and a link in the domain tree's welcome view) is pre-registered and works without a project. `erdStudio.setupAiHelper` (**Set Up My AI Helper**, `$(sparkle)`) is registered on the project path only and gets the ordinary fallback stub without one. Both are in `NO_LEGACY_ALIAS`. `erdStudio.trySampleProject` (**Try the Sample Project**, `$(beaker)`; the sample is a dbt project, so its palette entry is gated to `erdStudio.hasDbtProject` and only the dbt page of the panel links it) is pre-registered and in `NO_LEGACY_ALIAS`: `trySampleProject()` (`GettingStartedPanel.ts`) shows a modal confirm (`SAMPLE_CONFIRM_MESSAGE`, **Download**), then — when `vscode.extensions.getExtension('vscode.git')` exists — runs `git.clone` with the fixed `SAMPLE_REPO_CLONE_URL` (VS Code asks for the folder and offers to open it); with no Git extension, or if `git.clone` throws, an info message (`SAMPLE_FALLBACK_MESSAGE`: Download ZIP, unzip, Open Folder) whose **Open on GitHub** opens the fixed `SAMPLE_REPO_URL`. Both URLs are constants in `src/types/gettingStarted.ts` (vscode-free) and never come from a webview. The sample repo (`liam-machine/erd-studio-sample`, a Kimball jaffle-shop on DuckDB shipping `target/manifest.json` + `catalog.json`) is **not** bundled in the VSIX. `erdStudio.openExampleDiagram` (**Open Example Diagram**, in `NO_LEGACY_ALIAS`) is registered on the project path, so it works in any folder (an empty window gets the ordinary "Open a folder first" fallback stub): `openExampleDiagram()` (`src/commands/openExampleDiagram.ts`) feeds the inline `EXAMPLE_DBML` — the sample repo's six coffee-shop mart tables as a star schema, with ERD Studio's custom DBML properties — through the ordinary `importDbml` flow with only the file-reading half of the UI swapped (`exampleDbmlUi`), so the user still names the diagram and sees the dry-run summary before anything is written, and a plain folder gets `.erd-studio/` and `layers.json` only on that confirm. It goes in the `gold` layer when the project has one (else the import asks), has no `erd_layout` (the canvas lays it out on open), and ships no file (the VSIX 60-file cap). It is no longer offered on the start surfaces (they offer the example projects below); the setup skill's no-dbt route still names it.
- **The start screen** (`src/types/startActions.ts`, pure, shared by the host, the panel and the tests; `src/commands/start.ts`). Every surface a new user meets — the Welcome panel, the walkthrough and the empty Diagrams view — offers the same starts, led by the one the folder suggests. **Only** `startIntentFor({ hasProject, hasDbt, storage, hasDiagrams, found })` decides the suggestion (the **intent**), strongest signal first: `convert` (`erdStudio.storage` is `yaml` or `mixed`) > `drawFromDbt` (a dbt project) > `importSemanticModel` > `importSqlDdl` > `importDbmlFile` (what the folder's quick look `found`: a Power BI / Fabric semantic model, CREATE TABLE scripts, a DBML file; counted only while `startNeedsLook` holds — a DBML or new project, no dbt, **no diagram yet**: a project that has started is past its files) > `blank`; an empty window has none. **Only** `startActionsFor(ctx)` = `startActionsForIntent(intent, hasDbt)` decides the list, primary first and never more than four (`MAX_STARTS`): `drawFromDbt` → Draw from dbt, New Diagram, Import…, example; each direct import → that import, New Diagram, Import…, example (the generic **Import…** always stays as a quieter choice); `blank` → New Diagram, **example second** (someone with an empty folder sees a finished model before an import), Import…; `convert` → Convert, then the first three of what the project would otherwise offer (Draw from dbt's list with dbt, `blank`'s without; a pre-2.0 project is never looked at); no folder → only `example`. The three direct imports (`importSemanticModel` / `importSqlDdl` / `importDbmlFile`) run `erdStudio.importSemanticModel` / `erdStudio.importSqlDdl` / `erdStudio.importDbml` straight away, one click less than Import…'s picker, on their **quick path** (`{ quick: true }`: the folder's files, the layer and the name chosen, one confirm; see **The quick import** below — Import DBML…'s step-by-step dialog still starts on the DBML file the look found, chosen: `findDefaultFile`, `docs/dev/dbml.md`); their labels are **Import your Power BI semantic model**, **Import your SQL scripts** and **Import your DBML file** everywhere (`START_LABELS`, the quick pick's `START_PICK_ITEMS`, `package.json`; never "Power BI model": prose says "semantic model"), and the reason lines (`START_INTENT_REASONS`, no longer shown on the Welcome panel, which has no start card since Draft-first: "This folder has CREATE TABLE scripts.", "This folder has a Power BI or Fabric semantic model.", "This folder has a DBML file." — the kind of file only, never a name). Each surface shows one primary button and the rest as quiet links (the walkthrough and welcome views: one link alone on its line, the others inline). **The host's suggestion** is `StartIntentTracker` (`src/commands/startIntent.ts`, vscode-free; built in `activate()` on the project path, disposed with the context): `refresh()` looks at the folder through Import…'s own `detectImportSources` (`vscodeStartLook` in `importModel.ts`, a `CancellationTokenSource` behind an `AbortSignal`; no second detector, and `physicalTooling.ts` stays telemetry's) only when `startNeedsLook` holds and the last look is older than `START_LOOK_FRESH_MS` (60 s), cancels it after `START_LOOK_TIMEOUT_MS` (1.5 s; the folder then counts as holding nothing, and is not looked at again that session), shares one look between concurrent asks, writes nothing, and publishes the context key **`erdStudio.startIntent`** (`START_INTENT_CONTEXT_KEY`) only when the suggestion changes. It is asked, never on activation's own path, by the empty Diagrams view being drawn (the tree's `onLoadingChange(false)`, deferred a tick), the Welcome panel's status, and the walkthrough being opened by ERD Studio (`scheduleRefresh()`). Until it has published, the key is unset: the walkthrough shows `blank`'s step (the `!=` clauses below hold for an unset key), while the empty Diagrams view of a folder without dbt (and not from before 2.0) shows **Loading diagrams…** (its blank variant needs `erdStudio.startIntent == blank`), so New Diagram never shows first and turns into an import under the cursor; a refresh therefore always publishes, `blank` when the folder's state cannot be read. What the look finds never leaves the machine: telemetry counts only the suggestion's fixed key. Every start runs the hidden, pre-registered **`erdStudio.start`** (`START_COMMAND`; contributed so a link activates the extension, `commandPalette` `when: false`, in `NO_LEGACY_ALIAS` and `PRE_REGISTERED_COMMANDS`) with one argument `{ action, from }` — `from` is `welcome` / `walkthrough` / `sidebar` — written as `startCommandLink(action, from)` (`command:erdStudio.start?<encoded JSON array>`) in `package.json`. `runStart` validates it (`parseStartArgs`), counts `START_FEATURES[from][action]` (the funnel keys, `telemetry/README.md` → Onboarding funnel) and runs `START_ACTION_COMMANDS[action]` with `startActionArgs(action)` (`[{ quick: true }]` for the three direct imports — their quick path, below — and nothing for the others); without a valid argument it shows the same starts (with the tracker's findings) in a quick pick and counts nothing, then, last, **How do I export from Databricks, Snowflake, Power BI…?** (`START_PICK_GUIDE_ITEM`: the import guide, `{ from: 'startPick' }`). Its `executeCommand` passes the arguments on (`startActionArgs`, so a start link's direct import reaches its quick path). A surface the host can see showing a suggestion counts `START_INTENT_FEATURES[intent]` (`startSuggested<Intent>`, `featureOnce`): the empty Diagrams view each time it is drawn (the Welcome panel no longer shows a suggestion). `test/unit/startActions.test.ts` holds every start link in `package.json` to the rule in **every window** — the empty window, then each dbt / storage / found combination before and after `erdStudio.startIntent` is published, evaluating each `when` with `test/unit/helpers/whenClause.ts` — for the empty Diagrams view and the walkthrough alike: the visible entries' start links equal `startActionsFor`, exactly one of them is a button and it is the suggestion; `test/unit/startIntent.test.ts` covers the tracker. The project path late-binds the context (`startContext`, storage from `projectStorageOf`); the panel's status carries `storage`. New Diagram's cancels count `blankDiagramCancelled`; the empty Diagrams view, once drawn, counts `sidebarStartShown` (the tree's `onLoadingChange(false)`).
- **Draft-first: the start is a draft** (spec and package plan: `docs/dev/draft-first.md`; contract `src/types/draft.ts`). The first time someone deliberately turns to ERD Studio in a folder with no diagram, it shows a **draft** of their logical model — built from what the folder holds (CREATE TABLE scripts, a Power BI / Fabric semantic model, a DBML file, a dbt project) or, with nothing found, the coffee-shop example — as a **read-only diagram in an editor tab** (`erdStudio.draftPreview`, `src/providers/DraftPreviewPanel.ts` + `webview-draft/`, `dist/draft.js` / `dist/draft.css`; nonce-only CSP, every message checked by `parseDraftToHost`, the page runs no command and opens no URL), and **writes nothing until Keep**. Rules: (1) nothing is written before an explicit Keep and nothing on activation; building a draft only reads, through the imports' own bounded reads. (2) One writer per kind: Keep runs Import DBML's step 6 (`writeNewSubjectArea`), Draw from dbt's, or Open an Example…'s `writeFilesWithRollback` — no draft code writes a file. (3) The automatic draft is a prompt: it claims the window's one prompt (`SessionPromptGate` kind `draft`), and any draft on show claims it too when free, so nothing pops over it. (4) Telemetry gets fixed keys only (`draft*`, §11 of the spec; user cancels are features). **What opens one** (`DraftTrigger`): `sidebar` — the only automatic one: the empty Diagrams view was drawn (the ERD Studio icon; the tree's `onLoadingChange(false)` → `onEmptyDiagramsViewShown`), after the tracker's look and once activation's own prompt is decided (`activationPromptsSettled`), when `autoDraftDue` (`src/services/draftTriggers.ts`) holds: `erdStudio.startSuggestions` on, the folder's suggestions not off, no diagram, **no table**, no canvas open, and either a find this folder has not had automatically (`draftShown`) nor answered, or `blank` and this machine has not had the automatic example (`erdStudio.exampleDraftShown`, globalState); `convert` is never drafted. Its flag is written **before** it shows; it opens with `preserveFocus` and a progress bar on the Diagrams view (`withProgress({ location: { viewId: 'erdStudio.domainTree' } })`), and is **quiet**: anything the quick path would ask or say before the draft (several dialects, no CREATE TABLE after all, no layer, a file that does not read) ends it silently (logged; `draftUnavailable`, never a `*Cancelled` or `*Invalid` key), leaving the sidebar's starts. `prompt` — the start suggestion's **Show Me**; `start` — a start surface's primary import or Draw from dbt (the arguments carry `{ draft: 'start' }`, `startActionArgs`); `palette` — the step-by-step commands, which now end in a draft too; `changeOptions` — the flow a draft's **Change options…** ran; `example` — **Open an Example…**. **On the draft:** **Keep as Diagram** (an example in a folder: **Keep This Example**; a bundled project: **Save This Example…**) writes it, marks the folder as started (`DIAGRAMS_NUDGE_SHOWN_KEY`, the suggestion `answered`) and opens the diagram; **Change options…** is the quick path's step-by-step flow, preselected (SQL's file pick, the dialect, the layer and name; Draw from dbt's picker), ending in a draft; **Discard** and closing the tab write nothing; **More ways to start** run fixed host commands only (`DRAFT_OTHER_START_COMMANDS` in `src/providers/draftWiring.ts`: New Diagram… → `erdStudio.createDomain`, Import… → `erdStudio.importModel`, Bring In Your Data Model… → `erdStudio.showImportGuide` `{ from: 'draft' }`, Open an Example… → `erdStudio.openExampleProject`, Open Folder… → `vscode.openFolder`); the switcher (`Folder` for dbt models folders, `Model` for several semantic models, `Example`) redraws in the same tab; **Show details** is Review All…'s content as text. A Keep after the project's files changed outside ERD Studio (`DraftGeneration`, bumped by the semantic-dir watchers, own writes excluded) plans again: the same `importPlanFingerprint` / `dbtDraftFingerprint` writes at once, another redraws with "Your ERD Studio files changed, so the draft was redrawn. Check it and keep it again." One `createDraftPreview` per extension host, wrapped by `trackedDraftPreview` (the gate, the funnel keys, More ways to start, Keep's bookkeeping), is passed to every flow through its deps (`ImportDraftOptions`, `DbtDraftOptions`). **The walkthrough auto-opens only in an empty window** (`walkthroughAutoOpens`): a first run in a folder with no diagram is spent there and left for the draft (no other activation prompt takes that window; they ask in a later one); a first run whose window another prompt already holds stays owed (`walkthroughWaited`). An example project's new window claims the gate (`exampleOpen`). Tests: `draftWiring.test.ts`, `quickImport.test.ts` (Keep writes the modal's files byte for byte), `extension.activate.test.ts` → "draft-first".
- **Show Me Around, the onboarding guide** (`erdStudio.showMeAround`, **ERD Studio: Show Me Around**; pure steps, text, statuses and action ids in `src/types/onboardingGuide.ts`; host side `src/providers/guideWiring.ts`; the callout `webview/components/Guide/CoachMark.tsx` + `coachMarkPlacement.ts`, shared by `webview/components/Guide/CanvasGuide.tsx` and `webview-draft/components/DraftGuide.tsx`). - **`erd-studio changes`** (`src/cli/changes.ts`, `modelSnapshot.ts`, `modelChanges.ts`, `changesFormat.ts`) summarises how the ERD Studio model changed between `--base <git-ref>` and the working tree, for a pull-request comment: tables added / removed / renamed / moved / changed (columns added, removed and retyped, `pk` / `fk` / `nk` flags, alias, role, grain), relationships added / removed / with a new cardinality, diagrams added / removed / with tables added or removed, and each DBML relationships file's Refs added / removed / changed. Matching: tables by name without case; a rename only when exactly one removed and one added table share identical non-empty columns (names and types in order), otherwise an add and a remove; a move when the layer or schema differs and both versions have one (a flat YAML library converted to DBML is not a move); relationships by core's `linkKey`, cardinality compared after turning the new copy to face the old (`reverseRelationship`); diagrams by `<layer>/<name>`, so a JSON → DBML conversion is the same diagram (`movedFrom`). a **newer** marker (a teammate on a later ERD Studio) is the `FileState` `'newer'`, reported as "Update ERD Studio: these helper files are from a newer version: …" and `harness.newer`, never `update-harness`, and never replaced. `inventory` entries and `logicalTables[]` gain `format`, members come from `use` lines, and `file` may be `.dbml`. `diff` sends a missing table to `pathForNewTable` (`<layer>/tables/<schema>/<name>.dbml`); for a DBML owner an `add-relationship` fix names the file a new Ref goes in (the sync plan's `relationshipsPath`) and `remove-relationship` / `set-cardinality` name the file that holds the Ref (`storedIn`), changed in place with no `movesFrom`; a relationship dbt tests whose Ref a relationships file already holds but the diagram does not import gets the FixKind **`import-relationships-file`** (`file` is the diagram, `storedIn` the relationships file, `useLine` the exact `use * from '…'` line to add; never an `add-relationship`, whose second copy of the Ref would be a duplicate, error 5001); an unreadable `.dbml` table gets the FixKind **`fix-dbml-file`**, and the error codes gain **`dbml-invalid`** (with `file:line`) and **`not-a-diagram`** (a `--domain` that is a table or relationships file, or any `.dbml` outside `<layer>/diagrams/`). `export --domain` and `diff --domain` accept a `.dbml` diagram (`.erd-studio/gold/diagrams/sales.dbml` in the usage text). `dist/cli.js` bundles `@dbml/parse` (one copy, the root pin; `cli.noVscode.test.ts`).

## User-facing wording

Rules for the README, the user guides (`docs/dbt.md`, `docs/ai-assistants.md`, `docs/project-folder.md`, `docs/leaving-erd-studio.md`, `docs/modelling-patterns.md`, `docs/import-existing-models.md` and the `docs/examples/*/README.md` pages), the import guide's page, the Marketplace `description`, the walkthrough, the welcome views, the Welcome panel and the CHANGELOG:

- Positioning: a logical data model tool in Git that works with the user's own AI assistant, compared with a physical model from dbt today and more sources later. Tagline: "Design your data model in Git. Let your AI build from it."
- DBML is "an open format" or "the open-source schema language behind dbdiagram.io", **never "an open standard"**. ERD Studio is "free to use, source available under the PolyForm Shield License", **never "open source"**.
- ERD Studio's native storage is DBML, an open format, and its edits are byte-preserving (hand edits and comments survive). Positions live in the diagram file itself, as an `erd_layout` setting in its `Project` that other DBML tools ignore: say "the diagram file keeps the positions", never that other tools show ERD Studio's layout. Still never claim that export → dbdiagram.io → import is lossless, that dbdiagram.io opens the split project directly (`dbdiagram push` takes the single-file export, and dbdiagram.io lays it out itself), or that ERD Studio syncs with dbdiagram.io. Older projects are "YAML/JSON projects from before 2.0": they keep working, and **ERD Studio: Convert Project to DBML** moves one over.
- Prose says **diagram**, and so do the commands on a diagram: **New Diagram…**, **Open Diagram**, **Rename Diagram…**, **Delete Diagram** (`test/unit/uiWording.test.ts`; every string literal under `webview/`, `packages/renderer/src/` and `src/cli/` too, `test/unit/uiWordingSource.test.ts`). *Subject area* is left only in the file format (the v6 `subjectArea` key) and in the two format commands, **Set Up Subject Areas Directory** and **Migrate Subject Areas to the Central Table Library**. A command is named by its real title (**ERD Studio: New Diagram…**).
- Say **Set Up My AI Helper**, never "harness", in the README and onboarding copy.
- Explain the tabs once as **Logical** (your design) · **Physical** (read from dbt), on a surface that shows only in a dbt project. dbt is an add-on and shows up only in dbt projects: in a folder without `dbt_project.yml` (and in an empty window) the product shows no dbt word, control or teaser — no "Using dbt?", no "no dbt needed", no "as dbt model names are". Gate a dbt variant on `erdStudio.hasDbtProject` / `logicalOnly` rather than deleting text dbt users rely on. The README and the user guides are the place to say that dbt is optional.
- `/erd-studio-setup` and the `erd-studio` CLI work without dbt (the setup's no-dbt route designs a first diagram; the CLI needs a `.erd-studio` folder). Only `erd-studio diff` needs a `dbt_project.yml`: never tell a reader without dbt to install it.
- The root README never mentions telemetry and links only the AAC copy of the getting-started video (the jsDelivr `docs/assets/getting-started.mp4` URL).
- Every command, button and label named must exist in `package.json` or the UI as written.
- One label per action (the table above): never a second name for a start, the guide or the tour. Say "an open format, no lock-in" once (where DBML is introduced), "Each table is a file in .erd-studio/…" once (the Table Library), and "free to use" only in the README and the user guides, never in a prompt, toast or the import guide. No rhetorical questions on a start surface.
