# Import corpus

A large, pinned set of public schemas to measure ERD Studio's imports against: pg_dump and mysqldump output (Discourse, Mastodon, Magento, Odoo, Canvas, Moodle…), Rails `structure.sql` (GitLab, OpenStreetMap) and `schema.rb` (Mastodon, Forem), a Django pg_dump (NetBox), SQL Server projects and scripts (WideWorldImporters, Northwind, pubs, AdventureWorksDW, Bitwarden), Oracle sample schemas (HR, SH, CO), BigQuery, Redshift and SQLite DDL, TPC-H and TPC-DS, Chinook, Northwind and OMOP CDM in several dialects each, dbt projects and Power BI models (TMDL and model.bim). The warehouse dialects are the widest: Snowflake (schemachange scripts, Data Vaults, quickstart setups with procedures and `$$` bodies, SqlDBM output, TPC-DI, grammar and linter test corpora), Databricks and Spark (Unity Catalog industry models up to 8.8 MB, Lakeflow pipelines, notebook sources, Delta feature tours, Hive TPC-DS), BigQuery (`NOT ENFORCED` keys, nested `STRUCT`s, external tables, templated names), Redshift (encodings, sort and dist keys, Spectrum), 26 dbt projects (versioned models, contracts, dbt_constraints, ClickHouse, Trino) and 21 Power BI models (TMDL, `*.Dataset` folders, Direct Lake, model.bim from compatibility level 1200, Tabular Editor Save to Folder).

The committed [real-world samples](../../test/fixtures/real-world-imports/README.md) are the small, hand-checked set with floors in `npm test`. This corpus is the wide net: nothing is committed but the list, and nothing in it is a floor.

| File | What it is |
|---|---|
| `sources.json` | The list, by hand: repo, ref, files, dialect, licence, how a user would import it. |
| `manifest.json` | Generated by `pin.mjs`: each file's URL at a pinned commit and its SHA-256. |
| `pin.mjs` | Re-pins: resolves refs to commits and hashes every file (needs a GitHub token). |
| `fetch.mjs` | Downloads the manifest into `.cache/import-corpus/files/` (gitignored) and verifies every checksum. |
| `count_source.py` | Counts each source without ERD Studio (sqlglot, PyYAML; `requirements.txt`): the truth. |
| `../../test/unit/importCorpus.score.test.ts` | Imports one schema the way the extension does and scores it (skipped unless `IMPORT_CORPUS_DIR` is set). |
| `score.mjs` | The whole loop: fetch, count, score each schema in its own process, report. |
| `report.mjs` | The score table and the failure classes, from `<cache>/results/`. |
| `../../.github/workflows/import-corpus.yml` | The same loop on GitHub, run by hand (**Import corpus**, `gh workflow run import-corpus.yml [-f only=a,b]`); the report is the run's artifact. |

## Run it

```bash
python3 -m venv .cache/corpus-venv && .cache/corpus-venv/bin/pip install -r scripts/corpus/requirements.txt
node scripts/corpus/score.mjs --python .cache/corpus-venv/bin/python
node scripts/corpus/score.mjs --only pg-discourse,mysql-magento --no-fetch --python .cache/corpus-venv/bin/python
```

The report lands in `.cache/import-corpus/report/` (`score-table.md`, `failure-classes.md`, `scores.json`). On GitHub, run **Import corpus** (`import-corpus.yml`, manual only); the same files are the run's artifact. Neither the workflow nor these files start a release (`deploy.yml` ignores them).

## Safety

The downloaded files are untrusted data. `fetch.mjs` only downloads and hashes: it never runs, extracts or evaluates a file, writes them without the executable bit, keeps each schema in its own folder and refuses a path that would leave it. `count_source.py` reads them as text and runs with `python3 -I` from this folder. dbt projects are read from their yml: `dbt parse` is never run (it would execute the project's Jinja), so the dbt imports run without a manifest.

## How it scores

Each schema goes through `runSample` and `scoreSample` from `test/unit/realWorldScorecard.ts`, the same pipeline and metrics as the committed scorecard: the SQL import with the dialect detection picks (else the source's dialect, else `importAs` for a dialect the import does not offer) and the extension's default time limit; dbt's default scope, with the truth cut to that scope's folder by the folder `count_source.py` records for each model (its `.sql` file's under `models/`, else its yml's), so a model the import leaves out of the folder still counts as missing; the first semantic model in the folder. The truth comes from `count_source.py`, never from the importer. A Power BI relationship's "one" end is unique by the model's rules but not declared: the counter lists those as `impliedUniqueKeys`, which an import may add without it counting as an extra key, and without credit for it. Two tables of the same name in different schemas are two tables; the import names them `{schema}_{name}` (with the rename in its ledger), so the scorer compares them under those names (`qualifySameNames` in `realWorldScorecard.ts`; a relationship end that is ambiguous names its schema in the committed truth, while the counter's relationships do not, so in the corpus such a link can still show as extra). Where sqlglot cannot read a statement the counter reads it structurally and says so (the table's **Truth** column: `exact`, or `~N` statements read the approximate way). Snowflake types are kept as the source writes them (`NUMBER`, `TIMESTAMP_TZ(9)`; sqlglot would print `DECIMAL(38, 0)` and `TIMESTAMPTZ`), Snowflake `HYBRID` / `ICEBERG` tables and `CREATE OR ALTER TABLE` are tables (a `CREATE OR REPLACE` of a table takes the old one's own foreign keys with it, `CREATE OR ALTER` keeps them; a session's `TEMP` / `TEMPORARY` / `VOLATILE` table is not counted, Oracle's `GLOBAL TEMPORARY TABLE` is; a column's own `FOREIGN KEY REFERENCES t` is a foreign key to `t`'s primary key), a BigQuery name quoted whole (`` `project.dataset.table` ``) is split into its parts, and Spark, Hive and BigQuery strings take backslash escapes. A Tabular Editor Save to Folder is put back into the model.bim shape (relationships from `relationships/` or, with LocalRelationships, from each table's `TabularEditor_Relationships` annotation) and counted as model.bim. On the committed real-world SQL samples the counter matches the hand counts exactly for Pagila, Sakila, AdventureWorks, Snowflake and Databricks; it does not replay migrations (no DROP or RENAME), so it is not used on migration folders.

**Round trip.** For every SQL and Power BI schema that imports, the scorer also runs the DBML round trip of the generated tests (`test/unit/generated/dbmlRoundTrip.ts`: the converted DBML through Import DBML, exported with the rich export, imported again) and records what came back different, with the same allowances (see `docs/dev/generated-tests.md`). The table's **Round trip** column says `same`, how many items differ, or `threw`; `IMPORT_CORPUS_ROUND_TRIP=0` skips it.

Adding a schema: add it to `sources.json`, run `node scripts/corpus/pin.mjs --only <name>`, then `node scripts/corpus/score.mjs --only <name>`.
