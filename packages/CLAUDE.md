# Packages (`@erd-studio/core`, `@erd-studio/renderer`)

> Moved out of the root `CLAUDE.md` so it loads only when needed. Loads when you read files under `packages/`. Everything here ships to npm for a downstream viewer app; the always-on compatibility rules are in the root `CLAUDE.md`, and the background is in `docs/dev/compatibility.md`.

**npm workspaces (`packages/*`).** Two packages are published to npm — **automatically**, by `.github/workflows/publish-packages.yml`, whenever a change to them lands on `main` (see `docs/dev/releasing.md`) — and are consumed by a shipped downstream app (see `docs/dev/compatibility.md`). In the extension they are built **from source**: tsconfig `paths` (root, webview, mcp-server) and exact-match vitest aliases point `@erd-studio/core` / `@erd-studio/renderer[/editor|/store|/sizing]` at `packages/*/src`, while each package's `exports` point only at its `dist/` (`npm run build:packages`). `.vscodeignore` excludes `packages/**`; nothing there ships in the VSIX except what esbuild bundles.
- **`@erd-studio/core`** (`packages/core`) — the domain model types (`semantic`, `layer`, `display`, `discrepancy`, and the canvas edit messages in `canvasMessages.ts`) **and the pure raw-files → DisplaySubjectArea pipeline**: `domain.ts` (`parseSubjectAreaJson`, `validateSubjectAreaDocument`, `resolveSubjectAreaLayer`, `buildUnifiedSubjectArea`, `toLogicalStage`, `SubjectAreaFileError`, `SubjectAreaValidationError`, `NON_SUBJECT_AREA_DIRS`), `logicalModel.ts` (`parseTableText` — aliases resolved in one linear pass, optional `maxNodes` budget — and `isSafeTableName`), `layers.ts` (`validateLayersConfig`, `parseLayersText`), `displayDomain.ts` (`toDisplaySubjectArea`, `computeMissingPositions`), `positions.ts` (the former `positionService`), `loadDisplayDomain.ts` (one async call over a `readFile`, for hosts outside VS Code, with opt-in limits and four error classes) and the **one-way diagram exporters**: `exportDiagram.ts` (`DiagramExportFormat`, `DIAGRAM_EXPORT_FORMATS`, `DIAGRAM_EXPORT_FILE_EXTENSIONS`, `exportDiagram`, `diagramExportFileName`) over `exportMermaid.ts` (`toMermaid`), `exportDbml.ts` (`toDbml`) and `exportDbmlRich.ts` (`toDbmlRich`, format `dbml-rich` — see the end of this paragraph), sharing one traversal in `exportShared.ts`. They are pure functions over any `DisplaySubjectArea` (hosts pass the logical stage), deterministic, never throw on a minimal or older-core domain, export no positions, carry ERD semantics as readable lines in DBML table and column notes (never DBML's unique `as` for `alias`) or Mermaid key markers / `%%` comments, and carry a versioned header (`// erd-studio dbml-export v1` as DBML's first line, `%% erd-studio mermaid-export v1` right after Mermaid's `erDiagram`) — the output is a contract pinned by `.dbml` / `.mmd` goldens beside the `DisplaySubjectArea` ones. **Portability is part of the contract:** the DBML uses no custom properties (`[erd_…: …]` needs `@dbml/parse` ≥ 9.1; every older parser rejects the whole file) and no standalone `Note` blocks, and every output is read by the current `@dbml/parse` **and** the old `@dbml/core` 3.13.4 / 2.6.1 / 2.4.2 parsers (`readDbmlEverywhere` in `packages/core/test/exportParsers.ts` requires all four to read the same thing; 2.4.2, June 2022, is the promised floor — older releases reject schema-qualified tables or `<>`) — so a note's backslash that comes before another backslash or a `'` is followed by a space (with a comment), since no escape reads alike in old and new parsers; every Mermaid output must parse in Mermaid 10.0.0 (hence `erDiagram` first — 10.0 to 10.4 reject a comment before it) and the current release. Those parsers are exact-version devDependencies (`@dbml/parse`, `dbml-core-v3` / `dbml-core-v2` and `mermaid-current` npm aliases, `mermaid` at 10.0.0), each published at least two weeks before it was adopted; core's runtime dependencies are `yaml` and the exact `@dbml/parse` 11.0.0 pin, which only the `@erd-studio/core/dbml` subpath loads (native DBML storage; the main entry stays parser-free). The renderer's `.` entry re-exports them for the downstream viewer, and the extension reaches them through `src/services/diagramExport.ts` (`exportSubjectAreaFile`, vscode-free, bundled by `dist/cli.js`: `getSubjectArea` → `buildLogicalDisplaySubjectArea` → `exportDiagram`, so the canvas command and `erd-studio export` give identical bytes). A mapping change is a deliberate golden update plus a CHANGELOG line. **Rich DBML is the exception to the portability rules above, by design:** `toDbmlRich` (`// erd-studio dbml-export v2 (DBML 9.1+)`) carries ERD fields as custom properties named only in `dbmlRichProperties.ts` (shared with the extension's DBML import — never hardcode one), always quoted strings, Refs from the FK end (a one-to-one from its key end, since DBML reads its second end as the FK) with `?` on every non-PK end, and its positions in dbdiagram's `<name>.dbdiagram` (`dbdiagramLayout.ts`: `toDbdiagramLayout` / `serializeDbdiagramLayout` / tolerant `readDbdiagramLayout`; the shape comes from a file `dbdiagram pull` wrote, kept in `test/dbdiagram-pull/`, never from dbdiagram's CLI code). Its goldens are `<fixture>.rich.dbml` and `<fixture>.dbdiagram` (plus `rich-features.*`), read by `readDbmlRich` with `@dbml/parse` 9.1.1, 10.3.1 and 11.0.0 (`dbml-parse-v9` / `dbml-parse-v10` aliases and the pin itself), which must agree with no error, warning or NULL lint info. The export file base is `exportFileName.ts`, so a `.dbml` and its `.dbdiagram` always share it. The host services **delegate** to it and keep only file access, caching and messaging: `SubjectAreaService.getSubjectArea` reads the file then calls `parseSubjectAreaJson` → `validateSubjectAreaDocument` → `buildUnifiedSubjectArea`, `TableLibraryService.readTableFile` calls `parseTableText`, `LayerService.validateConfig` calls `validateLayersConfig`, and `SemanticEditorProvider.buildDisplaySubjectArea` calls `toDisplaySubjectArea` with the editor payload. Core warnings carry no prefix; each host adds its own (`[DomainService] `, `[LayerService] `; the host prefixes keep the pre-rename class names, which `logs.json` pins). `src/types/{semantic,layer,display,discrepancy}.ts` and `src/services/positionService.ts` are named re-export shims. Core may not import Node built-ins, `vscode`, React or React Flow. **Parity:** `test/unit/displayDomainGolden.test.ts` pins what the host posts (goldens in `packages/core/test/fixtures/golden`, regenerate with `UPDATE_GOLDEN=1` only for an intended change) and `packages/core/test/unit/loadDisplayDomain.golden.test.ts` holds core's one-call pipeline to the same files.
- **`@erd-studio/renderer`** (`packages/renderer`) — the diagram canvas: `TableNode`, `FkEdge`, `AnnotationNode`/`AnnotationEdge`, `DetailPanel` (with its editors), `Legend`, the `common/` key-badge and column-row components, the canvas hooks (`useColumnExpansion`, `useColumnReorder`, `useFocusWithinRow`, `useLongPressDrag`), the pure `lib/` helpers (`graphTransformer`, `nodeOverlays`, `edgeDistribution`, `nodeSizing`, `stageColors`, …), the canvas store slice and `styles/theme.css`. Components get their store from `CanvasStoreProvider` (React context) and post edits through the `CanvasHost` from `CanvasEnvironmentProvider` — never `acquireVsCodeApi()` directly. Entry points: `.` (viewer API and types), `/editor` (everything the webview uses), `/store` (store slice + context, no React Flow runtime) and `/sizing` (node size estimation for the ELK runner). `test/unit/packagesBoundary.test.ts` guards these rules.
  - **Viewer mode.** `ErdCanvas` (`src/ErdCanvas.tsx`, derived from `EditorCanvas` in `webview/App.tsx`) is the read-only viewer for pages outside VS Code: its own store per instance, `readOnly` forced, optional local-only dragging (`lib/dragHandleSides.ts` re-picks the moved nodes' edge sides with `pickHandleSides`; `resetLayout()` restores them). It sets `CanvasEnvironmentProvider`'s `viewer` flag, which components read with `useIsViewer()` to drop the affordances a domain's `readOnly` still shows (clickable relationship rows, the key-type menu arrow — kept but hidden so rows align — empty rationale fields and "+ Add", node context menu, column long-press, annotation double-click). Every viewer gate is `viewer ? … : <upstream expression>`, so the extension (no `viewer`) renders exactly as before; `test/unit/extensionMode.test.tsx` and `ErdCanvas.viewer.test.tsx` in the package pin both sides.
  - The README lists every `--vscode-*` variable the package's CSS and TSX read; a page embedding `ErdCanvas` must define them. Update that list when a component starts reading a new one.
