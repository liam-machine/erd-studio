# Changelog

All notable changes to `@erd-studio/core`. While `0.x`, a breaking change bumps the minor version.

## 0.5.0

> **For hosts that render committed projects.** A DBML table is now its schema folder and its name, so two tables of one name in different schema folders can sit on one diagram (ERD Studio 2.0.4). On such a diagram `DisplayTable.name` is `<schema>.<name>` for the two of them, with the table's own name in the new optional `tableName`; print and match `tableName ?? name` wherever `name` was read as a file stem, a warehouse name or a dbt model name, and never split `name` at a dot. Such a diagram is written `erd_schema_version: '8'`, which 0.4.x refuses ("Please update the extension"). Bump the pin to 0.5.0 and **bump the cache key**: a `DisplaySubjectArea` cached by 0.4.x for a diagram that already listed both tables shows one table twice. A project where no two tables share a name renders exactly as before.

### Added
- **Table identity** (`tableIdentity.ts`, main entry, parser-free): a DBML table is identified by its schema folder and file stem (`TableId`, `TableFileId` with the layer beside it), compared without case; the layer is not part of it. `tableIdKey(id)` is the comparison key, `tableIdOfPath(rel)` reads it from a `<layer>/tables/<schema>/<name>.dbml` path, and `sameTableId` compares two. `assignTableRefs(tables)` names each table of a scope by its bare name unless another table there has that name (then `<schema>.<name>`, `qualifiedRef`); a project with no shared name gets only bare names. `matchTableRef` / `resolveTableRef` / `resolveTableRefs` turn text back into a table by comparison (reference, `<folder>.<name>`, another qualifier, then a bare name only one table has), never by splitting on a dot; types `TableRefCandidate`, `TableRefStep`, `TableRefMatch`, `ResolveTableRefOptions`. Nothing reads or writes through them yet: every result and golden is unchanged.
- **Reading two tables of one name in different schema folders** (`bronze/tables/bqs/addresse.dbml` and `bronze/tables/ccc/addresse.dbml`). A diagram, display or export of a project where no two tables share a name is byte-identical to before; only a diagram that lists two such tables reads differently (it used to draw one of them twice, with the other's relationships).
  - `parseSubjectAreaDbml` names each `use` member by its reference: its name, or `<schema>.<name>` (the schema spelled as the use path's folder) when another member of the diagram has the same name in another schema folder. `members`, `logical.models`, positions keys, `linked_table` sticky links, `erd_stub_columns` entries and pending Ref ends all hold it. `DbmlMemberUse` gains the optional `ref`, `schema`, `layer` and `qualifier` (the specifier's), `DiagramUseRole` the optional `schema` and `layer`, and the reading the optional `layoutSharedBare`. An `erd_layout` line, sticky link or stub entry names a member by its reference, `<schema>.<name>` or a bare name only one member has; a qualified line claims its table first, and a bare name two members share (one line kept by an older version) goes to the first of them (`erdLayoutView`'s new optional `tables` argument; the view gains the optional `sharedBare`). `diagramSummaryDbml` and `subjectAreaMembersDbml` return the same references (`memberUses` keep their shape).
  - `readRelationshipsDbml` keeps a Ref between two same-named tables whose ends write different qualifiers (`ccc.addresse.id > bqs.addresse.id` was dropped as "joins a column set to itself"; `attachRelationships` still drops one whose two ends land on one table, a stale qualifier, with a warning), and the reading gains the optional `useTables` (each table a selective `use` line imports: name, qualifier, path).
  - `attachRelationships` tells same-named tables apart when the tables carry their file (`DbmlAttachTable` gains the optional `ref`, `path`, `schema`; `table.schema` may be passed): a Ref end resolves by the relationships file's own `use` line for its spelling (readings gain the optional `semanticPath`), then by its qualifier (schema folder, then declared schema), then by a name one table has; a qualifier that names no table still lands on the one table of its name, as before, unless its use line names another file that exists (`dbmlTableLookup`'s new `exists` option); an unqualified end is held to the same test when its own `use` line names another schema folder's file of its name, or when its file imports the name only from other schema folders, so a diagram showing one table of a name never draws a Ref its file says is about another (`contestedUsePaths` lists those paths too); an unqualified end several tables share goes to the one in `tables/public/`, else is not attached, with a warning that names every schema folder the file imports the name from. Ends and `byOwner` keys use the reference. New: `contestedUsePaths`, types `DbmlTableLookup`, `DbmlAttachReading`, `DbmlRefEndHint`, `DbmlUseTable`; `DbmlRefLocation` gains the optional `ownerPath` and `targetPath`. Tables with no schema folder keep the old rule (the first of the name).
  - The exports (`toDbml`, `toDbmlRich`, `toMermaid`, `exportDiagram`) write both tables of such a diagram, never leaving one out because its written name repeats: the DBML exports declare `Table bqs.addresse` and `Table ccc.addresse` (the schema, then `tableName ?? name`; a table with no schema, or one whose schema and own name another table on the diagram already declares, as in a copied schema folder, keeps the diagram's name, quoted), with their Refs, `TableGroup` entries, `erd_layout` lines and `linked_table` naming each table as the diagram does; Mermaid names the entities `"bqs.addresse"` and `"ccc.addresse"`, which Mermaid 10.0.0 and the current release read. Every existing export golden is byte-identical; new goldens `same-name-two-schemas.kunden.{dbml,rich.dbml,mmd}`. The storage-equivalence comparator keys by the diagram's names already and keeps the two apart.
  - `loadDisplaySubjectArea` reads each member from its own file and hands it on under its reference; `DisplayTable` gains the optional `tableName` (the table's own name, present only when `name` is `<schema>.<name>`), from the runtime-only `DiagramNamedTable` (`tableNameOf`). A member whose file is gone is never read from a file another member's line points at. A Ref end whose qualifier names none of the one member of its name, while its own `use` line names another file, costs one read of that file (none when a member was already looked for there; a failed read changes nothing). `findDbmlTable` receives a second argument (`DbmlTableHint`: the stale line's schema, layer and path), and `dbmlTableFinder` honours it: the hinted schema's file first, another schema's only when it is the one table of the name. A contested Ref end whose use path is gone is asked of the finder the same way: when it does not answer with the one table of the name the diagram shows, the end means a table elsewhere and is not drawn on it. A member read from another folder the lines name now warns, as one the finder finds does. Key evidence looks dbt up by `tableName` (`KeyedTable.tableName`).
- **Writing two tables of one name in different schema folders.** A write of a diagram where no two members share a name produces exactly the bytes it did before.
  - `editSubjectAreaDbml` pairs each member after the edit with its `use` line by identity: by name, then by the new optional `renamedMembers` (a member's reference before the edit → after it), then by the line that already imports its table's file. So a member whose reference changes when a table of its name joins or leaves the diagram (`addresse` ↔ `bqs.addresse`) keeps its line byte for byte, and its position, sticky links, stub entries and pending Ref ends follow it in the same edit. `after` may name members by any text `resolveTable` resolves; each is written under its reference (its name, or `<schema>.<name>` spelled as its file's folder, `assignTableRefs`). `pathChanged` is a set of the diagram's references; a qualified member is matched by its reference only, never by its file's stem. On a diagram that holds such a pair (before or after the edit), `linked_table` and `erd_stub_columns` are written as the object names them, and a bare `erd_layout` line an older version kept for two tables (`layoutSharedBare`) gives way to each member's own line on the next edit that changes something (once `erd_layout` holds no merge conflict). A member whose reference changed is never taken for an unlinked member an edit renamed.
  - `erd_schema_version`: `editSubjectAreaDbml` writes `'8'` (`DBML_TWIN_SCHEMA_VERSION`, new) on an edit that leaves a diagram with two members of one name, and `'7'` on the edit that leaves it none; a diagram with no pair keeps the version line it has (or none), and a no-op edit is byte-identical. A member whose line an edit cuts (its table deleted, in `pathChanged` with no file now) no longer counts: the table it shared a name with goes back to its bare reference in the same edit, and the diagram to `'7'` when no other pair is left. `renderNewSubjectAreaDbml` writes `'8'` for a new diagram with such a pair, its `erd_layout` lines under each member's reference. `editDiagramLayoutDbml` (a drag) marks a diagram that holds a pair but an older version left at another version `'8'` when it writes its lines; it never touches the version line of a diagram with no pair.
  - `withMemberRefs(layout, tables)` (new, `erdLayout.ts`): `withMemberSpelling` for members that carry their identity. Each member keeps one line, under its reference (the line spelled exactly so, else the first in code-unit order); every other line that names it is dropped: a case variant, a `<folder>.<name>` line beside the member's own (which the reader would otherwise prefer, so a drag never stuck), a bare line two members once shared. The diagram writer and `editDiagramLayoutDbml` (without `members`) use it; with bare references and no schema folders it is `withMemberSpelling`.
  - `rekeySubjectArea(obj, renames)` (new, main entry, parser-free): a v5 subject-area object with table references renamed in every place one is stored (`logical.models`, relationship ends, positions keys, sticky links, `stubColumns`), compared without case; a renamed position takes the place of a stray line of its new name. Renaming back with the inverse map gives the object again.
  - `editRelationshipsDbml` takes the optional `identify` callback (`DbmlTableText`: a Ref end's or `use` specifier's name, qualifier and the file its own `use` line imports). With it, `owners`, `renamedOwners`, `pathChanged`, `requalified`, `resolve` and the relationships' ends are keyed by what it returns (a library reference such as `ccc.addresse`), so renaming, moving or dropping one table of a pair re-spells, cuts and rewrites only its own Refs and `use` lines, and a Ref between the two (`ccc.addresse.id > bqs.addresse.id`) is no self-join. Without it, every output is byte for byte what it was.
  - The storage-equivalence comparator's Convert `schemaFallback` is given a table's own name (`tableName ?? name`).
  - Canvas messages can name a table not on the diagram by its file, for a host that tells two tables of one name apart: `AddExistingModelMessage.payload.sourcePath` and `AddExistingModelsMessage.payload.sourcePaths` (the Add Existing row's `ExistingTablePreview.sourcePath`, project-relative; one per name, `''` for a row with none), `OffDiagramRelationship.otherTablePath` (what "+ Add" posts as `sourcePath`), and `ExistingTablePreview.layer` / `.schemaFolder` (a DBML row's layer and schema folder). All optional: an older canvas or host sends and reads names alone, which mean the table the library finds by that name.
  - `dbmlRefEndHints(reading, ref)` (new, main entry, parser-free): what each end of a stored Ref says beside its table part (its qualifier and the table file the relationships file's own `use` line for it names), exactly as `attachRelationships` reads it, so a host that indexes Refs itself resolves their ends by the same rule.
  - `DbmlAttachResult` gains the optional `unresolved` (`DbmlUnresolvedRef`, new): each Ref the attach leaves undrawn because an end names a table that more than one schema folder has and nothing says which (`ambiguous`, with those folders and, when the end wrote one, its `qualifier`: `zzz` in `zzz.addresse`, a schema none of them is in), or because both ends land on one table with the same columns (`selfJoin`, a stale qualifier). Each already had its sentence in `warnings`; this says the same with its file and line, for a checker. Absent when there are none, so an attach of a project with neither returns the same object as before.

### Changed (breaking)
- `DisplayTable.name` can hold `<schema>.<name>`: for the two members of a DBML diagram that share a name from different schema folders (the schema spelled as the folder in each `use` path), so the field is still unique on the diagram and still what `DisplayRelationship.fromModel` / `toModel`, `viewConfig.positions` keys, `stubColumns` and `Annotation.linkedModel` refer to. Every other table's `name` is its own name, as before. The table's own name is the new optional `DisplayTable.tableName`, present only when it differs. The same references are what `DbmlSubjectAreaReading.members`, `logical.models`, `subjectAreaMembersDbml` and the attach's `byOwner` keys hold for such a diagram; their types are unchanged. A pinned MINOR because a reader that treats `name` as a file stem or a dbt model name must now read `tableName ?? name`.

### Changed
- `attachRelationships` / `dbmlTableLookup`: an unqualified Ref end whose relationships file's own `use` lines import tables of its name from two or more schema folders is no longer attached to the one table of that name the lookup sees (a diagram showing only one of them), but goes to the one in `tables/public/` among those it sees, else is reported in `unresolved`; `loadDisplaySubjectArea` then does not draw a Ref whose other end is so reported (its bare name would land on the member of that name), as the extension does not. A file whose `use` lines import each name from one schema folder attaches and draws exactly as before.
- `attachRelationships` / `dbmlTableLookup` / `contestedUsePaths`: the new optional `tableDirs` option, for a reader that sees only some of the library (the table folders its files' `use` lines name). With it, a qualified Ref end with no `use` line of its own whose qualifier names neither the folder nor the declared schema of the one table of its name in scope (`bqs.kunde.addresse_id > zzz.addresse.id` on a diagram showing `ccc.addresse`) lands on that table only when no file of its name exists in those folders, in the relationships file's own, or in the qualifier's own folder: another table of the name means nothing says the end is this one, so it is not drawn. `loadDisplaySubjectArea` passes the diagram's folders and reads those paths (a gone one is put to `findDbmlTable`, whose null says the name is shared), so core draws what the extension draws. A lookup without `tableDirs` (the extension's, over the whole library) is unchanged, and so is any project where one table has the name: a stale qualifier still lands on it.
- `outlineDbmlFile`: each `metadata` entry gains the optional `qualifier` (the schema the block writes before its table), so a checker finds the block's table among tables of one name in different schema folders.
- `loadDisplaySubjectArea` looks for a member whose `use` line names a file that is gone (and says its schema folder) as `dbmlTableFinder` does, with or without a finder: in the other table folders the diagram's lines name, a file of its name in its own schema folder first (its layer's first); else one in another schema folder only when a single schema folder holds the name. When two or more do, or the one that does is another member's own file, the member is drawn missing with a warning, never as one of them. To tell, it reads each of those folders' files of the name instead of stopping at the first, which costs more reads only on a diagram whose lines name three or more table folders. A diagram whose members are all where their lines say reads exactly as before.
- `CURRENT_SCHEMA_VERSION` is 8: a DBML diagram declaring `erd_schema_version: '8'` reads exactly as one declaring `'7'` (its `schemaVersion` is 8). The diagram writer writes 8 only for a diagram that holds two tables with one name in different schema folders (above), so a core that cannot tell them apart refuses that diagram ("Please update the extension") instead of drawing the two as one. Above 8 is refused as before. `DBML_SCHEMA_VERSION` (written) stays 7, and the JSON ceiling stays 6.

## 0.4.0

> **For hosts that render committed projects.** To draw a project stored as DBML (ERD Studio 2.0's default), a host needs this version and `dbml: dbmlStorageReader` (from `@erd-studio/core/dbml`) passed to `loadDisplaySubjectArea`, its bundler must include `@dbml/parse`, and its cache key needs a bump. A host on core 0.3.0 or older given a `.dbml` diagram path throws `SubjectAreaFileError('invalid-json')` with `transient: true`.
>
> **Context fields.** A table file written by this version spells its fields as bare settings (`purpose: '…'`, `open_questions: '…'`, `owner: '…'`), which no earlier core reads, and a project may hold a `.erd-studio/fields.yml`. To show a project's own field list, pass `readFieldsFile: true` to `loadDisplaySubjectArea`. The renderer's Detail panel changes with it, so bump the cache key.

### Added
- **Context fields**: the fields a project records on its tables and columns, built in or the team's own, and the one set of rules every reader, writer, check and renderer applies to them. Everything is exported from the main entry and is parser-free apart from `fieldsFile.ts`, which uses `yaml`.
  - **The catalogue** (`fields.ts`). `BUILT_IN_FIELDS` lists every built-in field in catalogue order, each a `FieldDefinition` with `key`, `scope`, `label`, `type`, `values`, `guidance`, `filledBy`, `showFor`, `status` and `home`. The other exports are `builtInField(key, scope)`, `STARTING_FIELD_LIST` (the fields a project without a fields.yml records: tables `grain, purpose, decisions, open_questions, role, scd_strategy, measures`; columns `natural_key, scd_type, additive_type`), and the types `FieldType`, `FieldFilledBy`, `FieldShowFor`, `FieldScope`, `FieldStatus`, `FieldHome`, `FieldDefinition` and `FieldList`, with the vocabularies `FIELD_TYPES`, `FIELD_FILLED_BY` and `FIELD_SHOW_FOR`. The table roles are `TABLE_ROLE_VALUES`, `DIMENSION_ROLES` and `FACT_ROLES`, read by `isDimensionRole`, `isFactRole` and `fieldApplies`. A field's value stays where it always lived. A built-in text field is in `rationale`, a typed built-in in its own property (`grain`, `modelRole`, `isNaturalKey`, `scdType`, `additiveType`), and a team field or the column field `business_rule` in `meta`. Nothing stores a second copy.
  - **The resolver.** `resolveTableFields(table, list?)` and `resolveColumnFields(column, table, list?)` return the `FieldRow`s a Detail panel draws. Each row has `id`, `definition`, `value`, `choice`, `source`, `editable` and `outsideChoices`. The listed fields come first, then retired built-ins with a value, then other built-ins with a value, then `meta` keys the list does not name. A field with a value always shows. `meta.dbml` is never a row (`DBML_IMPORT_META_KEY`). The resolver never throws on malformed input or input from an older core. An unknown type or home from a newer core gives a read-only row. Also exported: `fieldRowId` and `metaFieldDefinition`.
  - **Keys and spellings.** `FIELD_KEY_PATTERN` and `isReservedFieldKey` / `reservedFieldKeyReason` cover DBML's own settings, ERD Studio's own (`DBML_SETTING_NAMES`, `ERD_SETTING_NAMES`), `constructor` and `__proto__` (`UNSAFE_FIELD_KEYS`), and the prefixes `erd_`, `rationale_` and `meta_` (`RESERVED_FIELD_KEY_PREFIXES`). `isBareMetaKey` decides when a meta key is written bare. `rationaleSpellingNames` and `metaSpellingNames` list every DBML spelling of a field, in precedence order.
  - **Rationale keys.** `fieldKeyToRationaleKey` (`open_questions` → `openQuestions`), `rationaleKeyToFieldKey`, `isRationaleFieldKey`, and `RATIONALE_FIELD_KEYS`, the one order the storage writer and the exports use: `purpose, decisions, openQuestions, design, grainChoice, roleChoice, scdStrategy, measures, sourceOfTruth, freshness, knownIssues, retention`. The six keys of the first release keep their relative order. `RATIONALE_KEYS` stays exported, unchanged, as those six.
  - **`Rationale`** gains the optional `decisions`, `openQuestions`, `sourceOfTruth`, `freshness`, `knownIssues` and `retention`. `design`, `grainChoice` and `roleChoice` are retired fields: still read and shown, never offered. A model file's `rationale:` map is read for every key in `RATIONALE_FIELD_KEYS`, camelCase only (`open_questions:` there is not the field). Older cores ignore the new keys.
  - **`fields.yml`** (`fieldsFile.ts`). `parseFieldsText(text, { maxNodes?, maxChars? })` reads the file into a resolved `FieldList` plus `FieldsFileProblem`s, each with a stable `code` (`FIELDS_FILE_PROBLEM_CODES`), a `severity`, an optional `line` and `key`, an optional `mergeConflict: true` (a `fieldsYamlInvalid` for git conflict markers, `line` the first marker), and a message that names no file. It never throws on any text. A file that is not YAML, is not a map, or is over budget gives the starting set. A missing `tables:` or `columns:` section gives the starting set's fields for that scope. Aliases are followed against the budgets one at a time. `renderFieldsText(list)` writes a list back as fields.yml text that reads back the same. Also exported: `FIELDS_FILE_NAME` (`fields.yml`, next to `layers.json`) and `FIELDS_FILE_VERSION` (1).
  - **`DisplaySubjectArea.fields`** (optional): the project's resolved field list, set only when the project has a fields.yml. A renderer reads it as `fields ?? STARTING_FIELD_LIST`. It is set by the new `ToDisplaySubjectAreaOptions.fields`, or by `loadDisplaySubjectArea`'s new `readFieldsFile: true`. With that option the loader reads `{semanticDir}/fields.yml` once, right after `layers.json`. A missing file gives no list. A file longer than `maxDomainChars`, or one that is not YAML, gives a warning and no list. `maxYamlNodes` and `maxYamlChars` bound its expansion. It never adds an error class. The option is off by default, so existing read sequences and results are unchanged. A project without the file draws exactly what it drew before, and every existing golden is byte-identical.
  - **DBML storage** (`@erd-studio/core/dbml`). Every field is one setting, `<key>: '<value>'`, on the `Table` line or on the column, with no prefix: `purpose: '…'`, `open_questions: '…'`, `owner: '…'`.
    - `parseTableDbml` reads every spelling. A rationale field's value is the first non-empty one of `erd_K`, `K`, `erd_rationale_K` and `rationale_K`. A meta field is read from bare `k` (when `isBareMetaKey`), then `meta_k`, then `rationale_k` (k not a catalogue rationale key), then the `meta_json` entry; there `''` is a value. A bare reserved setting is not read and is kept byte for byte.
    - The reading gains the optional `fieldSpellings`. Each entry has `owner`, `home`, `key`, `spelling`, the optional `name` (the setting as the file writes it, such as `erd_rationale_purpose`; for a `meta_json` entry, the setting that holds it), `used` and `old`, for every field-bearing setting found, so a check can count old spellings and fields spelled twice. `rationale_<K>` of a retired built-in (`design`, `role_choice`, `grain_choice`) and an entry of an `erd_meta_json` are never old. They are not `problems`.
    - `renderNewTableDbml` writes rationale fields bare, in `RATIONALE_FIELD_KEYS` order. It writes a text meta value under a key that `isBareMetaKey` accepts bare. A reserved key, or a same-scope catalogue key such as `meta.purpose`, stays `meta_<k>`. Anything else goes in the one `meta_json`.
    - `editTableDbml` edits in place whichever spelling was read. A clear removes every spelling of that field's home. A no-op edit is still byte-identical. A `Metadata Table` or `Metadata Column` block that names the table by its `as` alias is edited and cleared like one that names it (it used to be read but never edited, so an edit came back overridden), and a rename or move leaves its target as it is.
    - `rationaleKeyOf` accepts every catalogue rationale key, so Import DBML reads the rich export's `rationale_decisions`, `rationale_open_questions` and the rest.
- `DisplayTable.layer` and `DisplaySubjectArea.layerConfigs` (both optional): `loadDisplaySubjectArea` gives each DBML diagram member the layer of the file it was read from, and the diagram every configured layer, so a renderer can badge a table borrowed from another layer with its own. Absent for YAML tables and from older cores; a renderer then draws the table as in the diagram's layer. The storage-equivalence comparator gains the row `tableLayers`, which drops both (a YAML read has neither).
- **Native DBML storage: the `@erd-studio/core/dbml` subpath.** The readers and writers of ERD Studio 2.0's `.dbml` table, relationships and diagram files, in its layer-first tree: `<layer>/tables/<schema>/<name>.dbml` (one `Table <schema>.<name>`), `<layer>/relationships/<file>.dbml` (Refs and the `use` lines they need) and `<layer>/diagrams/<name>.dbml` (table `use` lines, `use *` of the relationships files it imports, sticky `Note`s, then the `Project` with the positions in `erd_layout`). `parseTableDbml(text, stem, { schemaFolder }, parser?)` (the schema is the qualifier, else the folder; warnings `unqualifiedTable`, `schemaFolderMismatch`, `schemaProperty`), `readRelationshipsDbml` (with the optional `uses` and `otherElements`), `parseSubjectAreaDbml(text, filePath)` (refuses a path that is not `<layer>/diagrams/<n>.dbml`; the reading has `relationshipsUses`, `otherUses`, `useTableDirs`, `layoutProblems` and `layoutConflictLine`), `subjectAreaMembersDbml(text, filePath)`, `diagramSummaryDbml` (members, imports and unlinked names from a syntax-only parse) and `diagramUseRole` (what a diagram's `use` line points at), `readErdLayoutDbml` / `erdLayoutEntrySpan` / `editDiagramLayoutDbml` (a diagram's positions), `compileDbmlProject` (a multi-file compile, as other DBML tools read the project), `outlineDbmlFile` (a file's `use` lines, Enums, `Metadata` block targets and the Tables it declares), `renderNewTableDbml` (needs a schema) / `editTableDbml` (with `requalify` to move a table to another schema), `editRelationshipsDbml` (with `relationshipUnits`, `relationshipUnitsWithMembers`, `refUnitSortKey`, `usePathBetween`, `DBML_CONVERT_FIRST_MESSAGE`, and the edit fields `requalified` and `columnChanges`, which rewrites a Ref in place), `renderNewSubjectAreaDbml` (the `Project` last, with `positions`) / `editSubjectAreaDbml` (`relationshipsImportsFor(memberNames, current, unlinked)` decides the imports; `keepLayoutIfConflicted`), `applyTextEdits` / `TextEdit`, `DbmlEditRefused`, and `dbmlStorageReader`, the value to pass as `loadDisplaySubjectArea`'s `dbml` option. The writers splice at parser node offsets: a no-op edit returns the text byte for byte, comments and settings ERD Studio does not model survive, and a file that does not parse is refused, never regenerated. Every export is typed with this package's own types. The main entry stays parser-free, so a bundle that never imports the subpath never pays for the parser.
- **`formatDbml(text, options?)`** (from `@erd-studio/core/dbml`, with the types `DbmlFormatOptions`, `DbmlFormatResult` and `DbmlFormatSkipReason`): ERD Studio's one canonical `.dbml` layout. It changes white space only (two-space indents, aligned column names, types and settings, a long column or index settings list one per line, `use … from` lines aligned, at most one blank line) and checks its own output: the token sequence, every comment's text and the syntax tree must be unchanged, or the text comes back as it was with `skipped: 'self-check'`; a file with a syntax error comes back unchanged with `skipped: 'parse-errors'` and its `errors`. String literals (a triple-quoted note's inner indentation included), quote styles and block comments are never touched. The extension runs it after every DBML write and behind Format Document; the writers themselves still splice, so a no-op edit stays byte-identical. The writers' new-content layout follows it: `renderNewTableDbml` writes the body `Note` first with a blank line after it, and a column's settings as `pk`, ERD Studio's properties, meta, then `note` last; `editTableDbml` puts a setting it adds at its place in that order (after the last setting that sorts at or before it, so a `note` that was last stays last) and a new description first in the body; `editRelationshipsDbml` writes a blank line between the Refs of different foreign-key tables in any file it changes.
- `loadDisplaySubjectArea` gains the options `dbml` (a `DbmlStorageReader`; without it a `.dbml` diagram rejects with a `SubjectAreaValidationError` saying to pass it) and `maxRelationshipsChars` (a relationships file longer than this is not read, with a warning). A DBML diagram's members are read by their `use` paths (then the diagram's `useTableDirs`, then YAML), and only the relationships files it imports are read, so it draws what other DBML tools draw. A `.dbml` outside `<layer>/diagrams/` is refused before anything is read (`dbmlNotADiagramMessage`; for an ERD Studio 1.9 pre-release path, `legacyDbmlFileMessage`, saying to convert the project again). A JSON diagram reads no DBML tables.

### Changed
- **A DBML table file stores a column's `meta.dbml.not_null`, `unique`, `increment` and `default` as DBML's own settings** (`not null`, `unique`, `increment`, `default: …`), and `parseTableDbml` reads those settings back into `meta.dbml` (also from a hand-written file, which before left them unread). A `meta_json` holding them, as earlier 0.4.0 builds wrote it, reads exactly as before and `editTableDbml` leaves it in place until the value changes; a `default` whose text reads as a number, boolean or `null` stays in `meta_json`. The `DisplaySubjectArea` shape and the exporters' mapping are unchanged; a hand-written `not null` now reaches `meta.dbml`, so the rich export carries it in `meta_json` like an imported one.
- The diagram exports print the context-field rationale keys too. `toDbml`'s table note and `toMermaid`'s `%%` lines gain `Decisions:`, `Open questions:`, `Source of truth:`, `Freshness:`, `Known issues:` and `Retention:` lines. `toDbmlRich` writes them as `rationale_decisions`, `rationale_open_questions`, `rationale_source_of_truth`, `rationale_freshness`, `rationale_known_issues` and `rationale_retention`. All of them follow `RATIONALE_FIELD_KEYS` order. The six first-release keys keep their labels (`Purpose`, `Design`, `Grain choice`, `Role choice`, `SCD strategy`, `Measures`) and their relative order, so no export of an existing file changes. The rich export still spells fields `rationale_*` / `meta_*`, not the bare storage spellings. A project's fields.yml labels are never used by an export.
- DBML table files written by this version hold bare field settings, which earlier cores and the extension's 1.9 pre-releases do not read: they draw the table without those fields.
- `@erd-studio/core/dbml` keeps diagram compiles in their own small cache, so reading a diagram's tables no longer pushes the diagram out before an edit reads it again. What is read is unchanged.
- `CanvasEditMessage` now includes `AddExistingModelMessage`, `AddExistingModelsMessage` and `OpenFieldsFileMessage` (`{ type: 'openFieldsFile' }`, no payload), which the renderer's detail panel posts. `openFieldsFile` is editor-only: the viewer never posts it, and a host may ignore it or open its project's `fields.yml`. Additive, but a host that switches exhaustively over the union with a `never` check must handle the three new types.

### Changed (breaking)
- `@dbml/parse` **11.0.0** (exact) is a runtime dependency, loaded only by the `@erd-studio/core/dbml` subpath. A bundler that follows that subpath must include it.
- `CURRENT_SCHEMA_VERSION` is 7, the newest version read in any format. A JSON diagram declaring 7 or more is still refused (`CURRENT_JSON_SCHEMA_VERSION`); a DBML diagram's `erd_schema_version` above 7 is refused with the same "Please update the extension" text.
- `TableLoadErrorKind` gains `'dbmlSyntax'`, `'dbmlInvalid'` and `'dbmlStructure'`, so an exhaustive `Record` or `switch` over it needs cases. `TableLoadError` gains the optional `code` (the DBML parser's error code) and `target`.
- `SubjectAreaFileErrorReason` gains `'invalid-dbml'` (a DBML diagram that does not parse: transient, with `line` and `column`; not transient, with `mergeConflict: true`, for git conflict markers).
- The loader's warning for a table it cannot find now reads `Model "<name>" not found in the table library` (was `… not found in logical-models/`).
- `describeTableLoadError` says `table file could not be read` for a `read` failure (was `logical-models file could not be read`): the `read` kind carries no format, and a `.dbml` table file can fail it too. The YAML and DBML wordings are unchanged.
- Cores 0.3.0 and older cannot read DBML projects (see the note at the top of this section).
- `DiagramExportFormat` gains `'dbml-rich'` and `DIAGRAM_EXPORT_FORMATS` a third entry: an exhaustive `switch` or a `Record<DiagramExportFormat, …>` over it needs a case, and a picker built from `DIAGRAM_EXPORT_FORMATS` offers it. `DIAGRAM_EXPORT_FILE_EXTENSIONS` maps both `dbml` and `'dbml-rich'` to `dbml`, so a `.dbml` file name no longer names one format.

### Fixed
- The DBML readers, writers and `compileDbmlProject` are about a third faster: while a compile runs, each of the parser's file paths computes its cache key once instead of on every query. The results are unchanged, and the parser is left as it was afterwards.
- `parseSubjectAreaJson` (and so `loadDisplaySubjectArea`) reads a domain file that starts with a byte order mark, which used to be rejected as invalid JSON.
- `loadDisplaySubjectArea` keeps a `meta` key named `__proto__` on a model or column. The model file reader kept it, but the copy each listing gets dropped a text value and turned a map value into the meta's prototype.
