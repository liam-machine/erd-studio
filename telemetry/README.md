# ERD Studio usage telemetry collector

A small Cloudflare Worker that receives ERD Studio's anonymous daily usage
heartbeat and stores it in a Cloudflare D1 database.

Each install sends **at most one** small JSON document per UTC day, describing
the previous day in counts and buckets: how many times a canvas was opened,
which features were used, which error codes fired, the extension and VS Code
versions and the OS family. The extension sends it only when VS Code's own
telemetry setting is on **and** `erdStudio.telemetry.enabled` is not turned off.
It goes through `vscode.env.createTelemetryLogger`, so VS Code's telemetry
output channel shows exactly what was sent.

**Nothing in this directory is part of the extension.** It has no dependencies,
no build step and no npm install: the file that deploys is `src/index.js`
exactly as written. `telemetry/**` is listed in the repo's `.vscodeignore`, so
it never ships inside the VSIX, and neither `esbuild.js`, the tsconfigs nor the
npm scripts at the repo root may come to depend on it.

---

## Read this before you deploy it

Running this Worker means holding data about other people's use of the
extension. Keep these promises — the extension's README makes them to users on
your behalf:

1. **Store only the validated body fields.** A row is the fields in
   `schema.sql`, every one of them an enum, a bucket, a bounded integer, a date,
   a strictly matched version string or the install id — plus `received_day`,
   the UTC date the Worker received it. There is no free text anywhere in the
   schema. Unknown keys in the body are **dropped**, not stored.
2. **No IP addresses, no user-agents, no location, no headers.** The Worker
   never reads `request.cf` and reads exactly one header, `Content-Length`, as a
   size pre-check. Cloudflare itself sees the connecting IP to route the
   request, like any website; this Worker does not keep it, and there is no KV
   namespace, no rate limiter and no hash of it anywhere. Do not add one — if
   abuse ever needs handling, flip the kill switch instead.
3. **The install id is not a person.** It is a random UUID v4 generated by the
   extension, kept in its `globalState` and **rotated every 30 days** — never
   `vscode.env.machineId`. It exists so one install's retry on the same day
   overwrites its earlier row rather than counting twice.
4. **90-day retention, enforced by the Worker itself.** A daily Cron Trigger
   (`17 3 * * *` UTC) runs
   `DELETE FROM heartbeats WHERE received_day < date('now', '-90 days')`. Raw
   rows never live on Cloudflare longer than that. Only per-day **aggregates**
   (no install ids) are kept longer — see "The local archive" below.
5. **No payloads in logs.** `log()` in `src/index.js` takes fixed labels and
   numbers only; the tests capture every log line and search it for canaries.

If you change what is collected, change the contract in the extension, this
Worker, `schema.sql`, the extension README's telemetry section and the local
archive together.

## What it does

- `POST /v1/heartbeat` — validate, upsert, `204`. Everything else is `404`
  (another path) or `405` (another method on this path). No CORS headers: the
  caller is the VS Code extension host, not a browser.
- `KILL_SWITCH` truthy → every request `503` before any D1 access.
- Body over **2,048 bytes** → `413`, counted while streaming, so a missing or
  lying `Content-Length` does not help.
- A known field with a wrong type or out-of-range value → `400`, nothing
  written. `day` must be a real calendar date, not in the future and at most 7
  days before today (UTC). Unknown top-level keys and unknown `features` /
  `errors` keys are dropped; zero counts are dropped.
- Upsert on `(install_id, day)`, last write wins.
- A D1 failure → `503`. The extension drops failed heartbeats silently and never
  retries, so a D1 outage loses a day of data and nothing else.

## Deploy

```bash
cd telemetry

# 1. Authenticate (opens a browser, stores the token locally).
npx wrangler login

# 2. Create the database, then paste the printed database_id into
#    wrangler.toml (d1_databases[0].database_id, replacing REPLACE_WITH_D1_ID).
npx wrangler d1 create erd-studio-telemetry

# 3. Create the table and indexes.
npx wrangler d1 execute erd-studio-telemetry --remote --file schema.sql

# 4. Deploy. This also registers the custom domain and the retention cron.
npx wrangler deploy
```

The custom domain `erd-studio-telemetry.liam-is-an.ai` needs the
`liam-is-an.ai` zone on the same Cloudflare account; `wrangler deploy` creates
the DNS record. `workers_dev` is off, so the custom domain is the only door.

Smoke-test it (none of these write anything):

```bash
curl -si https://erd-studio-telemetry.liam-is-an.ai/v1/heartbeat | head -n 1                 # 405
curl -si https://erd-studio-telemetry.liam-is-an.ai/ | head -n 1                             # 404
curl -si -X POST https://erd-studio-telemetry.liam-is-an.ai/v1/heartbeat \
  -H 'Content-Type: application/json' --data '{}' | head -n 1                                # 400
```

### The kill switch

`wrangler.toml`'s `[vars]` is the source of truth for `KILL_SWITCH`; every
`wrangler deploy` re-applies it over the dashboard value.

- **Durable** — set `KILL_SWITCH = "on"` in `wrangler.toml` and
  `npx wrangler deploy`.
- **Fast** — dashboard → Workers & Pages → `erd-studio-telemetry` → Settings →
  Variables → `KILL_SWITCH = on`. Mirror it into `wrangler.toml` straight away
  or the next deploy undoes it.
- **Stop collecting and delete everything** — `npx wrangler delete` removes the
  Worker; `npx wrangler d1 delete erd-studio-telemetry` removes the data.

The extension treats every non-2xx the same: the heartbeat is dropped silently.
Turning collection off breaks nothing for users.

### Watch it

```bash
npx wrangler tail --format pretty
```

Lines look like `{"at":"…","event":"ok","status":204}`,
`{"at":"…","event":"denied","status":400,"reason":"shape"}` and, once a day,
`{"at":"…","event":"retention","deleted":42}`. That is the whole vocabulary.

## Querying

Ad hoc, from this directory:

```bash
npx wrangler d1 execute erd-studio-telemetry --remote --command \
  "SELECT day, COUNT(*) AS active, SUM(canvas_opens > 0) AS with_canvas FROM heartbeats GROUP BY day ORDER BY day DESC LIMIT 14"

# Feature adoption (features is a JSON object of counts)
npx wrangler d1 execute erd-studio-telemetry --remote --command \
  "SELECT j.key AS feature, COUNT(*) AS installs, SUM(j.value) AS uses FROM heartbeats h, json_each(h.features) j WHERE h.day >= date('now','-7 days') GROUP BY j.key ORDER BY installs DESC"
```

Prefer aggregates. There is rarely a reason to look at individual rows, and
none to copy `install_id` anywhere.

## The local archive

Because D1 keeps raw rows for only 90 days, the operator's machine keeps
**aggregates** forever: `.traffic/telemetry.mjs` in the main checkout (gitignored,
personal, not part of this repo's history) runs aggregate-only SQL through
`wrangler d1 execute --remote --json` and merges the results into
`.traffic/telemetry-{daily,features,errors,versions,env,setup}.csv`, one row
per day (or per day and feature / code / version / environment), plus
`.traffic/raw/telemetry-<date>.json`. No query selects `install_id`, and the
script refuses to run one that does.

It only writes **finished** days (before today, UTC), and re-reads every day
still complete in D1 on each run, replacing that day's rows — so heartbeats
that arrive late (up to 7 days) are picked up next time. Days older than 90
days are never re-read, because retention may already have removed some of
their rows; the archive written while they were complete is kept. It is run
at the end of `.traffic/log.mjs` by the weekly launchd job, and a wrangler
failure there prints one line and never breaks the GitHub logging. The
`erd-traffic` skill's report adds a "Usage (telemetry)" section once these CSVs
exist.

## Local development

```bash
npx wrangler d1 execute erd-studio-telemetry --local --file schema.sql
npx wrangler dev            # http://127.0.0.1:8787, local D1 simulation
```

## Checks

```bash
npm test       # Node's built-in runner, nothing to install
npm run check  # node --check, then tsc --noEmit over the JSDoc types (strict)
```

The tests drive the Worker's `fetch` and `scheduled` handlers against an
in-memory D1 stand-in that records every statement and bound parameter. They
cover routing, the kill switch, the body cap (including a streamed body with no
`Content-Length`), every rejection path, unknown-key dropping and the exact
column binding. The last group checks the privacy promises across the whole
run: no IP, user-agent, country or other header value is ever bound to SQL,
and no payload, header or install id ever appears in a log line.

They are invisible to the repo's vitest suite (whose `include` is
`test/unit/**` at the root) and nothing at the root runs them.
`telemetry/tsconfig.json` is local to this directory and not referenced by the
root build. `npm run compile`, `npm run build` and `npm test` at the repo root
must stay green in a clone that has never touched this directory.
